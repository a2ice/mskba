# Coordination

Модуль отвечает за опросы и процессы согласования, которые ещё не являются
мероприятиями или бронями.

Контекст поддерживает опросы с типизированными вариантами:

- авторизованный активный пользователь создаёт опрос;
- пользователь хранит один ballot и может менять выбор до закрытия, если
  создатель не запретил изменение уже отправленного голоса;
- создатель выбирает анонимное отображение только со счётчиками либо открытое
  отображение пользователей после раскрытия результатов;
- одиночный и множественный выбор проверяются на сервере;
- опрос закрывается создателем либо планировщиком по дедлайну;
- после закрытия создатель явно принимает один вариант;
- ничья, неясный результат или отказ создателя от решения не создают
  мероприятие;
- закрытие и решение идемпотентны.

`PollSubjectTypeEnum` различает текст, дату, время, дату-время, временной
интервал и площадку. `PollOptionValue` и `PollOptionValueFactory` нормализуют
значения перед записью в JSON `coordination_poll_options.value` и формируют
единый label для Web и Telegram. Площадочные варианты принимают только
подтверждённые и операционно активные площадки.

Если создатель разрешил пользовательские предложения, участник может добавить
вариант того же типа до закрытия. Предложение проходит те же проверки,
дедупликацию и лимит в 20 активных вариантов. Изменение публикует
`PollChanged`, поэтому связанные Telegram-сообщения синхронизируются после
commit.

Контекст не изменяет `Event` и `VenueBooking` напрямую. После принятия решения
создатель явно заполняет точные параметры мероприятия. Межконтекстный
`CreateEventFromCoordinationHandler` передаёт их штатному
`CreateEventHandler`, который повторно проверяет инварианты мероприятия,
доступности площадки и брони.

`coordination_event_transitions` хранит однозначную связь процесса, принятого
решения и созданного мероприятия. Уникальные ограничения и блокировка строки
session делают переход идемпотентным: повторный запрос возвращает существующее
мероприятие и не создаёт вторую бронь.

## Конкурентный доступ

Операции управления блокируют сущности в порядке
`coordination_sessions -> coordination_polls`. Переход к мероприятию продолжает
порядок `coordination_sessions -> venues`. Голосование сериализуется
блокировкой строки poll, что сохраняет правило «один ballot на пользователя»
и не создаёт цикл блокировок с закрытием. Добавление предложения также
блокирует poll, чтобы атомарно проверить дубликат и лимит. Для MVP это
сознательно более грубая, но простая и безопасная граница; при высокой нагрузке
её можно заменить атомарными upsert-операциями.

## Telegram

`telegram_chats` хранит подключённые чаты независимо от env-настройки одного
текущего чата. `telegram_coordination_publications` связывает один poll с
несколькими чатами и хранит Telegram message/poll identifiers отдельно для
каждой публикации. Выбранные публикации отправляются и обновляются очередью
после commit. Одиночный выбор принимается через идентифицированный callback:
при первом ответе Telegram-пользователь получает связанный аккаунт MSKBA.
Множественный выбор открывается в Mini App, чтобы первый callback не фиксировал
неполный ballot в опросе с запрещённым изменением голоса.

Общее сообщение показывает результаты во время открытого голосования только
для режима `always`: персональный режим `after_vote` нельзя корректно
представить одним сообщением для всего чата. После закрытия счётчики
показываются всем, а имена скрываются только у анонимного опроса.

Подключённые чаты управляются в `/admin/telegram-chats`. Текущий
`TELEGRAM_MAIN_CHAT_ID` регистрируется там идемпотентно как начальная запись,
но не ограничивает добавление других чатов.

## Права

Gate `coordination-create` обращается к
`UserOperationalPermissionChecker`. Активные пользователи имеют операционное
право `coordination.create` по умолчанию, но `admin+` может отключить его в
персональном snapshot на странице `/admin/users`.
