# Event module

Модуль хранит мероприятия, участие пользователей и бронирование времени площадки.

В интерфейсе используется термин «Мероприятие», а `Event` остаётся техническим именем единого агрегата. Тип задаётся `EventTypeEnum`: игра, тренировка или игровая тренировка. Турнир является отдельным агрегатом; каждый назначенный турнирный матч получает собственную композицию Event + primary Game + VenueBooking.

Создание мероприятия выполняется атомарно: под блокировкой строки площадки проверяются её физическое состояние, регулярное расписание либо режим 24/7 при отсутствии часов, исключения и пересечения с активными бронями; затем создаются `Event`, `VenueBooking` и участник-организатор. Единый порядок блокировок — сначала площадка, затем связанные записи — уменьшает риск deadlock и закрывает гонку двух одновременных бронирований.

Свободная площадка подтверждает бронь и публикует мероприятие сразу. Если legacy wizard выбирает площадку с оплатой или ручным подтверждением, legacy-бронь получает статус `pending`, а мероприятие остаётся черновиком. Страница явно предупреждает организатора, что до подтверждения оно скрыто из публичного каталога и Telegram. Новый VenueBooking-модуль уже реализует booking-first flow и создание Event из подтверждённой аренды; переключение wizard на этот flow остаётся отдельной интеграционной задачей, чтобы не поддерживать второй конкурирующий approval-сценарий.

Организатор или подтверждённый superadmin может отменить мероприятие до начала. `CancelEventHandler` соблюдает тот же порядок блокировок `venue -> event -> booking`, атомарно переводит мероприятие и бронь в `cancelled` и тем самым освобождает интервал. Право организатора определяется по `user_id` связанного actor, а не по конкретному `actor_id`: actor фиксирует контекст действия, но один пользователь может входить с разных устройств и через Telegram.

После `ends_at` опубликованное мероприятие можно явно перевести в `completed`, сохранить `result_description` и добавить до 12 итоговых фотографий. Фотографии используют общую polymorphic-модель `Media`, коллекцию `event_results`, WebP-нормализацию и максимальную сторону 1200 пикселей. Видео и учёт фактической посещаемости в первую итерацию не входят.

Организатор или ответственный с `event.participants.manage` может добавить пользователя через предикативный поиск. Поиск и серверное добавление независимо соблюдают настройку приватности `discoverability`; скрытого пользователя нельзя добавить подменой `user_id`. Управляемое добавление сначала сохраняет `tentative`, а `UpdateManagedEventParticipantStatusHandler` переводит не-организатора между `confirmed|tentative|left`. Проверка лимита выполняется в транзакции после блокировки `event -> participant`, поэтому параллельные подтверждения не могут переполнить состав. AJAX-интерфейс без перезагрузки переносит карточки между разделами и синхронизирует доступный состав мини-игры.

Поля `status_changed_by_actor_id` и `status_changed_at` отмечают последнее управляемое изменение. Самостоятельное решение пользователя очищает provenance; полной истории эти поля не заменяют.

Подтверждение статистики игры публикует `GameStatisticsConfirmed` и ставит `RecalculatePlayerObjectiveAssessmentsJob` в очередь. Уникальная задача с retry пересчитывает проекции объективных показателей затронутых игроков через `PlayerObjectiveAssessmentCalculator`; lock по пользователю не позволяет двум играм одновременно перезаписать одну проекцию устаревшим результатом.

Публичная standalone-игра канонически открывается на `events.show`, а управление спортивным проведением вынесено в явный `events.games.manage` после ACL-проверки. Вложенный публичный URL основной игры постоянно перенаправляется на Event; nested URL остаётся каноническим для игр тренировки. Быстрые агрегаты, ручной счёт и состав используют JSON endpoints и локальный loading overlay. Финальный popup пересчитывает очки из попаданий и отправляет полный snapshot в атомарный сценарий завершения: подтверждение primary Game одновременно завершает Event, а отмена основной игры отменяет Event и освобождает бронь. Telegram builder скрывает промежуточный счёт мини-игры до `completed`, хотя сама мини-игра сразу остаётся в карточке мероприятия.

Верхняя карточка standalone-игры показывает фактический `recruitment_mode`: «Готовые команды» либо «Отдельные игроки». Подпись «Команды из участников» используется только для вложенной мини-игры, стороны которой действительно формируются из участников родительского мероприятия.

Game поддерживает `whole_game` без технических периодов и `periods` с 2/4 дочерними GamePeriod.
Первый период стартует вместе с Game; между периодами ввод закрыт до явного запуска следующего;
последний период закрывается в транзакции завершения Game. GameAction периодной игры всегда
ссылается на активный период. Общий GamePlayerStatistic сохраняется отдельно, периодные срезы
воспроизводятся из действий и score snapshots.

Последовательность действий активной игры хранится отдельно в append-only `game_actions`. Семантическое действие и актуальные проекции счёта/статистики записываются одной транзакцией под блокировкой игры; уникальный `game_id + sequence` задаёт устойчивый порядок для play-by-play и будущей realtime-доставки. Ручные правки сохраняются как correction, поэтому они не маскируются под бросок или иной спортивный эпизод.

Подтверждённых участников можно пригласить стать ответственными. Назначение хранится отдельно от роли организатора и проходит состояния `pending`, `accepted` и `declined`: организатор отправляет запрос, участник видит предложенные права и принимает или отклоняет его, организатор может изменить permission snapshot, отменить запрос либо снять принятое назначение. У одного мероприятия может быть несколько ответственных с разными наборами прав. Права хранятся в `event_responsibility_permissions`, проверяются application-слоем для каждого действия и распространяются с корневого мероприятия на его мини-игры. Ответственный может делегировать только подмножество собственных прав. При выходе, отказе или повторном подтверждении состава ответственность и snapshot сбрасываются.

При создании мероприятия организатор явно решает, публиковать ли его в Telegram, и выбирает один или несколько активных чатов, для которых разрешена публикация мероприятий. Для каждой выбранной пары `event + chat` заранее создаётся независимая запись `TelegramEventPublication`; поэтому ошибка одного Telegram-чата не мешает синхронизации остальных, а повторный запуск job остаётся идемпотентным. Настройка чата ограничивает новые публикации, но уже созданные проекции продолжают синхронизироваться, чтобы опубликованная карточка не оставалась устаревшей.

Изменение публичного мероприятия или его состава публикует `EventChanged`. Telegram-модуль асинхронно проецирует это состояние во все выбранные чаты карточкой с inline-действиями участия. Полученный через webhook или long polling callback не меняет таблицы напрямую: пользователь разрешается по доверенному Telegram ID, при необходимости получает облегчённый аккаунт и проходит через `JoinEventHandler` либо идемпотентный `DeclineEventHandler`.
