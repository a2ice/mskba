# MSKBA UI/UX — UI First

## Обязательный порядок

1. Прочитай AGENTS.md, agent-rules.md, ui-design-system.md и [UI Studio](../../../docs/specification/ui-studio.md); изучи фактический код изменяемого экрана и существующие общие компоненты, токены, иконки, скрипты. Определи кодовый шаблон, темы оформления, поддерживаемые сценарии.
2. Для значимого UI/UX сначала создай страницу /uikit/{ui_name} в изолированном контуре. Привяжи к Issue, зафиксируй базовый SHA, ревизию, состояния и применимость тем. Не жди CI/merge/deploy приложения для итераций. Если контур недоступен — сообщи конкретный блокер; не подменяй приёмку релизом.
3. Переиспользуй реальный Blade/Vue, CSS, SVG, шрифты и скрипты проекта. Данные — fixtures с формой реального контракта; адаптеры действий — локальные. Не отправляй реальные запросы, сообщения, платежи, уведомления. Не копируй компонент ради демо. Не добавляй лишние тексты, eyebrow, заголовки или действия.
4. Новые общие ассеты и изменения существующих сначала держи локально в каталоге интерфейса/его ветке. Не меняй Core UIKit и соседние сценарии до приёмки. Отделяй предметный компонент от универсального. Для изменений Core укажи существующие потребители и риск регрессии.
5. Обязательно проверь все применимые опубликованные темы Filament по их slug (не только mode), минимум светлую и тёмную; отдельно кодовые шаблоны mskba_dark, mskba_streetball и другие, если задача их затрагивает. Не заимствуй цвета из другой темы. Новые CSS-переменные с корректными fallback на семантические токены; проверь тему с другой палитрой/шрифтом. Не имитируй живую DB-тему встроенным пресетом: укажи источник и hash снапшота. Неподдерживаемые комбинации помечай с объяснением, не засчитывай их проверенными.
6. Проверяй реальные ширины desktop/tablet/mobile (1440/768/390/360), клавиатуру, focus, hover, disabled, загрузку, пустое состояние, ошибки, переполнение, скроллы, гостевой/авторизованный сценарии по смыслу. Проверяй UX, а не только изображение. По возможности сравни две темы при одинаковых ширине и данных.
7. Передай владельцу ссылку, ревизию, базовый SHA, матрицу проверок и ограничения. Дождись явной визуальной/UX-приёмки конкретной ревизии; не запускай продуктовый релиз до неё. Мелкие правки текста/очевидной косметики по согласованному паттерну могут идти напрямую.
8. После приёмки перенеси именно принятый код, а не повторную вёрстку. Сверь изменения общего UIKit с актуальной веткой; обнови его эталон и документацию в том же PR. Подключи настоящую бизнес-логику и проверки, выполни штатный CI/merge/deploy по правилам проекта. Проверь после интеграции отсутствие визуальных отклонений. Фиксируй принятую ревизию и результат; не считай CI визуальной приёмкой.
