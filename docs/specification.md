## Назначение документа

`docs/specification.md` хранит общую техническую рамку проекта. Документ нужен, чтобы новые разработчики и AI-агенты понимали не только код, но и правила работы с архитектурой, задачами, ветками, документацией и проверками.

## Техническая картина проекта

- Backend: Laravel, PHP 8.3+.
- Frontend/assets: Vite, npm.
- Docker окружение: общие сервисы описаны в `compose.yaml`; local/dev настройки находятся в `compose.override.yaml`; VDS/prod настройки находятся в `compose.prod.yaml`.
- Доменные части приложения находятся в `app/Modules`.
- Текущие доменные модули: `Identity`, `Contact`, `Location`, `Media`, `Notification`, `Venue`, `Contract`, `Telegram`.
- Основная тема находится в `resources/themes/mskba_dark`.
- Минимальная тема-заготовка находится в `resources/themes/blank`.
- Внешний backlog быстрых записей ведется во внешнем файле `../backlog/todo.md`.

## Архитектурные принципы

- Сохранять разделение модулей на `Domain`, `Application`, `Infrastructure`, `Presentation`.
- Держать контроллеры тонкими.
- Выносить пользовательские сценарии и бизнес-действия в use case или application-сервисы.
- Держать доменные правила в доменном слое.
- Именовать классы value object с суффиксом `VO`, например `PasswordVO`.
- Не смешивать продуктовую логику с Blade-шаблонами и JS темы.
- Не добавлять абстракции без практической необходимости.

Если общий модуль `App\Modules\Shared` понадобится для низкоуровневых value object или классификаторов, его нужно вводить отдельной задачей. В текущей кодовой базе такого модуля нет.

Любое важное изменение архитектуры, пользовательского flow, роли, бизнес-процесса, интеграции или правила разработки должно сопровождаться обновлением документации.

с опубликованным текстом. Обязательная отметка регистрации валидируется сервером правилом `accepted`;
одной HTML-разметки для соблюдения инварианта недостаточно.

## Интеграции

Telegram Mini App интеграция находится в `App\Modules\Telegram`.

Конфигурация берется из `config/telegram.php` и env-переменных:

- `TELEGRAM_BOT_TOKEN`;
- `TELEGRAM_BOT_USERNAME`;
- `TELEGRAM_BOT_DOMAIN`;
- `TELEGRAM_MAIN_CHAT_ID`;
- `TELEGRAM_INIT_DATA_MAX_AGE`;
- `TELEGRAM_API_BASE_URL`;
- `TELEGRAM_API_IP`;
- `TELEGRAM_HTTP_PROXY`;
- `TELEGRAM_WEBHOOK_SECRET`.

Основной маршрут Telegram Mini App `GET /telegram` показывает общую страницу `welcome` в layout `theme::layouts.app` с флагом Telegram-контекста. Флаг добавляет `viewport-fit=cover`, CSS safe-area, data-атрибуты авторизации и асинхронную загрузку Telegram WebApp SDK. Прежняя отдельная страница остаётся на `GET /integrations/main` как временный legacy-интерфейс переходного периода.

Frontend берет подписанные данные сначала из `Telegram.WebApp.initData`, а при недоступном или медленном SDK — из параметра `tgWebAppData` hash-части launch URL. В обоих случаях строка без изменений отправляется на `POST /integrations/telegram/auth` и обязательно проходит серверную HMAC-проверку; fallback не ослабляет доверенную границу. Поэтому внешний SDK больше не блокирует рендер общей главной и не является единственной точкой отказа идентификации.

Backend не доверяет данным Telegram-пользователя с клиента напрямую. `TelegramMiniAppInitDataValidator` строит data check string, проверяет HMAC-подпись через bot token и ограничивает возраст `auth_date`. Только после успешной проверки `AuthenticateTelegramMiniAppUserHandler` ищет или создает связку в `telegram_accounts`.

Таблица `telegram_accounts` хранит связь Telegram-профиля с обычным пользователем MSKBA:

- `user_id`;
- `telegram_user_id`;
- `username`;
- `first_name`;
- `last_name`;
- `language_code`;
- `photo_url`;
- `last_auth_at`;
- `raw_data`.

Если связки еще нет, создается обычный `users`-аккаунт с `registration_channel = telegram_mini_app`, `status = unconfirmed`, `system_role = user` и стабильным техническим username вида `tg_{telegram_user_id}`. Telegram-вход логинит пользователя в Laravel-сессию, но не заменяет процесс подтверждения аккаунта.

После успешной Telegram-авторизации всегда ставится асинхронная задача `SyncTelegramProfileAvatarJob`. Если Mini App не передал необязательный `photo_url`, задача получает фотографию через Bot API `getUserProfilePhotos -> getFile`; deploy ставит backfill для Telegram-аккаунтов без локального аватара. Одинаковая ссылка или стабильный `file_unique_id` не обрабатываются повторно, а активный аватар с источником `upload` имеет приоритет.

Для публикации закрепленной кнопки Mini App в Telegram-чате или канале используется artisan-команда `telegram:publish-main-link`. Она отправляет сообщение с URL-кнопкой `https://t.me/{bot_username}?startapp=mskba_chat` и закрепляет его через Bot API. Для закрепления бот должен быть администратором чата/канала с правом pin messages.

`TelegramBotApiClient` является общей точкой исходящих Bot API-вызовов и скрывает токен из исключений. При сетевой блокировке можно передать HTTP proxy через `TELEGRAM_HTTP_PROXY` либо сохранить TLS-hostname и принудительно направить cURL на доступный адрес через `TELEGRAM_API_IP`. Способ получения обновлений выбирает `TELEGRAM_UPDATES_TRANSPORT=webhook|polling`, а команда `telegram:configure-updates` регистрирует или удаляет webhook в соответствии с режимом. Webhook проверяет `X-Telegram-Bot-Api-Secret-Token` через `hash_equals`. Production использует отдельный контейнер `telegram` с исходящим long polling, поскольку Telegram сообщает `Connection timed out` при доставке callback на VDS; offset хранится в Redis, а полученные callback передаются в обычную очередь.

## Площадки

Предметная область площадок находится в `App\Modules\Venue`. Базовая доменная модель `Venue` хранится в таблице `venues`.

Публичный `GET /venues` принимает валидируемые query-параметры `search`, `type`, `operational_status`, `access` и `view`. `ListVenuesHandler` сначала ограничивает выборку подтверждёнными либо доступными текущему actor-у площадками, а затем применяет пользовательские фильтры внутри той же SQL-выборки. Read model заранее загружает адрес локации и основную фотографию, чтобы список и карта строились из одного результата без N+1. `AddressDisplayFormatter` собирает публичный адрес из `city, street, building`, а для старого `raw_address` удаляет префикс страны. Режим карты лениво загружает API Яндекс Карт, выводит placemark для каждой площадки с координатами и использует фиксированные границы Москвы и ближайшего Подмосковья; переключение `list/map` не выполняет повторный запрос и сохраняется в URL.

Текущие поля площадки:

- `created_by_actor_id`;
- `location_id`;
- `canonical_venue_id`;
- `name`;
- `alias`;
- `type`;
- `requires_payment` - денормализованная проекция наличия применимых условий оплаты, `false` по умолчанию;
- `requires_booking_approval` - денормализованная проекция правила ручного подтверждения бронирования, `false` по умолчанию;
- `status`;
- `status_info`;
- `short_description` - краткий подзаголовок для карточек и шапки площадки;
- `full_description` - полное описание на публичной странице;
- `raw_address`;
- `deleted_at`;
- timestamps.

Текущие классификаторы площадок:

- `VenueStatusEnum` - жизненный статус записи: `unconfirmed`, `confirmed`, `blocked`;
- `VenueTypeEnum` - тип площадки.

Удаление площадок выполняется через `softDeletes()` и поле `deleted_at`, а пояснение к жизненному статусу, например причина блокировки, хранится в `venues.status_info`.

`Venue` имеет relation `creatorActor()` к `Actor` по `created_by_actor_id`, relation `location()` к `Location` по `location_id`, relation `canonicalVenue()` к канонической площадке по `canonical_venue_id`, relation `moderationRequests()` к заявкам модерации и relations `revisions()`/`draftRevision()` к предлагаемым изменениям подтверждённой площадки.

Теги площадок хранятся в `venue_tags` как связь 1:N через `Venue::tags()`. Каждая запись содержит `venue_id`, отображаемое `name` и нормализованный `slug`; уникальность пары `venue_id + slug` запрещает дубли внутри одной площадки, но одинаковое имя может использоваться у разных площадок. `VenueTagSynchronizer` обновляет набор тегов в той же транзакции, что создание или изменение паспортных данных площадки.

Публично видимы площадки со статусом `confirmed`. Дополнительно пользователь может видеть площадки через договорный доступ.

Если структурированная локация еще не создана, площадка может хранить fallback-адрес в `raw_address`.

Форма создания площадки использует backend endpoint `/integrations/address-suggest` для Yandex-подсказок адреса. Первый HTML-шаг запускает общий venue partial в режиме `compactCreate`: отображает название, тип и адрес, но сохраняет скрытый metro-select для автоматического заполнения компонентом подсказок. После `CreateAccountVenueHandler` контроллер перенаправляет на стабильный `account.venues.edit` URL созданной записи; полная форма редактирования остаётся общим вторым шагом. Endpoint нормализует ответ внешнего API, подбирает локальные станции метро и не раскрывает `YANDEX_MAPS_API_KEY` на клиенте. Пользовательский `AddressSuggestionDTO::label` собирается из структурированных компонентов `city, street, building`, поэтому страна остаётся доступна для географической проверки, но не удлиняет отображаемое значение. Общий JS-компонент инвалидирует предыдущий request id при каждом вводе, показывает единый loading/clear control и при очистке сбрасывает видимое значение, структурированные поля, признак выбранного адреса и автозаполненное метро.

Для определения адреса по текущей точке endpoint `POST /integrations/address-reverse` принимает проверенные `latitude` и `longitude`, защищён CSRF, ограничен rate limiter-ом и выполняет обратное геокодирование через тот же `AddressSuggestService`. Координаты передаются в JSON body и не попадают в URL/access log. Провайдер возвращает общий `AddressSuggestionDTO`, поэтому проверка страны, структурированные поля и подбор метро идентичны обычной подсказке. Telegram-клиент версии Bot API 8.0+ использует нативный `WebApp.LocationManager`, а в обычном браузере — стандартный Geolocation API. Геопозиция запрашивается только после явного нажатия; координаты не используются для фонового отслеживания. Форма считает адрес выбранным только после успешного ответа с полноценным адресом дома.

Telegram `WebApp.LocationManager` инициализируется только перед первым запросом; последующие нажатия используют `isInited` и сразу запрашивают новую точку через `getLocation()`. Любое ручное изменение текста адреса инвалидирует всю связанную структуру, включая координаты и метро, чтобы в форме не сочетались новый неподтверждённый адрес и данные прежней локации.

Telegram Mini App переиспользует публичные venue endpoints и application use cases, но отправляет запросы с `Accept: application/json` и маркером `telegram_flow`. Для этого потока `CreateVenueRequest` и `UpdateVenueRequest` требуют выбранную адресную подсказку, координаты и структурированный адрес; метро передаётся автоматически в скрытом поле. `VenueController` возвращает JSON для создания, обновления и отправки на модерацию, а обычные браузерные формы сохраняют redirect-based поведение. Глобальный exception renderer учитывает `Request::expectsJson()`, поэтому ошибки FormRequest на web-маршрутах возвращаются как JSON `422`, а не HTML-редирект.

Мобильный header общего layout рендерит профиль отдельно от desktop account-nav. Гость видит иконку пользователя с входом через существующую auth-модаль; авторизованный пользователь — фото из доступного profile/Telegram-источника либо Unicode-safe инициалы из первых двух букв имени. После Telegram AJAX-auth этот элемент обновляется без перезагрузки страницы.

Авторизованный endpoint `GET /account/venues/{id-alias}/moderation-state` доступен только actor-у с правом управления площадкой и возвращает вычисленную возможность отправки, текущее состояние и историю заявок с сообщениями. Telegram-форма запрашивает его после создания площадки, каждого сохранения (включая ошибочное) и отправки заявки. Кнопка модерации и история полностью строятся из свежего ответа, поэтому отклонённую площадку можно исправить и повторно отправить из того же окна, а устаревший клиентский флаг не блокирует сценарий.

Endpoint `GET /venues/search` возвращает универсальную JSON-выдачу для Telegram-поиска, предикативных select и карты. Базовые необязательные параметры: `query`, `venue_id`, `type`, `status`, `metro_station_id`, `requires_payment`, `requires_booking_approval`; дополнительные контекстные параметры: `confirmed_only`, `operational_status`, `starts_at`, `duration_minutes` и `limit`. Без дополнительных параметров сохраняется пользовательский visibility scope `ListVenuesHandler`. `query` регистронезависимо ищется в кэшированной проекции названия, описания, адреса/улицы, тегов и метро. Точный `venue_id` используется общим selector для повторной проверки уже выбранной площадки при изменении временных условий: клиент сохраняет выбранный идентификатор и подпись, но блокирует отправку формы, если площадка перестала удовлетворять условиям.

`VenueSearchCache` хранит в основном cache store (Redis в штатном Docker runtime, `array` в тестах) версионированную поисковую проекцию и на 60 секунд результаты безопасных публичных запросов `confirmed_only`. Наблюдатель за площадкой, тегами, адресно-метровыми сущностями, расписанием и `VenueBooking` увеличивает версию при изменениях; старый ключ перестаёт читаться и истекает по TTL. При фильтрации конкретного интервала расписания загружаются eager loading, пересекающиеся брони выбираются одним запросом, после чего применяется `VenueEventAvailability`. Это UX-оптимизация, а не источник истины: `CreateEventHandler` повторяет проверку под транзакционной блокировкой.

Коммерческие условия аренды площадки хранятся отдельно в append-only версиях
`venue_booking_policies`. Только одна версия площадки помечена активной; новая
публикация создаёт следующую версию, а не переписывает предыдущую. Политика
задаёт доступные зоны, шаг и границы длительности, lead time, горизонт
бронирования, hold/payment/cancellation windows и цены. Денежные значения
хранятся и вычисляются как integer minor units вместе с ISO currency, без
float-арифметики. Публикацию выполняет владелец или участник Contract ACL с
`manage_booking_policy`; проверка повторяется в application handler.

Публичный расчёт аренды доступен только при включённом `rental_flow` и активной
включённой политике. `QuoteVenueBookingHandler` интерпретирует локальное время в
timezone расписания площадки, проверяет шаг, длительность, lead time, горизонт,
разрешённую зону и текущую доступность. Результат сохраняется в
`venue_booking_quotes` как неизменяемый snapshot версии политики, запроса,
формулы и итоговой суммы. Клиентские `amount_minor` и `policy_version_id` не
участвуют в расчёте. Quote сам по себе не удерживает слот; будущая команда
создания заявки обязана проверить срок действия и повторно подтвердить snapshot.
Публикация политики создаёт audit log и после commit инвалидирует поисковый кэш.

Новый коммерческий агрегат аренды использует ту же таблицу `venue_bookings`, но
отделён от Event полем `flow=rental`, nullable `event_id` и моделью модуля
`VenueBooking`. Старые строки `flow=legacy` и статус `PENDING` не меняют смысл:
они продолжают занимать интервал. Новый `REQUESTED` слот не занимает;
`HELD` занимает его до защиты, `CONFIRMED` — без временного deadline, а
`REJECTED`, `CANCELLED` и `EXPIRED` терминальны. До включения conflict engine
новый flow остаётся закрыт выключенным по умолчанию feature flag.

Каждая rental-бронь ссылается на исходный quote и копирует его snapshot,
заявителя, область и интервал. Текущие hold/payment deadlines, payment state и
optimistic version находятся в корне агрегата. Все изменения статуса проходят
через `VenueBookingLifecycle` и application handlers; прямой Eloquent update
статуса запрещён. Handler сначала блокирует площадку как mutex, затем строку
брони, проверяет права и ожидаемую версию и атомарно добавляет запись в
append-only `venue_booking_transitions`. Ошибка откатывает и состояние, и
timeline; событие публикуется только after commit. JSON read model возвращает
не только статус, но и допустимость каждого следующего действия с безопасным
машинным reason code. Event остаётся `null` вплоть до отдельной команды из
подтверждённой брони.

Конкурентное занятие ресурса проверяет единый `VenueBookingConflictService`.
Интервалы полуоткрытые: соседние `[start,end)` и `[end,next_end)` совместимы.
`WHOLE` пересекается с любой областью, одинаковые половины пересекаются, разные
половины совместимы. Блокирующие статусы — legacy `PENDING` и новые
`HELD/CONFIRMED`; `REQUESTED` ресурс не занимает. Перед Hold и повторной
проверкой Confirm transaction блокирует venue как mutex, затем найденные
пересекающиеся booking rows по id и target booking. Благодаря venue mutex два
параллельных transaction не могут одновременно пройти пустой range query даже
в MySQL без подходящего gap lock. Ошибка конфликта возвращает `409
BOOKING_CONFLICT` и только безопасные варианты следующего времени, не сведения
о чужой заявке. Timeline и доменное событие при rollback не создаются.

Каждая изменяющая rental-команда имеет UUID idempotency key. Receipt с actor,
именем команды, correlation ID, каноническим payload hash и результатом
создаётся в одной транзакции с агрегатом и timeline. Повтор того же key и
payload возвращает сохранённый результат; изменение payload или endpoint при
том же actor+key отклоняется как `IDEMPOTENCY_KEY_REUSED`. HTTP требует ключ
явно, а внутренний адаптер может сгенерировать его для одноразовой команды.

Доменные события брони записываются в `venue_booking_outbox_messages` внутри
той же транзакции. После commit очередь пытается доставить message, а минутный
scheduler повторяет pending и восстанавливает processing claim, зависший более
пяти минут. Доставка at-least-once: event содержит уникальный message ID, а
listener с критическим эффектом использует `VenueBookingEventConsumer::once`.
Consumer receipt и эффект выполняются одной транзакцией, поэтому ошибка эффекта
не помечает message обработанным.

`SiteSummaryService` кеширует в основном cache store суточное количество опубликованных/завершённых мероприятий типов `game` и `game_training`, а также общее количество незаблокированных и неудалённых пользователей. Observer-ы `Event` и `User` инвалидируют ключи после commit, поэтому незавершённая транзакция не может преждевременно наполнить кеш старыми данными. Online presence — отдельная Redis Sorted Set: ID пользователя является member, timestamp активности — score; middleware и frontend heartbeat обновляют score, просроченные members удаляются по временному окну. Такой presence атомарен и не удваивает пользователя при нескольких вкладках. Административный список пользователей читает один snapshot Sorted Set со score и сопоставляет его с текущей страницей аккаунтов, избегая N+1 Redis-запросов. Redis-сводка является presentation-проекцией, а не источником истины для мероприятий или аккаунтов. На главной суточный badge ведёт в журнал с составным фильтром `games` (`game` + `game_training`) и текущей датой; при нулевом online соответствующий badge скрывается.

Для ветки тегов поисковый запрос дополнительно проходит через `CyrillicTransliterator` и `Str::slug`, после чего сравнивается с `venue_tags.slug`. Поэтому поиск тегов не зависит от регистра и не требует DB-specific оператора `ILIKE`; исходное сравнение с `VenueTag::name` остаётся fallback для значений, не образующих slug.

Условия оплаты представлены nullable-признаком `requires_payment`: `null` означает «не указано», `false` — явно бесплатный доступ, `true` — платный. Подтверждение бронирования задаётся независимым `requires_booking_approval`. Свободный доступ вычисляется только для явной комбинации `requires_payment === false && ! requires_booking_approval` через `Venue::hasFreeAccess()`, а не хранится третьим boolean. Поэтому неизвестные условия никогда не приводят к автоматическому подтверждению брони. При свободном доступе создание брони свободного слота сразу получает подтверждённое состояние; достаточно атомарно убедиться в отсутствии пересекающейся активной брони. Проверку пересечений необходимо выполнять внутри транзакции с блокировкой или ограничением уровня БД, иначе два параллельных запроса смогут занять один интервал.

Общая форма создания и редактирования площадки позволяет выбрать «Не указано / Бесплатно / Платно» и независимо включить подтверждение бронирования. Эти значения проходят через FormRequest и application handlers; для подтверждённой площадки они входят в payload ревизии и дифф модерации. Миграция переводит прежнее неявное `false` у всех неуличных площадок в `null`, сохраняя явно бесплатными существующие уличные площадки. Изменение условий и паспортных данных выполняется в одной транзакции.

Оба поля являются денормализованными проекциями будущих сущностей условий. Изменение тарифов или правил подтверждения должно в той же транзакции пересчитывать соответствующий boolean через единый application-сервис. До появления таких сущностей значения доступны в форме площадки как временный источник настройки. Миграция старого `is_free = false` консервативно включает оба требования, поскольку из прежнего составного признака невозможно достоверно восстановить, какое именно условие действовало.

Alias площадки строится из названия общим `App\Support\Text\CyrillicTransliterator` с явной русской транслитерацией, включая `ш -> sh`, `щ -> shch`, `ч -> ch`, `ж -> zh`, `х -> kh`, `ц -> ts`, `ю -> yu` и `я -> ya`. Alias нужен только для читаемого URL и не участвует в определении дублей; одинаковые названия и alias разрешены.

Создание и изменение паспортных данных требуют структурированную локацию с координатами. `VenueProximityService` вычисляет расстояние Haversine между точками одинакового типа. Радиус сильного конфликта по умолчанию равен 50 метрам, радиус кандидата — 200 метрам; значения настраиваются через `VENUE_DUPLICATE_STRONG_RADIUS_METERS` и `VENUE_DUPLICATE_CANDIDATE_RADIUS_METERS`. Площадки разных типов в одной точке считаются разными: например, школьный спортивный зал и уличная площадка.

Публичный throttled endpoint `GET /venues/proximity-check` принимает тип и координаты, использует тот же `VenueProximityService` и возвращает наличие ближайшей подтверждённой площадки в сильном радиусе. `address-suggest.js` вызывает его только после получения валидных координат из подсказки или reverse geocoding и повторяет проверку при смене типа. Ответ используется как неблокирующее UX-предупреждение; серверные проверки use case и транзакционная проверка подтверждения остаются источником истины.

После создания площадки dispatchится `FindVenueDuplicatesJob`, который ищет подтверждённые и неподтверждённые площадки того же типа в радиусе кандидата и создаёт pending-записи в `venue_duplicates`. Кандидат хранит пару `venue_id`/`duplicate_venue_id`, исторически совместимый `matched_by=address`, статус `pending|merged|rejected`, score и metadata с фактическим расстоянием и применёнными порогами.

Повторное создание одинаковой неподтвержденной или заблокированной площадки тем же пользователем запрещено. Авторство сравнивается по `creatorActor.user_id`. Поэтому разные пользователи могут создать одинаковые неподтвержденные записи, но один пользователь не может создать две свои версии одной и той же площадки.

Канонический публичный идентификатор маршрута площадки имеет вид `{id}-{alias}`, например `/venues/42-shkola-1794`: ID однозначно определяет запись, а alias сохраняет читаемость URL. Все новые публичные ссылки используют этот формат. Alias-only URL временно остаются fallback-маршрутами для старых ссылок. Административные resource-маршруты `/admin/venues/{venue}` используют стандартный primary key `venues.id`; модель `Venue` не переопределяет глобальный route key на неуникальный alias.

Админский маршрут `admin.venues.duplicates` (`/admin/venues/duplicates`) показывает кандидатов дублей. Действие merge принимает группу площадок и выбранную главную площадку: дубли получают `canonical_venue_id`, кандидаты получают статус `merged`. Merge не меняет жизненный статус площадки и не подтверждает главную площадку автоматически. Если в группе уже есть `confirmed`-площадка, backend требует оставить главной именно ее. До подтверждения модератор может поменять главную площадку повторным merge группы. Merge дополнительно пишет audit event `merged` в `audit_logs`.

Модерация подтверждения площадки вынесена в отдельные таблицы:

- `moderation_requests` - заявка модерации с `type = venue`, `subject_id`, необязательным `venue_revision_id` и статусом `pending|approved|rejected`;
- `venue_revisions` - полный JSON-снимок предлагаемых паспортных данных, структурированной локации, тегов и состава галереи подтверждённой площадки;
- `moderation_messages` - сообщения пользователя, гостя и модератора по заявке через `sender_id`/`receiver_id` actors.

Владелец управляет площадкой в личном кабинете: редактирует данные на `/account/venues/{id-alias}/edit`, а статус и полную историю модерации видит на `/account/venues/{id-alias}/status`. После сохранения данных форма редактирования также предлагает сразу отправить первичную площадку или ревизию подтверждённой площадки на модерацию через `POST /account/venues/{id-alias}/moderation`. Публичный маршрут `/venues/{id-alias}` отвечает только за просмотр. Пока есть pending-заявка, повторная отправка и изменение черновика запрещены: edit-страница продолжает показывать фактические данные и фотографии, но fieldset и действия галереи становятся недоступными с пояснением о необходимости дождаться решения. Серверные use cases независимо повторяют этот запрет под блокировкой. Для первичной модерации `venue_revision_id` остаётся `null`, поскольку неподтверждённая площадка ещё не является публичной. Изменения подтверждённой площадки записываются в единственную неприменённую `VenueRevision`, а заявка ссылается на неё. Администратор рассматривает pending-заявки в `/admin/venues`: окно заявки вычисляет и показывает только отличия опубликованной версии от ревизии — старое и новое значение основных полей, характеристик площадки и удобств, а также изменения метро, тегов, координат и галереи. Наборы тегов, метро и удобств сравниваются независимо от порядка. Подтверждение ревизии атомарно применяет снимок данных и галерею, переводит заявку в `approved` и сохраняет площадке статус `confirmed`; отклонение сохраняет публичную версию неизменной и оставляет ревизию для исправления. Блокировка площадки выполняется отдельным изменением `VenueStatusEnum::BLOCKED` и заполняет `status_info`.

Инварианты изменения площадки:

- паспортные поля самой площадки (название, тип, описания, адрес и привязанная локация) разрешено редактировать только у неудалённой площадки, пока она не подтверждена;
- обычное редактирование паспортных полей также запрещено, пока существует moderation request со статусом `pending`; superadmin использует отдельный административный use case и является явным исключением;
- подтверждённая площадка сохраняет утверждённые паспортные данные неизменными до одобрения связанной ревизии; пользовательское исправление всегда проходит повторную модерацию;
- связанные с деятельностью площадки сущности (например, расписание, медиа, слоты, услуги и другие операционные данные) можно создавать, изменять и удалять, только пока площадка не удалена и не имеет статус `blocked`; статус `confirmed` сам по себе операционную работу не запрещает;
- soft-deleted площадка недоступна как для изменения паспортных полей, так и для работы со связанными операционными сущностями;
- административные lifecycle-действия — soft delete, восстановление, блокировка и снятие блокировки — являются явными исключениями из этих ограничений;
- ограничения должны проверяться на backend в общем доменном/application-правиле после загрузки актуального состояния площадки; скрытие элементов UI служит только дополнительной подсказкой и не считается защитой инварианта.

Публичная карточка площадки отдельно показывает модерационный статус и вычисляемое физическое состояние `Открыта|Закрыта`. Модерационные значения `unconfirmed|confirmed|blocked` не участвуют в вычислении доступности. Базовое операционное состояние хранится отдельно в `venues.operational_status`: `active` разрешает работу по расписанию, `temporarily_closed` принудительно показывает площадку закрытой. Для активной площадки без расписания показывается `Открыта`, а в поле часов — `Не установлено`; при заполненном расписании доступность определяется по timezone и текущему интервалу дня. В главном блоке показывается только основная фотография; остальные фотографии собраны в горизонтальную ленту с прокруткой, а клик открывает модальный просмотр с переключением стрелками и клавиатурой. На desktop шапка показывает пятизвёздочный рейтинг с пропорциональной жёлтой заливкой и текстовую кнопку бронирования. На мобильном рейтинг и бронирование переходят на отдельную строку, рейтинг представлен одной звездой и числом, а действие бронирования — кнопкой-иконкой. Название сохраняется полностью до 30 символов, более длинное сокращается с доступной подсказкой полного значения. Бронирование и текущие слоты пока остаются заглушками.

Регулярное расписание хранится в `venue_schedules` и `venue_schedule_intervals`. `venue_schedule_exceptions` задаёт замену на конкретную дату: `is_closed = true` закрывает весь день, иначе интервалы из `venue_schedule_exception_intervals` заменяют регулярные часы. Пересекающиеся интервалы и неполные пары времени запрещены; соседние интервалы, где конец одного совпадает с началом другого, разрешены. Изменение выполняется транзакционно после `lockForUpdate()` площадки. Доступ имеют владелец/bootstrap-создатель, участник активного договора с `edit.schedule` и подтверждённый `superadmin`, пока площадка не удалена и не заблокирована. Для бронирования отсутствующее или полностью пустое недельное расписание означает доступность 24/7; исключения конкретных дат продолжают действовать. Если существует хотя бы один регулярный интервал, день недели без интервалов считается закрытым.

В публичной карточке `short_description` отображается под названием, `full_description` - отдельным блоком между hero и якорным меню, а в hero вместо описания показываются адрес и ближайшее метро.

Каноническая точка входа находится на `/venues/create`, отправка формы идет через `POST /venues`. Личный кабинет не имеет отдельного create/store маршрута площадок и ведет пользователя на этот же URL. GET-страница и POST-сценарий требуют аутентификацию и доступны неподтвержденным и подтвержденным пользователям, кроме заблокированных аккаунтов. Для гостя действие «Добавить площадку» открывает общую форму входа/регистрации; после успешной аутентификации пользователь автоматически продолжает создание. Происхождение создания фиксируется через user actor.

`VenueFeatureEnum` и JSON-поле `features` в текущей кодовой базе отсутствуют.

## Опросы и согласования

`App\Modules\Coordination` отделяет предварительное согласование от строгих
инвариантов мероприятия и брони. `CoordinationSession` хранит организатора,
контекст и общий статус процесса; `Poll` — вопрос, режим выбора, дедлайн и
видимость результатов и флаг `is_anonymous`; варианты, ballots и selections
хранятся отдельными сущностями. Пользователь имеет не более одного ballot на poll и до закрытия
может атомарно заменить свой выбор, только если создатель включил
`allows_vote_changes`. При выключенной настройке первый ballot остаётся
неизменяемым; повторный запрос отклоняется application handler, а не только UI.
Обе настройки формы по умолчанию выключены: ballot неизменяем, состав голосов
открыт.
`is_anonymous` управляет только публичным представлением: для анонимного poll
выводятся счётчики, для открытого после раскрытия результатов — также имена
пользователей. Связь ballot с `user_id` сохраняется в обоих режимах для
уникальности голоса и возможности его изменить.

Закрытие poll не создаёт мероприятие. После ручного закрытия или дедлайна poll
переходит к ожиданию решения, и только создатель может явно принять один
вариант. Он вправе не принимать ничью, неоднозначный результат или любой
другой исход. Одиночный session после решения завершается самостоятельным
результатом Coordination.

`CoordinationFlowTypeEnum` выделяет одиночный процесс, подготовку нового
мероприятия и изменение существующего. В цепочках polls имеют `step_order` и
`depends_on_poll_id`; одновременно открыт только текущий шаг. Принятие решения
вызывает `CoordinationFlowAdvancer`, который активирует следующий draft poll,
а после последнего решения завершает session. Поддержаны типизированные
варианты текста, даты, интервала времени и площадки; их структура валидируется
на HTTP- и application-границах.

Для шага площадки `CoordinationFlowAdvancer` читает решения даты и времени и
повторно вызывает `VenueEventAvailability`. Недоступные, закрытые, удалённые,
неподтверждённые или занятые площадки выключаются до начала голосования.
Проверка является снимком для голосования, поэтому создание или перенос
мероприятия всё равно повторяет доменные проверки на актуальном состоянии.

Завершённая цепочка создания только предзаполняет форму `Event`; создание
остаётся явным действием пользователя. `ApplyEventCoordinationHandler`
применяет цепочку изменения через `UpdateEventHandler`, а не обновляет модели
Event напрямую. Coordination-транзакция завершается до входа в transaction
boundary площадок и бронирования, чтобы не смешивать блокировки двух контекстов.
После изменения площадки, начала или длительности
`participation_confirmation_version` мероприятия увеличивается. Ответы
неорганизаторов с прежней версией не входят в актуальный состав до повторного
подтверждения; подтверждение обновляет версию существующего участия.

Помимо полной цепочки поддержаны короткие flow:
`event_attendance`, `event_time_selection` и `event_venue_selection`.
Первый хранит фиксированные venue/start/duration и варианты типа
`PARTICIPATION`. Их payload содержит стабильный `intent`
`going|not_going|thinking`; видимый label может быть изменён автором.
Пользовательское предложение получает `intent=custom`, поэтому не превращается
в подтверждённого участника автоматически. Перед созданием Event UI показывает
ответы всех проголосовавших, заранее отмечает `going` и передаёт вручную
проверенный список `participant_user_ids`. Handler принимает только
проголосовавших в attendance-flow, проверяет вместимость и создаёт участие с
актуальной `participation_confirmation_version`.

В `event_time_selection` вариант — время начала при фиксированных площадке,
дате и длительности. В `event_venue_selection` вариант — площадка при
фиксированных точном начале и длительности. Одиночная площадка выбирается
общим `predictive-selector`, который используется формой Event. Изменение
начала или длительности не очищает выбранную площадку: selector запрашивает её
по точному `venue_id` с новыми условиями и либо подтверждает доступность, либо
сохраняет выбор в невалидном состоянии с сообщением о конфликте. Длительность
короткого flow nullable: `VenueEventAvailability::resolveEndsAt()` при
отсутствии явного значения завершает интервал на ближайшей границе текущего
рабочего интервала, следующей активной брони или дня. Для flow с несколькими
вариантами вычисление повторяется после принятия решения, а форма Event
получает фактическое число минут; Event допускает такую вычисленную
длительность, даже если она не кратна 30 минутам. Исходные и предложенные
пользователями варианты проходят `VenueEventAvailability` при добавлении.
Поскольку доступность может измениться после голосования, `CreateEventHandler`
повторяет проверку расписания, физического состояния и пересечений с бронями
непосредственно при создании мероприятия.

Создание защищено Gate `coordination-create`. Пока все активные
незаблокированные пользователи имеют это операционное право по умолчанию.
Проверка вынесена в `UserOperationalPermissionChecker`, чтобы будущий
персональный список permissions и управление admin+ не меняли контроллеры и
доменный процесс.

Создание постоянной команды защищено отдельным Gate `team-create` и
операционным правом `team.create`. Оно разрешено по умолчанию только
подтверждённому незаблокированному аккаунту и может быть персонально отозвано
через существующее администрирование operational permissions. Управление
конкретной командой не следует из этого глобального права: оно определяется
создателем и permissions активного membership-контракта команды. Snapshot прав
редактируется для любого принятого активного участника, а не только менеджера.
Исключение отделено от приглашения правом `team.members.remove`, запрещено для
владельца, капитана и самого выполняющего действие пользователя и транзакционно
деактивирует membership-контракт вместе с удалением спортивных назначений.
Перевод активной команды в черновик через пользовательское действие удаления
разрешён только её создателю, независимо от его системной роли; договорные права
редактирования команды этого полномочия не дают. Backend повторно проверяет
отсутствие связанных игровых сторон, а UI требует явного подтверждения.

Telegram-канал спроектирован как many-to-many проекция poll на чаты.
`telegram_chats` хранит каждый подключённый чат, а
`telegram_coordination_publications` — отдельные message/poll identifiers и
состояние публикации для пары poll × chat. Текущая конфигурация одного чата
идемпотентно регистрируется как начальная запись, но не является доменным
ограничением; дополнительные чаты подключаются в админке. При создании автор
выбирает активные чаты. После commit событие `PollChanged` ставит независимые
задачи синхронизации публикаций, защищённые Redis-lock на publication id и
повторяемые с backoff; ошибка сохраняется у конкретной публикации.

Для single-choice Telegram использует inline callback. Callback проверяет
точную пару chat/message/poll, создаёт либо находит связанный аккаунт через
`ResolveTelegramUserHandler` и вызывает общий `VoteInPollHandler`, поэтому web
и Telegram соблюдают одинаковые инварианты ballot. Повторный callback того же
варианта идемпотентен. Multiple-choice открывается через Mini App: набор
вариантов нельзя безопасно собирать последовательными callback при
`allows_vote_changes = false`. Публичное Telegram-сообщение показывает
результаты открытого опроса только в режиме `always`; персональное
`after_vote` остаётся web-представлением, так как сообщение в чате общее.
После закрытия кнопки голосования исчезают, а решение и результаты
синхронизируются. Событие `PollActivated` создаёт публикации следующего шага в
тех же чатах, где был опубликован предыдущий poll, после чего обычный
`PollChanged` запускает независимую синхронизацию сообщений.
Открытый одиночный опрос не дублирует варианты в тексте Telegram-карточки:
они уже представлены inline-кнопками. После закрытия кнопки исчезают, поэтому
карточка показывает варианты вместе с итоговыми счётчиками. Истёкший дедлайн
обрабатывает `coordination:close-expired`, ежеминутно запускаемый отдельным
контейнером `scheduler`; закрытие публикует `PollChanged` и обновляет каждую
связанную Telegram-карточку.

Для конкурентных управляющих операций используется единый порядок блокировок
`coordination_sessions -> coordination_polls`. Голосование блокирует poll и
обновляет ballot в одной транзакции. Это сознательно грубая сериализация MVP,
которая исключает потерянные обновления и вероятный deadlock из-за обратного
порядка блокировок. Telegram API не вызывается внутри транзакции: внешняя
доставка выполняется queued job после commit, поэтому медленный API не
удерживает доменные блокировки. Применение изменения Event запускается после
завершения Coordination-транзакции; таким образом процесс не удерживает
`coordination_polls` при получении блокировок `venues -> events -> bookings`.

## Мероприятия и бронирование

Новый flow аренды внедряется независимо от legacy-создания Event и закрыт четырьмя
переключателями в `config/features.php`: `rental_flow`, `coordination`,
`external_payment`, `attendance_v2`. Все переключатели читаются через
`FeatureFlags`, по умолчанию выключены и могут включаться независимо переменными
`FEATURE_VENUE_RENTAL_*`. Новые HTTP-маршруты должны использовать middleware
`venue-rental-feature:{feature}`: обычный web-запрос получает неотличимый от
отсутствующего маршрута `404`, JSON-клиент — `404` с машинным кодом
`feature_disabled`. Handlers, listeners и jobs проверяют тот же `FeatureFlags` до
выполнения новой логики. Отключение флага не меняет и не удаляет созданные новым
flow данные, а legacy-маршруты не помещаются под эти middleware до завершения
rollout.

Если новый flow вызывается из общего HTTP-маршрута, который нельзя целиком закрыть
middleware аренды (например, из мастера создания мероприятий), application handler
обязан дополнительно проверить и master flag, и `VenueRentalRollout` для текущего
пользователя и площадки. Mutation не должна создавать сущность, detail-маршрут
которой тот же пользователь затем не может открыть из-за более строгого rollout.

`VenueRentalCoordination` — отдельный агрегат предварительного интереса, не
связанный с legacy `CoordinationSession` и его опросами. Он фиксирует venue,
scope, `[starts_at, ends_at)`, organizer actor/user, видимость сбора и отдельную
видимость списка участников. Активное участие хранится в
`venue_rental_coordination_participants`; уникальная пара coordination/user и
блокировка корня делают повторный или конкурентный Join идемпотентным, а
leave/rejoin сохраняет одну историческую строку.

Создание сбора использует `QuoteVenueBookingHandler` для проверки текущей
политики и доступности, но не сохраняет quote как резерв, не создаёт
`VenueBooking`/`Event` и не входит в conflict checker. Явная команда Convert
блокирует coordination, проверяет organizer actor, получает новый quote для
сохранённого интервала и вызывает общий `RequestVenueBookingHandler` с UUID
idempotency key. Результат — только `REQUESTED`, поэтому ресурс по-прежнему не
занят до отдельной команды Hold. Если новый quote недоступен, связь с booking и
смена статуса откатываются. События coordination публикуются after commit; Join
создаёт уведомление организатору без ложного сообщения о бронировании.

Операции состава используют порядок
`venue_rental_coordinations → venue_rental_coordination_participants`.
Конвертация не держит coordination при будущем захвате venue mutex: она
завершается на `REQUESTED`, а Hold позднее использует установленный порядок
`venues → venue_bookings`. Это исключает обратный цикл блокировок между двумя
агрегатами.

Attendance V2 моделируется отдельно от legacy coordination poll сущностями
`venue_booking_attendance_rounds` и
`venue_booking_attendance_responses`. Раунд создаётся только requester actor-ом
для booking в состоянии `HELD` с будущим `effective_protection_until`.
Сервер вычисляет `deadline_at = min(requested_deadline,
effective_protection_until)`; attendance никогда не изменяет booking deadline.
Уникальный nullable active marker допускает историю закрытых раундов, но не
более одного открытого на booking.

При открытии создаётся неизменяемый список приглашённых canonical confirmed
users. Их nullable response принимает `yes|no|maybe`; повтор того же значения
идемпотентен, а смена ответа под блокировкой корня пересчитывает сохранённые
YES/NO/MAYBE/PENDING counters. `threshold_reached_at` обеспечивает однократный
ThresholdReached при первом достижении `minimum_yes_responses`. Персональные
ответы показываются по `responses_visibility=participants|organizer`, тогда как
агрегаты доступны каждому приглашённому.

Порядок изменяющих блокировок —
`venues → venue_bookings → venue_booking_attendance_rounds → responses`.
Respond повторно проверяет статус и protection deadline booking, поэтому
просроченный или уже подтверждённый hold не принимает ответ даже до фоновой
синхронизации. Ежеминутная команда
`venue-booking:close-expired-attendance` закрывает дедлайны, а booking events
Confirmed/Cancelled/Expired/Rejected закрывают связанный open round. События
attendance и уведомления отправляются after commit; ни ответ, ни threshold не
являются командой VenueBooking.

Истечение hold обслуживает ежеминутная команда
`venue-booking:expire-due`, запланированная с `onOneServer` и
`withoutOverlapping`. `VenueBookingExpiryDispatcher` делает короткую выборку по
существующему индексу `(status,effective_protection_until)`, ограничивает batch
и не открывает транзакцию на весь набор. Для каждой строки ставится отдельная
`ExpireVenueBookingIfDueJob` с observed optimistic version и ISO deadline.

Worker до блокировки отбрасывает уже неактуальные status/version/deadline, а
затем вызывает общий `ExpireVenueBookingHandler`, который допускает только
system actor и повторяет проверку через `VenueBookingLifecycle` под порядком
`venues → venue_bookings`. UUIDv5 idempotency key детерминирован из
booking/version/deadline, поэтому duplicate delivery создаёт не более одного
timeline/outbox effect. Гонки с Confirm, будущими Extension и payment callback
завершаются stale noop, если они успели изменить status, version или effective
deadline.

Отдельные expiry columns не вводятся: `terminal_at` хранит момент, а
append-only transition — reason и system actor. `effective_protection_until`
является единственным scheduler deadline и в будущем включает активное payment
window. Метрики `metrics:venue_booking:expiry:{scheduled|completed|stale|failed}`
показывают работу очереди. API возвращает `server_time` и effective deadline;
клиент не является источником истины для истечения.

Модуль `App\Modules\Event` содержит:

- `Event` — мероприятие с типом `game|training|game_training`, организатором-actor, площадкой, локализованным временем, видимостью и лимитом участников;
- `EventParticipant` — уникальное участие пользователя в мероприятии с ролью организатора или участника и состоянием `confirmed|tentative|left`;
- `VenueBooking` — занятый интервал площадки со статусом `pending|confirmed|cancelled`.

Ответственность участника хранит состояние приглашения в `EventParticipant`, а его контекстный ACL — в `event_responsibility_permissions`. Enum `EventResponsibilityPermissionEnum` задаёт атомарные действия для мероприятия и дочерних мини-игр. Уникальная пара `(event_participant_id, permission)` является фактическим snapshot назначения; отсутствие строки означает запрет. Snapshot редактируемый, но новые enum cases не расширяют существующие назначения автоматически. Миграция задачи 069 выдаёт полный snapshot прежним `pending|accepted` назначениям, сохраняя их старую семантику.

`EventManagementAccess::allows()` сначала разрешает любое действие организатору и подтверждённому superadmin, затем ищет принятое назначение пользователя на корневом мероприятии и требуемую строку permission. Мини-игра не образует отдельный management scope. Изменяющие состояние use cases проверяют конкретный permission; агрегатный `canManage()` используется только для видимости общего контейнера управления и доступа к закрытому представлению.

`EventResponsibilityPermissionManager` валидирует snapshot и запрещает ответственному выдавать права за пределами собственного effective-набора. `mini_game.statistics.manage` требует `mini_game.score.manage`, поскольку расширенная статистика сохраняется вместе со счётом. Режим только счёта имеет отдельный endpoint и не меняет индивидуальные показатели или состояние готовности статистики. Формы используют общий `partials.forms.toggle`, а групповой переключатель не создаёт отдельного backend-permission.

`AddEventParticipantHandler` при управляемом добавлении сохраняет пользователя как `tentative`: такой пользователь отображается в «Думают» и не резервирует место. `UpdateManagedEventParticipantStatusHandler` под блокировкой `event -> participant` повторно проверяет `event.participants.manage` и переводит не-организатора между `confirmed|tentative|left`; переход в `confirmed` дополнительно проверяет лимит. Переход из confirmed сбрасывает ответственность и её permissions. JSON-ответы возвращают нормализованную карточку и актуальный confirmed count. `event-show.js` перемещает карточку между секциями, обновляет счётчики и состав конструктора мини-игры, удерживая loading overlay только на секции участников.

`event_participants.status_changed_by_actor_id` и `status_changed_at` хранят только provenance последнего управляемого изменения, а не audit history. Управляемое добавление и смена статуса записывают actor и время; самостоятельные web/Telegram-сценарии очищают оба поля. UI показывает время и tooltip с actor только при наличии этой пары.

`/events` загружает featured-фото площадки и две первые дочерние игры без N+1, поддерживает `venue_id` и `has_mini_games` вместе с прежними фильтрами. На мобильном заголовок использует компактный размер и стандартное действие «Назад», toolbar центрирует «Фильтры» и «Создать», а карточка отделяет компактное превью и заголовок от расположенных ниже метаданных. В каталоге показывается название площадки и короткий адрес `street + building`; полный адрес сохраняется в данных модального окна карты. Геофильтр намеренно не отправляет запрос до появления модели пользовательской геопозиции и правил радиуса.

`/events/{game}` является единым read/manage-представлением, а прежний `/events/{game}/game` сохраняется как совместимый redirect. UI выводит действия по атомарным permissions. Счёт, полный snapshot статистики и состав сохраняются AJAX-запросами; секция-источник удерживает общий image-upload loading overlay. Быстрый ввод обновляет агрегированные `game_player_statistics`, а итоговый пересчёт на клиенте формирует team scores перед атомарным `saveAndCompleteStatistics`. Сервер повторно валидирует состав, попытки/попадания и права, поэтому клиентский пересчёт не является доверенной границей. Ограничение «после начала» применяется только к мини-игре с явно заданным временем; у игры без расписания технически унаследованный период родительского мероприятия не блокирует ручное завершение.

Telegram-проекция всегда перечисляет созданную мини-игру, но показывает её score только при `childGame.status=completed`. Промежуточные autosave-события по-прежнему синхронизируют карточку мероприятия, однако builder заменяет текущие значения счёта на `—:—` до завершения.

Подтверждение статистики публикует `GameStatisticsConfirmed`. Listener не выполняет агрегацию в HTTP-запросе, а ставит уникальный по игре `RecalculatePlayerObjectiveAssessmentsJob` с повторными попытками. Job запускает `PlayerObjectiveAssessmentCalculator`, который для каждого затронутого пользователя собирает статистику всех подтверждённых игр и обновляет `player_objective_assessments`. Короткая cache-lock по `user_id` сериализует конкурентные пересчёты одного игрока; задача остаётся идемпотентной благодаря `updateOrCreate`. Профиль читает готовую проекцию, показывает число учтённых матчей, достоверность и только ненулевые рассчитанные метрики. Самооценка хранится и редактируется независимо.

Изменение permissions блокирует корневое мероприятие, затем целевой `EventParticipant`. Операции мини-игр соблюдают порядок `parent event -> child game -> game detail/sides`. Единый порядок снижает риск deadlock при одновременном изменении назначения, состава и игрового состояния.

`CreateEventHandler` выполняет единый transaction boundary. Внутри транзакции он сначала блокирует строку `venues` через `lockForUpdate()`, затем `VenueEventAvailability` проверяет подтверждение и физическую доступность площадки, регулярное расписание либо режим 24/7 при его отсутствии, исключение конкретной даты и пересечение полуоткрытых интервалов (`existing.start < requested.end AND existing.end > requested.start`). Соседние интервалы не пересекаются. После проверки атомарно создаются мероприятие, бронь и участник-организатор.

`CreateEventRequest` разрешает старт с предыдущей целой минуты относительно `now`: минутный допуск компенсирует время заполнения и доставки формы, а более ранние значения отклоняются. Форма предлагает ближайшую текущую минуту, выбирает 60 минут длительности по умолчанию и не принимает `ends_at` от пользователя. `CreateEventHandler` повторно проверяет длительность для вызовов вне HTTP и рассчитывает `ends_at = starts_at + duration_minutes`. Форма лишь помогает начальными значениями, а бизнес-ограничения обеспечиваются сервером.

Общий partial `partials.venues.predictive-selector` и `venue-selector.js` используют `/venues/search` как удалённый источник Tom Select. Форма мероприятия передаёт `confirmed_only=1`, `operational_status=active`, начало и длительность; изменение времени очищает прежний выбор. Тот же набор параметров загружает до 200 координат в модальное окно Яндекс Карты, а клик по placemark устанавливает значение исходного select. Модальные окна карты и просмотра площадки находятся выше fixed-шапки и нижнего мобильного bar; в Telegram Mini App они занимают всю доступную высоту, а их размеры и внутренние отступы учитывают CSS-переменные Telegram content safe area и системные `safe-area-inset-*`.

Турнир намеренно исключён из `EventTypeEnum`, HTTP-валидации и ограничения `events.type`: он должен моделироваться отдельным агрегатом, который объединяет несколько игр, а не притворяться одной бронью площадки.

Маршрут `tournaments.index` и его тема являются только presentation-scaffold будущего агрегата: они предоставляют отдельный пункт меню, периоды `all|current|upcoming|past` и валидируемые фильтры `query|date_from|date_to`. До проектирования доменной модели этот экран не читает и не создаёт турнирные данные.

Единый порядок «сначала venue, затем связанные booking/event записи» обязателен для будущих обработчиков переноса и отмены. Он сериализует конкурентные бронирования одной площадки и снижает вероятность deadlock. Одной проверки `exists()` без блокировки было бы недостаточно: два параллельных запроса могли бы одновременно увидеть свободный интервал.

`UpdateEventHandler` изменяет паспортные поля мероприятия и переносит бронь только между свободными площадками. Перед транзакцией фиксируются исходный и запрошенный `venue_id`; внутри транзакции обе строки площадок блокируются по возрастанию `id`, затем блокируются мероприятие и его бронь. Стабильный порядок предотвращает deadlock при встречных переносах `A -> B` и `B -> A`. После блокировки handler проверяет, что исходная площадка не была конкурентно изменена.

При изменении площадки, начала или длительности обе площадки должны иметь свободный доступ. `VenueEventAvailability` повторно проверяет целевую площадку, расписание и пересечения, исключая `id` собственной текущей брони. Мероприятие и `VenueBooking` обновляются одной транзакцией; при конфликте прежняя бронь сохраняется. Для начала переноса действует тот же минутный допуск относительно текущего времени, что и при создании. Несвободные площадки пока позволяют менять только паспортные поля: перенос и отмена согласуемых броней требуют отдельного процесса.

При любом редактировании `UpdateEventHandler` повторно проверяет право через `EventManagementAccess` и сравнивает новый лимит с числом подтверждённых участников. `JoinEventHandler` использует ту же блокировку строки события, поэтому конкурентные update/join не могут оба принять устаревшее значение вместимости. Существующий `CancelEventHandler` этой задачей не меняется; отдельные условия отмены несвободной брони должны проектироваться вместе с её согласованием.

`ShowVenueHandler` выбирает до пяти ближайших броней `pending|confirmed` с `ends_at > now()`. На публичной странице всегда показывается занятый интервал, но название и ссылка добавляются только для опубликованного публичного мероприятия.

`ListEventsHandler` разделяет период и итог мероприятия. `period=past` означает только `ends_at <= now()` и включает публичные мероприятия `published|completed`, а для организатора — также его собственные записи остальных статусов. Представление отдельно маркирует `completed` как «Состоялось», `cancelled` как «Отменено», а закончившееся мероприятие без итога как «Итог не указан». Такое публичное `published`-мероприятие остаётся доступным организатору для позднего вызова `CompleteEventHandler`. Предстоящий и прошедший журналы используют единый блок фильтров: на desktop он раскрыт постоянно, а на мобильном экране и в Telegram Mini App свёрнут в компактную секцию «Поиск» и после раскрытия показывает полноширинные поля.

HTTP-журнал передаёт в `ListEventsHandler` необязательные GET-фильтры `type`, `date_from`, `date_to`, `status=all|not_cancelled|cancelled` и, только для прошедшего периода, `outcome=completed|unmarked`. Значение статуса по умолчанию — `not_cancelled`: глобальное условие исключает `cancelled`, включая собственные мероприятия организатора. `all` добавляет публичные отменённые записи к допустимым статусам периода, а `cancelled` дополнительно ограничивает выдачу только ими. Для совместимости старый `outcome=cancelled` нормализуется в `status=cancelled`. Границы дат интерпретируются как включительные локальные сутки в `config('app.timezone')`, переводятся в UTC и применяются к `starts_at`. Фильтры добавляются поверх существующего visibility scope, а `withQueryString()` сохраняет их в пагинации.

Мероприятие должно целиком помещаться в один рабочий интервал одного локального дня площадки. Для свободного доступа без активной rental-политики legacy booking и опубликованный Event по-прежнему создаются одной транзакцией. Активная `VenueBookingPolicy` переключает мастер на новый booking-first flow: `QuoteVenueBookingHandler` формирует неизменяемый quote, `RequestVenueBookingHandler` создаёт rental-бронь, а `venue_booking_event_intents` хранит валидированный payload будущего Event/Game и выбранные Telegram-чаты. До состояния `confirmed` Event отсутствует. `VenueBookingConfirmed` доставляется через transactional outbox; идемпотентный listener под блокировками `venue -> booking` вызывает `CreateEventFromConfirmedVenueBookingHandler`, а уникальные `events.booking_id` и `venue_booking_event_intents.venue_booking_id` защищают от повторной материализации. Несвободная площадка без активной политики возвращает ошибку конфигурации и не создаёт legacy `pending`/draft пару. Существующие legacy-записи остаются доступными, но новые этим путём больше не появляются.

`CancelEventHandler` разрешает организатору или подтверждённому superadmin отменить мероприятие до `starts_at`. Он соблюдает порядок `venue -> event -> booking` и атомарно переводит мероприятие и бронь в `cancelled`, сохраняет actor, время и необязательную причину. Организатор определяется по user связанного actor, а не по равенству `actor_id`, поскольку один пользователь может действовать через разные устройства и каналы.

PostgreSQL хранит абсолютные значения `timestamptz` в UTC, а пользовательские даты и время интерпретируются и показываются в часовом поясе приложения (`Europe/Moscow`). Поскольку Laravel передаёт Carbon-параметры в SQL без текстового UTC-offset, timezone PostgreSQL-сессии обязательно совпадает с `APP_TIMEZONE`; это задаётся `database.connections.pgsql.timezone` через `DB_TIMEZONE` с fallback на `APP_TIMEZONE`. Иначе SQL-сравнения с `now()` (автоматическое закрытие опросов, журналы мероприятий и занятые слоты) срабатывают со сдвигом на разницу часовых поясов.

Наступление `ends_at` не завершает мероприятие автоматически. `CompleteEventHandler` явно переводит опубликованное мероприятие в `completed`, сохраняет `completed_at`, actor и отдельное `result_description`, не заменяя исходный текст анонса. Итоговые изображения хранятся в polymorphic `media` с morph alias `event` и collection `event_results`: до 12 JPEG/PNG/WebP по 10 МБ нормализуются в WebP с максимальной стороной 1200 пикселей. PHP transport настроен с запасом (`upload_max_filesize=12M`, `post_max_size=14M`), а nginx принимает тело до 20 МБ; пользовательский лимит контролируется Laravel-валидацией. Описание конкретного изображения использует `media.description`. Отметки участников нормализованы в `event_result_photo_tags`: запись связывает media с пользователем и хранит координаты `position_x`/`position_y` в процентах. Обновление описания и полного набора отметок выполняется одной транзакцией с блокировкой мероприятия и media; backend дополнительно проверяет, что каждый отмеченный пользователь состоит в участниках этого мероприятия. Видео, фактическая посещаемость, подтверждение ожидающих броней и перенос мероприятия остаются следующими расширениями.

После успешного transaction boundary обработчики создания, изменения, отмены, завершения и участия публикуют `EventChanged`. `QueueTelegramEventPublicationSync` ставит немедленную и отложенную до начала мероприятия `SyncTelegramEventPublicationJob`; поэтому внешняя сеть не входит в транзакцию и не удерживает блокировки базы. Job под cache lock создаёт либо обновляет одну запись `telegram_event_publications` на мероприятие и соответствующее сообщение основного чата. Черновик не публикуется, перевод в приватный режим удаляет прежнее сообщение, отмена и завершение закрывают действия участия.

Для постоянных команд исходное `base_name` сравнивается через `normalized_name`:
регистр и повторяющиеся пробелы игнорируются, `ё` приводится к `е`.
`name_sequence` формирует публичное имя с суффиксом `№N`. Частичный уникальный
индекс защищает пару `(normalized_name, name_sequence)` только для активных,
неудалённых постоянных команд. На PostgreSQL распределение номера дополнительно
сериализуется transaction-level advisory lock по нормализованному названию;
это устраняет гонку двух одновременных созданий без блокировки несвязанных
названий. Временные команды оставляют эти поля пустыми.

`team_venue_relations` хранит уникальную пару `team_id + venue_id` и тип `desired|confirmed`.
Текущий flow создаёт только `desired` для подтверждённых площадок. Право `team.venues.manage`
входит в snapshot договорных permissions; создатель команды получает все права вычисляемо. Добавление и
удаление сериализуются блокировкой `teams`, а unique constraint защищает от дублей. Удаление `confirmed` через
текущий UI запрещено, чтобы будущий согласуемый flow не мог быть обойдён командой.

`team_hiring_positions` хранит активные и закрытые вакансии постоянной команды. Счётчики `spots_total` и
`spots_filled` определяют остаток; JSON-массив `positions`, nullable `minimum_experience_years`, `gender` и `description`
являются описательными критериями, а не authorization-фильтром игрока. `team.hiring.manage` управляет вакансиями.

`team_join_requests.team_hiring_position_id` связывает заявку с конкретной вакансией. Активная вакансия принимает
целевую заявку независимо от `teams.accepts_join_requests`; флаг ограничивает только общие заявки. Принятие идёт
под единым порядком блокировок `team → hiring position → join request`, атомарно увеличивает `spots_filled` и закрывает
заполненную вакансию. Этот же порядок используется при подаче целевой заявки, чтобы конкурентные отклики и приёмы
не переполнили вакансию. Отклонение, блокировка и разблокировка также блокируют `team → join request`, поэтому не могут
конкурентно перезаписать уже принятое решение.

Гостевой CTA заявки использует общий auth modal и `redirect_to`. Выбранное действие сохраняется на время
авторизации в `sessionStorage`, а URL возврата содержит только его открытое описание. После входа frontend
сверяет оба значения и отправляет обычную CSRF-защищённую POST-форму; простой переход по URL не создаёт заявку.
Все способы входа, включая VK и Telegram, получают одинаковый URL возврата. Backend остаётся единственным
источником бизнес-валидации и не требует подтверждённого контакта или participation-role игрока.

Telegram-карточка использует inline callbacks `event:{id}:join|leave`, а не нативный poll: сайт может атомарно принять или отклонить действие и показать пользователю результат, не создавая второе независимое состояние голосования. Webhook либо `TelegramUpdatesPoller` быстро ставит `ProcessTelegramCallbackJob` в очередь. Обработчик сверяет `chat_id`, `message_id`, `event_id` с сохранённой публикацией и доверяет идентификатору только из `callback_query.from.id`, а не из `callback_data`.

`TelegramEventMessageBuilder` формирует текстовую проекцию мероприятия: игровые типы (`game`, `game_training`) получают заголовок «Играем на {площадка}», остальные сохраняют собственный title; тип активности и описание выводятся с явными подписями, а пустое описание заменяется прочерком. Описание ограничивается длиной сниппета до HTML-экранирования, чтобы вместе с остальными полями оставаться внутри лимита сообщения Telegram.

Кнопка просмотра Telegram-карточки использует deep link Main Mini App `https://t.me/{bot}?startapp=event_{id}`. Подписанный Telegram `start_param` проходит через `TelegramMiniAppStartDestinationResolver`: разрешён только формат `event_{id}`, мероприятие должно существовать, а клиент получает исключительно относительный внутренний маршрут. После успешной Mini App-авторизации frontend выполняет переход внутри текущего WebView. Произвольный URL из параметра запуска не принимается, поэтому этот сценарий не создаёт open redirect.

Rental coordination использует отдельную проекцию
`telegram_venue_rental_publications` с foreign keys на coordination, nullable
booking и зарегистрированный Telegram chat. Публичный сбор публикуется в
активные чаты с `publishes_coordination`; private сбор в чат не попадает.
`TelegramVenueRentalMessageBuilder` выводит фиксированный интервал, participant
count и вычисляет предупреждение о незанятом слоте из текущего booking status.
Created/Joined/Closed/Converted и booking lifecycle events ставят
`SyncTelegramVenueRentalPublicationJob`; job выполняет Bot API вне доменной
транзакции, сериализуется cache lock, повторяется с backoff и пересоздаёт
удалённое сообщение.

Callback `rentalcoord:{coordination_id}:join|leave` принимается только для
сохранённой тройки coordination/chat/message. `callback_query.from.id`
резолвится через канонический `TelegramAccount`, после чего адаптер вызывает
общие `JoinVenueRentalCoordinationHandler` или
`LeaveVenueRentalCoordinationHandler`; неподтверждённый пользователь не
проходит application invariant. Уникальные `callback_id` и nullable
`update_id` сохраняются в `telegram_venue_rental_updates`; cache lock защищает
одновременный replay, а повтор completed callback только отвечает актуальным
status/participation. Webhook и polling передают update ID в общий callback job.

Deep link имеет allowlisted формат
`rental_coordination_{public_uuid}`. Resolver проверяет флаг `coordination`,
существование сущности и для private-сбора organizer/active participant ACL,
после чего возвращает только относительный route. Доверенная граница Mini App
не меняется: `initData` сначала проходит HMAC и age validation, авторизует
канонического пользователя в Laravel-сессии и только затем используется для
перехода и обычных защищённых HTTP-команд.

`ResolveTelegramUserHandler` под cache lock по Telegram ID находит существующую связь либо атомарно создаёт `User`, профиль, `TelegramAccount` и подтверждённый Telegram-контакт. Регистрация из чата получает канал `telegram_chat`; последующая Mini App-авторизация переиспользует эту связь и не создаёт второй аккаунт.

Обычный web-вход предоставляет два Telegram-сценария. Официальный Telegram Login Widget показан как быстрый вариант: `TelegramLoginWidgetDataValidator` проверяет HMAC-SHA256 полного стандартного payload с ключом `SHA256(bot_token)` и ограничивает возраст `auth_date` настройкой `telegram.login_widget_max_age`. Альтернативный вход создаёт 256-битный base64url challenge с TTL `telegram.bot_login_ttl`, связывает его с секретом браузерной сессии и открывает deep link `/start login_{token}`. Бот принимает команду только в личном чате того же Telegram-пользователя и отправляет inline-кнопку `auth:login:{token}`. Подтверждение сохраняет immutable Telegram ID в challenge, а браузерный polling атомарно потребляет его под cache lock, создаёт Laravel-сессию и удаляет ключ. Это исключает повторное применение ссылки и подмену браузера. Оба варианта используют resolver с каналом `telegram_web` и общий `CompleteTelegramWebAuthenticationHandler`.

Заблокированный пользователь не получает Laravel-сессию, а `SafeAuthenticationRedirectResolver` принимает только относительный или same-origin URL. Username применяется только как отображаемый атрибут и не участвует в объединении аккаунтов. `JoinEventHandler` сохраняет положительный ответ, а отдельный идемпотентный `DeclineEventHandler` создаёт или переводит участие в `left`. Блокировка строки `events` сохраняет лимит при конкурентных кликах.

Публичный web-интерфейс меняет собственный ответ через `SetEventParticipationHandler`. Handler принимает `confirmed`, `tentative` или `left`, внутри транзакции первым блокирует строку мероприятия и только затем читает и обновляет участие. Поэтому два конкурентных подтверждения не могут занять одно последнее место. `tentative` и `left` не учитываются в лимите; организатор не может сменить собственный статус через этот сценарий. Telegram-обработчики сохраняют совместимые состояния той же модели.

Страница `events.show` имеет отдельную mobile-first композицию вместо `section-sidebar`: до появления итоговых фотографий hero использует collection `gallery` площадки, затем приоритет получает collection `event_results`. Hero содержит фотографии, счётчик и наложенные снизу навигационные точки, поэтому горизонтальный свайп работает по всей его площади; нажатие на итоговую фотографию показывает или скрывает компактные чёрные подписи с публичными именами отмеченных участников. Позиция hero-подписи вычисляется из координат исходного снимка с учётом масштаба и crop-offset `object-fit: cover`. Полноэкранная event-галерея использует единый кадр `16:9` с `object-fit: cover`, поэтому фотографии заполняют слайд без чёрных полей, а переключение не вызывает вертикальных скачков. На небольших экранах боковые стрелки заменяются кликабельными навигационными точками под кадром, а кнопка закрытия становится компактнее. Описание и имена отмеченных участников находятся в абсолютной полупрозрачной панели поверх нижнего края изображения и не влияют на высоту слайда; панель использует единый шрифт `10px` и вертикальные отступы `10px`, круглая кнопка сворачивает её вниз и возвращает обратно. Название мероприятия в этой панели не дублируется. Нажатие на имя включает только соответствующую прозрачную область с белой рамкой прежнего компактного размера, центрированную по сохранённым координатам. Публичное имя и суммарная статистика бросков, подборов, передач, потерь и фолов внутри рамки скрыты по умолчанию; при наведении, фокусе или нажатии вся область получает фон `rgba(0,0,0,.5)` и показывает данные. `EventPlayerStatisticsSummaryBuilder` учитывает только подтверждённую статистику дочерних мини-игр, а ссылка «Подробнее» ведёт на последнюю такую игру игрока; черновики и неподтверждённые значения в публичный агрегат не входят. Username не попадает в публичные данные отметки; при отсутствии имени используется нейтральная подпись «Участник #ID». Заголовок, время, площадка и выровненная по первой строке цветовая точка вычисляемого состояния набора расположены отдельным блоком ниже. Точка использует иконный tooltip без дополнительного декоративного вопросительного знака. Локация открывает модальное окно Яндекс Карт с координатами площадки. Кнопки участия выводятся только пользователю, который вправе изменить ответ: организатор не получает неактивные действия; заполненность скрывает «Пойду» для нового участника, но не блокирует ответы «Думаю» и «Не пойду» и не мешает уже подтверждённому участнику освободить место. `tentative` представлен подписью «Думаю», а списки `confirmed`, `tentative` и `left` отображаются отдельными группами «Идут», «Думают» и «Не идут». После закрытия блок состояния отдельно показывает доступность записи и фактический итог, включая ещё не заполненный итог прошедшего мероприятия. Сводка содержит три выровненные колонки: число участников в формате `текущее/лимит` при наличии лимита, тип и состояние бронирования. Данные организатора, участников, отметок и профилей отмеченных пользователей, дочерних игр и их подтверждённой статистики загружаются заранее без N+1-запросов. Неизвестные покрытие, цена или Telegram-контакт не имитируются. Клиентский `event-show.js` отвечает за прокрутку hero, редактор описаний и отметок с локальными `@`-подсказками и AJAX overlay, ленивую инициализацию карты, раскрытие описания и выбор share-механизма; изменение участия остаётся серверным бизнес-действием.

`GameDetail.scoring_type` хранит независимый от размера состава набор правил: `streetball` оценивает ближний/средний/дальний бросок как `1/1/2`, `basketball` — как `2/2/3`, штрафной в обоих случаях равен одному очку. `GamePlayerStatistic::points()` является единым backend-калькулятором для AJAX, итоговых таблиц и серверного рендера; frontend получает тип правил для оперативного предпросмотра той же формулы. Миграция добавления поля назначает существующим играм `streetball` и пересчитывает командный счёт подтверждённых игр из сохранённой статистики; индивидуальные очки не хранятся отдельно и вычисляются при чтении.

## Мероприятия, игры и турниры

Утверждённая целевая композиция организационного `Event`, спортивной `Game`, отдельного агрегата
`Tournament` и структурного `TournamentMatch` описана в
[ADR Event, Game и Tournament](specification/event-game-tournament-architecture.md). Точные таблицы,
ключи, ограничения и стратегия данных зафиксированы в
[целевой схеме соревнований](specification/competition-schema.md).

Предыдущий [Event/Game Separation](specification/event-game-separation.md) сохраняется как история
задачи 084 и описание части runtime до завершения рефакторинга 086, но больше не задаёт целевую
границу standalone и tournament games.

`game_actions` является append-only журналом игровых действий, а не заменой текущих
проекций `game_sides.score` и `game_player_statistics`. Запись содержит монотонный
`sequence` внутри игры, тип действия, необязательные сторону, игрока, очки, actor,
время и расширяемый JSON payload. UI передаёт семантический контекст броска или
показателя вместе с полным snapshot статистики; оба состояния сохраняются в одной
транзакции. Ручное изменение итоговых чисел фиксируется как correction.

Все игровые write-сценарии блокируют строки в порядке `event → game → game_sides`.
Номер следующего действия вычисляется только после `FOR UPDATE` игры и дополнительно
защищён уникальным индексом `(game_id, sequence)`. Это сериализует конкурентные
записи одной игры, не создавая глобальной блокировки между разными играми. Live-page
использует последнее действие с указанной стороной для восстановления активной
команды после reload; correction без стороны не сбрасывает эту проекцию.

## Админка

Админская часть находится в `App\Modules\Admin`.

Текущая структура:

- `Application/UseCases` - read models для dashboard, users, venues, placeholder events/teams, content и settings;
- `Presentation/Http/Controllers` - тонкие controllers, которые вызывают use case и возвращают themed pages.

Routes находятся под prefix `/admin` и middleware `auth`, `can:access-admin-panel`.

Текущие route names:

- `admin.dashboard` - `/admin`;
- `admin.dashboard.legacy` - `/admin/dashboard`, redirect на `/admin`;
- `admin.users`;
- `admin.users.status.update`, `admin.users.bulk-delete`, `admin.users.bulk-restore` - управление аккаунтами только для `superadmin`;
- `admin.venues`;
- `admin.venues.edit` и `admin.venues.update` - административное редактирование активной площадки только для `superadmin`;
- `admin.venues.duplicates`;
- `admin.events`;
- `admin.teams`;
- `admin.content`;
- `admin.audit`;
- `admin.settings`.

Gate `access-admin-panel` определен в `App\Providers\AccessServiceProvider` и использует `User::isAdmin()`. Это означает системную роль `admin` или выше и подтвержденный аккаунт.

Gate `edit-venues-as-superadmin` требует подтвержденный аккаунт и точную системную роль `superadmin`. Проверка продублирована в `AdminUpdateVenueHandler`, чтобы административный use case нельзя было вызвать в обход HTTP middleware. Обновление переиспользует `VenueDetailsUpdater`, общий для пользовательского и административного сценариев; обычный `UpdateVenueHandler` по-прежнему применяет предметные ограничения владельца. Удаленные площадки административным редактированием не загружаются и требуют предварительного восстановления.

`ShowEditableVenueHandler` разрешает показать владельцу форму при pending-модерации в режиме чтения, а `UpdateVenueHandler` запрещает изменение после `SELECT ... FOR UPDATE` площадки. Это защищает сохранение формы, открытой до отправки заявки, даже при обходе disabled-контролов браузера. Submit, update и review используют единый порядок конкурентных блокировок: сначала строка `venues`, затем связанные `moderation_requests`. Approve изменяет заявку и статус площадки атомарно в одной транзакции; событийный listener остаётся идемпотентным downstream-обработчиком и не выполняет повторное обновление уже подтверждённой площадки.

Галерея площадки использует polymorphic `Media` collection `gallery` и стабильные morph aliases `venue` и `venue_revision`. Ограничение коллекции — три изображения и ровно одно основное при непустой галерее. `WebpImageNormalizer` принимает целевой максимальный размер: аватар сохраняет прежние 200 px, фотография площадки использует 500 px. Общий frontend-модуль `image-upload` управляет `aria-busy` и loading-overlay для аватара и всех вариантов галереи площадки; redirect-формы включают его на submit, а Telegram AJAX-сценарий гарантированно снимает в `finally`. Venue photo endpoints поддерживают redirect-based web-формы и JSON-контракт для Telegram Mini App; Telegram получает после каждой операции актуальный состав галереи и URL последующих действий. Для подтверждённой площадки существующие фотографии представлены в payload ревизии ссылками `published`, новые файлы принадлежат `VenueRevision` и представлены ссылками `draft`. Удаление опубликованной фотографии до одобрения означает только исключение ссылки из чернового состава. При одобрении draft-media перепривязываются к `Venue`, исключённые файлы soft-delete-ятся, а физическое удаление запускается через `DB::afterCommit`, чтобы откат транзакции не оставил базу без файла.

Конкурентный сценарий применения ревизии защищён блокировками в порядке `venue → moderation_request → venue_revision`. Пока заявка `pending`, пользовательские endpoints не разрешают менять ни поля, ни галерею. Снимок хранит `base_content_version`, а каждое прямое изменение опубликованных данных или галереи увеличивает `venues.content_version`; поэтому административная правка, сделанная после создания ревизии, не будет молча затёрта её последующим одобрением. Модератор применяет снимок, обновляет media и завершает заявку внутри одной транзакции, поэтому частично опубликованного состояния не возникает.

Навигация страницы площадки использует один набор anchor-ссылок и общий `IntersectionObserver` в `venue-show.js`. На desktop ссылки присутствуют в sidebar и во внутренней sticky-панели контента. При ширине до 900 px sidebar становится горизонтальной sticky-панелью под фиксированной шапкой, внутренняя панель скрывается, а блоки состояния и управления не занимают мобильный viewport. При смене активной секции JS синхронно обновляет оба набора ссылок и центрирует активный пункт мобильной панели; повторяющиеся цели наблюдаются только один раз.

Gate `manage-users-as-superadmin` защищает изменение статуса, массовое удаление и восстановление пользователей. Точная роль также проверяется в FormRequest и application handlers. Собственный аккаунт действующего superadmin нельзя изменить или удалить этим сценарием. Удаление пользователя представлено `SoftDeletes`: `deleted_at` создаётся в исходной users-миграции, а `UserStatusEnum` содержит только `unconfirmed`, `confirmed` и `blocked`.

Dashboard использует отдельный layout `theme::layouts.admin-dashboard`. Внутренние admin-разделы используют общий `theme::layouts.section-sidebar` с admin sidebar partial, чтобы сохранить единую двухколоночную композицию проекта.

Админка начиналась как read-only каркас, но теперь содержит отдельные moderation и venue actions. Полный CRUD, сохранение настроек и content persistence должны добавляться отдельными задачами. Audit log доступен как read-only раздел `/admin/audit`.

## Аудит

Техническая модель audit logging описана в [Audit logging](architecture/audit.md).

Audit фиксирует изменения доменных сущностей в `audit_logs` и связывает запись с `Actor`, если действие выполнялось в HTTP-flow. Это отдельный системный журнал изменений данных, а не runtime-логи приложения.

## Контракты

Предметная область контрактов находится в `App\Modules\Contract`.

Текущие модели:

- `Contract`;
- `ContractMembership`;
- `ContractRelation`;
- `ContractPermission`.

Текущие таблицы:

- `contracts`;
- `contract_memberships`;
- `contract_relations`;
- `contract_permissions`.

В текущей реализации первым production-scope является `membership_contract` для связи `venue -> user`. Фактические права контракта хранятся в `contract_permissions` как snapshot выданных permissions:

- `view`;
- `edit`;
- `edit.schedule`.

`contract_relations` закладывает схему для будущих связей сущность-сущность, но relation-contract ACL для событий, команд, компаний и других доменов пока не реализован. Его нужно описывать как направление развития, а не как готовую часть системы.

В таблице `contracts` есть поле `assigned_by`, а модель `Contract` содержит relation `assignedByUser()`.

## Целевая модель контрактов

Целевая техническая модель контрактов описана в [Contracts](specification/contracts.md).

Контракты разделяются на два семейства:

- `membership_contract` - связь пользователя с предметной сущностью (`venue -> user`, `team -> user`, `event -> user`, `company -> user`);
- `relation_contract` - связь сущности с сущностью (`event -> venue`, `team -> venue`, `team -> team` и похожие).

Старая модель `holder/provider/customer` удалена из текущей схемы и не является универсальной ACL-моделью. Такие значения допустимы только как контекстные роли отдельных relation types, например сервисного договора. Для остальных связей роли сторон и access levels должны определяться policy конкретного `scope_type` или `relation_type`.

Для `venue` membership стартовые access levels:

- `owner`;
- `admin`;
- `manager`;
- `staff`;
- `agent`.

Шаблон access level используется как preset при выдаче контракта, но в конкретном контракте должен сохраняться фактический snapshot permissions. Это позволяет старшей роли снять часть прав при выдаче `admin` или другого уровня и не расширять старые контракты автоматически при изменении шаблона.

`venues.created_by_actor_id` в целевой модели является audit/source field, а не самостоятельным источником владения. Право владельца площадки должно задаваться `membership_contract` со `scope_type = venue` и `access_level = owner`. Пока у площадки нет действующего owner membership contract, user, связанный с actor-создателем, получает управленческий доступ как bootstrap-owner. После появления owner membership contract управление определяется контрактами, а creator fallback больше не даёт полную власть над этой площадкой.

Fingerprint не используется для владения или переноса доступа к площадке. Создание площадки требует аккаунт, поэтому её actor-создатель всегда связан с user. Модель и таблица `actor_claims` отсутствуют.

## Темы и представления

Текущая конфигурация тем находится в `config/themes.php`.

Сейчас есть две директории:

- `resources/themes/mskba_dark` - основная проработанная тема с большинством страниц пользовательской части;
- `resources/themes/blank` - минимальная тема-заготовка.

Активная тема по умолчанию: `mskba_dark`.

`ThemeResolver` выбирает активную тему из `APP_THEME`, регистрирует namespace `theme` и подключает Vite inputs активной темы.

Основная тёмная тема задаёт контраст вторичного текста централизованными CSS-токенами. Bootstrap-классы вспомогательного текста и placeholder всех полей должны использовать эти токены, а не стандартные светло-тематические значения Bootstrap; частные компоненты могут менять оттенок только для отдельной семантики, например ошибки или предупреждения.

Метод `ThemeResolver::page()` использует fallback `theme::pages.system.view_not_found`, если запрошенной страницы нет. Такой fallback должен существовать в активной теме, иначе отсутствующая страница приведет к ошибке рендера вместо аккуратного view.

Маршрут `/dashboard` сейчас есть, но view `pages/dashboard.blade.php` отсутствует в обеих текущих темах.

В теме `mskba_dark` элементы пользовательского интерфейса с атрибутом `title` автоматически получают кастомный tooltip. JS enhancer переносит текст из `title` в кастомный tooltip и удаляет нативный `title`, чтобы не было двойной подсказки браузера. По умолчанию используется вариант `question` с отдельной кнопкой `?`; для уже существующих визуальных маркеров можно указать `data-tooltip-variant="title"`, чтобы tooltip был привязан к самому элементу без дополнительной иконки.

Для разделов с левой колонкой используется общий grid-based layout `theme::layouts.section-sidebar`. Он задает композицию: breadcrumbs, sidebar слева и основной content panel справа. Sidebar заполняется секцией `section-sidebar`, основной контент - секцией `section-content`. Если в sidebar нужен навигационный список, нужно использовать общий partial `theme::partials.menu.sidebar` и добавить соответствующий handler в `config/menus.php`, как это сделано для `venues`. Заголовки content panel используют общий класс `layout-content-title`. Layout предназначен для разделов вроде площадок, игр, тренировок, событий, команд и внутренних разделов с sidebar.

Каталоги площадок, мероприятий и команд используют общий визуальный компонент
`catalog-card` из `css/catalog-card.css`. Общие классы отвечают за поверхность
карточки, изображение, бейджи, заголовок, описание, действия и компактную
мобильную типографику; предметные классы страниц задают только различающиеся
grid-схемы и метаданные. Это сохраняет единое поведение при изменении мобильных
размеров и не связывает уникальные блоки мини-игр, доступа и состава.
На мобильном экране превью использует `aspect-ratio: 1 / 1` и
`align-self: start`: оно масштабируется от ширины своей колонки и не растягивается
по высоте вслед за соседним текстовым содержимым.

Шапки этих каталогов используют общий компонент `catalog-toolbar`. Быстрый
поиск постоянно находится в основной строке, а раскрываемая область содержит
только расширенные условия. На мобильном экране текст действий и переключателей
скрывается, но иконки сохраняют доступные имена и tooltip; поиск остаётся
видимым. Переключатель списка и карты площадок располагается между поиском и
остальными действиями. Sticky-toolbar не оборачивается в короткий контейнер
формы, иначе границы родителя прекращают фиксацию сразу после шапки. Внешнее
поле поиска связывается с расположенной ниже GET-формой расширенных условий
стандартным HTML-атрибутом `form`.

На viewport до 768 пикселей модуль `mobile-sidebar-navigation` переносит существующий `.section-sidebar-layout__aside` в слот общей мобильной навигации. Узел переносится, а не клонируется, поэтому формы, значения и JS-состояние sidebar остаются единственными. Горизонтальный tablist внизу панели переключает главное меню и контекстный sidebar; вкладки реализуют ARIA tab pattern и клавиатурную навигацию. При возврате к desktop sidebar восстанавливается по DOM-маркеру в исходную grid-позицию.

Layout предоставляет необязательную секцию `section-mobile-sticky-navigation` между breadcrumbs и основной grid. Страница площадки использует её для горизонтальных якорных ссылок. На мобильном секция получает `top` из `--site-header-height`; общий JS обновляет токен по фактической высоте шапки, а Telegram ResizeObserver повторяет обновление при изменении safe-area. Поэтому sticky-элемент и `scroll-margin-top` целевых секций не зависят от фиксированной высоты обычного браузера.

Account-страницы напрямую используют `theme::layouts.section-sidebar` и передают `theme::partials.account.sidebar` как `sidebarPartial`. Отдельный `theme::layouts.account` больше не используется, чтобы account и публичные предметные разделы имели одну layout-сетку и одинаковую ширину sidebar.

## Редакционный контент

Материалы хранятся в bounded context `Content`. Подтверждённый пользователь с системной ролью `editor` или выше управляет ими через `/admin/content`, но роль редактора сама по себе не открывает остальные административные разделы.

Публикация в `/news` и Telegram независима. Материал может находиться только в ленте, только в выбранных Telegram-чатах, сразу в обоих каналах или оставаться черновиком. При первой публикации в ленте фиксируется `feed_published_at`; повторное редактирование не меняет исходную дату публикации.

Тип `material` является самостоятельным. Типы `event` и `venue` требуют выбрать существующую связанную сущность. Тип `user` может ссылаться на конкретного пользователя, но без такой связи обозначает материал для всех пользователей. Связь с командой появится вместе с предметным модулем команд и не моделируется строковым идентификатором заранее.

Полное описание хранится как Markdown и преобразуется через CommonMark с удалением произвольного HTML и запретом небезопасных URL-схем. Благодаря этому редактор может размещать ссылки внутри статьи без разрешения исполняемого HTML.

В полном тексте материала и в полном описании турнира поддерживается безопасный shortcode краткой карточки площадки: `[popup type="venue" id="7" view="short"]Школа №1794[/popup]`. Renderer заменяет только явно разрешённую комбинацию `venue + short` на системную кнопку, а все остальные конструкции остаются обычным текстом. На странице используется один общий modal, данные площадки загружаются только по клику через публичный preview endpoint с обычной проверкой доступа. Совместимый компактный синтаксис `[sc:popup;short_info;venue;7]Школа №1794[/sc]` поддерживается для ручного ввода.

Telegram-доставка работает асинхронно. Для каждой пары «материал + чат» существует одна `telegram_content_publications`: job создаёт сообщение, обновляет его после редактирования и удаляет при отключении публикации. Dispatch выполняется после commit, а Redis lock сериализует работу с одним Telegram-сообщением.

Обложка проходит общий `WebpImageNormalizer`, сохраняется на public disk в WebP и ограничивается 1200 пикселями по большей стороне.

Кнопка Telegram-сниппета использует Mini App start parameter `content_{id}` и всегда открывает страницу материала. Отдельная ссылка действия и Markdown-ссылки работают уже внутри статьи, поэтому Telegram-переход не обходит редакционный текст.

Материал с обложкой публикуется через Telegram `sendPhoto`: нормализованная обложка передаётся по публичному URL, а краткий текст и Mini App-кнопка остаются в caption. Повторная синхронизация использует `editMessageMedia`; переход между публикацией с обложкой и без неё заменяет прежнее сообщение и сохраняет новое состояние в `telegram_content_publications.message_type`.

## Breadcrumbs

Partial `theme::partials.breadcrumbs` строит цепочку навигации через `App\Presentation\Breadcrumbs\BreadcrumbsResolver`.

Все сегменты breadcrumbs ограничены 13 символами: более длинная подпись отображает первые 10 символов и многоточие, а полное значение доступно в tooltip. Семантическая цепочка при этом сохраняет все промежуточные элементы. Справа от цепочки находится общая кнопка «Назад», которая возвращает пользователя через browser History API.

На ширине до 560 px список сегментов может переноситься внутри доступной ему области, не вытесняя кнопку «Назад» из секции breadcrumbs.

Resolver может использовать:

- имя текущего маршрута;
- `breadcrumb` defaults маршрута;
- заголовок страницы, если он передан в partial.

В текущих маршрутах `breadcrumb` default явно задан только для маршрута `venues`.

Соглашение вида `section.index` полезно для новых разделов, но текущие route names не везде ему следуют (`venues`, `account`). Поэтому документация не должна утверждать, что все текущие breadcrumbs уже построены по этому соглашению.

## Docker и окружения

Текущая Docker-схема описана в [Docker Environment](specification/docker-environment.md).

Локальный compose остается DB-only: `postgres` и `adminer`.

Production compose добавлен отдельно и содержит `phpfpm`, `nginx`, `db`, `redis` и build-only сервис `node`. Старую версию проекта можно полностью удалять вместе с БД, контейнерами, volume и другими артефактами, если они мешают новой production-схеме.

## Базовый сидер

`DatabaseSeeder` является production-safe bootstrap сидером. Он не создает demo users, demo venues, contracts, fake profiles или случайные данные.

Текущий сидер создает и обновляет только:

- identity bootstrap пользователя `superadmin` со статусом `confirmed`, системной ролью `superadmin` и базовым профилем;
- справочник московского метро: `metro_lines` и `metro_stations`.

Пароль `superadmin` задается только при первом создании пользователя. Повторный запуск сидера обновляет роль, статус и профиль, но не сбрасывает пароль существующего пользователя.

Справочник метро берется из локального файла `database/seeders/data/moscow_metro.json`. Файл подготовлен из публичного набора `nalgeon/metro`, который указывает HeadHunter API как upstream источник. Сидер не выполняет сетевые запросы во время запуска.

## Процесс работы с задачами

Разработка ведется через задачи из `docs/tasks.md`. Для каждой задачи создается папка `docs/tasks/{NNN}` с описанием, планом, статусом и итогами. Дополнительный внешний backlog быстрых записей и важных возникающих задач ведется во внешнем файле `../backlog/todo.md`.

Подробнее: [Процесс работы с задачами](specification/task-workflow.md).

## Git workflow

- Старт задачи выполняется только из чистой ветки `main`.
- Для задачи создается отдельная ветка в стиле conventional commit: `type/NNN`.
- Примеры: `feature/123`, `fix/124`, `docs/125`, `refactor/126`.
- После выполнения и проверки задача коммитится в своей ветке.
- Затем запрашивается подтверждение на merge в `main`.
- После merge задача отмечается выполненной в `docs/tasks.md` уже из `main`.

## Проверки качества

Минимальные проверки выбираются по затронутой области:

- PHP/backend: `composer test` или `make test`.
- Frontend/assets: `npm run build` или `make build`.
- Стиль PHP: `make lint` или `make format`.
- Маршруты: `php artisan route:list`.
- Кеши Laravel: `php artisan optimize:clear` или `make optimize-clear`.
- Документация: `git diff --check`.

Если проверку невозможно выполнить, это нужно явно зафиксировать в описании задачи и в итоговом сообщении.
