# MSKBA — единая контрактная система (PR #557)

Дата: 2026-11-01. Целевая ветка: dev. Production не изменяется.

## Концепция

- Создание сущности регулируется глобальным операционным правом; управление существующей сущностью — контекстными контрактными permissions. Права Filament глобальны, независимы и не выдаются контрактами.
- Membership связывает пользователя с объектом; Relation связывает два объекта. Юридическое соглашение — частный случай, а не определение сущности Contract.
- Доступ даётся только при активном принятом договоре, в пределах срока, наличии нужного permission и требуемого подтверждения. Срок передаваемых полномочий ограничен договором назначающего.
- Название не даёт прав; шаблон сохраняет набор разрешений для будущего копирования, не меняет уже выданные договоры.
- Разные правовые основания и подтверждения не смешиваются: legal_nature, verification_requirement, ContractVerification и документы.

## Мероприятия и игры

- Единая область управления — Event. Game/mini-game не получают самостоятельного владельца и используют контракт Event; турнирный матч сохраняет ограниченное явное разрешение Tournament MANAGE_GAMES.
- При создании Event создаётся контракт организатора с полным набором EventResponsibilityPermissionEnum. Создание из публичного wizard, бэк-офиса, самостоятельной игры, занятия и внешних use case обслуживает одна точка Event created.
- При назначении другого организатора из бэк-офиса контракт ждёт принятия; прямое редактирование через Filament остаётся независимым.
- Старые организаторы, accepted/pending назначения ответственных и их permissions переносятся в ContractMembership с сохранением статуса, ссылкой из EventParticipant и истории. Статусы участников/права в прежней модели используются только для синхронизации интерфейса, не для авторизации.
- Спортивное участие, составы, счёт, статистика и результаты остаются предметными сущностями и не являются основанием выдачи управленческих прав.
- Финансовые полномочия не добавляются обычным участникам и не включаются в обычный шаблон статистика.

## Шаблоны

- Системные пресеты по контексту объекта (лига, сезон, команда, турнир, площадка, секция, мероприятие).
- Бэк-офис: отдельный раздел «Шаблоны контрактов» в группе «Контент» для уполномоченных пользователей с global backoffice.contract.view/manage; можно создавать, редактировать и удалять личные/общие шаблоны с проверкой соответствия permissions типу сущности.
- Пользовательские: личные для всех объектов одного типа или общие внутри конкретной сущности.
- Хранятся название, список permissions и область использования. Выбор шаблона копирует значения в форму, изменения допускаются до приглашения. Сохранение и изменение шаблона требует права управлять контрактами и не может содержать отсутствующие у назначающего права.
- При изменении шаблона существующие ContractPermission остаются неизменными. Шаблон не является дополнительным источником доступа.

## Основания и документы

- Технические контракты не требуют дополнительных документов. Подтверждаемые полномочия и юридические соглашения требуют верификации до применения прав.
- ContractVerification содержит проверяемый источник, решение, reviewer, дату, причину и срок. ContractEvidenceDocument хранит PDF/JPEG/PNG/WebP до 10 МБ на приватном диске. Получатель, назначающий и авторизованный менеджер видят свои файлы; чужие файлы закрыты.
- Решение по документам в бэк-офисе требует независимого права, причины и не допускает самоподтверждения получателем. Вносится в историю договора.
- Одобренный VenueOwnershipClaim создаёт подтверждённый контракт коммерческого владельца, связанный с заявкой; исторические решения VenueOwnership импортируются без создания новых владельцев.
- Одобрение заявки площадки может опираться на документы и проверяемые сведения прежнего предметного процесса. Добавление площадки и коммерческая собственность не эквивалентны.

## Критерии приёмки на dev

1. Создать Event и standalone Game: собственник имеет Event owner-contract, игрок без контракта не управляет; отдельный Game owner не создаётся.
2. Через управление Event пригласить ответственного, проверить pending, accepted, declined и revoke; статус интерфейса совпадает с эффективными правами.
3. Попробовать расширить права, сократить срок, истечь срок; проверять недопущение эскалации, сходимость Event/Games и отсутствие финансового доступа.
4. Создать мероприятие с другим владельцем в Filament: получатель принимает приглашение; до принятия в публичном контуре нет управленческих прав.
5. Старые Event из резервной копии: повторный backfill не дублирует owners и назначения; booking-first, публикация занятия и турнирные матчи сохраняют корректную авторизацию.
6. Создать и применить шаблоны, изменить/удалить их и убедиться, что существующие договоры не меняют свой permission snapshot.
7. Создать не-технический контракт, принять, приложить документ. До решения модератора прав нет; подтвердить/отклонить с причиной. Третьему пользователю скачать документ нельзя.
8. Проверить существующее подтверждённое владение площадкой, новый claim, истечение верификации и отсутствие коммерческих разрешений у обычного primary_manager.
9. Проверить будущую дату начала и истёкшие командные контракты в TeamManagementAccess и интерфейсе.
10. Запустить PHP CI, PostgreSQL migration checks 16/17, Vite build и ручные smoke в обеих темах.

## Границы и rollback

- Конкретные документы и спорные права владения проверяются человеком; отметка legal_agreement сама по себе не подтверждает действительность юридического документа.
- Исторические площадочные документы сохраняются в VenueOwnership и доступны через исходный ограниченный интерфейс, не публикуются в медиабиблиотеку.
- Система не создаёт relation contract на каждую игру. Контракт Event и подтверждения площадок не наделяют пользователя административным правом входа в Filament.
- Слияние допустимо только после успешного полного CI и RBAC PostgreSQL Migration на одном и том же финальном head SHA. Проверка dev в браузере — отдельная стадия.
