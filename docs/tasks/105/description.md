# 105 — Унифицировать формирование участников самостоятельных и турнирных игр

Самостоятельная игра должна использовать общие с турнирными матчами правила, экраны и сервисы управления составом с минимальными отличиями. После утверждения сторон спортивный runtime `Game` не должен зависеть от того, были стороны получены из самостоятельного набора, balanced-пула или `TournamentMatch`.

Для самостоятельной игры поддерживаются два режима:

- **готовые команды** — при создании можно не указывать команды, указать одну уже известную команду либо сразу обе. Одна известная команда остаётся кандидатом и позволяет сценарий «моя команда ищет соперника»; половинчатая `GameSide` при этом не создаётся. Организатор может приглашать команды, а представители команд с соответствующим правом — подавать заявки, пока стороны не утверждены;
- **отдельные игроки** — участники подают заявки, после чего организатор формирует ровно две сбалансированные команды по общей с balanced-турниром механике и при необходимости корректирует preview вручную.

Турнирный матч получает команды из расписания турнира. Для самостоятельной игры существует явное состояние **«стороны утверждены»**. До фактического начала организатор может снять утверждение, заменить стороны и утвердить их заново. Снятие утверждения не удаляет заявки и принятых кандидатов. После фактического старта стороны, состав и основные настройки неизменяемы.

`GameSide` и `GameRosterEntry` являются финальным снимком спортивных сторон. Заявка/приглашение или предварительно выбранная команда сами по себе не создают половинчатую сторону. При утверждении состава все игроки roster должны быть представлены в `EventParticipant`; обратное неверно — участник Event может присутствовать на мероприятии и не входить в игровой roster.

Участием команды в самостоятельных играх управляет владелец команды либо активный участник с постоянным правом команды **«Управлять участием команды в играх»**. Назначать это право может владелец или участник с правом управления правами команды. Право относится к конкретной команде, а не даёт пользователю глобальный доступ ко всем командам.

## Инварианты старта

Фактический старт запрещён, пока:

- для самостоятельной игры не установлен флаг утверждения сторон;
- нет ровно двух `GameSide`;
- один и тот же игрок присутствует на обеих сторонах;
- на одной из сторон недостаточно игроков для требуемого стартового состава;
- не выполнены существующие правила starters/captain.

После фактического старта снять утверждение или пересобрать стороны нельзя.

## Критерии готовности

- единые доменные правила и переиспользуемые UI-компоненты не дублируют турнирную механику;
- самостоятельная игра допускает сценарии «без команды», «одна известная команда ищет соперника» и «две заранее известные команды»;
- заявки и приглашения защищены авторизацией, транзакциями и стабильным порядком блокировок;
- одна команда не может занимать обе стороны;
- предварительный кандидат не материализуется как единственная `GameSide`;
- утверждение сторон можно снять и установить повторно только до фактического старта;
- после начала игры состав и основные настройки изменять нельзя;
- при утверждении roster синхронизируется с организационным слоем `EventParticipant`;
- ключевые переходы статусов и конкурентные сценарии покрыты тестами;
- продуктовая и техническая документация актуализированы.

## Этапы реализации

1. Добавить режим набора standalone-игры, admission-модель и явный флаг утверждения сторон.
2. Разрешить создание игры с нулём, одной или двумя предварительно выбранными командами без половинчатой `GameSide`.
3. Реализовать team/user applications и invitations, включая право `team.game_participation.manage`.
4. Вынести общий balanced engine из Tournament и подключить его к standalone individual draft.
5. Свести финальную материализацию `GameSide + GameRosterEntry` к общему сервису и использовать его в standalone и tournament scheduling.
6. Добавить management/public UI, уведомления, realtime-обновления и полный набор feature/concurrency-тестов.
