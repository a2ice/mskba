# 023 - Переработать статусы площадок и добавить модерационные заявки

## Оригинальное описание

Нужно сделать флоу, при котором пользователь может отправить свою площадку на модерацию со страницы редактирования своей площадки, например `/venues/na-dubninskoi/edit`.

Если площадка отправлена на модерацию, на этой же странице должен отображаться результат модерации и сообщение о причине отклонения. Модератор может отклонить заявку, если пользователь допустил опечатку или нужно запросить дополнительные сведения. Также должен быть статус площадки `blocked`, например если пользователь настойчиво отправляет повторные заявки без исправлений.

После обсуждения принято важное уточнение: `VenueStatusEnum` должен содержать только жизненные статусы площадки (`unconfirmed`, `confirmed`, `blocked`). Удаление должно решаться через soft delete. Дубли и заявки на модерацию не должны быть статусами площадки.

## Подробное описание

Задача состоит из трех связанных, но разных слоев:

1. Жизненный статус площадки.
2. Дубли площадок.
3. Заявки на модерацию и переписка по ним.

### Целевая модель статусов площадки

`VenueStatusEnum` должен описывать только состояние самой площадки:

- `unconfirmed` - площадка еще не подтверждена как публичная;
- `confirmed` - площадка подтверждена и публично видима;
- `blocked` - площадка заблокирована и недоступна для повторных заявок.

`removed` удаляется из enum и заменяется `softDeletes()` в таблице `venues`.

`duplicate` удаляется из enum: дубль - это не жизненный статус площадки, а relation-состояние через `canonical_venue_id` и `venue_duplicates`.

В `venues` добавляется `status_info` nullable text для причины блокировки или служебного пояснения к статусу.

### Дубли площадок

Дубли должны определяться через:

- `venues.canonical_venue_id`;
- таблицу `venue_duplicates`;
- статусы кандидатов дублей в `VenueDuplicateStatusEnum`.

Merge дублей не должен переводить площадку в `VenueStatusEnum::DUPLICATE`. Вместо этого дубль получает `canonical_venue_id`, а жизненный статус остается отдельным.

### Модерационные заявки

Для модерации создается отдельная таблица `venue_moderation_requests`.

Минимальные поля:

- `venue_id`;
- `submitted_by_actor_id`;
- `reviewed_by_user_id`;
- `status`: `pending`, `approved`, `rejected`, `blocked`;
- `submitted_at`;
- `reviewed_at`;
- timestamps.

Для сообщений создается таблица `venue_moderation_messages`.

Минимальные поля:

- `venue_moderation_request_id`;
- `direction`: `incoming`, `outgoing`;
- `author_actor_id`;
- `author_user_id`;
- `message`;
- timestamps.

`incoming` - сообщение пользователя при отправке или повторной отправке заявки.

`outgoing` - ответ модератора: причина отклонения, просьба о дополнительных данных, причина блокировки.

### Пользовательский флоу

- Владелец площадки открывает `/venues/{alias}/edit`.
- На странице доступно минимальное редактирование данных площадки.
- Если нет pending-заявки и площадка не заблокирована, пользователь может отправить площадку на модерацию.
- При отправке создается `venue_moderation_requests.status = pending` и optional incoming-сообщение.
- Если последняя заявка отклонена, на edit-странице отображается outgoing-сообщение модератора.
- Если площадка заблокирована, повторная отправка недоступна, показывается `venues.status_info` и/или последнее outgoing-сообщение.

### Админский флоу

В `/admin/venues` для площадок с pending-заявками должны появиться действия:

- подтвердить;
- отклонить с причиной;
- заблокировать с причиной.

Подтверждение переводит площадку в `confirmed` и заявку в `approved`.

Отклонение оставляет площадку `unconfirmed`, заявку переводит в `rejected`, сохраняет outgoing-сообщение.

Блокировка переводит площадку в `blocked`, заполняет `status_info`, заявку переводит в `blocked`, сохраняет outgoing-сообщение.

## Результат

Реализована первая полноценная версия флоу модерации площадок:

- жизненный статус площадки очищен от `duplicate` и `removed`;
- удаление площадки переведено на soft delete;
- дубли определяются через `canonical_venue_id` и `venue_duplicates`;
- добавлены модерационные заявки и сообщения;
- владелец может открыть `/venues/{alias}/edit`, сохранить минимальные данные и отправить площадку на модерацию;
- администратор может подтвердить, отклонить или заблокировать pending-заявку из `/admin/venues`;
- причина отклонения/блокировки отображается владельцу на странице редактирования.

## Риски и технические заметки

При рефакторинге duplicate workflow важно не потерять существующие связи `canonical_venue_id`.

Миграция enum должна аккуратно обработать существующие значения `duplicate` и `removed`: `duplicate` превращается в `unconfirmed` с сохранением `canonical_venue_id`, `removed` должен быть переведен в soft delete.

Админские решения по заявкам должны выполняться атомарно в транзакции с блокировкой строки заявки и площадки, чтобы две параллельные модерации не дали разные итоговые статусы.
