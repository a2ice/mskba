# 023 - Переработать статусы площадок и добавить заявки модерации

## Оригинальное описание

Нужно сделать флоу, при котором пользователь может отправить свою площадку на модерацию со страницы редактирования своей площадки, например `/venues/na-dubninskoi/edit`.

Если площадка отправлена на модерацию, на этой же странице должен отображаться результат модерации и сообщение о причине отклонения. Модератор может отклонить заявку, если пользователь допустил опечатку или нужно запросить дополнительные сведения. Также должен быть статус площадки `blocked`, например если пользователь настойчиво повторно отправляет площадку без исправлений.

После обсуждения принято важное уточнение: `VenueStatusEnum` должен содержать только жизненные статусы площадки (`unconfirmed`, `confirmed`, `blocked`). Удаление должно решаться через soft delete. Дубли и заявки модерации не должны быть статусами площадки.

## Подробное описание

Задача состоит из трех связанных, но разных слоев:

1. Жизненный статус площадки.
2. Дубли площадок.
3. Заявкаы модерации и переписка по ним.

### Целевая модель статусов площадки

`VenueStatusEnum` должен описывать только состояние самой площадки:

- `unconfirmed` - площадка еще не подтверждена как публичная;
- `confirmed` - площадка подтверждена и публично видима;
- `blocked` - площадка заблокирована и недоступна для повторных заявок.

`removed` удаляется из enum и заменяется `softDeletes()` в таблице `venues`.

`duplicate` удаляется из enum: дубль - это не жизненный статус площадки, а relation-состояние через `canonical_venue_id` и `venue_duplicates`.

В `venues` добавляется `status_info` nullable text для причины блокировки или служебного пояснения к статусу.

### Дубли площадок

Дубли должны определяться через:

- `venues.canonical_venue_id`;
- таблицу `venue_duplicates`;
- статусы кандидатов дублей в `VenueDuplicateStatusEnum`.

Merge дублей не должен переводить площадку в `VenueStatusEnum::DUPLICATE`. Вместо этого дубль получает `canonical_venue_id`, а жизненный статус остается отдельным.

### Заявкаы модерации

Для модерации создается отдельная таблица `moderation_requests`.

Минимальные поля:

- `type`: `venue`;
- `subject_id`;
- `submitted_by_actor_id`;
- `reviewed_by_user_id`;
- `status`: `pending`, `approved`, `rejected`;
- `submitted_at`;
- `reviewed_at`;
- timestamps.

Для сообщений создается таблица `moderation_messages`.

Минимальные поля:

- `moderation_request_id`;
- `sender_id`;
- `receiver_id`;
- `message`;
- timestamps.

`sender_id` и `receiver_id` ссылаются на `actors`, чтобы единообразно хранить сообщения пользователей, гостей и модераторов.

### Пользовательский флоу

- Владелец площадки редактирует её данные на `/venues/{alias}/edit`.
- Статус, причина отклонения/блокировки и отправка на модерацию вынесены на `/venues/{alias}/status`.
- На странице доступно минимальное редактирование данных площадки.
- Если нет pending-заявки и площадка не заблокирована, пользователь может отправить площадку на модерацию.
- При отправке создается `moderation_requests.status = pending` и optional сообщение пользователя.
- Если последняя заявка отклонена, на status-странице отображается последнее сообщение модератора.
- Если площадка заблокирована, повторная отправка недоступна, показывается `venues.status_info` и/или последнее сообщение модератора.

### Админский флоу

В `/admin/venues` для площадок с pending-заявками должны появиться действия:

- подтвердить;
- отклонить с причиной;
- заблокировать с причиной.

Подтверждение переводит заявку в `approved` и диспатчит событие, которое переводит площадку в `confirmed`.

Отклонение оставляет площадку `unconfirmed`, заявку переводит в `rejected`, сохраняет сообщение модератора.

Блокировка не является действием по заявке: это отдельное ручное изменение статуса площадки в `blocked`, причина хранится в `venues.status_info`.

## Результат

Реализована первая полноценная версия флоу модерации площадок:

- жизненный статус площадки очищен от `duplicate` и `removed`;
- удаление площадки переведено на soft delete;
- зафиксирован инвариант: паспортные поля подтверждённой или удалённой площадки не редактируются, а связанные операционные сущности доступны для изменений только у неудалённой и незаблокированной площадки;
- дубли определяются через `canonical_venue_id` и `venue_duplicates`;
- добавлены заявки модерации и сообщения;
- владелец может изменить данные на `/venues/{alias}/edit`, а на `/venues/{alias}/status` проверить статус и отправить площадку на модерацию;
- администратор может подтвердить или отклонить pending-заявку из `/admin/venues`;
- причина отклонения/блокировки отображается владельцу на странице редактирования.

## Риски и технические заметки

При рефакторинге duplicate workflow важно не потерять существующие связи `canonical_venue_id`.

Миграция enum должна аккуратно обработать существующие значения `duplicate` и `removed`: `duplicate` превращается в `unconfirmed` с сохранением `canonical_venue_id`, `removed` должен быть переведен в soft delete.

Админские решения по заявкам должны выполняться атомарно в транзакции с блокировкой строки заявки, чтобы две параллельные модерации не дали разные итоговые статусы. Подтверждение площадки выполняется подписчиком события `ModerationRequestApproved`.
