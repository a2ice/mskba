# DEV: обновление расписания при посещении

Первая реализация задачи 308: без Cron и без общего live execution engine.
Фоновая очередь Redis `venue-schedule-refresh` изолирована от обычных задач.
Повторные посещения используют общий pending marker (120 секунд), прежний
FindSport lock и cooldown 300 секунд. Неуспешная попытка не удаляет снимок.

## Подключение существующего источника

1. DEV → Filament → площадка → Интеграции. Сохранить и вручную применить
   полный снимок разрешённого FindSport, если ещё не применялся.
2. Активировать источник (проверенный API, ровно один зал, занятость и цены).
3. Активировать конфигурацию в режиме «Тестирование» и переключатель
   «Обновлять при посещении». Существующие выключенные настройки не меняются
   автоматически. Для production требуется отдельный релиз и
   `VENUE_INTEGRATIONS_VISIT_REFRESH_ENABLED=true` + статус mskba_allowed.
4. После 5 минут открыть страницу площадки/зала. Страница показывается сразу,
   на расписании статус обновления; при завершении Reverb инвалидирует
   фрагмент, fallback проверяет только локальное состояние раз в 5 секунд.
5. Отключение источника/конфигурации/переключателя прекращает фоновые задания.
   Ручное получение и существующая проверка при открытии дня/расчёте
   сохраняют свои независимые разрешения.

Проверить desktop/mobile/legacy, два окна, свежий снимок, отключённый источник,
недоступность провайдера и Reverb. Отдельно проверить worker:
`docker compose --env-file .env -f compose.dev.yaml -f compose.dev.local.yaml ps venue-schedule-queue`.

Первичное автоматическое применение без ручной проверки, общий MCP/API
исполнитель, автоматический периодический опрос и failover нескольких
источников не входят в этот этап. Пять минут — действующее ограничение
публичного FindSport refresh, а не новый произвольный TTL.
