# 316/003 — Совместимость новой архитектуры с существующей production-БД

Статус: **запланирована; запрещено запускать на живой БД без согласования**.

- Зафиксировать схемы, миграции, таблицы `users/profiles/venues/venue_courts/events/teams/tournaments/content_items/page_seo_settings/media` и прочие связанные таблицы, FK, soft-delete, counters и aliases.
- **Не копировать production-БД на dev как обязательное условие.** Production остаётся источником истины; dev — независимая тестовая БД с собственными ID и содержимым.
- Аудировать миграции, которые ещё не применены на production, и проверить, что новая архитектура читает старые данные. Добавить необходимые **неразрушающие** Laravel migrations/backfill. Проверить FK, уникальные aliases, routeIdentifier и отсутствие конфликтов. При необходимости провести безопасный dry-run в изолированной среде, но не вводить обязательный перенос БД на dev.
- Отдельные идемпотентные backfill-команды для данных, которые требуют преобразования; `--dry-run` по умолчанию и подробный отчёт о конфликте.
- Нельзя вставлять dev data в prod или заменять prod IDs ID тестового dev, даже при совпадающем имени.
- Даты, авторство, истории участия, статистика, SEO-переопределения и ссылки на изображения неизменны, пока не принято другое решение.
- Непосредственно перед production deploy сделать backup текущей PostgreSQL-БД и медиа; должна быть возможность восстановления. Миграции выполняются на **существующей production-БД** через `php artisan migrate --force` в контролируемом деплое.

Приёмка: миграции и чтение прежних сущностей/ID совместимы; production row counts и связи до/после проверены; публичные прежние URL проверены post-deploy. Production не трогать без отдельного разрешения.
