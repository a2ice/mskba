# 316/004 — URL & content parity

Статус: **запланирована**.

- Удалить заглушки с публичных route `/feed`, `/teams`, `/coordination`, `/faq/**` и др. только после восстановления актуального контента и поведения на новой теме.
- Новая тема должна корректно читать сохранённый контент и системные ключи **из существующей production-БД**, использовать прежние aliases и ID-based routeIdentifiers. Разница записей dev/prod нормальна и не требует синхронизации.
- Запретить soft 404 (страница 200 с «Раздел в разработке»). Реальный 404 — только для фактически отсутствующей страницы; не маскировать отсутствие данных перенаправлением на главную.
- Реестр разрешённых legacy mapping. Сначала сохраняем путь, только затем 301 на предметно идентичный canonical.
- Проверить meta/H1/body/images/alt/schema, media файловое хранилище, действующие внешние ссылки, robots, пагинацию и sitemap.
- Автотесты per-URL и ручная проверка популярных переходов, включая ошибки импорта/невидимые сущности.

Приёмка: до production реализованы необходимые публичные шаблоны и динамические маршруты; после применения migrations на production все старые индексируемые адреса отдают прежний контент с 200 (либо доказанный 301), без missing assets и soft404.

## Промежуточный этап — fallback публичных шаблонов

- В `mskba_app` отсутствуют Blade-шаблоны `news.*`, `events.*`, `tournaments.*`, `sports-sections.*`, `participants.index`, `coordination.*` и `faq.*`; существующий `ThemeResolver::page` в этих случаях показывал `system.view_not_found` с HTTP **200**.
- На переходный период разрешён **точечный fallback** на исходный `mskba_dark` только для перечисленных опубликованных GET-страниц при отсутствии app-шаблона: реальные контроллеры, БД и SEO остаются без изменений. После появления нового Blade fallback перестаёт применяться автоматически.
- Промежуточный UI этих страниц остаётся старой темы — **это не окончательный перенос дизайна** и не автоматическая гарантия сохранения всех prod URL. HTTP и контент проверять на production после согласованного релиза.
- Нельзя делать общую подмену на все аккаунтные/административные страницы; не создавать soft-404 с успешным статусом для публичных страниц.

## Dev acceptance: `/events` Page Builder override

После PR #683 на `dev.mskba.ru/events` рендерился не каталог из `mskba_app/views/pages/events/index.blade.php`, а опубликованная CMS-страница с H1 «MSKBA — баскетбол в Москве». HTTP 200 сам по себе не означает корректное содержимое.

Миграция `2026_11_12_150000_restore_laravel_events_catalog_on_dev.php` восстанавливает Laravel-каталог **только** на `APP_ENV=staging` + `APP_URL=https://dev.mskba.ru`, используя существующую обратимую операцию `PageBuilderPublisher::setOverrideEnabled(false)`. Контент Page Builder остаётся опубликованным и доступным для повторного включения в редакторе; `main` и production-БД не меняются.

После деплоя проверить `/events`: H1 «Мероприятия», фильтры, ссылки на реальные события и отсутствие soft-404; для редакционных CMS-публикаций — сохранность snapshot/override истории.

## Этап 316/004 — подробные страницы игр, турниров и секций

- Проверена текущая структура: страницы событий (включая игру и live-режим), турниров и секций уже существуют как сложные функциональные Blade-шаблоны в `mskba_dark` (участие, результаты, расписание, карты, регистрация). Их упрощённая замена нарушила бы функциональный parity; сохраняем действующий публичный bridge, пока отдельные полноценные версии `mskba_app` не готовы.
- Устранён пропуск whitelist временного `ThemeResolver` fallback: `events.game-show`, `events.game-live`, `events.game-qr-join`, `tournaments.on-site-registration`. Эти маршруты раньше могли отдавать пустую `MSKBA App theme` заглушку с HTTP 200.
- Добавлены feature tests в `SeoLegacyEntityDetailParityTest`: обычная опубликованная тренировка, standalone game, mini-game, live, публичное QR-присоединение, турнир с URL `id-alias`, регистрация на турнире, секция по alias. Проверяются 200, контент конкретной БД, SEO title/canonical, 404 на несуществующие сущности и noindex dev.
- Production-БД по-прежнему не изменять. Проверка URL базируется на одинаковых prod-данных до/после production deploy, а не на несовпадающих записях dev/prod.
