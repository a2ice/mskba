# 218 — Оптимизировать локальную тестовую стратегию и CI без потери regression gate

## Контекст

Текущий GitHub Actions workflow `.github/workflows/ci.yml` запускается на каждый
pull request в `main` и выполняет один полный job:

- checkout;
- PHP 8.4 + Node 22;
- Composer install;
- подготовка Laravel;
- проверка production compose;
- `php artisan test`;
- npm install;
- production frontend build.

`phpunit.xml` включает целиком `tests/Unit` и `tests/Feature`. Следовательно,
текущий CI не выбирает тесты по роутам или изменённым файлам: перед merge
выполняется полный PHP regression suite.

Тесты проекта уже хорошо разбиты по предметным каталогам:
`tests/Feature/Venue`, `Event`, `Identity`, `Finance`, `Pricing`,
`Tournament`, `Team`, `SportsSection` и т.д. Это позволяет сделать быстрый
локальный контур без ослабления финальной проверки.

Отдельная проблема локальной работы через VS Code/Codex: полный suite может
упираться в PHP `memory_limit=128M`, выдавать большой объём вывода и провоцировать
повторные тяжёлые прогоны. Лимит PHP-процесса не является лимитом токенов Codex,
но лишний вывод, повторный анализ ошибок и повторные запуски косвенно увеличивают
рабочий контекст агента.

## Цель

Разделить две ответственности:

1. **быстрый локальный feedback loop** для человека/Codex;
2. **полный независимый regression gate** в GitHub перед merge.

Локальная оптимизация не должна превращаться в механизм, который решает, какие
регрессии можно не проверять перед merge.

## Решение

### 1. Полный CI остаётся authoritative gate

Для code PR перед merge должен сохраняться полный набор проверок. Нельзя заменять
его выбором тестов только по route diff, имени папки или эвристике зависимостей.

Причина: изменение общего middleware, модели, migration, enum, permission,
service provider, shared contract или инфраструктурного сервиса может затронуть
контуры, в которых не менялся ни один route.

### 2. Контекстные локальные команды

Добавить стабильные команды для разработки, например:

```bash
make test-unit
make test-context context=Venue
make test-context context=Pricing
make test-file path=tests/Feature/Venue/VenueOwnershipClaimWorkflowTest.php
make test-filter filter=PricingCatalogTest
make test-full
```

Названия могут быть уточнены при реализации, но интерфейс должен позволять Codex
запускать минимально необходимую проверку без ручного конструирования docker/php
команды каждый раз.

`test-context` должен использовать уже существующую структуру
`tests/Feature/{Context}`; при наличии одноимённого `tests/Unit/{Context}`
запускается и он.

### 3. Политика для Codex / IDE

Зафиксировать в developer documentation:

- после небольшого изменения сначала запускать конкретный test/file/filter;
- затем профильный context suite;
- полный suite локально запускать только когда изменение затрагивает shared code,
  миграции, общие middleware/contracts либо когда нужно воспроизвести CI;
- финальный полный suite всё равно выполняет GitHub CI.

Автоматический анализ diff может **подсказывать** связанные suites, но не должен
быть единственным safety gate.

### 4. PHP memory diagnostics

Перед изменением лимитов проверить реальный runtime локального Codex/Docker:

```bash
php -r 'echo ini_get("memory_limit"), PHP_EOL;'
php --ini
```

Если 128M действительно является причиной падения полного suite, предоставить
явную test-only команду с повышенным memory limit, например через
`php -d memory_limit=512M artisan test`, не меняя production runtime глобально.

Повышение лимита не должно скрывать тест с реальной утечкой памяти: сначала
фиксируется, какой test/suite упирается в лимит.

### 5. Компактный вывод

Локальные test-команды должны по возможности использовать компактный режим
PHPUnit/Laravel и не печатать полный успешный лог, если он не нужен. При падении
должен сохраняться достаточный вывод для диагностики.

Цель — уменьшить шум терминала и объём материала, который IDE-agent вынужден
перечитывать.

### 6. Docs-only PR

Сейчас документационный PR всё равно запускает полный PHP suite и frontend build,
хотя production deploy уже корректно игнорирует `docs/**` и `README.md`.

Нужно сделать дешёвый docs-only путь, но сохранить один предсказуемый итоговый
required check:

- workflow всегда стартует на PR;
- сначала определяется тип изменений;
- для docs-only выполняются только проверки документации/целостности ссылок;
- для code changes выполняются PHP regression + production compose + frontend;
- итоговый gate имеет стабильное имя, чтобы branch protection не зависал из-за
  полностью пропущенного workflow.

Если branch protection не использует required checks, всё равно сохранить
одинаково читаемый результат CI.

### 7. Параллелизация полного suite — только после измерения

Не дробить PHP suite на множество runner jobs только ради архитектурной красоты.
Сначала измерить длительность текущих этапов.

Если PHP tests действительно являются bottleneck, рассмотреть shards по
предметным группам, при этом:

- все группы запускаются;
- shared/integration tests не теряются;
- failure любой группы блокирует merge;
- суммарное время runner minutes не должно необоснованно вырасти.

## Не делать

- не выбирать CI-тесты по Laravel routes;
- не считать `app/Modules/X` гарантией, что затронут только X;
- не пропускать полный regression suite для обычного code PR;
- не поднимать production `memory_limit` только из-за локальных тестов;
- не заставлять Codex после каждого маленького edit запускать весь проект.

## Проверки готовности

- есть документированная локальная test strategy;
- есть простые команды file/filter/context/full;
- локальный контекстный прогон не требует полного suite;
- причина 128M диагностируется и test-only override при необходимости работает;
- code PR по-прежнему получает полный regression gate;
- docs-only PR не тратит ресурсы на PHP/frontend без необходимости;
- итоговый CI status остаётся однозначным перед merge.

## Наблюдение при постановке задачи

Документационный PR #243 показал проблему на практике: при изменениях только в
`docs/**` GitHub всё равно установил PHP/Node/Composer и прогнал весь suite.
Из 972 тестов 971 прошёл, а один `VenueShowPageTest` упал на слишком широком
`assertDontSee('Jun')`. Параллельный CI Task 217 прошёл успешно, поэтому этот
случай нужно рассматривать отдельно как хрупкую проверку/недетерминированный
failure, а не как регрессию документационного PR.

Это дополнительный аргумент в пользу docs-only пути и более точных локальных
проверок, но не повод ослаблять regression gate для code PR.
