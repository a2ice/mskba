# 177 — Связать спортивные секции с постоянными командами

## Контекст

SportsSection из Task 170 сейчас может быть связана с площадкой, но не с постоянной командой. Требуется позволить одной постоянной команде иметь несколько связанных секций.

## Доменная модель

Связь является `Team 1 → N SportsSection`, а не many-to-many:

- одна постоянная команда может иметь много секций;
- одна SportsSection относится максимум к одной команде;
- в `sports_sections` добавить nullable `team_id` с FK на `teams`;
- при физическом удалении команды связь должна становиться `NULL`, а секция не должна удаляться вместе с командой (`nullOnDelete` или эквивалентная безопасная стратегия);
- добавить `Team::sportsSections()` и `SportsSection::team()`.

Pivot-таблица здесь не нужна: она создала бы ложную семантику many-to-many и усложнила бы уникальность принадлежности.

## Название связанной секции

Название остаётся полем самой `SportsSection`, а не атрибутом relation.

При создании секции из контекста команды:

- `team_id` предзаполнен выбранной командой;
- `name` по умолчанию предзаполнен названием команды;
- пользователь может изменить название секции до сохранения и позднее обычным разрешённым редактированием.

Таким образом у одной команды могут существовать, например, несколько секций с разными названиями, расписаниями, тренерами, площадками и тарифами.

## UI и flow

Добавить безопасный flow:

- создание новой секции из контекста команды;
- выбор/смена связанной команды в управлении секцией, если пользователь имеет необходимые полномочия;
- снятие связи с командой без удаления секции;
- отображение связанной команды в account/public SportsSection UI;
- отображение связанных секций в подходящем management-контексте команды.

Не вводить скрытого автоматического ACL через сам факт связи.

SportsSection продолжает использовать собственные `owner|manager`, head coach и permissions из Task 170. Связь с Team сама по себе не должна давать team manager право редактировать секцию. Для создания секции из Team-контекста нужно явно проверить подходящее существующее Team permission и одновременно сохранить действующие требования SportsSection к подтверждённому coach; конкретное Team permission выбрать и документировать при реализации, а не выводить неявно из relation.

## Инварианты

- временная команда не может быть организационным владельцем долгоживущей SportsSection;
- связывать можно только существующую постоянную команду;
- IDOR: пользователь не может назначить секции произвольный `team_id` без требуемых полномочий;
- архивирование/блокировка команды не уничтожает секцию; публичное отображение relation должно учитывать фактическую доступность команды;
- изменение Team не должно задним числом менять snapshot уже созданных TrainingSession/Event.

## Каталог и фильтры

Подготовить relation для дальнейшего использования Task 178:

- eager-loading без N+1;
- фильтрация SportsSection по Team;
- возможность показать badge/link команды на карточке секции.

Сам перевод каталога на `default_category` в эту задачу не входит.

## Критерии приёмки

- одна Team имеет N SportsSection, SportsSection — не более одной Team;
- pivot не создаётся;
- создание из Team предзаполняет название команды, но название секции остаётся редактируемым;
- unlink не удаляет секцию;
- relation не обходит SportsSection ACL;
- feature/domain tests покрывают создание, linking/unlinking, IDOR, удаление/архивирование Team и отсутствие каскадного удаления SportsSection;
- документация Task 170/specification обновлена;
- `git diff --check` и профильные tests.
