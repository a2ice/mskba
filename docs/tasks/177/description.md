# 177 — Связать спортивные секции с постоянными командами

## Контекст

SportsSection и Team — самостоятельные сущности. Для связи между ними заранее не фиксировалась кардинальность, потому что реальный сценарий допускает общую школу/секцию с несколькими командами, например «Химки», «Химки-96», «Химки-98».

## Решение по кардинальности

Проверены три варианта:

1. `Team 1 → N SportsSection` не подходит: одна секция не сможет объединять несколько постоянных команд.
2. `SportsSection 1 → N Team` покрывает школу с несколькими командами, но искусственно запрещает одной команде быть связанной с несколькими тренировочными контурами.
3. Выбрана модель **`SportsSection M ↔ N Team`** через отдельную таблицу связи.

M:N не делает одну сущность владельцем другой, покрывает оба направления связи и не смешивает их права доступа, составы, расписания и lifecycle.

## Реализация

- добавлена таблица `sports_section_team` с составным первичным ключом `(sports_section_id, team_id)` и обратным индексом `(team_id, sports_section_id)`;
- на моделях SportsSection и Team добавлены `belongsToMany` relations;
- связывать можно только постоянные команды (`temporary_for_event_id IS NULL`);
- создание связи требует права `section.manage` на секции и `team.settings.edit` на команде;
- удаление связи требует `section.manage` и не удаляет Team или SportsSection;
- сама связь не выдаёт никаких дополнительных прав ни в Team, ни в SportsSection;
- добавлен отдельный account-экран «Команды» для управляемой секции;
- изменение связи не меняет уже созданные TrainingSession/Event snapshots;
- Task 178 сможет фильтровать секции по команде через relation и eager loading без N+1.

## Названия

Название остаётся свойством SportsSection. Общая секция может называться «Химки», а связанные команды — «Химки-96», «Химки-98» и т.д. Если позже появится создание секции из команды, имя команды может быть только начальным предзаполнением.

## Проверки

`SportsSectionTeamRelationTest` покрывает:

- несколько Team у одной SportsSection;
- одну Team у нескольких SportsSection;
- unlink без удаления сущностей;
- запрет связи без управления Team;
- отсутствие расширения Team ACL после связи;
- запрет временной Event-команды;
- IDOR для account-экрана связи.

## Критерии приёмки

- выбранная кардинальность зафиксирована до merge;
- схема БД соответствует решению M:N;
- linking/unlinking и права покрыты тестами;
- документация Task 170 обновлена итоговой моделью;
- полный CI должен пройти до merge.
