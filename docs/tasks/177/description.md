# 177 — Связать спортивные секции с постоянными командами

## Контекст

SportsSection сейчас может быть связана с площадкой, но не с постоянной командой. Связь с командами нужна, однако её кардинальность **не считается утверждённой заранее**.

Показательный реальный сценарий: одна общая секция/школа «Химки» может объединять несколько постоянных команд, разделённых по возрасту или составу — например, «Химки-96», «Химки-98». Поэтому прежняя предварительная гипотеза `Team 1 → N SportsSection` не должна автоматически превращаться в `sports_sections.team_id`.

## Обязательная точка согласования перед реализацией

Когда дойдём до Task 177, сначала отдельно сравнить минимум три модели:

1. `Team 1 → N SportsSection` — одна секция относится максимум к одной команде.
2. `SportsSection 1 → N Team` — секция/школа является общей структурой для нескольких команд.
3. `SportsSection M ↔ N Team` через pivot — одна секция может работать с несколькими командами и одна команда потенциально может использовать несколько секций.

Решение принимается только после проверки реальных flow: ownership, ACL, создание сущностей друг из друга, тренеры, расписание, площадки, заявки и будущие фильтры каталога.

До этого решения:

- не добавлять `sports_sections.team_id`;
- не создавать pivot «на всякий случай»;
- не фиксировать кардинальность в specification как принятую;
- не выводить права одной сущности из самого факта relation.

## Названия

Название остаётся свойством `SportsSection`. Для сценария общей секции она может называться «Химки», а связанные команды — «Химки-96», «Химки-98» и т.д.

Если будет flow создания секции из команды, название команды допустимо использовать как начальное предзаполнение, но не как обязательное постоянное имя.

## Общие инварианты

Независимо от выбранной кардинальности:

- связываются постоянные команды, если отдельно не принято иное правило;
- unlink не удаляет секцию или команду;
- relation не должна автоматически расширять SportsSection ACL или Team ACL;
- архивирование/блокировка одной сущности не должно уничтожать другую;
- изменение relation не меняет задним числом snapshot уже созданных TrainingSession/Event;
- каталог Task 178 должен поддерживать фильтрацию по итоговой Team relation без N+1.

## Критерии приёмки

- до миграции явно зафиксирована выбранная кардинальность и причины выбора;
- схема БД соответствует этому решению;
- linking/unlinking и permissions покрыты тестами;
- документация Task 170/specification обновлена итоговой моделью;
- `git diff --check` и профильные tests проходят.
