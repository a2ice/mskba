# 325 — Объединение production и dev данных MSKBA

## Цель и приоритеты

Решение владельца проекта от 17.11.2026: новая версия кода и схемы — из dev;
пользователи, способы авторизации, команды, турниры, игры и история их связей —
из действующего production; ценные площадки, залы, настройки и реальные
учётные записи dev импортируются с обязательным сопоставлением объектов.

Это расширяет первоначальный план задачи [316](../316/description.md), где
импорт записей dev в production ещё не входил в объём. SEO- и URL-gates 316
не ослабляются. Источники не изменяются до успешной репетиции.

## Что установлено по репозиторию (не по живым БД)

- Исторические файлы миграций main/dev на 17.11.2026: 169 общих
  идентичных и ещё 116 в dev.
- Идентичность исходного текста миграций не доказывает совпадение реальных
  схем и сохранность конкретных данных.
- Есть users.canonical_user_id и user_duplicates (задача 101).
  Это identity resolution, не универсальный перенос исторических профилей.
- Права владельцев команд/турниров восстанавливаются через contract
  backfill; площадкам нельзя назначать коммерческих собственников без
  договорного подтверждения.
- Runtime-данные PostgreSQL и медиа в GitHub недоступны. Численность
  пользователей, совпадения учётных записей и объём коллизий не измерены.

## Инварианты безопасности

1. Никаких операций с живой production-БД до подтверждённых бэкапов,
   успешного восстановления и репетиции на изолированной копии.
   Не выполнять destructive migrate:fresh, db:wipe, TRUNCATE и
   pg_restore --clean на исходных базах.
2. Не смешивать числовые ID двух источников. Для импорта dev составлять
   устойчивую карту (source, entity_type, source_id) → target_id.
   Проверять FK, уникальность и polymorphic scope_type/scope_id.
3. Финансовые записи, кошельки, реальные или тестовые платежи, счета,
   внешние холды, возвраты и бонусные операции: отдельный блок сверки,
   вне универсального автопереноса.
4. Не переносить тестовые полномочия, системные аккаунты, session records,
   токены, очереди, ключи и secrets из dev в prod.
5. Совпадение email/phone/Telegram/FIO само по себе только кандидат на
   объединение. Доступ к prod-аккаунту и права не выдавать без проверенного
   владения или предусмотренного superadmin resolution.
6. Сохранять prod password hashes, verified contacts, статусы и прежние
   способы входа. Проверять совместимость шифрования (APP_KEY);
   не подменять prod-ключ dev-ключом.
7. Сохранять фотографии, аватары, логотипы, документы с checksum и
   ссылками. Бэкап БД без media backup — не полная резервная копия.
8. Старые production URL и идентичность сущностей из задачи 316 сохранять.
9. Персональные snapshots хранить только в защищённой временной среде.
   Не загружать dumps, PII, mapping с реальными пользователями и
   credentials в GitHub.

## Этап A — фактическая инвентаризация

- [x] Проверить diff исторических миграций GitHub.
- [x] Подготовить read-only CLI для агрегатов PostgreSQL и сравнения.
- [ ] Получить runtime-доступ к production и dev.
- [ ] Снять на обоих источниках фактическую схему, ledger миграций,
      количества пользователей, команд, турниров, игр, площадок,
      договоров, зальных зон, медиа и критических зависимостей.
- [ ] Проверить наличие исторического PostgreSQL volume
      mskba_postgres_data и ценность его данных.
- [ ] Классифицировать real/test/dev-only объекты и коллизии.

Инструменты инвентаризации запускаются на КОПИЯХ БД в отдельном окружении
с кодом этой ветки (не требуют добавления команды в текущий main):

    php artisan mskba:data-merge:audit --label=prod --output=/secure/path/mskba-prod-inventory.json
    php artisan mskba:data-merge:audit --label=dev --output=/secure/path/mskba-dev-inventory.json
    python3 scripts/data-merge/compare-inventories.py /secure/path/mskba-prod-inventory.json /secure/path/mskba-dev-inventory.json

Отчёты содержат только названия схемы, миграций, агрегированные counts и
контрольные hashes. Команда не ищет дубли личностей и ничего не переносит.

## Этап E — выпуск

- [ ] Два повторных прогона из одинаковых snapshots дают одинаковый
      результат и нулевые критические необработанные конфликты.
- [ ] 100% подтверждённых production users/teams/tournaments/games
      присутствуют с правильными собственниками и историей.
- [ ] Всё из утверждённого whitelist dev перенесено; исключения
      перечислены и приняты явно.
- [ ] Нулевые orphan FK/polymorphic links. Проверены авторизация,
      уведомления, права, бронирования и SEO-гейты 316.
- [ ] Подготовлен проверенный rollback к старому code+DB+media,
      учитывающий новые записи после переключения.
- [ ] На финальном cutover остановить записи на ОБОИХ источниках,
      сделать свежий consistent snapshot, собрать final candidate,
      повторить import/gates, переключить production, открыть записи,
      выполнить smoke.
- [ ] Dev остаётся отдельным окружением, без доступа к живой prod DB.
      Для дальнейшей разработки использовать независимые данные.
- [ ] После релиза проверить новые регистрации, Telegram, финансы
      и контроль URL/поисковой индексации по задаче 316.

## Решение на данный момент

Предпочтение: копия production + dev-миграции + whitelist import dev.
Это должно сохранить prod первичные ключи и исторические маршруты.
Окончательно направление выбирается только по результатам A–C.
Реальные БД ещё не проверены: backup, перенос, авторизация и production
deploy НЕ считаются выполненными.

## Дополнительный путь инвентаризации без Desktop Commander (17.11.2026)

RDC-подключения недоступны из-за исчерпанного лимита. Для фазы A добавлен
отдельный workflow `.github/workflows/data-merge-remote-audit.yml`,
который подключается через уже имеющиеся SSH-секреты GitHub Actions к
раздельным prod/dev runtime и исполняет исключительно SELECT в PostgreSQL
с включённым `default_transaction_read_only=on`.

Workflow печатает **только агрегированные counts, список последних пяти
названий миграций, версии PostgreSQL, отпечаток структуры, SHA кода**
и факт наличия исторического volume; никаких пользовательских строк,
логинов, контактов, секретов или дампов в GitHub Actions logs не отправляется.
При неожиданном несовпадении APP_URL/APP_ENV выполнение останавливается.
Используется одноразовый push-trigger изменения самого workflow и ручной
workflow_dispatch; production deploy workflow не запускается.

Результат этого SSH-аудита не заменяет проверку настоящих резервных копий.
Реальное объединение на isolated candidate, импорт, smoke и cutover
остаются заблокированы до подтверждённого доступа к копиям данных.
