# 068D — типизированные варианты

Статус: реализовано.

## Реализовано

- редакторы для текста, даты, времени, даты-времени, временного интервала и
  площадки;
- `PollOptionValue` нормализует значение, формирует единый label для Web и
  Telegram и предоставляет стабильный ключ поиска дублей;
- `PollOptionValueFactory` проверяет payload в зависимости от `subject_type`;
- площадкой может быть только подтверждённая и операционно активная сущность;
- организатор может разрешить пользовательские предложения;
- предложение проходит тот же value object и серверные инварианты, что и
  исходные варианты;
- повторяющиеся предложения и превышение лимита в 20 вариантов запрещены;
- после добавления публикуется `PollChanged`, поэтому Telegram-публикации
  обновляются штатным асинхронным процессом.

## Формат `coordination_poll_options.value`

- `text`: `{"value": "..."}`;
- `date`: `{"date": "YYYY-MM-DD"}`;
- `time`: `{"time": "HH:MM"}`;
- `datetime`: `{"datetime": "YYYY-MM-DDTHH:MM"}`;
- `time_interval`: `{"starts_at": "HH:MM", "ends_at": "HH:MM"}`;
- `venue`: `{"venue_id": 123}`.

JSON остаётся техническим хранилищем discriminated value, но произвольный
payload в него не попадает: запись разрешена только через фабрику.

## Конкурентный доступ

Добавление пользовательского варианта блокирует строку poll. Внутри этой
границы повторно проверяются статус, дедлайн, разрешение предложений, лимит и
дубликат. Благодаря этому два одновременных запроса не обходят лимит.

Последовательные poll намеренно не входят в эту подзадачу. Для них нужен
отдельный lifecycle решений и переходов; он описан в 068F.
