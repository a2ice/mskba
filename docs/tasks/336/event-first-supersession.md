# Task 336 — отмена групповой архитектуры, замена на Event-first

Принято 18.11.2026. **Эта запись заменяет прежнюю концепцию PlayOpportunity/PlayGroup, собраний и выборов администраторов.** Основная спецификация: [Event-first revision](../287/event-first-revision-20261118.md).

## Что не внедрять из PR #850

- Новые PlayOpportunity, PlayGroup, отдельные group membership, group elections, group candidate/vote/assembly, group-owned discussion и group-only права;
- Автоматическое создание групп из PlayIntent и параллельную модель участия;
- Полный merge #850: он содержит неприемлемую теперь схему и связанные миграции.

## Что можно выборочно перенести

- `SocialActionLimiter` — строгий общий лимит изменяющих действий пользователя (3 за скользящие 60 секунд) с блокировкой canonical user;
- `SocialWallService`, `EventSocialWallController`, `SocialWallEntry` и необходимые миграции **только в части Event**, без group scopes и мёртвых внешних ключей;
- Транзакционную историю переходов `EventParticipant` (confirmed/tentative/left), идемпотентность, актуальные счётчики, права участников/организатора;
- Комментарии до 200 символов, soft-delete с зачёркиванием, скрытие модератором, раздельные вкладки обсуждения и истории;
- Тесты Event wall, RSVP, лимита, конкурентных запросов, безопасности. Повторно проверить применимость для активной темы `mskba_app`, а не переносить только `mskba_dark`.

## Граница релиза

Один Event с организатором и обсуждением. Отдельная бронь только через существующий Booking flow. PlayIntent — источник подписчиков, а не группа. Создание без определённых площадки/даты — явное состояние согласования; нельзя подменять null фиктивной датой, молча резервировать слот или отправлять уведомление о конкретной игре без достаточных параметров.

PR #851 — рабочий черновик, не merge до реализации всех перечисленных сценариев, зелёного CI и проверки desktop/mobile/TMA. После merge — отдельно проверить фактический production deploy.
