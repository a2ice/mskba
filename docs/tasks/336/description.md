# 336 — Мероприятие как центр подбора игроков и общения

**Решение 18.11.2026:** прежняя концепция динамических групп интересов, выборов администратора и отдельной организационной сущности отложена как избыточная. Используем существующее Event и ответственного организатора. Draft PR #850 не вливать целиком: взять только независимую стену мероприятия и журнал RSVP, без PlayOpportunity/PlayGroup.

## Пользовательский процесс

1. Два входа в **один и тот же** диалог создания Event: каталог /events без площадки по умолчанию и страница /venues/{id}, где текущая площадка подставляется, но может быть заменена. Один backend: events.store → SubmitEventWizardHandler → Event.
2. Указание типа, названия, площадки, даты/времени, длительности, открытости, лимита и описания. Краткая форма с основными полями, полный прежний wizard остаётся. На этом этапе место и дата обязательны: действующие Event, availability, подбор и расписания требуют venue_id/starts_at/ends_at. Факультативное место/время — будущий отдельный проект, не выдумывать фиктивные значения.
3. Для опубликованной открытой игры или игровой тренировки с началом в будущем асинхронно после commit ищем активные PlayIntent с включённым notify_matches и подходящими площадкой, доступом, географией, удобствами, датами, временным окном, форматом и длительностью (когда указаны). Для тренировки с явно требуемым форматом игры — нет совпадения. Отправляем ссылку на Event через текущие UserNotification и game_delivery_channels. Избранное само по себе не означает согласие на игровые рассылки.
4. Уникальная пара (Event, канонический User) в event_interest_notification_deliveries не даёт дублей на retries, RSVP или при нескольких совпавших подписках. Себе, заблокированным, удалённым и при private/draft рассылки нет. Email/Telegram через существующие jobs, только по подтверждённому контакту и разрешённым пользовательским настройкам.
5. Адресат открывает страницу и выбирает «Пойду / Думаю / Не пойду». Счётчики берутся из актуального EventParticipant. Изменения статуса попадают в неизменяемую системную историю; комментарии до 200 символов, удаление — перечёркивание. Не более 3 пользовательских социальных действий за скользящие 60 секунд на канонического пользователя; no-op не расходует лимит. Доступ к переписке только по серверным правам участников.
6. Обсуждение и история на странице Event имеют табы, сохраняют breadcrumbs, sidebar, header/footer и мобильную навигацию. Организатор наделён текущими штатными правами, отдельного избираемого администратора группы нет.
7. Мероприятие не равно Booking. Организатор использует существующий quote/hold/оплату и правила подтверждения зала позже. Публикация с отложенным бронированием честно обозначает отсутствие резерва.

## Границы и приёмка

- Отдельные группы, выборы, самостоятельный PlayAssembly и голосования площадок отложены. При необходимости опросы можно добавить в Event через существующий Coordination.
- Нативный dialog, значения остаются в памяти страницы при закрытии, закрытие backdrop — только pointerdown+pointerup на фоне. Использовать поля, select и кнопки штатной темы; тестировать мобильную и desktop-версию.
- Протестировать два входа, venue preselect, смену площадки, разные типы/форматы и обязательные поля, отсутствие фиктивной аренды.
- Протестировать уведомления: одна доставка на Event/канонического пользователя, отключённый notify_matches, неподходящий день, private/draft, повторное событие, verified contacts.
- Протестировать RSVP: транзакционный журнал/счётчики, 3/60, удаление зачёркиванием, гостевой и чужой доступ.
- Только зелёный CI и релизная приёмка разрешают merge в main; дальше действует штатный production deployment.
