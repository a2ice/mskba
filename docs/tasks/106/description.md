# 106. Новый wizard создания мероприятий

## Статус

Реализовано в `feature/106`; после merge доступно на production по отдельному route `/events/create/wizard`. Текущий flow `/events/create` пока остаётся основным до отдельного переключения CTA после ручной проверки.

## Цель

Сделать единый адаптивный wizard для создания `game`, `training` и `game_training`, который показывает пользователю только понятные продуктовые решения, динамически перестраивает следующие шаги и сохраняет существующие серверные гарантии создания `Event + VenueBooking + Game`.

## Базовые решения

- Тип мероприятия обязателен и влияет на граф следующих шагов. Если тип передан во входной ссылке, он выбран по умолчанию, но остаётся изменяемым.
- Для `game` обязательны формат и режим набора. Preset автоматически задаёт технические поля (`side sizes`, scoring, timing); расширенные поля показываются только для `custom`.
- Дата/время и длительность обязательны и влияют на доступность площадки.
- Площадка обязательна. Используется существующий predictive venue selector и серверная `VenueEventAvailability`.
- Игровая зона является физическим ресурсом и не зависит от типа или формата мероприятия. Для площадки минимум с двумя кольцами доступны вся площадка, половина A и половина B; занятые варианты отключаются по данным серверной проверки.
- При `preformed_teams` команды на этапе создания необязательны. Выбор своей управляемой команды фиксирует её как собственный selection; выбор чужой доступной команды приводит к invitation/consent flow задачи 105.
- Команды с выключенным `accepts_competition_invitations` скрыты от внешнего выбора, но остаются доступны собственному уполномоченному представителю.
- При `individual_draft` команды не выбираются; участники набираются после создания, затем формируются balanced-команды.
- Название генерируется автоматически и не должно быть обязательным отдельным решением пользователя, хотя остаётся редактируемым и серверно required.
- Описание, лимит участников и Telegram-публикация являются пропускаемыми.
- Перед submit показывается review; отсутствие команд является предупреждением, а не блокирующей ошибкой.
- Незавершённый wizard не создаёт Event/бронь в БД. Реальное создание происходит только финальным submit через существующий `events.store`.
- Нативный submit до финального review блокируется, повторный submit защищён.
- После server-side validation error введённые значения восстанавливаются и wizard возвращается к релевантному шагу.
- Поиск площадок сохраняет двухкольцевую площадку в выдаче, если свободна хотя бы одна допустимая половина, и повторно переоценивает зоны после изменения времени.

## Шаги

### Игра

1. Тип мероприятия.
2. Формат и набор.
3. Дата, время, длительность.
4. Площадка и игровая зона.
5. Команды либо описание дальнейшего individual recruitment.
6. Название/описание/видимость.
7. Публикация.
8. Проверка и создание.

### Тренировка / игровая тренировка

1. Тип мероприятия.
2. Дата, время, длительность.
3. Площадка.
4. Участники/лимит.
5. Название/описание/видимость.
6. Публикация.
7. Проверка и создание.

`game_training` не получает глобальный обязательный формат игры: внутренние мини-игры создаются отдельно и могут иметь разные форматы.

## UI

- Desktop: основной card wizard + sticky summary справа.
- Mobile: один вопрос на экран, progress сверху, sticky navigation снизу.
- Team picker: два слота сторон, predictive search, сетка логотипов 4×4 видимой области на desktop и 3 колонки на mobile.
- Review позволяет вернуться на конкретный шаг.

## Безопасность миграции UI

Новый route: `/events/create/wizard`. Текущий `/events/create` остаётся неизменным и доступным как fallback. Основные CTA намеренно не переключены: production deploy задачи 106 нужен для ручной проверки desktop/mobile flow. Переключение основных CTA выполняется отдельным финальным изменением после подтверждения.
