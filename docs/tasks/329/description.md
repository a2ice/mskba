# 329 — Ручное назначение и безопасное объединение дублей площадок на production

## Проблема

После переноса dev → production обнаружены дубли площадок, включая две подтверждённые карточки «Кампус на Яхромской». Старый детектор работает по расстоянию/типу площадки, а административное объединение отвергает пару, если обе записи подтверждены. При этом исходное объединение только записывало canonical_venue_id и не скрывало дублирующую подтверждённую карточку публично.

## Решение

- В Filament «Контент → Дубли площадок» добавить действие **«Пометить как дубль»**: поиск обеих существующих площадок по имени/ID, выбор пары и создание кандидата с matched_by=manual; подтверждённость обеих записей не меняется. Действие само по себе не меняет карточки и не объединяет данные.
- Существующее действие «Объединить» допускает две подтверждённые карточки, если выбранная каноническая остаётся подтверждённой. Дубль получает canonical_venue_id, is_published=false; обе записи и их история остаются в БД. Ссылка на дублирующую публичную карточку по numeric ID делает 301 на основную. Отдельные данные залов/медиа не копируются автоматически.
- **Безопасность:** если дублирующая площадка содержит мероприятия, бронирования, договорные права, интеграции или расписание залов — объединение отклоняется с перечислением препятствий; нужен отдельный перенос зависимостей. Нельзя обходить это снятием подтверждения.
- Детектор не перезаписывает ручную классификацию и не переоткрывает уже объединённые/отклонённые пары.
- Правила авторизации существующего VenueDuplicateResource остаются прежними, журнал аудита сохраняется.
- Новые проверки: два подтверждённых объекта, скрытие из публичного каталога и редирект, защитный отказ при зависимостях, повторное обнаружение.

## Изменение с точки зрения пользователя

Администратор может найти две ошибочно задублированные площадки, создать кандидата и выбрать основную запись без переключения статуса подтверждения. При наличии связанных операционных данных операция остановится с понятной причиной; пользователи не потеряют бронирования.

## Контроль выпуска

Отдельный PR в main для production (не смешивать с feature/327 в dev). PR #821 прошёл CI и успешно развернут в production (workflow #44276688900). Убедиться в наличии действия в Filament при доступе администратора; фактическое слияние конкретных дублирующихся площадок — отдельная операция. Никаких автоматических правок конкретных данных «Кампус на Яхромской» в рамках релиза кода нет: обе записи нужно сверить по ID, залам, бронированиям и договорным правам перед объединением.

## Уточнение 18.11.2026: конфликт прав у #11 и #20

При фактической попытке объединения #11 (основная) и #20 (дубль) админка показала «есть связанные договорные права». Ручное назначение кандидата работает; защита объединения блокировала **любые**, даже исторические записи `contract_memberships`.

Решение:
- В окне «Объединить» показывать активные и исторические роли каждой выбранной площадки и предложить **явный выбор** для действующих договоров: ничего не изменять (по умолчанию, блокирующий режим), перенести действующие роли с #20 на #11, либо сохранить права #11 и завершить действующие роли #20. Исторические договоры и их членства остаются неизменными и не мешают связыванию записей.
- Менять договорные права может только подтверждённый суперадминистратор. Передача прав не допускается при конфликте ответственных/владельцев на основной площадке; завершение прав не удаляет договоры и фиксирует автора, дату и причину.
- Подтверждённое имущественное владение, договоры со связанными правоотношениями, права на залы, активные пользовательские ограничения и все прежние операционные блокировки требуют отдельного разрешения; тихий перенос недопустим.
- Вся операция (проверки, изменения договорных прав, canonical link, скрытие дубля, статус кандидата, аудит) проводится в одной транзакции. При любой ошибке сохраняются прежние состояния.

**Для пары #11/#20:** выбрать #11 основным, #20 дублем. Если на #11 уже есть ответственный по каталогу, нельзя молча перенести другого ответственного #20; суперадминистратор может сознательно выбрать «Сохранить права основной, завершить действующие роли дубля» после просмотра списка прав в модальном окне. При наличии юридически подтверждённого владения — отдельный процесс, не этот быстрый перенос.

Публикацию кода выполнять через отдельный PR в `main`, успешный CI и штатный production workflow. Не считать реальные данные #11/#20 уже объединёнными до подтверждения операции и проверки публичной страницы.
