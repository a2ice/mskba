# Task 164 — Публичный выбор зала и параметры конкретного зала

## Контекст

Task 162 ввёл `VenueCourt` как отдельный физический зал внутри `Venue`, а Task 163 привязал к конкретному залу бронирования, quotes и Events. На публичной странице площадки при этом пользователь должен понимать, какой именно зал он сейчас просматривает, а характеристики, занятость, активности и входы в бронирование не должны смешивать несколько физических залов одного комплекса.

## Цель

Сделать `VenueCourt` полноценным публичным контекстом страницы площадки и расширить модель зала физическими и коммерческими параметрами.

## Публичный selector и URL

- у площадки с несколькими залами в шапке отображается selector текущего зала;
- основной зал остаётся на каноническом URL `/venues/{venue}`;
- остальные залы доступны по `/venues/{venue}/courts/{court}`;
- nested URL основного зала делает permanent redirect на канонический URL площадки;
- выбранный зал используется для занятости, блока «Игры и мероприятия», CTA создания/бронирования и ссылки на расчёт аренды;
- legacy записи с `venue_court_id = NULL` сохраняют консервативную venue-wide семантику и остаются видимыми/блокирующими для любого зала.

## Характеристики площадки

Первой карточкой блока «Характеристики площадки» добавить «Количество залов».

- при одном зале показывается количество `1`;
- при нескольких залах рядом с количеством доступен selector;
- selector синхронизирован с selector в шапке и ведёт на тот же public court URL;
- «Количество колец» и «Покрытие» берутся из выбранного `VenueCourt`.

## Параметры `VenueCourt`

Добавить:

- `hoops_count` — `1` или `2`;
- `surface_type` — тип покрытия;
- `allows_whole` — можно ли арендовать весь зал;
- `allows_halves` — можно ли арендовать отдельную половину.

`supports_halves` остаётся физической capability и синхронизируется с количеством колец: два кольца позволяют физическое деление, одно кольцо — нет.

### Покрытия

Использовать enum со значениями:

- `parquet` — Паркет / спортивное дерево;
- `sports_pvc` — Спортивный ПВХ / линолеум;
- `rubber` — Резиновое покрытие;
- `rubber_crumb` — Резиновое покрытие с крошкой;
- `asphalt` — Асфальт;
- `concrete` — Бетон;
- `acrylic` — Акриловое покрытие / hard court;
- `other` — Другое.

Покрытие хранится на уровне зала, поскольку разные залы одной площадки могут иметь разные поверхности.

## Управление залами

На `/account/venues/{venue}/courts` для каждого зала доступны:

- название и alias;
- порядок;
- количество колец;
- покрытие;
- «Разрешить аренду всего зала»;
- «Разрешать аренду половин».

При `hoops_count = 1` UI скрывает возможность аренды половин, а backend принудительно сохраняет `allows_halves = false`.

При попытке уменьшить зал с двух колец до одного изменение запрещается, если существуют будущие occupying-бронирования `HALF_A`/`HALF_B` этого зала.

## Наследование

При создании нового зала, если отдельные значения не переданы:

- количество колец наследуется из характеристик родительского Venue;
- `allows_whole` и `allows_halves` наследуются из активной `VenueBookingPolicy`;
- наследованное `allows_halves` применяется только если зал физически поддерживает половины.

После создания настройки зала независимы и могут быть более строгими, чем общая политика площадки. Для half-booking должны выполняться и физическое, и коммерческое разрешения.

## Event wizard

Если пользователь начинает создание мероприятия из контекста конкретного зала:

- CTA передаёт `venue_id` и `venue_court_id`;
- wizard сохраняет `venue_court_id` до финального POST;
- если пользователь внутри wizard меняет площадку, preset court сбрасывается, чтобы hall id другой площадки не мог попасть в запрос;
- backend Task 163 остаётся источником истины и проверяет принадлежность зала площадке.

## Совместимость и безопасность

- не ослаблять privacy rules публичных Events;
- сохранить индикатор достоверности Task 161 и логику `information_warning`;
- public activity endpoint не показывает private/unpublished Event;
- court другого Venue и soft-deleted court недоступны как выбранный контекст;
- существующие callers без court продолжают работать через primary court;
- alias нового зала сохраняет существующую семантику auto-suffix (`small`, `small-2`) внутри одного Venue.

## Acceptance criteria

- площадка с несколькими залами имеет рабочий selector в шапке и в карточке «Количество залов»;
- non-primary court имеет отдельный public URL, primary court остаётся на canonical Venue URL;
- occupancy и activities показывают данные выбранного зала и legacy NULL записи, но не данные другого зала;
- CTA создания мероприятия и аренды сохраняют выбранный court;
- в админке можно установить 1/2 кольца, покрытие и разрешения whole/halves;
- `hoops_count = 1` всегда означает `supports_halves = false` и `allows_halves = false`;
- новый зал наследует разумные значения от родительского Venue/booking policy;
- будущая аренда половины защищает зал от несовместимого уменьшения числа колец;
- regression suite, frontend build и CI зелёные.
