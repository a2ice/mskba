# 102 - Добавить авторизацию и привязку аккаунта через VK ID

## Оригинальное описание

Добавить авторизацию через VK по аналогии с уже существующей авторизацией через Telegram.

## Подробное описание

Нужно добавить VK ID как независимый внешний способ входа в MSKBA, не смешивая его с Telegram-специфичной моделью и функциями Telegram Mini App, бота и уведомлений.

Пользовательский сценарий:

- в общей форме входа доступна кнопка «Войти через VK ID»;
- после перехода в VK ID и успешного подтверждения пользователь возвращается на безопасный callback MSKBA;
- ранее привязанный VK ID авторизует canonical-пользователя;
- при первом входе через ранее неизвестный VK ID создаётся новый неподтверждённый аккаунт MSKBA с каналом регистрации VK ID;
- если пользователь уже авторизован, в аккаунте можно отдельно привязать VK ID;
- если VK ID уже принадлежит другой identity-группе, автоматическая перепривязка или объединение запрещены: создаётся кандидат на дубль для существующего безопасного процесса объединения;
- заблокированный исходный или canonical-пользователь не получает новую сессию.

Технический контракт:

- использовать Authorization Code Flow VK ID с обязательными `state` и PKCE;
- хранить одноразовое OAuth-состояние только в серверной сессии, ограничивать время его жизни и удалять после callback;
- выполнять обмен authorization code и получение профиля через отдельный VK ID client, не доверять данным профиля из браузера;
- не хранить access/refresh tokens после завершения входа, пока приложению не нужен долгосрочный доступ к VK API;
- хранить стабильный идентификатор VK ID, отображаемые профильные данные, исходный безопасный payload и время последней авторизации в отдельной таблице `vk_accounts`;
- защищать создание пользователя и привязку конкурентной блокировкой и транзакцией;
- принимать только локальные безопасные return URL через существующий `SafeAuthenticationRedirectResolver`;
- конфигурацию APP ID, redirect URI и endpoint-ов получать из environment/config; текущий PKCE-контракт не требует client secret.

## Затрагиваемые области

- новый модуль `App\Modules\Vk` с доменной моделью, application use cases, HTTP client и контроллерами;
- модель пользователя и enum канала регистрации;
- OAuth routes входа и привязки;
- общий auth popup и страница подключённых способов входа в аккаунте;
- canonical identity и поиск конфликтующих внешних идентификаторов;
- privacy-документация и техническая документация интеграций;
- миграция `vk_accounts`;
- миграция расширения существующего `users.registration_channel` значением `vk_id`;
- feature-тесты OAuth state/PKCE, callback, повторного входа, блокировки и конфликта привязки.

## Этапы

1. Спроектировать и зафиксировать OAuth-контракт VK ID и границы модуля.
2. Добавить схему данных, конфигурацию и серверный VK ID client.
3. Реализовать начало OAuth, callback, создание/вход пользователя и безопасную привязку.
4. Добавить кнопку в auth popup и страницу управления VK ID в аккаунте.
5. Обновить продуктовую и техническую документацию.
6. Выполнить targeted-тесты, общий релевантный suite и frontend build.

## Критерии готовности

- вход через VK ID работает для нового и существующего VK-пользователя;
- callback с отсутствующим, просроченным, повторным или неверным `state` отклоняется;
- PKCE verifier не передаётся клиенту повторно и очищается после callback;
- одна VK identity не создаёт несколько пользователей при конкурентных запросах;
- VK identity другой identity-группы не перепривязывается автоматически;
- canonical alias приводит к авторизации canonical user;
- конфиденциальные OAuth-токены не сохраняются в базе, логах и frontend-разметке;
- при отключённой конфигурации кнопка VK ID не отображается, routes возвращают контролируемую ошибку;
- документация содержит необходимые переменные окружения и инструкцию настройки callback URI.

## Результат выполнения

Реализован отдельный модуль VK ID с OAuth 2.1 Authorization Code + PKCE, одноразовым серверным `state`, безопасным callback и серверным получением профиля. Добавлены создание и повторный вход пользователя, авторизация canonical identity, блокировка входа заблокированных аккаунтов, привязка из личного кабинета и передача конфликтующей VK identity в общий процесс поиска дублей.

Access/refresh-токены не сохраняются. В `vk_accounts` записываются только стабильный VK ID, имя, фамилия, аватар, время входа и минимальный whitelisted payload. Добавлены migration, environment-пример, кнопки входа, страница VK ID в аккаунте и feature-тесты основных сценариев.

После первой production-проверки устранена несовместимость с уже существующей MySQL-схемой: отдельная миграция расширяет `users.registration_channel`, чтобы база принимала канал `vk_id`. На свежей тестовой базе значение уже присутствовало из актуального enum, поэтому дефект проявлялся только при обновлении существующей базы.
