# 003 - Привести Docker-инфраструктуру проекта к единой dev/prod схеме

## Оригинальное описание

Привести Docker-инфраструктуру проекта к единой dev/prod схеме.

Нужно привести Docker-конфигурацию к профессиональной схеме, где:

- есть один основной `docker-compose.yml`;
- различия между окружениями задаются через переменные окружения и override-файлы;
- локальная разработка и production максимально похожи по составу сервисов;
- dev-инструменты не попадают в production (такие как mailpit, например);
- `Makefile` содержит удобные команды для работы с dev/prod окружениями.

Источник задачи: `B002` из внешнего backlog `../backlog/todo.md`.

## Подробное описание

На этапе планирования дополнительно зафиксировано:

- текущий `docker-compose.yml` использует устаревший project name `mskba`;
- сервис `app` фактически является контейнером `php-fpm`, но назван не по роли, а слишком общо;
- deploy workflow `.github/workflows/deploy.yml` жестко завязан на старую схему `app db nginx`;
- текущий `Makefile` не разделяет dev/prod workflow;
- локальная и production-схемы нужно выровнять от чистой целевой структуры, а не через точечные правки.

Согласованная целевая схема:

- project name: `mskbanew`;
- базовая общая схема для dev и prod:
  - `phpfpm`
  - `nginx`
  - `db`
  - `redis`
- dev-only сервисы:
  - `mailpit`
  - `adminer`
  - `node`, если он действительно нужен для локальной сборки/разработки;
- `mailpit` и `adminer` не должны попадать в production;
- различия между средами должны задаваться через override-файлы и/или переменные окружения, а не через два несвязанных compose-файла.

План реализации:

1. Пересобрать Docker-конфигурацию с нуля вокруг канонического `docker-compose.yml`.
2. Переименовать сервис `app` в `phpfpm` и привести nginx-конфиг к новому имени upstream.
3. Добавить `redis` в базовую схему.
4. Вынести dev-only сервисы в отдельный override-файл.
5. Привести `Makefile` к удобным командам для dev/prod сценариев.
6. Обновить GitHub Actions deploy workflow под новую production-схему.
7. Обновить документацию по окружению и зафиксировать итог в этой задаче.

Ограничения и ожидания:

- локальная и production-среды должны быть максимально похожи по базовому набору сервисов;
- production не должен тянуть dev-only инструменты;
- naming должен быть единым и читаемым;
- изменения допустимо делать как чистую целевую схему без совместимости со старым Docker-стеком, так как прод можно пересобрать заново;
- при необходимости нужно предусмотреть удобный способ полного пересоздания среды.

Проверки:

- проверить `docker compose config` для базовой схемы;
- проверить `docker compose -f docker-compose.yml -f ... config` для dev-override;
- при необходимости запустить локальную среду и убедиться, что Laravel отвечает через `nginx -> phpfpm`;
- при необходимости проверить, что deploy workflow ссылается на актуальные сервисы.

## Результат выполнения

Реализована новая каноническая Docker-схема проекта:

- базовый `docker-compose.yml` теперь использует project name `mskbanew`;
- сервис `app` заменен на предметное имя `phpfpm`;
- базовая общая схема для dev и prod приведена к набору:
  - `phpfpm`
  - `nginx`
  - `db`
  - `redis`
- dev-only сервисы вынесены в `docker-compose.dev.yml`:
  - `mailpit`
  - `adminer`
  - `node`
- nginx upstream переведен на `phpfpm:9000`;
- `Makefile` разделен на команды для base/dev сценариев;
- GitHub Actions deploy workflow переведен на актуальные service names;
- добавлен технический документ `docs/specification/docker-environment.md`.

Дополнительно:

- базовая Docker-схема выровнена на переменные из Laravel `.env.example` для БД;
- в `docker/app/Dockerfile` добавлено расширение `redis`, так как проект уже ориентирован на `REDIS_CLIENT=phpredis`;
- побочный незапрошенный diff из миграции пользователей убран, чтобы задача оставалась строго инфраструктурной.
- на production подтвержден фактический путь репозитория `/var/www/mskba`, поэтому deploy workflow оставлен на этом server path; `mskbanew` используется как Docker project name, а не как обязательное имя каталога на сервере.

## Проверка результата

Выполнены проверки:

- `docker compose config`
- `docker compose -f docker-compose.yml -f docker-compose.dev.yml config`
- `docker compose build phpfpm`

Результат:

- базовая compose-схема валидна;
- dev override корректно мерджится с базовой схемой;
- образ `mskbanew-phpfpm` собирается успешно.

Примечание:

- на текущей машине `docker compose config` все еще показывает имя базы `mskba`, потому что Docker читает существующий локальный `.env`;
- локальный `.env` в рамках задачи намеренно не изменялся;
- канонические defaults в коде и в `.env.example` уже переведены на `mskbanew`.
