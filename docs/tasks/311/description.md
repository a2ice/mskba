# 311 — Оплаты вне MSKBA, задолженности и напоминания представителям площадок

## Цель
После реализации ручного бронирования (Task 310) дать владельцам, коммерческим агентам и ответственным пользователям площадки операционный кабинет контроля **фактически полученных вне MSKBA** платежей, ожидаемых сумм и просрочек. Сохранить принцип: подтверждение бронирования не означает подтверждения оплаты.

## Контекст и переиспользование
- В проекте уже есть `VenueBookingPaymentAttempt`, `VenueBooking.payment_state`, `VenueBookingPaymentState`, `ConfirmVenueBookingPaymentHandler`, отдельное право `rental.payments.confirm`, audit и события.
- Сейчас manual payment confirmation требует `HELD`, `CLAIMED`, действующего окна оплаты; позднее подтверждение по уже `CONFIRMED` бронированию невозможно штатным путём. Не подменять существующий provider payment flow и не переставлять бронирование в `HELD` задним числом.
- Task 310 вводит режим `external_manual` с возможностью подтвердить бронь до оплаты, указать ожидаемый срок/комментарий, позднее зафиксировать полное получение денег. Task 311 дополняет этот режим аналитикой, частичными поступлениями, контролем долгов и напоминаниями.

## Доменная модель
- По каждой подтверждённой вручную брони: сумма к получению в minor units / валюта / получатель (зал или другое юридически/договорно определённое лицо), срок оплаты (nullable), сумма фактически полученных средств, остаток, статус `not_due / due / partially_paid / paid / overdue / forgiven / disputed` как производная/учётное состояние, без ложных утверждений о движении средств MSKBA.
- Учитывать источник quote/snapshot и уже оформленные скидки/комиссии; внешняя задолженность относится конкретному получателю, а не кошельку MSKBA. Не создавать fictitious wallet transactions.
- Создавать журнал поступлений по брони: `amount_minor`, `received_at`, `method` (cash, SBP_direct, bank_transfer, other), `recorded_by_actor_id`, комментарий, необязательное подтверждение/референс. Допускать частичную и несколько оплат, отмену/корректировку только компенсирующей записью с причиной и аудитом; исключать превышение остатка без явного сценария переплаты.
- Финансовый факт помечать как *зафиксировано ответственным*, без приравнивания к банковскому подтверждению, если портал не получал платёжное событие.
- Основной booking остаётся `CONFIRMED` даже если платеж `not_due/overdue`; смена payment state не должна задним числом отменять бронь или изменять занятие слота.
- Определение должника только при положительном остатке и наступившем сроке; без срока — `ожидается оплата`, не просрочено.
- Миграции/версии, lock+idempotency/CSRF и immutable history. При cancelled/rejected/expired учитывать отмены и согласованные обязательства отдельно, не формировать автоматический долг из отклонённых заявок.

## UI для ответственных пользователей площадок
- Таблица «Оплаты по бронированиям»: площадка/зал, бронь, плательщик (только в рамках разрешений), дата/длительность, сумма, получено, остаток, срок, статус, ответственный, последнее действие.
- Фильтры: площадка/зал, ожидают оплату, просрочено, оплачено, частично оплачено, период, ответственный, срок. Общие суммы по доступным пользователю площадкам.
- Карточка брони: история решений и оплат, комментарии, изменить ожидаемый срок с обязательной причиной, «Зафиксировать поступление», в том числе после `CONFIRMED`; не показывать кнопку без `rental.payments.confirm`.
- Право `rental.payments.view` на просмотр и `rental.payments.confirm` на фиксацию/изменения; ограничения contract membership по Venue, superadmin. Не раскрывать данные других площадок.

## Напоминания
- В ЛК ответственного — подписка на напоминания: «ожидают оплаты сегодня», «просроченные», «новые задолженности»; opt-in, настройка частоты (например ежедневная сводка) и каналов через существующие UserNotificationPreferences. Возможность отключить; учитывать timezone и доступные каналы.
- Планировщик Laravel по реальным due dates, идемпотентные outbox/Jobs и dedup: не слать повторы при неизменном состоянии, прекратить при оплате/смене полномочий. Не спамить пользователю-заказчику; отдельная функция напоминания плательщику — только будущая задача с явной политикой согласий.
- Сигналы и показатели: сумма ожидаемая, просроченная, среднее время получения денег. Без раскрытия конфиденциальных сведений в публичных частях портала.

## Обязательный дизайн-контракт
- Перед реализацией смотреть `docs/specification/ui-design-system.md`, реальный UI Kit через Filament → Дизайн → Темы оформления, существующие страницы бронирований и страниц игрока; применять готовые токены/компоненты, не копировать локальные стили. Для backoffice — существующий Filament-гайдлайн.
- Попапы/таблицы/формы строго по утверждённому дизайну: крестик закрытия, никаких лишних eyebrow/пояснений; desktop и mobile, до 360px без горизонтальных обрезаний. Изменение общего компонента — только с обновлением UI Kit и документации по действующему процессу.
- В PR указать использованные UI Kit-эталоны и приложить скриншоты/чек-лист desktop/mobile.

## Приёмка
- Сценарий: бронь 6500 ₽ подтверждена, `received=0`, завтра срок; на следующий день ответственное лицо отмечает 6500 ₽ наличными/СБП и комментарий; остаток становится 0, paid, история и actor сохраняются.
- Дополнительные проверки: частичная оплата 2000 + 4500; due date null/not overdue; просрочка при смене даты; изменение срока с аудиторским следом; повторная команда и гонки; скрытые финансовые данные вне прав; уведомления opt-in/отключение/дедупликация; cancel/refund/dispute edge.
- PostgreSQL feature/unit, privacy/access tests, ручной smoke desktop/mobile; зелёный CI -> merge в `dev` -> успешный deploy -> инструкция проверки -> пользовательская приёмка. Не начинать до приёмки 310. Не трогать main/prod.
