# 006 — Конфликты, блокировки и конкурентный доступ

## Цель
Гарантировать отсутствие двойной аренды при одновременных запросах.

## Статус
Выполнена в `feature/115`.

## Доменные изменения
Интервалы полуоткрытые `[start,end)`. `WHOLE` конфликтует со всеми, одинаковые половины конфликтуют, `A` и `B` могут сосуществовать.

## Миграции
Нормализованный scope (`WHOLE|A|B`), start/end UTC, индексы `(venue_id,status,start_at,end_at)`; половины разрешены лишь при двух физических зонах и включённой policy.

## Handlers и сервисы
Единый conflict checker используется hold, reschedule, extension и confirm.

## Права
Никакой override конфликта через UI; аварийный admin flow — отдельная явно аудируемая команда.

## UI/API
409 с машиночитаемой причиной и актуальными вариантами, без раскрытия приватных данных чужой брони.

## События и jobs
Метрика конфликтов; событие не публикуется при rollback.

## Тесты
Параллельные транзакции для whole/A/B, соседние интервалы, повторный запрос, reschedule.

## Обратная совместимость
Legacy бронь без scope трактуется как `WHOLE`.

## Критерии приёмки
- mutex: сначала lock venue, затем пересекающиеся bookings по id, target и дочерние строки;
- два конкурирующих hold не занимают один ресурс;
- исключён MySQL gap-race за счёт блокировки venue.

## Результат выполнения

- добавлен единый `VenueBookingConflictService` с полуоткрытой геометрией
  `[starts_at, ends_at)`: `WHOLE` конфликтует с любым scope, одинаковые половины
  конфликтуют, а `HALF_A` и `HALF_B` могут удерживаться одновременно;
- блокирующими считаются legacy `PENDING` и новые `HELD/CONFIRMED`;
  `REQUESTED` и терминальные статусы не занимают ресурс;
- Accept и Confirm используют общий checker. После venue mutex пересекающиеся
  записи блокируются `FOR UPDATE` по возрастанию id до блокировки target booking;
  тот же сервис является обязательной точкой подключения будущих reschedule и
  extension commands;
- venue mutex закрывает gap-race: даже если SQL не нашёл существующей строки в
  пустом диапазоне, второй transaction не пройдёт проверку до commit первого;
- при выдаче hold повторно проверяется физическая возможность деления площадки;
  уменьшение числа зон также учитывает активные `HELD`;
- legacy availability, поиск и публичная занятость теперь учитывают `HELD`, но
  старые Event-first маршруты и статус `PENDING` сохраняют прежнее поведение;
- HTTP возвращает `409`, `code=BOOKING_CONFLICT` и до трёх безопасных следующих
  времён без раскрытия данных чужих заявок; конфликт пишет структурированный log
  и cache counter, но не меняет timeline и не публикует `VenueBookingHeld`;
- тесты покрывают whole/A/B, одинаковые половины, соседние интервалы, legacy
  `PENDING`, повторную проверку физических зон, rollback истории и метрику.

Риск deadlock снижается единым глобальным порядком: `venue → пересекающиеся
bookings по id → target booking → child rows`. Нельзя добавлять handler, который
сначала блокирует booking, а затем venue: при встречном выполнении он образует
цикл ожидания. Для PostgreSQL/MySQL venue row служит mutex, поэтому защита не
зависит от gap-lock поведения конкретной СУБД.
