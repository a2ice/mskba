# 006 — Конфликты, блокировки и конкурентный доступ

## Цель
Гарантировать отсутствие двойной аренды при одновременных запросах.

## Доменные изменения
Интервалы полуоткрытые `[start,end)`. `WHOLE` конфликтует со всеми, одинаковые половины конфликтуют, `A` и `B` могут сосуществовать.

## Миграции
Нормализованный scope (`WHOLE|A|B`), start/end UTC, индексы `(venue_id,status,start_at,end_at)`; половины разрешены лишь при двух физических зонах и включённой policy.

## Handlers и сервисы
Единый conflict checker используется hold, reschedule, extension и confirm.

## Права
Никакой override конфликта через UI; аварийный admin flow — отдельная явно аудируемая команда.

## UI/API
409 с машиночитаемой причиной и актуальными вариантами, без раскрытия приватных данных чужой брони.

## События и jobs
Метрика конфликтов; событие не публикуется при rollback.

## Тесты
Параллельные транзакции для whole/A/B, соседние интервалы, повторный запрос, reschedule.

## Обратная совместимость
Legacy бронь без scope трактуется как `WHOLE`.

## Критерии приёмки
- mutex: сначала lock venue, затем пересекающиеся bookings по id, target и дочерние строки;
- два конкурирующих hold не занимают один ресурс;
- исключён MySQL gap-race за счёт блокировки venue.
