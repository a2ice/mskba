# 014 — Переписка, realtime и уведомления

## Цель

Добавить безопасный канал общения по заявке и бронированию, не смешивая пользовательскую переписку с неизменяемым доменным timeline и не превращая сообщения в способ обхода бизнес-команд.

## Доменные изменения

- Ввести отдельную сущность `BookingConversation` и сообщения с автором, временем, типом и необязательными вложениями.
- Участниками переписки являются только стороны конкретной заявки/брони и пользователи с явно выданным коммерческим правом.
- Доменные решения остаются в timeline бронирования; текст сообщения сам по себе не меняет статус, цену, срок hold или площадку.
- Хранить отметки прочтения отдельно от сообщения, чтобы один пользователь не менял общее состояние записи.

## Миграции

- Добавить таблицы conversations, messages и read markers с внешними ключами и индексами по брони, участнику и времени.
- Для вложений использовать существующий безопасный механизм media/storage либо отдельную полиморфную связь без дублирования бинарных данных.
- Старые бронирования получают переписку лениво при первом сообщении; обязательный backfill не требуется.

## Handlers и сервисы

- `SendBookingMessage`, `MarkConversationRead`, `AttachConversationFile`.
- Проверять состояние брони и полномочия на сервере при каждой команде.
- Broadcast выполнять только после commit; повторная доставка события не должна создавать второе сообщение.
- Добавить ограничение частоты, размера и допустимых MIME-типов вложений.

## Права

- Читать и писать могут заявитель, владелец площадки и уполномоченные участники соответствующих сторон.
- Superadmin получает доступ только для поддержки/модерации с записью факта просмотра в аудит.
- Запретить IDOR: принадлежность conversation к booking проверяется независимо от переданного клиентом идентификатора.

## UI/API

- В карточке бронирования показать переписку, непрочитанные сообщения и явные системные записи timeline.
- Визуально и семантически отделить сообщения пользователей от системных событий.
- Предусмотреть пагинацию назад, оптимистичную отправку с client id и fallback polling при недоступном WebSocket.
- Вложения открывать безопасно, без исполнения активного содержимого.

## События и jobs

- `BookingMessageSent`, `BookingConversationRead`.
- Realtime-события публикуются в приватный канал с серверной авторизацией.
- Уведомление второй стороне отправляется асинхронно и дедуплицируется по message id и каналу доставки.

## Тесты

- Feature-тесты доступа сторон, отказа постороннему пользователю и superadmin-аудита.
- Тесты повторной команды, повторного broadcast, пагинации и read markers.
- Тесты MIME/размера вложений, rate limit и XSS-безопасного вывода.
- Realtime-тесты reconnect, пропущенного события и fallback polling.

## Обратная совместимость

- Переписка включается feature flag и не меняет существующие уведомления или timeline.
- При выключенном realtime страница остаётся полностью работоспособной через HTTP.
- Исторические бронирования отображаются без блока переписки до появления первого сообщения.

## Критерии приёмки

- Переписку видят только полномочные участники конкретной брони.
- Сообщения не могут напрямую менять доменное состояние.
- Повторная доставка не создаёт дубликатов, а UI восстанавливается после reconnect.
- Пользовательские сообщения, системный timeline и уведомления различимы и доступны с клавиатуры.
