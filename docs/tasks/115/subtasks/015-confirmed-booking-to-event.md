# 015 — Создание Event из подтверждённой брони

## Цель

Связать аренду с существующими мероприятиями так, чтобы `Event` создавался только из подтверждённой брони, а источником истины по занятости площадки оставался booking aggregate.

## Статус

Выполнена в `feature/115`.

## Доменные изменения

- Добавить явную связь `Event -> confirmed Booking` и уникальное правило «не более одного Event на одну бронь».
- В Event копируются площадка, зона, интервал и необходимые коммерческие snapshot-данные, но изменения занятости выполняются через бронирование.
- Для переноса Event использовать команду reschedule брони с повторной проверкой конфликтов, а не прямое изменение времени Event.
- Поведение Event при отмене подтверждённой брони зафиксировать политикой: отмена, архивирование или ручное решение владельца; не оставлять неявную рассинхронизацию.

## Миграции

- Добавить nullable `booking_id` с внешним ключом и уникальным индексом для новых Event.
- Исторические Event остаются без booking_id и продолжают работать по legacy-сценарию.
- Backfill допустим только для однозначно сопоставимых записей и запускается отдельной проверяемой командой.

## Handlers и сервисы

- `CreateEventFromConfirmedBooking` — транзакционная и идемпотентная команда.
- `RescheduleBookedEvent` делегирует проверку интервала booking-сервису и синхронизирует Event после успешного commit.
- `HandleConfirmedBookingCancellation` применяет зафиксированную политику и пишет оба результата в аудит.
- Запретить создание Event для REQUESTED, HELD, REJECTED, CANCELLED и EXPIRED.

## Права

- Создать Event может заявитель брони либо пользователь с правом управления мероприятиями этой стороны.
- Перенос требует одновременно права на Event и права действовать по бронированию.
- Superadmin может выполнить аварийное действие только с обязательной причиной и audit trail.

## UI/API

- После CONFIRMED показать действие «Создать мероприятие» либо ссылку на уже созданное.
- На Event показывать площадку, зону и статус связанной брони.
- Попытка прямого изменения занятого интервала должна направлять пользователя в flow переноса брони.
- Legacy Event без booking_id визуально помечать только в админском интерфейсе.

## События и jobs

- `EventCreatedFromBooking`, `BookedEventRescheduled`, `ConfirmedBookingCancellationApplied`.
- Подписчики обновляют read projections после commit.
- Retry одного события не должен создавать второй Event или повторный перенос.

## Тесты

- Создание только из CONFIRMED и отказ для остальных статусов.
- Повторный и конкурентный вызов создаёт один Event.
- Перенос повторно проверяет конфликт и атомарно синхронизирует обе модели.
- Тесты отмены брони по каждой поддержанной политике.
- Regression-тесты legacy Event без booking_id.

## Обратная совместимость

- Поле booking_id nullable; существующие мероприятия и матчи не требуют немедленной миграции.
- Старые маршруты Event сохраняются, но для связанных записей сервер запрещает обход booking-команд.
- Включение новой связи выполняется feature flag по типу/источнику Event.

## Критерии приёмки

- Один confirmed booking создаёт не более одного Event даже при retry и конкуренции.
- Event не становится вторым источником истины для занятости.
- Перенос и отмена не оставляют рассинхронизированные время, площадку или статус.
- Legacy Event продолжают открываться и редактироваться по прежним правилам.
