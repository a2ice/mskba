# 069 - Добавить настраиваемые права ответственных за мероприятие

## Оригинальное описание

При назначении ответственного организатор должен выбирать его права на
конкретное мероприятие. По умолчанию включены все доступные права, но их можно
изменять фирменными переключателями как до принятия приглашения, так и после.
Права должны раздельно управлять мероприятием и его мини-играми, включая
состав, счёт, статистику и завершение.

## Подробное описание

### Цель

Заменить текущее правило «принятый ответственный может управлять всем
агрегатом» явным и редактируемым permission snapshot конкретного назначения
`event participant -> parent event`.

Snapshot не является неизменяемым: организатор может обновить его в любой
момент. Явное хранение означает только то, что новый permission, добавленный в
код позднее, не выдаётся существующим ответственным автоматически.

### Модель прав

Добавить доменный enum permissions и отдельные записи прав, принадлежащие
назначению ответственного. Предварительный набор атомарных прав:

- мероприятие: редактировать основные данные;
- мероприятие: управлять участниками;
- мероприятие: назначать ответственных;
- мероприятие: вести итог и фотогалерею;
- мероприятие: завершать;
- мероприятие: отменять;
- мини-игры: создавать;
- мини-игры: редактировать параметры;
- мини-игры: назначать состав;
- мини-игры: вести счёт;
- мини-игры: вести полную статистику;
- мини-игры: завершать;
- мини-игры: удалять.

«Полное управление мероприятием» и «Полное управление мини-играми» являются
только UI-пресетами, переключающими атомарные permissions соответствующего
раздела. Они не сохраняются как самостоятельные права.

Организатор и подтверждённый `superadmin` сохраняют полный доступ независимо
от snapshot. Ответственный с правом назначения других ответственных может
выдать или изменить только подмножество собственных effective permissions.
Организатор этим ограничением не связан.

### Хранение и жизненный цикл

- создать таблицу `event_responsibility_permissions` с внешним ключом на
  `event_participants`, строковым permission и уникальной парой
  `(event_participant_id, permission)`;
- при первом приглашении все permissions выбраны по умолчанию и передаются
  формой явно;
- повторное приглашение после отказа сохраняет новый выбранный snapshot;
- организатор может редактировать права pending- и accepted-назначения;
- принимающий приглашение видит предложенный набор прав;
- снятие ответственности, выход участника и другие существующие сценарии
  сброса ответственности удаляют permission snapshot;
- права ответственного родительского мероприятия действуют на его мини-игры,
  но отдельные назначения на мини-играх не создаются.

Изменение snapshot выполняется транзакционно. При изменении ответственным прав
другого ответственного блокируются сначала родительское мероприятие, затем
целевой participant; единый порядок нужен, чтобы не добавить новый источник
deadlock рядом с уже используемым порядком блокировок агрегата мини-игр.

### Authorization

Расширить `EventManagementAccess` проверкой конкретного permission. Общий
`canManage()` больше не должен служить разрешением любого управляющего
действия: каждый use case и endpoint проверяет минимальное требуемое право.
Проверки должны находиться в application/use-case слое, а видимость элементов
Blade повторяет effective permissions только как UX и не является защитой.

Отдельно проверить отсутствие повышения привилегий, прямые запросы к скрытым
действиям и изменение прав после того, как ответственный уже открыл страницу.

### Интерфейс

- форма назначения открывает список прав с уже существующим общим partial
  `partials.forms.toggle`;
- права визуально разделены на «Мероприятие» и «Мини-игры»;
- групповые переключатели включают и выключают весь раздел;
- после назначения доступно редактирование выданных прав;
- приглашённый пользователь видит перечень прав до принятия решения;
- страницы мероприятия и мини-игры показывают только разрешённые действия.

Backend API и UI не должны зависеть друг от друга: тот же permission resolver
в дальнейшем сможет управлять шагами мобильного wizard или динамического
popup без изменения доменной модели.

### Границы задачи

В задачу не входят новый mobile wizard, глобальный popup-manager, сворачиваемые
вкладки и сохранение их UI-состояния между страницами. Это зафиксировано
отдельным backlog item. Redis не нужен для самого сворачивания popup: состояние
открытых вкладок в одном браузере разумно хранить в `sessionStorage` или
`localStorage`; Redis уместен позднее для серверного черновика, нескольких
устройств, совместного ведения или восстановления состояния независимо от
браузера.

## Декомпозиция

### Permission enum и матрица действий

| Permission | Защищаемые действия |
| --- | --- |
| `event.update` | форма редактирования и `UpdateEventHandler` |
| `event.participants.manage` | поиск кандидатов и добавление участников |
| `event.responsibilities.manage` | приглашение, изменение прав и снятие другого ответственного |
| `event.result.manage` | изменение уже сохранённого итога и управление итоговой галереей |
| `event.complete` | первое завершение мероприятия с фиксацией результата |
| `event.cancel` | отмена мероприятия и освобождение брони |
| `mini_game.create` | создание мини-игры родительского мероприятия |
| `mini_game.update` | название, время, формат и названия сторон мини-игры |
| `mini_game.roster.manage` | изменение составов сторон |
| `mini_game.score.manage` | сохранение только текущего счёта |
| `mini_game.statistics.manage` | сохранение счёта и индивидуальной статистики игроков |
| `mini_game.complete` | завершение игры и подтверждение готовой статистики |
| `mini_game.delete` | удаление мини-игры |

`mini_game.statistics.manage` функционально включает возможность сохранять
счёт. В UI включение полной статистики автоматически включает право счёта;
выключение счёта автоматически выключает полную статистику. Это исключает
набор, при котором пользователь может ввести расширенную статистику, но не
может сохранить обязательный для неё счёт.

### Application API

- `EventManagementAccess::allows/assertAllows` принимают требуемый enum;
- organizer и superadmin проходят любую проверку;
- responsible проходит проверку только при `accepted` и наличии сохранённой
  строки permission;
- `canManage` остаётся агрегатным UX-признаком «есть хотя бы одно право», но не
  используется для защиты изменяющих состояние use cases;
- invitation handler принимает валидированный массив permissions и заменяет
  snapshot внутри транзакции;
- отдельный update handler меняет snapshot pending/accepted назначения;
- update handler проверяет право делегирования и запрет повышения привилегий;
- lifecycle-сценарии сброса ответственности удаляют permissions через FK
  cascade при удалении participant либо явно при очистке его статуса.

### HTTP и UI

- POST существующего invitation route получает `permissions[]`;
- новый PUT/PATCH route назначения обновляет только permission snapshot, не
  меняя статус принятия;
- приглашение и редактирование используют одну partial-форму с двумя группами
  фирменных toggle;
- групповые toggle вычисляются из атомарных значений и управляются небольшим
  JS-контроллером без отдельного persisted-поля;
- карточка pending-приглашения показывает кандидату названия предложенных прав;
- контроллер страницы передаёт карту effective permissions, по которой Blade
  скрывает конкретные формы и ссылки;
- для режима «только счёт» добавляется отдельное сохранение счёта, не меняющее
  индивидуальную статистику. Текущий endpoint полной статистики требует
  `mini_game.statistics.manage`.

### Миграция существующих назначений

Все существующие `pending` и `accepted` назначения получают полный набор
permissions, потому что до задачи 069 они создавались с ожиданием полного
управления. `declined` и назначения без статуса не получают строк прав.
Backfill выполняется в той же schema migration как перенос текущей семантики;
в runtime отсутствие строк означает отсутствие прав, а не legacy full access.

### Наборы тестов

1. Полный snapshot по умолчанию и отображение прав приглашённому.
2. Принятие назначения и доступ только к выбранным действиям.
3. Редактирование pending/accepted snapshot организатором.
4. Ответственный делегирует только подмножество собственных прав.
5. Запрет прямых HTTP-запросов для каждого отсутствующего permission.
6. Раздельные режимы: только счёт, состав, полная статистика и завершение.
7. Очистка snapshot при снятии ответственности, выходе и смене подтверждения.
8. Backfill существующих pending/accepted назначений полным набором.
9. Сохранение полного доступа organizer и superadmin.

## Результат

Реализован редактируемый permission snapshot каждого назначения ответственного:

- добавлены enum, модель, relation и таблица `event_responsibility_permissions`;
- прежние pending/accepted назначения получают полный набор при миграции;
- organizer и superadmin сохраняют полный доступ, остальные действия защищены
  конкретными permissions в application-слое;
- приглашение и последующее редактирование snapshot запрещают privilege
  escalation и соблюдают порядок блокировок агрегата;
- режим только счёта отделён от полной статистики;
- UI использует общие фирменные toggle, групповые пресеты и адаптивную раскладку;
- приглашённый видит права до принятия, а управляющие экраны скрывают
  недоступные действия;
- lifecycle выхода, отказа и повторного подтверждения очищает snapshot;
- управляемое добавление участника стало двухэтапным (`tentative -> confirmed`),
  динамически обновляет секции «Думают»/«Участники» под общим loading overlay и
  требует явного подтверждения организатора или ответственного;
- карточка показывает время последнего управляемого изменения статуса и через
  tooltip — изменившего actor; самостоятельное решение очищает эту отметку;
- продуктовая, техническая и модульная документация актуализирована.

Локальная migration применена. Релевантные feature-тесты, Blade compilation,
formatter и frontend production build входят в итоговую проверку задачи.
