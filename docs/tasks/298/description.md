# 298 — Рабочее пространство группы интересов: организация игры и бронирование

## Цель
Постоянная страница группы из Task 297 — точка реальной работы игроков, организаторов, владельцев и уполномоченных сотрудников площадки. Добавить функциональные разделы и действия **последовательно**, опираясь на доменные процессы, а не создавая дубль Event/Booking.

## Роли и сценарии
- **Участник с активным интересом:** видеть релевантные предложения, инициировать сбор, обсуждать удобные дату/время и формат, получать приглашение, явно подтверждать/отклонять конкретные условия, видеть историю. Гостю — просмотр разрешённого минимума и безопасный переход через вход.
- **Инициатор/организатор:** создать ровно один активный процесс для конкретной игровой возможности; настроить подбор состава, согласование слота и стоимости, делегировать разрешённые функции, проверить готовность участников.
- **Владелец/администратор площадки:** видеть разрешённую ему агрегированную информацию, предложить доступный зал/интервал, цену/условия и статус брони. Право управления конкретной площадкой проверять сервером через существующий `VenueAccessResolver`/venue permissions. Нельзя управлять чужими группами или голосовать вместо игроков.
- Поддержать ссылки на создаваемые **Event** и **VenueBooking** и их актуальные статусы; чат/голосования/системные сообщения вводить как отдельные этапы, без декоративных нерабочих элементов.

## Технические границы
- Использовать проектный Task [287](../287/description.md) для `PlayOpportunity/PlayAssembly/CoordinationSession` и антидублирования, [288](../288/description.md) для venue-side предложений/аналитики. Не плодить второй двигатель групповых игр.
- Группа — стабильный контейнер по площадке. Одна группа может иметь множество **последовательных/независимых** попыток организации, но у каждой конкретной возможности максимум один активный Assembly с транзакционной защитой.
- Бронирование через существующие feature flags, `QuoteVenueBookingHandler`, `VenueBooking` lifecycle и court-aware доступность; участники подтверждают **фактическую** стоимость и условия перед hold/payment. Интерес/группа сами по себе ничего не бронируют и деньги не списывают.
- Права, приватность личного расписания, audit trail, race/retries/idempotency, уведомления `service` vs `marketing`, состояния «занято», «изменена цена», «истекло предложение» обязательны.
- В API отдавать собственный scope для участника, организатора и venue staff; не использовать скрытые кнопки как проверку доступа.

## Этапность при реализации
1. Read-only раздел «Обсуждения и сборы» (если нет Assembly — пустое состояние), действующие связи группы и процессов.
2. Запуск/подтверждение/приглашения по согласованным правилам Task 287.
3. Согласование слота и интеграция с quote/booking с повторной проверкой доступности и цен; ссылки и таймлайны.
4. Владелец/администратор: просмотр, предложения и предложения группам по Task 288; см. также промокоды Task 299–300.

## Приёмка
Два конкурирующих организатора не создают дубль; доступы участников и venue admin изолированы; слот и сумма повторно проверяются на booking; никакая заявка/подписка не равна оплаченной брони; закрытие/отмена и повторный сбор сохраняют историю. E2E + permissions, concurrency, pricing, Reverb/idempotency tests.

**Приоритет:** после MVP страницы 297 и согласования 287/288. **Статус:** запланировано, не включено в MVP 297.
