# Регламент автоматизированного выполнения

- Перед каждым действием коротко записать в отчёте/issue цель, ожидаемый результат и затрагиваемые файлы/сценарии. При отсутствии изменений — без лишних коммитов.
- Каждый рабочий цикл: прочитать Epic #1034, связанные issues, актуальные main/PR/CI/release checkpoint (#340); проверить публичные / и /venues, старые URL и 5xx. Начать с #1035, далее брать только незаблокированную небольшую задачу по зависимостям. Проверить отсутствие конкурирующего PR; не дублировать чужую работу.
- Если production нестабилен: остановить релиз SEO, вести только read-only аудит, фиксировать блокер. Не пытаться чинить несвязанные ошибки без безопасного отдельного плана. Не менять prod DB напрямую, секреты, доступы, финансы, auth и booking lifecycle; не форсить ветки.
- Код/документация: отдельная ветка от актуального main, малый diff, PR в main; проверить изменённые файлы, CI должен быть фактически зелёным. Не merge при неизвестном статусе/конфликте/красном CI. Не включать auto-merge если отсутствуют обязательные проверки. После merge подтвердить deploy нужного SHA и smoke; если не подтверждено, оставить pending, не закрывать issue. Не переносить dev данные на prod.
- Контент: только фактические данные и проверенные ссылки, уникальный intent, без doorway/keyword stuffing; публикация на сайте с подтверждением URL через авторизованный scoped редакционный API. Если нет доступа — готовить черновик, не обходить ограничения. Не отправлять массовые сообщения, не покупать ссылки, не публиковать отзывы от имени пользователей.
- Измерять органику через GSC/Вебмастер/Метрику при наличии доступа, связать с обезличенной аналитикой заявок, оплат, повторов; неизвестные показатели обозначать явно. Никаких PII в отчётах.
- Ежедневный рабочий цикл (будни, ориентир 09:00 MSK): выбрать одну задачу, выполнить доступный безопасный шаг, сохранить evidence/PR, обновить issue. При блокере указать причину и следующую доступную задачу. Не обещать работу между запусками.
- Еженедельная сводка (понедельник): 28 дней vs предыдущие 28, прогресс, ссылки/метрики, ошибки, изменения, следующие 3 приоритета. D+1/7/30 после релизов. Контроль 30/60/90 дней. Согласовать публикацию по необходимости с владельцем только при реальном высокорисковом изменении или недостающем доступе; штатные безопасные шаги разрешены.
- Формат отчёта: «Что делаем → Что фактически сделано → Evidence → CI/deploy/smoke → блокеры → следующий шаг». Отмечать только подтверждённые факты.
