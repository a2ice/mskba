# 138 — Realtime-управление и переписка по заявке на аренду

## Оригинальное описание

Привести действия подтверждающей стороны к обычному стилю кнопок и расположить
их в ряд. Показывать отправителя заявки и открывать по нажатию popup переписки.
Рядом с именем и на стороне заявителя показывать число новых сообщений. Обе
стороны должны получать сообщения и изменения статуса заявки через WebSocket без
ручного обновления страницы, по аналогии с realtime-обновлением поздней заявки
на участие в турнире.

## Подробное описание

Существующий защищённый conversation flow аренды остаётся единственным источником
сообщений. Его текущая встроенная секция переносится в общий modal-компонент, а
REST endpoints загрузки, отправки, вложений и read marker переиспользуются без
создания второй таблицы или второго протокола чата.

Для каждой открытой страницы заявки добавляется приватный booking-канал,
доступный тем же пользователям, которым разрешён просмотр заявки. Канал сообщает:

- об изменении `optimistic_version` и проекции заявки после commit;
- о новом сообщении, в том числе первом сообщении ещё не созданной ранее беседы.

Клиент после события состояния запрашивает актуальную JSON-проекцию и
перерисовывает статус и доступные действия либо, если структура страницы могла
существенно измениться, безопасно обновляет страницу. WebSocket остаётся быстрым
сигналом, а HTTP-проекция — источником истины. При недоступном realtime клиент
периодически синхронизируется через тот же endpoint.

## Пользовательские сценарии

- представитель площадки видит имя заявителя и число непрочитанных сообщений;
- нажатие на имя открывает popup переписки и отмечает показанные сообщения
  прочитанными;
- заявитель видит заметную кнопку «Новые сообщения (N)» и открывает тот же popup;
- новое сообщение появляется у второй стороны без перезагрузки, а счётчик растёт,
  если popup закрыт;
- принятие, подтверждение, отклонение или отмена заявки автоматически обновляет
  открытую страницу второй стороны;
- действия представлены в одной строке: положительное основное действие —
  оранжевое, отклонение и отмена — вторичные;
- при разрыве WebSocket страница продолжает синхронизацию резервным polling.

## Архитектурные ограничения

- авторизация booking-канала и conversation endpoints повторяет
  `VenueBookingAuthorization`; UUID и содержимое заявки не раскрываются посторонним;
- broadcast изменения создаётся только после commit через существующий
  `BookingProjectionUpdated`, поэтому клиент не запрашивает незакоммиченное
  состояние;
- сетевые вызовы и broadcast не выполняются под доменными блокировками, что не
  расширяет lock window и не создаёт новый порядок блокировок;
- unread считается только по сообщениям другой стороны после read marker;
- сообщения остаются неизменяемыми и идемпотентными по `client_id`.

## Статус

Выполнено.

## Результат

- действия владельца приведены к стандартным primary/secondary кнопкам в строку;
- заявитель и число новых сообщений показаны в верхней карточке;
- переписка перенесена в общий popup, отправка текста и вложений работает без
  перезагрузки, просмотр автоматически обновляет read marker;
- приватный booking-канал доставляет первое сообщение и новую optimistic version,
  conversation-канал продолжает доставлять сообщения активной беседы;
- обе стороны автоматически перечитывают изменённую заявку; предусмотрен polling
  каждые 15 секунд при разрыве или задержке WebSocket;
- уведомление о сообщении ведёт сразу к открытому popup переписки.
