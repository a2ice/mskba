# Task 192 — 2D/3D режим персонажа игрока и референсы лица

## Контекст

Текущий Player Character на странице роли игрока уже использует единую метрическую сцену `200 × 250 см`, сохраняет appearance state в `player_profiles.extra.character` и умеет отображать authored 3D/GLB-модель. 3D-пайплайн пока остаётся экспериментальным: модели и одежда требуют дальнейшей доработки в Blender.

На ближайшем этапе основной пользовательский режим должен стать 2D, а текущий 3D — остаться доступным только администраторам для разработки и проверки. Архитектура при этом должна быть готова к последующей генерации 2D-модели через image API без привязки UI к конкретному генератору.

## Цель

Сохранить один конфигуратор и одну метрическую сцену, но разделить способ визуализации персонажа:

- `2d` — основной режим для всех пользователей;
- `3d` — экспериментальный режим только для `admin` и `superadmin`;
- рост, вес, телосложение и appearance state общие для обоих renderer;
- переключение режима происходит без полной перезагрузки страницы;
- при загрузке/ошибке предыдущая валидная визуализация остаётся на экране;
- добавить приватные референсы лица для будущей генерации;
- подготовить контракт для женского параметра объёма груди и будущего блока экипировки.

## Renderer contract

### Единая сцена

2D и 3D отображаются внутри существующего `account-player-character-stage`. Нельзя создавать отдельную шкалу или отдельный экран для каждого renderer.

Метрическая система остаётся прежней:

- ширина сцены — 200 см;
- высота сцены — 250 см;
- `0 см` — линия пола;
- рост персонажа и marker используют ту же шкалу в обоих режимах.

### 2D

На этой итерации 2D использует статический штатный preview. Он является временным placeholder и не пытается имитировать результат AI-генерации.

Позднее renderer получает URL последнего успешно сгенерированного изображения, а генератор будет работать через отдельный application service / prompt builder. Vue/Blade/JS не должны собирать provider-specific prompt.

### 3D

3D остаётся текущим authored Three.js/GLB renderer, но загружается лениво только когда действительно выбран режим `3d`.

Backend — source of truth для доступа. Попытка обычного пользователя выбрать `3d` должна вернуть `403`; UI показывает понятную ошибку и возвращает switch в `2d`.

Текущий временный доступ:

- `admin` — разрешён;
- `superadmin` — разрешён;
- остальные system roles — запрещены.

Это временное продуктовое правило. В будущем доступ к AI-генерации и/или расширенным renderer может зависеть от тарифа, поэтому проверка не должна быть зашита только в визуальный компонент.

## UX переключения

Переключение выполняется AJAX-запросом через player-profile mutation endpoint.

Состояния:

1. пользователь переключает renderer;
2. текущая картинка/модель остаётся видимой;
3. поверх сцены появляется компактный индикатор загрузки;
4. backend подтверждает новый режим;
5. для `3d` только после успешной загрузки Three.js/GLB сцена переключается на 3D;
6. при любой ошибке остаётся предыдущая валидная визуализация, spinner снимается, показывается сообщение;
7. если 3D не загрузился после успешного сохранения режима, клиент best-effort откатывает сохранённый режим обратно в `2d`.

Пустой stage при ошибке недопустим.

## Appearance state

Общие параметры не зависят от renderer:

- пол — только из `Profile.gender`;
- рост;
- вес;
- телосложение;
- причёска;
- цвет волос;
- facial hair;
- skin tone / будущий inferred skin tone;
- текущая примерка формы.

Для женского профиля добавляется опциональный ручной параметр `chest_volume`. Он не определяется по фотографии автоматически.

`player_profiles.extra.character` должен обновляться merge-операцией, чтобы обычное сохранение appearance не удаляло `render_mode` и будущие renderer/generation metadata.

## Референсы лица

Это отдельные фотографии **лица для модели**, а не публичные аватары пользователя.

Слоты:

- `front` — анфас;
- `left` — левый профиль;
- `right` — правый профиль.

Для будущей генерации минимально ожидаются анфас + один профиль, третий профиль рекомендован. На текущем этапе отсутствие полного набора не блокирует сохранение профиля, поскольку AI-генерация ещё не подключена.

### Хранение

- исходный high-res файл не сохраняется;
- после загрузки изображение сразу нормализуется в WebP;
- максимум 512 px по большей стороне;
- JPEG/PNG/WebP;
- EXIF orientation учитывается существующим `WebpImageNormalizer`;
- хранение — private/local disk, не публичный `/storage`;
- на каждый слот хранится только последняя успешно нормализованная версия;
- если новая загрузка невалидна/не обработалась, предыдущий валидный reference не удаляется.

### Будущая AI-валидация

После подключения image API загрузка каждого слота должна проходить semantic validation:

- `front` действительно анфас;
- `left` действительно левый профиль;
- `right` действительно правый профиль;
- на изображении пригодное для reference лицо.

При несовпадении ракурса новый reference не заменяет предыдущий.

На этой итерации UI явно сообщает, что AI-проверка ракурса ещё не подключена; система не должна изображать такую проверку эвристиками.

## Skin tone

В будущем skin tone допускается определять по подтверждённым face references и применять ко всему персонажу. Геометрические параметры тела по фотографиям не выводятся — они остаются ручными настройками.

## Outfit — следующий этап

Экипировка должна развиваться независимо от тела/лица. Будущий input генератора делится как минимум на:

- `appearance` — тело/волосы/лицо;
- `face references`;
- `outfit` — размер одежды, комплект, цвета, принт/номер и другие параметры.

Текущую примерку `uniform_kit` и цветов команды сохраняем для backward compatibility. Полноценный outfit editor в Task 192 не входит.

## Acceptance criteria

- обычный игрок по умолчанию видит 2D внутри существующей метрической сцены;
- 2D и 3D используют один и тот же scale/stage;
- переключение renderer не перезагружает страницу;
- обычный пользователь получает `403` на `3d`, switch автоматически возвращается в 2D;
- admin/superadmin может включить 3D;
- Three.js/GLB не загружается для пользователя, который остаётся в 2D;
- во время переключения текущий renderer остаётся видимым, поверх него показывается spinner;
- ошибка не очищает последнюю валидную визуализацию;
- `render_mode` не теряется при последующем сохранении appearance;
- женский профиль может сохранить `chest_volume`, мужской не получает этот параметр из payload;
- доступны три слота face references;
- face reference сохраняется private WebP максимум 512 px;
- замена reference атомарна с точки зрения пользователя: невалидная новая загрузка не удаляет старую;
- UI не заявляет AI-проверку ракурса до подключения provider;
- существующая примерка формы/цветов команды не ломается;
- feature tests и frontend build проходят.
