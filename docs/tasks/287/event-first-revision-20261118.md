# MSKBA — Event-first организация игры (принято 18.11.2026)

## Решение

**Event — единственное рабочее пространство конкретной игры или мероприятия.** Не создавать новую групповую сущность PlayOpportunity/PlayAssembly, выборы администратора, отдельное групповое членство или вторую ленту RSVP. Проект PR #850 **не вносить целиком**: допускается аккуратный перенос только повторно проверенных компонентов стены мероприятия, журналирования и server-side limiter.

Исходные подписки `PlayIntent` остаются индивидуальными условиями поиска и сигналами уведомления, но не создают мероприятие, не регистрируют пользователя и не инициируют бронь. Координация и опросы — в существующем Event/Coordination.

## Два входа в одну форму

1. С площадки: «Хочу здесь играть» → «Создать мероприятие / игру» → единая форма создания. Выбранный Venue и, если пользователь на странице зала, Court автоматически предвыбраны, но можно изменить. Ни один параметр, переданный из URL, не принимается без server-side проверки.
2. Из /events: «Создать мероприятие» → та же форма без предвыбранной площадки. Параметры типа, названия, описания, доступности участникам, формата игры, количества участников, длительности, места и времени в одних и тех же компонентах.

В актуальном `main` модули `events.wizard` и `events.create` расходятся по теме; для `mskba_app` wizard редиректит в `events.create` и теряет `venue_id`/`venue_court_id`. Исправлять в едином разрешённом сценарии. Native modal с keyboard/focus/Enter/error и восстановлением данных при закрытии; не терять breadcrumbs/sidebar по гайдлайну. Никаких двух независимых форм/обработчиков.

## Уровни определённости мероприятия

- **Согласование**: можно создать открытый Event без окончательно выбранной площадки и/или времени — это проект игровой встречи, не подтверждённый слот. UX ясно показывает, что место/дата ещё обсуждаются; нет фиктивной занятости, удержания, цены, календарного обещания, брони или уведомления «в этот день».
- **Планируется**: есть достаточно параметров для поиска подписчиков; Event живёт отдельно от брони. Даже выбранный Venue и timestamp не равны резервированию. При изменении существенных условий прежние подтверждения явки требуют пересмотра/явного информирования согласно существующим правилам.
- **Бронь подтверждена**: исключительно фактический статус VenueBooking. Все проверки конфликта слотов, стоимости и полномочий используют готовые use cases.
- **Проведено / отменено**: существующий lifecycle Event.

Сейчас `CreateEventRequest::rules` требует `venue_id` и `starts_at`, а `CreateEventHandler` безусловно получает и блокирует Venue, проверяет занятость и записывает starts_at/ends_at. Нужно отдельно расширить доменную схему и create/update/list/show/SEO, не решать отсутствующую дату фиктивной датой в будущем.

## Подписки → событие → уведомления

Матчить только **опубликованные открытые для участия** события, для которых указаны все нужные параметры проверки. Match — по существующим `PlayIntent`, canonical user и активной подписке с разрешённым `notify_matches`:
- выбранная площадка и/или реально совместимые георадиус + exclude list;
- форматы, обязательные удобства, доступность/платность и тип зала, когда заявлены;
- реальные дата, день недели, регулярность/разовая дата и временные окна, длительность;
- состояние Event, доступность набора, блокировки/приватность и статус контакта;
- отсутствие совпадения или неполные Event-параметры — **не отправлять** уведомление, а не игнорировать фильтры.

Сервис match не резервирует площадку. После commit создать идемпотентные уведомления с ключом (event_id + canonical_user_id + meaningful_revision + category) через существующий Notification pipeline и каналы `game_delivery_channels`; отдельная частотная защита, отписка и исключение организатора; email/Telegram — только подтверждённые и разрешённые пользователем контакты. Ссылка ведёт на Event, без автоматического RSVP. На изменение площадки/даты — корректная переоценка и предотвращение повторного спама.

## Общение и история мероприятия

- Отдельные вкладки «Обсуждение», «История действий» на странице Event в принятом layout (включая breadcrumbs/sidebar, mobile и TMA).
- Организатор обладает уже существующими правами Event, без избрания администратора. Название задаётся при создании и может быть изменено авторизованным менеджером Event.
- Только участники и организатор имеют доступ к приватной стене; публичность самого Event не публикует сообщения.
- «Пойду» = confirmed, «Думаю» = tentative, «Не пойду» = left в существующем EventParticipant. Счётчики отражают **последнее текущее** состояние, а каждое изменение создаёт историю («X пойдёт», «X не пойдёт»). Повторы одного состояния не создают новую историю и не съедают лимит. Менять статус могут только разрешённые участники, с реальной проверкой вместимости и race conditions.
- Сообщение ≤200 символов, удаление автором — зачёркнутое прежнее сообщение на месте; модератор может скрыть недопустимый текст. Системные записи о статусах — неизменяемые.
- **Единый серверный лимит: не более 3 изменяющих действий пользователя в скользящие 60 секунд** для комментариев, удаления и RSVP, включая старые endpoints, с canonical user lock и атомарным аудитом. Системная запись события не расходует второй токен. При превышении HTTP 429 и Retry-After.
- Не дублировать EventParticipant, не переписывать историю и не создавать новый независимый механизм присутствия.

## Реализация, зависимость и приёмка

1. Заморозить тяжёлую групповую концепцию 287/336 и не merge #850 целиком. Выделить в отдельный PR от main лишь совместимые Event social changes и тесты.
2. Восстановить оба входа и единый modal/wizard со всеми полями, серверной проверкой и адаптивным layout.
3. Поддержать неопределённые место/дату в Event как явный договорный статус (без фальшивой брони); обновить все потребители и тесты.
4. Доставку PlayIntent→Event, idempotency/afterCommit, разрешённые каналы и негативные случаи.
5. Feature/unit/integration/concurrency/notifications, desktop/mobile/TMA, темы и smoke tests. **Merge в main только после зелёного CI**, затем проверить фактический деплой production и отсутствие регрессий.

Отдельные постоянные сообщества по интересам и выборы их администраторов исключены из этого релиза и могут быть рассмотрены только на основании будущей продуктовой потребности.

- `app/Modules/Event/Presentation/Http/Requests/CreateEventRequest.php`: `venue_id` и `starts_at` обязательны.
- `resources/themes/mskba_app/views/pages/venues/show.blade.php`: `createEventUrl` передаёт venue/court, а `EventWizardController::show` в теме app редиректит лишь с `type`; кнопка уже есть в дополнительном aside, но отсутствует в основном «Хочу здесь играть».
- `app/Modules/PlayInterest/Domain/Models/PlayIntent.php`: хранятся фильтры формата, дат, окон, географии и флаги/каналы уведомлений; автоматическую доставку новых Events по полному matching на момент проверки считать **неподтверждённой**.
- `EventParticipantStatusEnum`: confirmed / tentative / left; не создавать второй RSVP.
