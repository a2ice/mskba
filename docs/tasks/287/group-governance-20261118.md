# Управление группами интересов: названия, выборы администратора, полномочия

**Принято к включению в продуктовую концепцию 18.11.2026. Реализации ещё нет.** Дополнение к [спецификации страницы группы](group-interest-workspace-20261118.md) и задаче [287](description.md). Не заменяет публичные роли MSKBA/Filament и не даёт права управлять чужими площадками.

## 1. Название и идентичность

У одной `PlayOpportunity` два независимых имени:
- `generated_title` — сервер формирует из **действительно общего** формата, географии и времени; изменяется лишь при существенном пересчёте общего контекста;
- `custom_title` — опциональное переопределение, изменяемое **текущим избранным администратором данной группы** или уполномоченным сотрудником MSKBA через Filament. Максимум 80 Unicode-символов после trim, без HTML/управляющих символов/пустого значения.

Отображение: `custom_title ?: generated_title`. Действие «Вернуть автоматическое» очищает `custom_title`, не сохраняет копию автоназвания. История `group_title_changes`/аудит хранит прежнее/новое, актёра, источник `group_admin|backoffice`, время, причину служебного override. При смене администратора кастомное название **остаётся**, новый администратор может изменить. Название не участвует в алгоритме matching/deduplication, не изменяет `public_uuid`, URL и историю.

Filament: отдельный раздел **«Сообщества → Группы интересов»** (наименование группы меню адаптировать к актуальному UI): список, состояние и состав группы, generated/custom/preview title, текущий администратор, история выборов, просмотр участников и ограниченная модерация. Только пользователи с явным backoffice permission могут изменять название/назначать или снимать администратора с обязательным служебным объяснением и аудитом. Само получение статуса администратора группы **не даёт** доступа к Filament.

## 2. Один администратор на группу

`play_opportunities.admin_user_id` (nullable) и `admin_assigned_at/admin_assignment_source` — единственный текущий источник полномочий. Администратор — пользователь с **подтверждённым аккаунтом и действующим участием в данной группе**, не системная роль. Не существует двух параллельных администраторов; любые назначения и смены проходят транзакционную блокировку записи группы, проверку версии и историю. Администратор может иметь эту роль в нескольких группах без объединения полномочий.

Состояния: `no_admin`, `has_admin`, `election_open`; статус выборов независим от статуса самой группы.

### Члены группы

Право выдвигаться и голосовать: подтверждённый незаблокированный канонический пользователь с активным соответствием `PlayOpportunity`; учетная запись с soft-delete, отсутствие активного PlayIntent или снятие членства блокирует новые голоса и групповую власть. Несколько PlayIntent/identity aliases одного пользователя никогда не дают более одного голоса. Не путать пользователей из площадочного избранного с участниками конкретного совпадения.

Если администратор теряет право участвовать/заблокирован или сам слагает полномочия: **сразу прекращается доступ к административным действиям**; `admin_user_id` очищается контролируемой транзакцией, в истории фиксируется причина; группа открывает выборы. Нельзя автоматически назначать другого игрока по дате регистрации.

## 3. Как стать кандидатом

Кнопка `Стать администратором группы` (если администратор есть, рядом `Предложить смену администратора`) → фирменный popup:
- Текст `Почему участники должны выбрать тебя?` — **от 20 до 1000 Unicode-символов** после trim; plain text, серверная валидация и защита от небезопасного контента. Чётко объяснить роль и полномочия.
- Подача заявки `POST` создаёт запись кандидатуры; не даёт прав до окончания выборов. Не более одной активной заявки кандидата в раунде; нельзя подавать заявку за другого человека.
- Если активного раунда нет — он начинается, иначе заявка добавляется в существующий. Несколько кандидатур отображаются в **одном** фиксируемом сверху информере-баннере; доступны текст заявок, кандидаты, даты, голоса/порог и кнопки выбора. Длинные тексты свернуты с `Подробнее`.
- Сменить мотивационный текст при уже открытом голосовании без пересмотра чужих голосов нельзя: после первого голоса текст блокируется; заявку можно отозвать (голоса по ней снимаются), повторная подача в том же раунде не позволяет бесконечное переобъявление.
- Выдвижение кандидата не создаёт новое `CoordinationSession` для игровой организации и не является «обычным опросом», который может создавать лишь избранный администратор. Это **системные выборы** с отдельной ролью и проверками.

## 4. Голоса, кворум и смена

### Порог

Победа требует **строго больше половины всех имеющих право голоса участников группы и не менее 3 уникальных поддержавших**:
`required(N) = max(3, floor(N/2)+1)` при `N >= 3`.

**Малая группа, N=2:** специальное исключение — оба голосуют за одного кандидата (`required=2`). Одиночная группа не выбирает администратора и не получает административных действий. Кандидат может поддержать собственную кандидатуру; иначе выбор в группе из 3 никогда не был бы достижим. Непроголосовавшие учитываются в общем числе N; сравниваем с **всем электоратом**, не лишь с явившимися.

| N | Голосов для избрания |
|---|---|
| 2 | 2 |
| 3 | 3 |
| 4 | 3 |
| 5 | 3 |
| 6 | 4 |
| 8 | 5 |
| 10 | 6 |
| 20 | 11 |

### Голосование с несколькими кандидатами

- **Один голос одного канонического пользователя за одного кандидата в пределах одного раунда**: `unique(round_id, user_id)`, с `candidate_id` как изменяемым значением. Переключение на второго кандидата `UPDATE` в транзакции: прежнему минус один, новому плюс один. Поддержка двух кандидатур параллельно невозможна даже при конкурентных AJAX запросах.
- **Предложение против «гонки быстрого клика» (нуждается в утверждении):** раунд длится до 7 дней, но не завершается назначением ранее чем через 24 часа после первой заявки. Через 24 часа при достижении порога избрание автоматически завершается; иначе продолжается до 7 дней. На 7-й день при отсутствии порога — без победителя, имеющийся администратор остаётся; при отсутствии администратора новый раунд доступен после небольшого anti-spam cooldown.
- Кандидатуры, поддержка, прогресс и срок отображаются всем eligible членам. Голоса можно переставлять только до закрытия раунда. По достижении порога один победитель назначается атомарно; текущий администратор заменяется **в той же транзакции**, без периода с двумя администраторами. Отправить уведомление кандидату/участникам и зафиксировать событие смены.
- Правила roster: `election_rounds` сохраняют снимок допустимых избирателей и N на открытие раунда, не допуская изменения порога от каждого входа на страницу или лавинообразного добавления новых аккаунтов. Новые участники голосуют в **следующем** раунде; отпавшие/заблокированные не могут голосовать и их голоса не учитываются в результате. При существенном изменении состава во время голосования (предлагаемый порог: >20% участников, либо число eligible стало ниже кворума) раунд отменяется и создаётся новая версия с новым снимком; не «переигрывать» победителя задним числом.
- Раунд с несколькими кандидатами не может назначить двух: >50% при одном голосе математически исключает двух победителей; сервер дополнительно использует row-level lock и проверяет статус раунда в транзакции.
- **Смена администратора — такой же раунд**. Действующий администратор не вправе блокировать кандидатуры или голосование о смене. Пока победитель не утвержден, текущий админ действует; проигравший не сохраняет «остаточные» полномочия. В Filament служебные полномочия регулируются независимо, с обязательным audit trail.
- Рекомендация против циклических перевыборов: короткий cooldown (например 7 дней) после удачных выборов, кроме ухода/блокировки администратора или служебного вмешательства; детали настроить на отдельном UX-проходе.

## 5. Групповые права (изменение к раннему концепту)

**Только текущий администратор группы** может инициировать и управлять **групповыми** процессами:
- создавать и настраивать официальные групповые опросы по месту/времени/формату;
- запускать `PlayAssembly`, готовить игру и открывать существующий Event wizard **от имени группы**;
- инициировать заявку на аренду/оформление брони от имени группы через действующие `QuoteVenueBookingHandler` → `RequestVenueBookingHandler` и управлять её переходами в границах уже существующих прав;
- публиковать важные объявления и изменять название группы.

**Обычный участник** по-прежнему оценивает площадки, предлагает время/место, пишет/зачёркивает свои сообщения, голосует за администратора, участвует в разрешённых администратором групповых опросах, подтверждает/отклоняет личное участие, вступает в существующие Event/Booking согласно их правам, сообщает о нарушениях. Не может создать групповое мероприятие, бронирование, сбор или обычный игровой опрос под группой.

**Не расширять автоматически личные права на весь портал:** член группы может создавать **личное** мероприятие или аренду по действующим общим правилам портала; лишь группа/соответствующая метка и автоматическое привязывание к `PlayOpportunity` запрещены неадмину. В противном случае нельзя скрытно ломать общие маршруты `Event` и `VenueBooking`.

**Критически:** быть выбранным администратором не значит владеть площадкой, иметь доступ к чужим средствам, право оплачивать/списывать деньги за игроков, ставить подтверждения за участников или обходить policy/feature flags Event/Booking. Само оформление или изменение конкретной брони требует существующих серверных полномочий и, при необходимости, правомочного плательщика/организатора. Отдельно различать `group administrator`, `event organizer`, `venue owner/staff` и `booking responsible party`. При смене group admin **не передавать автоматически** права/обязательства в уже созданном Event/Booking; для этого требуется штатный безопасный workflow передачи.

Для `CreateEventFromCoordinationHandler` и `CoordinationAccess` нужен явный scope группе: имеющаяся `canManage()` проверяет конкретного автора опроса. Замена проверки на «админ группы» в глобальных маршрутах без scope запрещена. Для `VenueRentalCoordinationController` аналогично добавить проверку `group context` при создании от имени группы, не ограничивая другие независимые сборы.

## 6. Отсутствие администратора / Filament

- Группа без админа остается доступна для обсуждения, предложений площадок и времени, выбора кандидата и чтения истории, но **не** запускает игровые опросы, мероприятие или бронь от имени группы до избрания.
- Для двух человек — исключение единогласия из пункта 4; если участники не договорились, они могут продолжать пользоваться **обычными личными** механизмами Event/Booking (без привязки от имени группы).
- Filament superadmin/уполномоченный оператор может принудительно назначить, заменить или снять администратора, отклонить/аннулировать манипулятивные заявки, завершить раунд со служебной причиной. Это не должно представляться как добровольный результат голосования: в истории явный тип `staff_override`.
- При служебной смене администратора открытый раунд нужно явно завершить/аннулировать с уведомлением голосовавших, чтобы не возникала конкурирующая автоматическая смена через несколько минут.

## 7. Модель/валидация/приёмка

Предлагаемые записи: `play_opportunities.generated_title/custom_title/admin_user_id/admin_assigned_at`; `play_group_election_rounds` (status, eligible snapshot/version, voter_count, opened_at, earliest_close_at, deadline, winner, administrator_before); `play_group_election_candidates` (round, user, message 20–1000, status, nominated_at); `play_group_election_votes` (round, canonical_user, candidate; unique round/user); `play_group_governance_audits` (change, old/new, actor, source, timestamp). Физическая модель может быть иной, но инварианты остаются.

API (план): `GET /play/opportunities/{uuid}/election`; `POST /play/opportunities/{uuid}/candidates`; `PUT /play/opportunities/{uuid}/election/my-vote`; `DELETE /play/opportunities/{uuid}/election/my-vote`; `PATCH /play/opportunities/{uuid}/title`; группа/админ-права в существующих API через серверный policy. Mutations: auth, canonical identity, confirmed, CSRF, group ACL, idempotency, rate limits, DB transaction + row lock; `409` для устаревшего раунда и `403` для посторонних.

### Тесты

1. При N=2 оба голоса позволяют выбрать; N=3 — только все 3; N=6 — 4; N=20 — 11. Нет двойных голосов для alias/нескольких PlayIntent.
2. Две параллельные заявки начинают **один** раунд; десяток параллельных POST не создают два выбора/администратора. Голос переносится `A→B`, не копируется.
3. 20-символьная мотивация принимается, 19-символьная отклоняется (Unicode/trim), изменять текст после первого голоса нельзя. Баннер содержит все кандидатуры без отдельных competing виджетов.
4. По завершении окна назначается ровно один администратор; старый теряет group-admin права атомарно. В других группах/общих действиях его права не изменяются.
5. Group admin может дать собственное custom name и откатить к автогенерируемому; Filament operator с правом может сделать то же с audit, не меняется `public_uuid`. Пользователь без group admin/служебного права не может.
6. Неадмин не может создавать **групповые** Event/Booking/Coordination даже прямым POST; участники могут оценивать/писать/голосовать. Group admin не может создавать бронь без штатного разрешения/подтверждения владельца, делать платежи или подтверждать чужую явку.
7. Soft-deleted/blocked/expired participant отстраняется от голосования и админских функций; при запрете админа группа не получает фантомного второго администратора. Параллельный staff override и завершение выборов не конфликтуют.
8. UI mobile/desktop/TMA, клавиатура и popup: баннер над основным контентом, таймер/порог/статус прозрачны, FAQ объясняет правила голосования.
