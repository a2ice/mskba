## 0. Текущее состояние (по коду main на 18.11.2026)

- Личный интерес хранится в `PlayIntent` / `play_intents`, пользовательский термин — **игровая подписка**, основной раздел ЛК — `/account/subscriptions`. Есть условия по venue/радиусу/типу, weekdays/dates/windows, cadence, format, amenities и поля доставки уведомлений. Поля `notify_matches` и `game_delivery_channels` сами по себе не гарантируют реально работающую рассылку совпадений.
- `RecommendVenuesForIntent` ранжирует подходящие площадки по собственным критериям подписки; `RecommendPlayableSlots` проверяет конкретные залы/слоты по актуальной занятости, **не резервирует**. Существующий `VenueSubscriptionAudience` агрегирует людей, подходящих к **одной площадке**, и учитывает избранное; он НЕ вычисляет факт совпадения двух игроков по общему времени и формату.
- `/venues/{venueId}/interest-group` уже существует: это **постоянная группа конкретной площадки**, с аудиторией, разрешёнными предложениями и доступными сборами на аренду. Сборы — `VenueRentalCoordination`, не `PlayAssembly`.
- `CoordinationSession/Poll/PollBallot`, `CreateEventHandler`, `EventVenueInterest`, `QuoteVenueBookingHandler`, `RequestVenueBookingHandler` уже реализуют собственные процессы. Не создавать вторые голосования/мероприятия/брони с независимыми жизненными циклами.
- В теме есть единый FAQ-попап, читающий опубликованные материалы из `/faq/help-content`, активируется `data-mskba-faq-section` и `data-mskba-faq-article`.

## 1. Терминология и жизненные циклы

1. **Мой интерес** = личная игровая подписка `PlayIntent`; может быть несколько; «хочу играть» не означает «приду».
2. **Совпадение** = проверенная совместимость предпочтений нескольких уникальных канонических пользователей; не обещание их участия.
3. **Группа совпадения / игровая возможность** = `PlayOpportunity`, стабильная серверная сущность с публичным UUID и динамической страницей, составом, вариантами площадок/времени, оценками и общей стеной. Не равно группе аудитории площадки `VenueInterestGroup`. Её отображаемое название формирует система, а не участник.
4. **Сбор / согласование конкретной игры** = `PlayAssembly` со ссылкой на `PlayOpportunity` и действующий `CoordinationSession`, инициатором и управленческими правами, собственным состоянием и дедлайнами.
5. **Мероприятие** = существующий `Event` со своими участниками, статусами и разрешениями; **бронь** = существующий `VenueBooking` и quote/payment lifecycle. Группа сохраняет явные scoped-ссылки и показывает только разрешённые объекты. В группе могут последовательно возникать разные игры; у одной конкретной возможности максимум один активный Assembly.

### Правило названия группы (принято 18.11.2026)

**Не просить ни одного участника назвать общую группу.** У группы нет единственного автора: она формируется сервером автоматически из объективного пересечения `PlayIntent`. Генерация понятного заголовка — ответственность сервиса представления `PlayOpportunity`, а не `PlayAssembly` или `Event`.

- Шаблон: `Баскетбол {общий формат} · {общая география/подтверждённая площадка} · {общее время}`. Примеры: `Баскетбол 3×3 · Дмитровская · Будни вечером`, `Баскетбол 5×5 · Север Москвы · Воскресенье`. Это примеры формата заголовка, не утверждение фактического наличия совпадений.
- **Общий формат** — только формат(ы), которые подходят всем. Если общий формат ещё не определён однозначно, перечислить короткий набор или показать `Формат уточняется`; не придумывать 3×3, когда у пользователей есть разные пожелания.
- **География** — общий район/метро/ориентир, если он надежно определяется из географического пересечения. Если выбран единственный обязательный Venue, показывать его официальное наименование. Не использовать одну из *предложенных, но не согласованных* площадок как название всей группы.
- **Время** — совместимый день недели/часть суток или дата, только если это действительно пересечение; иначе нейтральное `Время уточняется`. Время в заголовке — описание предпочтения, а не гарантия доступного слота.
- **Запасной вариант** при недостатке данных: `Поиск баскетбольной игры` с нейтральным контекстом; название должно быть читаемым и без внутренних UUID/ID.
- Имя — **отображаемое поле, не идентификатор и не ключ дедупликации**. Каноническая ссылка остается `/play/opportunities/{public_uuid}`; изменение состава, названия района или предпочтительного времени не меняет URL/UUID и не теряет стену или историю.
- При существенном пересчете пересечения сервер может обновить автозаголовок и зафиксировать событие/версию отображаемых условий. Нельзя менять заголовок после каждого голоса, сообщения или перестановки кандидатов, создавать «скачущий» UI. Использовать снимок совместимости, обновлять только при фактическом изменении общего формата/места/времени.
- **Разные названия разных объектов:** группа `PlayOpportunity` — генерирует система; `PlayAssembly` — инициатор может назвать/изменить с автоподстановкой; `Event` — название задает организатор в штатном Event wizard. Переименование Event не переименовывает группу.
- Никакого публичного поля ручного редактирования названия группы; при необходимости редакторские override и модерация — отдельное решение.

### Движение состояний

`play_intent: active → candidate matches → play_opportunity: discussing → play_assembly: collecting/agreeing → confirmed decision → Event/Booking via existing handlers`; независимо доступны `paused, cancelled, expired, closed`. Действия никогда не переводят интерес прямо в оплаченную бронь или подтверждённую явку. При изменении времени/места/суммы персональные подтверждения инвалидируются.

## 2. Алгоритм совпадений (общий → частный)

### Условия совместимости

- Учитывать только активные, неистёкшие подписки не заблокированных канонических пользователей, один человек = одна голосующая/учитываемая единица даже при нескольких PlayIntent.
- **Жёсткие фильтры:** ненулевое пересечение форматов; совместимое географическое множество реальных площадок; запреты/excluded IDs; обязательные удобства; indoor/outdoor и free/paid; общая будущая возможность по дате/дню и времени не короче требуемой длительности; неперекрывающаяся занятость на момент точной проверки. Не объединять, если нет хотя бы одного общего выполнимого варианта.
- **Временные правила:** `once` — конкретные даты/период в пределах существующего 30-дневного горизонта; `regular` — weekday и окна, раскрытые в конкретные будущие даты на 4 недели; `flexible` — интервалы пользователя или широкое «готов рассмотреть варианты», без выдуманного подтверждения. Ночные интервалы `end_next_day`, timezone площадки и DST учитываются при переводе в UTC.
- **География:** `venue_id` без похожих = только этот Venue; `include_similar_venues` = основной и допустимые альтернативы; `venue_id=null` = поиск по центру/радиусу/параметрам. Если место совсем не задано, не создавать группу «весь город» автоматически: запросить уточнение географии для точного совпадения.
- **Валидация группы:** недостаточно «A совместим с B, а B с C» — должен существовать хотя бы один общий вариант для каждого члена группы. Не собирать транзитивные ложные группы.
- **Предложение совпадения** возможно от 2 участников. Для формата 5×5 не называть 2–9 человек «собранной командой»: показывать `заинтересованы X, для игры ориентир Y`. Любой подтверждённый участник может инициировать организацию без специальной роли.
- **Обновление:** пересчёт по сохранению/паузе/сроку подписки и связанным изменениям площадок/свободных окон; идемпотентный job/проекция. Не создавать новую `PlayOpportunity` при каждом чтении страницы и не дублировать сходные возможности для одной общей области, формата и временного окна. Стабильный UUID, версии состава/критериев и архив истории при закрытии.
- Результат объяснять причинами: `3 игрока подходят по формату 3×3, средам 19:00–21:00, радиусу 5 км`. Не показывать фиктивный «процент вероятности игры».

## 3. «Мои подписки» — видимость совпадений в ЛК

На **каждой** игровой подписке отобразить отдельную динамическую секцию `Совпадения`:
- при отсутствии: «Пока совпадений нет. Мы ищем игроков по этим условиям» + изменить критерии;
- при наличии: `Найдено N совместимых игроков · M игровых возможностей` (отдельные показатели, без двойного учёта), последние изменения, 1–3 карточки групп, CTA `Обсудить игру`, `Все совпадения`;
- у группы: понятное название (район/ориентир, формат, ближайшее подходящее время), число подходящих игроков, статус, наличие Event/Booking, подписан ли пользователь на сервисные оповещения; «потенциально» не равно «подтвердили участие»;
- несколько персональных подписок, попавших в одну группу, не создают в ЛК повторную физическую группу; сервер возвращает идентичный `opportunity_id`, в ответе — `matched_intent_ids` только для владельца;
- новая группа / существенные изменения — сигнал в ЛК и через разрешённые каналы; без спама, дедупликация `user + opportunity + version + event_type`, возможность отключить уведомления именно этой группы.

API-предложение: `GET /account/play-intents/{id}/matches` с личным scope, пагинацией и версией проекции.

## 4. Динамическая страница группы совпадений

Предлагаемый canonical URL: `/play/opportunities/{public_uuid}` (UUID без прямых числовых id и возможности простого перебора). Существующий `/venues/{id}/interest-group` остаётся зонтичной страницей площадки и **ссылается** на конкретные доступные возможности; она не должна становиться псевдонимом группы без площадки.

### Шапка и сводка

- Breadcrumb: `ЛК → Мои подписки → Совпадения → [группа]`. Автозаголовок из общих условий, например `Баскетбол 3×3 · Север Москвы · среда вечером`, статус `Подбор / Обсуждение / Согласование / Игра создана / Завершено`.
- Блок `Что у нас совпало`: форматы, общие географические ограничения, **общие** временные окна, сколько заинтересованы и сколько подтвердили конкретную игру, без разглашения чужих индивидуальных расписаний.
- Вверху заметная ссылка-кнопка `Как это работает?` открывает **существующий** общий FAQ-диалог со статьёй `play-interest-group-howto`.
- Раздел `Участники`: число уникальных аккаунтов, разрешённая публичная часть профилей; скрытые личные атрибуты/контакты/конкретные расписания не показываются. Доступ к оценкам/стене только при активном подтверждённом участии в совпадении.
- Раздел `Уже организуются / Созданные мероприятия`: только явно связанные с этим PlayOpportunity/Assembly объекты, дата, место, доступный состав, реальный Event status, Booking status; ссылки и контекстные действия по существующим permissions.
- При отсутствии мероприятий: явное «Пока игр и бронирований нет». Не выводить любые посторонние события данной площадки как «созданные группой».

### Площадки и оценки (главная рабочая часть)

- Для интереса без конкретного Venue формировать 3–7 **реально подходящих всем по обязательным условиям** кандидатов; при конкретном Venue — показывать его приоритетно и разрешённые альтернативы, если включены похожие. При отсутствии единого кандидата — отобразить, что требуется уточнить критерии, не выдавать неподходящие объекты за совпадение.
- Карточка: название, адрес/метро, карта, расстояние до общей зоны, доступность и стоимость только при подтверждённом актуальном quote, ограничения, предлагаемые даты/время и статус проверки, общее число откликов. При отсутствии данных — честное `Не проверено`.
- **Личная оценка площадки от 1 до 10**, изменяемая; один актуальный голос на канонического пользователя/venue/opportunity, без самоудвоения подписками. Дополнительно `Не подходит мне` как явный отказ (оценка 1 не обязательно означает «вообще нельзя»); голос «пока не оценил» не приравнивать к 0.
- **Доступность участника применительно к этой площадке:** режим `Дни недели` (один/несколько дней + временные интервалы) либо `Конкретная дата` (будущая дата и время), с возможностью нескольких вариантов; длительность наследуется/уточняется. Указанное здесь предложение НЕ меняет глобальную подписку и само по себе НЕ подтверждает явку. Данные сохраняются отдельно от голосования по месту.
- **Комментарий к конкретной площадке** (предложение: plain text до 300 символов). Не смешивать с общей стеной. Один пользователь может редактировать свою оценку/предложения; история существенных изменений доступна для аудита.
- **Порядок кандидатов:** сначала исключить несовместимые с обязательными условиями, затем по числу участников, которые поддерживают (например, оценка 7–10) и имеют пересекающееся предложенное время; после этого средняя оценка **с количеством голосов**, удобство общих времён/фактическая доступность и расстояние. Без фиктивного «10 из 10 от группы», если проголосовал один человек. В карточке показывать основания: `4 из 6 оценили, средняя 8,3/10; у 3 совпало время`. Рейтинг алгоритма и пользовательские баллы раздельны; отсутствие оценки — нейтрально.
- Участник группы может предложить другую площадку, но она проходит прежние hard filters, правила исключений и проверку наличия. Ограничить количество активных кандидатов и дубликаты.

### Общая стена

- Лента сообщений по группе (последние/новые, пагинация; textarea и счётчик `0/200`, кнопка отправки AJAX, toast); показывает автора в пределах согласованной публичности и время.
- **Только подтверждённый, не заблокированный пользователь, имеющий актуальное право участвовать в данной группе, может писать.**
- Не более **3 новых сообщений за скользящие 60 секунд на канонического пользователя по всем группам** (иначе можно обойти лимит, переходя между группами), серверный общий RateLimiter/Redis; на превышение HTTP `429` и `Retry-After` + дружелюбное сообщение и отображаемая пауза. Максимум **200 Unicode-символов после trim** на сервере, frontend только помогает. Контроль в транзакционном/атомарном контуре, защита от двойного POST (`client_request_id`).
- На первом этапе plain text, без HTML, вложений и автопубликации внешних ссылок; экранирование, CSP, CSRF, серверные политики, модераторское скрытие, soft delete, жалоба. Правки собственных сообщений (если включим) не должны позволять обходить rate limit.
- **Пользовательское удаление — визуальное зачёркивание, а не исчезновение сообщения (принято 18.11.2026):** автор нажимает `Удалить`, сервер фиксирует `deleted_at` и `deleted_by_user_id` (или эквивалентный статус), запись остается в той же позиции хронологической ленты. Содержимое показывается внутри `<s>`/`text-decoration:line-through` с приглушённым стилем и надписью `Сообщение удалено автором`. Не заменять исходный текст на заглушку при обычном пользовательском удалении, не возвращать сообщение в список активных для поиска и реакций. Повторная отправка такого же текста — новое сообщение и новый расход лимита 3/60. Удаление не освобождает квоту.
- Повторное удаление идемпотентно; только автор (канонический пользователь) может удалить свое сообщение. Нельзя отвечать на зачёркнутое сообщение и использовать его как активное действие. При снятии доступа/удалении аккаунта соблюдать отдельную политику приватности.
- **Модераторское скрытие отличается от авторского удаления**: при оскорблениях, раскрытии контактов, запрещённой информации модератор может скрыть исходный текст для обычных участников, оставив только статус `Скрыто модератором` и аудит для уполномоченных сотрудников. Зачёркивание не является достаточной мерой безопасности для опасного контента.
- Комментарии ≠ личные сообщения/чат Event. По умолчанию не слать каждому участнику push на каждый комментарий: оповещать о новых существенных решениях и назначенных сборах; для стены — опциональная подписка/дайджест.
- Гостю / неподтверждённому / вышедшему из группы показывать понятное readonly-состояние без раскрытия чужих приватных сведений.

## 5. Переход к игре и бронированию

- Любой подтверждённый участник, имеющий доступ к группе, может нажать `Начать согласование игры`. При одновременных нажатиях нескольких людей сервер возвращает **один** активный PlayAssembly на конкретную возможность, а не дубликаты. Пользователь становится инициатором; можно назначить помощников по имеющейся схеме permissions.
- Собранные оценки/временные предложения подсказывают **варианты** для официального `CoordinationSession/Poll/PollBallot` (выбор Venue, даты, времени). Сбор предложений на странице не должен исподволь становиться отдельным вторым голосованием об обязательствах.
- После выбора варианта показать конкретные зал, стоимость/макс. долю, время, состав, дедлайн подтверждения; каждый участник подтверждает эти условия лично. Отказ/истечение/изменение версии снимают подтверждение и запускают новое согласование.
- `Создать мероприятие` вызывает **существующий** сценарий `CreateEventHandler` / event wizard с предзаполненными выбранным местом/временем/форматом и с сохранением group/assembly linkage; организатор видит итог перед подтверждением, участие не создаётся автоматически для всех заинтересованных.
- `Забронировать площадку` открывает существующий `QuoteVenueBookingHandler` → `RequestVenueBookingHandler`, с выбором конкретного зала/зоны и актуального времени/стоимости, с server permission/feature flags. Допустим поддерживаемый существующей системой сценарий **Event с отложенной бронью**; не заставлять всегда бронировать первым или всегда создавать Event первым. Group/Assembly сами по себе не резервируют и не списывают средства.
- Возможность `Присоединиться к мероприятию` — только если оно действительно открыто для участия; использовать существующий lifecycle `EventParticipant`. Показывать бронь отдельно: `нет / предзаявка / ожидает / удерживается / подтверждена / отменена` в зависимости от реального enum.
- При завершённой игре/сборе сохранять историю и возможность нового **независимого** сбора той же долгосрочной группы. Разрешать несколько НЕ пересекающихся игр на разные слоты и не создавать дубли конкурирующих Assembly по одному слоту.

## 6. Доступность, безопасность, согласие

| Контекст | Чтение | Оценка/время/стена | Запуск Assembly | Event/Booking |
| --- | --- | --- | --- | --- |
| Гость | только безопасный тизер/вход | нет | нет | нет |
| Подписка активна, совпадение подтверждено, контакт не подтверждён | ограниченные данные группы | нет | нет | существующие правила |
| Подтверждённый участник совпадения | разрешённые участникам данные | да | да | по существующим permissions/feature flags |
| Не входящий в группу пользователь | нет приватных сведений | нет | нет | нет |
| Инициатор/помощник | scoped доступ к процессу | да | управление только делегированным | существующие разрешения |
| Администратор/модератор | по служебным правам | модерация/аудит | без подмены голоса | по ролям |

- Показывать групповые **агрегаты** времени, а не личные окна других пользователей. Пользователь видит свои собственные записи; опубликованные им оценки/комментарии только в нужном контексте.
- Учитывать канонический пользовательский ID, soft delete аккаунта, блокировку и отозванную подписку; фаворит площадки сам по себе **не даёт права** в не привязанной к ней группе совпадения.
- При закрытии/изменении PlayIntent обновлять membership; историю собственных комментариев сохранять в архиве с корректным visibility, архивную группу нельзя использовать для новых сборов без нового актуального совпадения.
- Отдельные policies для `view`, `vote`, `comment`, `initiate`, `manage`, `book`, с серверной проверкой в каждом use case; ссылки нельзя выдавать вместо разрешений.

## 7. Предлагаемая модель и API (без миграций на этапе планирования)

- `play_opportunities` — `id/public_id`, серверный generated/display title (cache/snapshot, не пользовательский ввод), scope fingerprint/version, format/time/geo summary, lifecycle, timestamps.
- `play_opportunity_members` — `opportunity_id + canonical_user_id` unique, provenance `matched_intent_ids` или отдельная join-таблица, membership/current/archived timestamps, consent and access snapshot.
- `play_opportunity_venues` — venue/court candidate, suggestion origin, eligibility snapshot, timestamps.
- `play_opportunity_venue_ratings` — unique `opportunity_id + venue_id + canonical_user_id`, rating 1–10 либо unsuitable, timestamps.
- `play_opportunity_time_choices` — `opportunity_id, venue_id, user_id, mode=weekly|once, weekday/date, start/end, timezone`; nullable venue только если общий выбор времени до площадки.
- `play_opportunity_venue_notes` — короткие per-venue заметки с автором.
- `play_opportunity_wall_posts` — comment text <=200, creator canonical, visual delete flag/`deleted_at`/`deleted_by_user_id` (авторское зачёркивание, исходный текст остаётся видимым), отдельный moderation-hidden state (текст не виден обычным участникам), idempotency UUID, timestamps.
- `play_assemblies` — scoped opportunity, organizer, status, active opportunity uniqueness/concurrency constraint, `coordination_session_id`, snapshots and versions; `play_assembly_event_links` / `booking_links` или обоснованный полиморфный linkage, не копии событий/броней.
- API: личный индекс совпадений; scoped чтение страницы; mutation рейтинга/времени/заметки/стены; старт или повторный вход в Assembly; ссылки на официальные existing Event/Booking use cases. Все mutating endpoints используют CSRF/auth, policies, троттлинг, идемпотентность, валидаторы, сервисные ошибки `422/403/404/409/429`.

## 8. FAQ, встроенный в единую модалку

Кнопка вверху: `data-mskba-faq-section="other"` + `data-mskba-faq-article="play-interest-group-howto"` (секцию согласовать с реальным каталогом FAQ перед публикацией). Статья создаётся **через существующий Content/FAQ** и редактируется из Filament, не как жёстко вшитый HTML.

### Черновик статьи «Как договориться об игре»

**Что это за группа?** MSKBA нашла игроков с пересекающимися предпочтениями по месту, времени и формату. Пока это только возможность собраться — не готовая игра.

**Как выбрать площадку?** Посмотри предложенные варианты, поставь каждой подходящей площадке оценку от 1 до 10. Оценку можно поменять. Если место совсем не подходит — отметь это отдельно. Система учитывает голоса всех участников и покажет, почему предлагает ту или иную площадку.

**Как предложить время?** Для каждой площадки выбери удобные дни недели и интервалы либо конкретную будущую дату и время. Предложение не гарантирует свободный зал: перед арендой MSKBA ещё раз проверит расписание и стоимость.

**Зачем комментарий к площадке?** Чтобы кратко пояснить, что нравится или не нравится в конкретном варианте. Общая стена ниже предназначена для обсуждения всей игры.

**Как пользоваться стеной?** Подтверждённые участники могут писать сообщения длиной до 200 символов. Не более трёх сообщений за минуту. Пожалуйста, обсуждай игру по существу и уважай остальных: спам, оскорбления и реклама могут быть скрыты модератором.

**Кто может создать игру?** Любой подтверждённый участник может запустить согласование. Система предложит выбрать место и время, после чего участники отдельно подтвердят конкретные условия.

**Когда игра считается организованной?** Только после оформления мероприятия и необходимых подтверждений; аренда — отдельный процесс со своим фактическим статусом. Голос, комментарий и добавление площадки в избранное не являются бронью или согласием платить.

## 9. Этапы внедрения (каждый — отдельный тестируемый инкремент)

1. **Матчинг + ЛК (ядро):** корректная серверная совместимость по времени/формату/месту, проекция/идентичность PlayOpportunity, карточки `Совпадения` в `/account/subscriptions`. Проверить false-transitive, canonical dedupe, ночные интервалы, географию, паузы, soft delete, права; пока read-only.
2. **Страница группы + справка:** стабильный UUID, заголовок, совместимые условия, участники с privacy, связанные Event/Booking read-only и повторное использование штатного FAQ. При пустом списке — объяснение/редактирование личных критериев.
3. **Площадки, баллы и время:** candidates + общий рейтинг участников, отдельная оценка 1–10, unsuitable, weekly/one-off proposals, per-venue notes, проверяемое ранжирование с количеством голосов, ограничения и фильтры; без бронирования при выборе.
4. **Стена:** только confirmed participants, 200 символов, 3/60с на пользователя globally, 429/Retry-After, публикация AJAX, пагинация, модерация и безопасный UX.
5. **Assembly + штатные процессы:** запуск единственного процесса, переиспользование Coordination, персональное подтверждение, безопасные переходы в Event и Booking; версии/права/конкурентность.
6. **Оповещения и полировка:** действительно отправляемые уведомления о новом совпадении/решении в allowed channels; дедупликация/дайджест/мьют; пустые состояния, TMA/mobile/desktop, нагрузка и мониторинг. Предложения площадки по task 288 отдельно.

### Сквозная приёмка

- Два интереса с совпадением времени/географии/формата получают одну общую страницу, каждое видно в своём ЛК; несовместимые не создают фиктивную группу. При A↔B и B↔C, но A не совместим с C, система не объединяет всех троих.
- Один пользователь не дублируется при 2+ подписках, не может голосовать дважды или обойти лимит стены через другие группы/параллельные POST.
- По каждому Venue честно показываются личная оценка, число оценок, групповой рейтинг, общие реальные будущие окна и неизвестная/проверенная доступность.
- Стена: неподтверждённому и постороннему 403, третий пост принимается, четвёртый за 60 секунд — 429; не более 200 символов; ошибки не стирают введённый текст. Удалённое автором сообщение остаётся с зачёркнутым исходным текстом в прежней позиции, лимит не возвращается; модерируемое содержимое скрывается для обычных зрителей.
- FAQ открывается глобальным popup без второй реализации.
- Одновременные действия двух инициаторов не создают два Assembly/две брони. Мероприятие и бронь имеют только фактические статусы и проверенные permissions. Изменение времени/зала/цены требует нового согласия.

## 10. Принятые уточнения и оставшиеся UX-решения

1. Видимость группы: предлагается **по умолчанию только участникам совпадения**, а сторонним — не более безопасного тизера. Публикуемую ссылку в Telegram рассматривать отдельно.
2. Доступ: ограничить комментарии и оценки подтверждёнными участниками, но неподтверждённым дать прочитать безопасную часть своей группы и подтвердить контакт.
3. Горизонт поиска: **30 дней** для разовых запросов (существующий контракт) и раскладка регулярных интересов на ближайшие **4 недели** (предложение).
4. Рейтинг: «поддержали/доступны по времени» важнее средней оценки, чтобы один голос `10` не побеждал четыре `8`; алгоритм и порог `7+` предложены, требуются UX-примеры.
5. Общая стена: **3/60 секунд глобально по каноническому пользователю**, max 200, только plain text, **авторское удаление зачёркиванием** (принято) / отдельное скрытие при модерации; per-venue заметки отдельно.
6. Связь с местами: VenueInterestGroup остаётся общим зонтиком, opportunity — конкретная пересекающаяся возможность; изменения существующих маршрутов не требуется.
7. Порядок оформления: **Event-first с отложенной бронью и booking-first** остаются возможными там, где поддерживаются существующей системой; не вводить третий механизм.

### Решения, принятые 18.11.2026

- Название группы формируется автоматически из объективно общих параметров; инициатор отдельно называет сбор, организатор — мероприятие; адрес группы неизменен.
- Авторское удаление сообщения оставляет видимое зачёркнутое сообщение на стене; модератор может скрыть опасное содержимое полностью.
