# 140 - Переработать popup-wizard поиска мероприятий и добавить географические справочники

## Оригинальное описание

Переработать два popup-wizard на главной странице (`Мероприятия` и `Площадки`), унифицировать навигацию по шагам и полноценно реализовать сценарий поиска мероприятий.

Дополнительно в рамках этой задачи ввести минимальные справочники городов и районов/округов, связать их с адресами и использовать при определении локации через Yandex API.

Рабочая ветка: `feature/140`.

## Подробное описание

### 1. Общий UX popup-wizard

Оба popup-wizard получают единый нижний bar управления:

- `Назад` слева;
- `Далее` справа;
- на шагах, которые можно пройти без выбора, между ними показывается ссылка `Пропустить`;
- bar постоянно доступен внизу popup, в том числе на длинных шагах;
- клик по варианту на основном шаге только выбирает значение и больше не переводит пользователя автоматически на следующий основной шаг;
- переход между основными шагами выполняется через `Назад` / `Далее`;
- на финальном шаге вместо `Далее` допускается контекстное действие `Готово`.

Для popup площадок на этом этапе меняется общий navigation contract, без глубокой переработки предметного содержимого — отдельная детализация поиска площадок будет сделана после сценария мероприятий.

### 2. Popup `Мероприятия` — вкладка `Найти`

Eyebrow `Игры и тренировки` заменить на `Мероприятия`.

Основные шаги:

1. `Тип`;
2. `Параметры`;
3. `Где`;
4. `Когда`;
5. `Результаты`.

#### Шаг 1 — тип мероприятия

Варианты:

- `Не важно` — выбран по умолчанию;
- `Игра`;
- `Тренировка`;
- `Игровая тренировка`;
- `Турнир`.

Каждый вариант получает существующий проектный tooltip с иконкой `?` без подчёркивания.

#### Шаг 2 — параметры

Содержимое зависит от типа, выбранного на предыдущем шаге.

Для `Игра`:

- формат: `Не важно`, `Баскетбол 5×5`, `Стритбол 3×3`, `Стритбол 1×1`;
- режим: `Не важно`, `Готовые команды`, `Отдельные игроки`.

Использовать существующие доменные значения `GameFormatEnum` и `GameRecruitmentModeEnum`.

Для `Тренировка` и `Игровая тренировка`:

- пока нет дополнительных типов/форматов/режимов;
- показывается пустой state;
- шаг можно пропустить.

Для `Турнир`:

- формат: `Не важно`, `Баскетбол 5×5`, `Стритбол 3×3`, `Стритбол 1×1`;
- порядок набора: `Не важно`, `Открытая лига`, `Фиксированный состав`.

Использовать существующие `GameFormatEnum` и `TournamentEnrollmentPolicyEnum`.

Если на первом шаге выбрано `Не важно`, второй шаг не смешивает несовместимые фильтры и может быть пропущен.

#### Шаг 3 — где

Первый уровень:

- `Не важно` — выбран по умолчанию;
- `Указать локацию`.

После выбора `Указать локацию` раскрывается вложенный вертикальный mini-wizard.

В начале доступна кнопка `Текущая локация`, которая переиспользует существующий сценарий геолокации страницы `/venues/create`: browser/Telegram geolocation -> backend reverse geocoding -> Yandex.

При ошибке:

`Не удалось получить геопозицию. Попробуйте ещё раз или введите вручную ниже`.

Подшаги локации:

1. город;
2. район/округ;
3. метро;
4. улица и площадка.

Завершённые подшаги превращаются в редактируемые badges. Нажатие на badge возвращает к соответствующему подшагу.

`Не важно` считается завершённым выбором, но не участвует в фильтрации.

##### Город

Использовать новый справочник `City`.

Если доступен один город, он выбирается автоматически. Если городов несколько — показывается пустое значение `Выбрать город`, а также `Не важно`.

Первоначально в справочник добавить:

- Москва (`moscow`);
- Химки (`khimki`).

##### Район/округ

Использовать новый справочник `District`, связанный с `City` как `City 1 -> N District`.

Для Москвы ввести административные округа:

- ЦАО — Центральный административный округ;
- САО — Северный административный округ;
- СВАО — Северо-Восточный административный округ;
- ВАО — Восточный административный округ;
- ЮВАО — Юго-Восточный административный округ;
- ЮАО — Южный административный округ;
- ЮЗАО — Юго-Западный административный округ;
- ЗАО — Западный административный округ;
- СЗАО — Северо-Западный административный округ;
- ЗелАО — Зеленоградский административный округ;
- НАО — Новомосковский административный округ;
- ТАО — Троицкий административный округ.

Для Химок ввести районы/микрорайоны:

- Старые Химки;
- Новые Химки;
- Новокуркино;
- Левобережный;
- Клязьма-Старбеево;
- Сходня;
- Подрезково;
- Новогорск;
- Другие территории.

Если для города районов нет, автоматически выбрать `Не важно` и перейти к метро.

##### Метро

Переиспользовать существующий справочник `MetroStation` и predictive UI.

Варианты:

- `Выбрать метро`;
- `Не важно`;
- станции доступного города.

##### Улица и площадка

Улица — predictive input через существующую backend-интеграцию Yandex. В запрос подставляется выбранный город, если город не `Не важно`.

Площадка — переиспользовать существующий predictive venue selector.

Выбранная улица влияет на поиск площадки. Если после выбора площадки пользователь меняет улицу, выбранная площадка сбрасывается.

#### Шаг 4 — когда

Диапазон дат:

- `От` — текущий день;
- `До` — текущий день + 7 дней.

Использовать timezone приложения. Конечная дата не может быть раньше начальной.

#### Шаг 5 — результаты

При переходе на шаг показывать стандартный loading overlay/preloader поверх контейнера результатов.

Результаты должны объединять подходящие:

- игры;
- тренировки;
- игровые тренировки;
- турниры.

Нужен отдельный read-only discovery endpoint/read model, потому что текущие `events.index` и `tournaments.index` не дают единого контракта и не покрывают все новые фильтры.

После изменения предыдущего фильтра пользователь может вернуться к результатам и выполнить поиск заново.

### 3. Географические справочники Location

Добавить в модуль `Location` сущности:

#### City

Поля:

- `id`;
- `name` — русское название;
- `alias` — уникальный slug, по умолчанию английское/латинское название (`moscow`, `khimki`);
- `short_name` — nullable сокращённое название;
- `description` — nullable описание;
- timestamps.

Связь: `City hasMany District`.

#### District

Поля:

- `id`;
- `city_id`;
- `name` — русское название;
- `alias` — уникальный в пределах города slug;
- `short_name` — nullable сокращённое название;
- `description` — nullable описание;
- timestamps.

Связь: `District belongsTo City`.

Термин `District` используется как общий технический уровень для административного округа Москвы и района/микрорайона другого города. В UI допустим контекстный текст `Район / округ`.

### 4. Связь Address с City и District

В `addresses` добавить:

- nullable `city_id` FK -> `cities`;
- nullable `district_id` FK -> `districts`.

Текущее строковое поле `addresses.city` не удалять: оно остаётся snapshot исходного структурированного ответа геокодера и обеспечивает обратную совместимость/отображение.

Новые связи:

- `Address belongsTo City`;
- `Address belongsTo District`.

При сохранении `district_id` application layer обязан гарантировать, что район принадлежит выбранному `city_id`.

### 5. Определение City/District из Yandex

Расширить `AddressSuggestionDTO` и Yandex provider административными компонентами, достаточными для определения города и района/округа.

После получения структурированного Yandex-адреса отдельный resolver сопоставляет названия провайдера со справочниками MSKBA и возвращает `city_id`/`district_id`.

Требования:

- не привязывать доменную модель напрямую к формату Yandex;
- нормализовать регистр, пробелы, сокращения и служебные слова при сопоставлении;
- город определять независимо от района;
- если город найден, а район однозначно не найден — сохранять `city_id`, `district_id = null`;
- неизвестный город/район не создавать автоматически из внешнего API;
- новые и отредактированные адреса должны получать ссылки автоматически;
- существующие адреса можно безопасно backfill по текущему строковому `addresses.city`; `district_id` оставлять nullable, если его нельзя определить без повторного геокодирования.

### 6. Админ-справочник

Добавить раздел админки для работы с географическими справочниками.

Минимальные возможности:

- список городов;
- создание/редактирование города;
- просмотр районов выбранного города;
- создание/редактирование/удаление района;
- редактирование `name`, `alias`, `short_name`, `description`;
- защита уникальности alias;
- запрет удаления города/района, если действие нарушит целостность существующих данных; допустимо оставить FK nullable и перед удалением явно обнулять ссылки только через управляемый action.

В UI раздел называется `Города и районы` либо `География`; внутри Москвы районы отображаются как административные округа.

### 7. Начальные данные

Добавить production-safe idempotent seeding справочника:

- Москва и её 12 административных округов;
- Химки и перечисленные районы/микрорайоны.

Повторный запуск seed не должен создавать дубли и не должен затирать осмысленные изменения администратора без явной необходимости.

### 8. Проверки

Минимально защитить тестами существенную бизнес-логику:

- связи City/District/Address;
- уникальность и принадлежность District к City;
- сопоставление Yandex structured address -> city/district;
- корректный fallback `district_id = null`;
- discovery endpoint и ключевые комбинации фильтров;
- отсутствие регрессии существующего address suggest/reverse flow.

Frontend:

- `npm run build`;
- ручная desktop/mobile проверка обоих popup-wizard;
- проверка browser geolocation и fallback ручного ввода.

## Принятые решения планирования

- задача использует номер `140`, потому что `feature/139` уже занята;
- `City` и `District` входят в Task 140 как фундамент шага локации, а не выделяются в независимую задачу;
- строковое `Address.city` сохраняется;
- справочник не пополняется автоматически данными Yandex;
- неизвестный район не блокирует сохранение адреса;
- `Другие территории` в Химках является обычной справочной записью и не используется как автоматический fallback для любого неизвестного района;
- содержимое вкладки поиска площадок пока не расширяется: только общий wizard footer/navigation contract.

## Результат

Реализация 001–008 завершена в `feature/140`.

С точки зрения пользователя popup `Мероприятия -> Найти` теперь представляет единый пятишаговый wizard `Тип -> Параметры -> Где -> Когда -> Результаты`, не выполняет auto-advance после выбора option, поддерживает необязательные шаги, редактируемые выбранные значения и выдаёт Event/Tournament внутри того же popup с loading/empty/error состояниями.

В `Location` добавлены канонические справочники `City`/`District`, production-safe начальные данные Москвы и Химок, связь адресов через nullable `city_id`/`district_id`, Yandex resolver и административный CRUD `Города и районы`. Строковое `Address.city` сохранено для обратной совместимости.

Discovery реализован отдельным read-only endpoint `GET /home/event-discovery`; географические фильтры проходят через `Venue -> Location -> Address/MetroStation`. Для обычных мероприятий выдаются только `published + public`, для турниров — `confirmed`.

В ходе итогового статического review найден и исправлен lifecycle-дефект: discovery мог инициализироваться раньше общего footer. Теперь `home-event-discovery-loader.js` лениво загружает финальный слой после `modal:opened` и монтирования navigation DOM.

Техническая документация обновлена в `docs/specification/location.md`, `docs/specification/homepage-event-discovery.md` и подзадачах Task 140.

Executable verification ещё не завершён: CI проекта запускается только на pull request в `main`, где выполняются `php artisan test` и `npm run build`. После отдельного согласования PR необходимо дождаться зелёного CI и выполнить desktop/mobile smoke-check по `subtasks/009-docs-and-verification.md`. Merge в `main` до этого не выполняется.
