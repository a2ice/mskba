# 286 — Реализация: серверный инкремент 1 (2026-10-24)

**Статус:** WIP в [PR #418](https://github.com/a2ice/mskba/pull/418). **Не готово к merge/deploy:** новый интерфейс `mskba_app` остаётся строго local-only до отдельного разрешения; подключённые компьютеры Dmitanium и MacBook Pro были offline при начале разработки. Документационная программа — [PR #413](https://github.com/a2ice/mskba/pull/413).

## Реализовано в ветке

- `play_intents`: персональные (canonical User) интересы с optional Venue, геоточкой и радиусом, режимом `flexible/once/regular`, днями/датами, интервалами, форматами, длительностью, доступом free/paid, удобствами `preferred/required`, независимыми настройками сервисных и коммерческих уведомлений, статусом и TTL.
- `PlayIntentController`: приватные JSON-веб-маршруты создания/полного редактирования, просмотра, pause/resume/cancel, каталога активных удобств. Веб-сессия/CSRF сохраняются; доступ к чужой записи проверяется на сервере и даёт 404.
- `PlayIntentManager`: сохранение под каноническим User, обязательная проверка публичного Venue, derivation координат выбранной площадки, одноразовый UUID `client_request_id` для повторной отправки после стандартной авторизации. При конкурентной попытке используется уникальность `user_id+client_request_id`; один и тот же запрос не создаёт два интереса.
- `RecommendVenuesForIntent`: кандидаты по условиям местоположения/радиуса, активных площадок и amenities. `required` исключает отсутствующие объекты, `preferred` влияет на ранжирование; статус доступности `not_checked`.
- `RecommendPlayableSlots`: вариант на **конкретную дату/время** и указанную длительность, до ±120 минут (30-мин шаг), рейтинг время 45% / расстояние 35% / удобства 20%; использует `VenueEventAvailability` для каждого зала и проверяет действующее расписание и существующую занятость. Результат `available_at_check` не является резервом и требует повторной проверки перед Booking; комнаты без подтверждённого расписания не маркируются свободными.
- Feature-тесты: базовый CRUD, scope/IDOR, скрытая площадка, once/regular, даты/ночные интервалы, требования Amenity, идемпотентный повтор после входа, точный слот и семантика «доступно только на момент проверки».

## Существующие контракты, которые сохраняем

- `AuthDialog`/`RegistrationWizard`, предвыбор `role=player`, обязательный privacy onboarding и возврат в UX — только в будущей локальной интеграции в `mskba_app`; текущий API **сам не создаёт роль и не обходит privacy**.
- `PlayIntent` не создаёт Event, VenueBooking или обязательств оплаты.
- Проверка слотов не означает резерв и не гарантирует, что место останется свободным.
- Списки индивидуальных интересов приватны и не отдаются администраторам площадки.

## Важные границы текущего инкремента

`RecommendPlayableSlots` ранжирует запрос на **определённый день/время** и не выстраивает автоматически все возможные даты/окна для регулярных интересов; поддержка инициации групп/голосований не входит в 286 (это задача 287). Ночные игровые мероприятия через полночь сейчас ограничены базовым `VenueEventAvailability`; такие интервалы не следует ошибочно маркировать свободными.

**Статус не меняем на «Готово» до реализации и приёмки всех сценариев.**

## Прямой UI → dev по разрешению пользователя (24.10.2026)

Пользователь **явно разрешил пропустить local-only для задачи 286 и развернуть UI на dev**. Это исключение **не распространяется** на остальные задачи MSKBA App или main/prod.

В ветке добавлены:
- Реальная \`mskba_app\`-страница \`venues.show\` на прежнем публичном маршруте, данные из \`ShowVenueHandler\` (галерея, адрес, amenities, опубликованная занятость) без fake metrics и вымышленных слотов.
- Vue \`PlayIntentDialog\` в Modal 1.1, формы времени / формат / radius / amenity priorities; светлые/тёмные CSS-токены действующего UI Kit.
- Интеграция текущего AuthDialog и RegistrationWizard с preselected \`player\` **только** при запуске этого flow; pending draft хранится в sessionStorage и используется единожды после успешной авторизации и обязательного privacy onboarding.
- Серверное подтверждение \`PlayIntent\` требуется для экрана «Настройки приняты».
- Страница \`/account/play-interests\` и actions pause/resume/cancel и просмотр кандидатов площадок.
- Feature UI-render тест для страницы Venue и раздела интересов, поверх серверных тестов.

**Ограничения первой проверки dev:** рейтинг игроков, совместимые группы, события с открытым набором, сервисные уведомления и полноценный calendar slot finder в публичном UI **ещё не завершены**. Секция доступности явно предупреждает, что отсутствие занятого слота не доказывает доступность брони. Ссылка бронирования на новой странице пока ведёт в расписание; полноценная миграция booking UX остаётся отдельным этапом 006. Не скрывать эти ограничения.

**Релиз:** PR #418 до окончания CI/deploy и visual review остаётся черновым; после deploy ссылку/хэш/проверки записать сюда. Это разрешённый dev-only UI-инкремент, а не закрытие всей 286.

## Улучшение: пользовательское название интереса (2026-10-24)

- Поле **«Название интереса»** в общем Vue-диалоге создания/редактирования `PlayIntent`, необязательное (до 80 символов), например «Игры зимой» или «Стритбол по выходным».
- Значение хранится в `play_intents.name` (nullable) и возвращается через приватный API; имя не влияет на matching, ранжирование, публичность или права.
- Заголовок карточки «Мои интересы»: сохранённое название, если оно есть; иначе прежний **«Интерес №{id}»**. Старые строки не изменяются миграцией.
- Пробелы по краям удаляются на сервере; пустое или состоящее только из пробелов значение превращается в `null`, откат к стандартному заголовку.
- Переименование работает через существующий `PUT` и сохраняет ID интереса, текущие условия, owner scope и paused-status. Параметр проходит через pending auth draft без нового запроса.
- Нужны зелёные PHP-тесты и Vite, затем автоматический deploy в `dev`. Изменение не затрагивает production и задачи 287/288.

## UI-уточнение: тип площадки — только при подборе похожих (24.10.2026)

По результатам визуальной проверки `dev` выбор **«Не важно / Открытая / Крытая»** перенесён из общих условий под чекбокс **«Подбирать похожие площадки»**, непосредственно после радиуса и перед доступом. При выключенном чекбоксе настройка не показывается и сервер нормализует `venue_kind=any`. Это предотвращает случайное исключение конкретной площадки, с которой пользователь начал «Хочу здесь играть».

Для `include_similar_venues=true` тип ограничивает **только альтернативные площадки**. Исходная `venue_id` остаётся кандидатом даже если её тип не совпадает с указанным для альтернатив. Все дополнительные операции с резервами/заявками не затрагиваются. Обновлены тесты venue-first и соответствия типов. Публикация — через CI в `dev`, без изменений prod.
