## Что предложено пользователем

- Сменить CTA «Хочу играть» на «Хочу играть здесь» либо менее обязательный «Как здесь играть?». **UX-гипотеза:** главный CTA «Хочу здесь играть», ссылка «Как это работает?» — информационный путь; финальное решение за пользователем.
- В самом верху модального окна — краткое человеческое объяснение «ничего не обязывает» и «Подробнее». Раскрытая инструкция имеет независимую прокрутку и `max-height: 300px`, не растягивает общий modal за безопасный viewport.
- Для гостя под объяснением показать просьбу авторизоваться; нажатие открывает **стандартный** диалог входа/регистрации, при регистрации предвыбирается роль «Игрок» и предлагаются настройки приватности для участия в сценарии.
- Для каждого блока выбора, где это имеет смысл, предустановить **«Не важно»**: время, дни, формат, ограничения и частота — отсутствие жёсткого фильтра, а не скрытое обязательство по всем слотам.
- Время выбирать **отдельно для каждого дня/даты**, с «Не важно» внутри каждого дня; выбор «Утро/День/Вечер/Ночь» раскрывает точный диапазон в границах части суток. Несколько отдельных интервалов в один день — допустимый сценарий.
- Перенести частоту/регулярность выше выбора дат/дней; она определяет соответствующий UI. Отдельно определить, что такое «выполнено» у разового интереса.

## Контракт открытия и авторизации

1. Вход из Venue/карточки: venue preselected; форма остаётся общей с criteria-first entry.
2. Гость открывает modal, читает пояснение и может смотреть/предварительно заполнять поля. Сохранение требует входа и, если предусмотрено backend, завершённого обязательного privacy onboarding.
3. Нажатие на notice открывает **уже существующий** AuthDialog; не делать независимый второй auth stack или обход обязательной регистрации.
4. Регистрационный Wizard получает **начальное** `role=player`, которое пользователь вправе изменить. При существующем аккаунте не переписывать роли автоматически.
5. Предложить privacy preset **как явно проверяемые настройки**. Не предустанавливать согласие на публикацию персональных данных или маркетинговые рассылки и не обойти обязательные юридические шаги. Для matching по умолчанию использовать обезличенное агрегирование.
6. Пока происходит login → registration → privacy completion, draft `PlayIntent` должен сохраняться безопасно (серверная сессия или краткоживущий opaque token). После реального подтверждения session/auth обновить данные modal и вернуть выбор, не сохранять намерение автоматически и не терять focus.
7. Доступность управления временным draft и правила допуска незавершённого аккаунта — вопрос отдельного implementation review.

## Предлагаемый сценарий ввода

Сверху вниз:
1. Заголовок «Хочу здесь играть» / площадка.
2. Свернутое пояснение + «Подробнее», прокручиваемый раскрытый текст ≤300 px.
3. Гостю — notice входа; авторизованному — спокойное пояснение настройки.
4. **«Как часто хочешь играть?»**: `Не важно` (по умолчанию; любые подходящие случаи), `Разово` (хочу одну игру), `Регулярно` (повторяющийся интерес).
5. Контекстный календарный выбор (даты или дни недели), возможность `Не важно` и уточнить.
6. Для каждого выбранного дня/даты — `Не важно` для времени либо кнопки частей суток; при выборе части появляется диапазон, который можно сузить. В нужных сценариях — несколько интервалов в одном дне.
7. Формат игры: `Не важно` по умолчанию, либо 1×1 ... 5×5 (множественный выбор).
8. Отключённая по умолчанию/согласованная отдельно опция `Подбирать похожие`, раскрывающая центр, радиус, hard/soft характеристики, допустимый временной сдвиг; самостоятельный criteria-first flow стартует с открытой географией.
9. Предпросмотр охвата предпочтений и отдельные переключатели сервисных уведомлений / разрешённых предложений площадок, затем save (при госте — auth gate).

`Не важно` — единичная взаимоисключающая опция в каждой группе; изменение конкретного параметра автоматически отключает его, а сброс всех значений возвращает `Не важно`. Сохранение слишком широкого интереса допускается после информирования о низкой точности совпадений и контролируемой частоте уведомлений.

## Разово, регулярно, не важно

**Предложение к согласованию:** три варианта *потребности в играх*, не одно поле `is_recurring`:
- **Не важно (по умолчанию)**: готов рассматривать разовые игры и потенциальные регулярные группы, но **не** даёт автоматического согласия участвовать в серии. Интерес остаётся активным до паузы/отмены/TTL.
- **Разово**: хочу найти одну игру на выбранную дату, диапазон дат или «в ближайшие N дней». Ни «нашёл совпадение», ни «проголосовал», ни «создан Event» не означают «выполнено». В промежуточном состоянии «Ожидает игру» возможен возврат в поиск при отмене.
- **Регулярно**: предпочитаю повторяющиеся недельные окна, например Вт 19–22, Чт 18–21; участие в одном мероприятии не завершает намерение.

Предлагаемые состояния интереса: `active`, `paused`, `completed`, `expired`, `cancelled`, с отдельной связью с активным кандидатом/согласованием/мероприятием, чтобы матчинг не превращал статус в псевдо-EVENT.

Для разового `completed` только после **состоявшейся игры и подтверждённого факта участия**, либо явного действия пользователя «Уже сыграл / Завершить поиск» с отличием ручного закрытия от проверенного факта. `Event.completed` само по себе не доказывает присутствие каждого желающего. При недоступности доказуемой явки — предложить пользователю подтверждение; не отмечать автоматически выполненным при первом совпадении. Когда поиск разовой игры ограничен датами/TTL, отсутствие результата → `expired`, не `completed`.

При регулярном поиске важно не создавать повторные мероприятия или приглашения на одно и то же время; уже принятая игра учитывается при следующих рекомендациях.

## Модель времени и валидация

**Предлагаемые рамки суток, нуждаются в UX-подтверждении:**
- Утро: 06:00–12:00.
- День: 12:00–18:00.
- Вечер: 18:00–22:00.
- Ночь: 22:00–06:00 следующего дня.

Ночная пятница означает **Пт 22:00 → Сб 06:00**, явно отражать дату перехода. В PostgreSQL нормализовать временные отрезки с timezone/date, не терять принадлежность к выбранному дню, корректно обрабатывать DST. Точные времена в UI с шагом 30 мин как начальное предположение, но пользователь может задать несколько интервалов; допустимость игры определяется полным пересечением окон с требуемой длительностью, а не одним совпавшим моментом.

`Не важно` для выбранного дня означает весь день доступен **для подбора**, не гарантированное присутствие/согласие играть 24 часа. При `Не важно` для дней неделя считается открытой для рекомендаций; как часто уведомлять — отдельный контроллер предпочтений, а не подразумеваемая бесконечная рассылка.

## Нужно подтвердить

1. Точная надпись CTA: «Хочу здесь играть» или «Как здесь поиграть?» (разделить информационный и action flow?).
2. Будет ли дефолт `Не важно` для частоты, и нужен ли явный краткий TTL (например, 30 дней).
3. Разово: даты из календаря, «в ближайшие 7/14/30 дней» или оба режима; какая дата автоматически закрывает истёкший поиск.
4. Рамки частей суток, возможность их комбинирования, шаг диапазонов и поддержка нескольких интервалов для одного дня.
5. Нужно ли требовать role=player и подтверждённый аккаунт до сохранения; какие privacy-настройки нужны как минимальные для безопасного matching без публичности профиля.
6. Адаптивная компоновка модального окна и точка входа на **ещё не спроектированной** новой Venue page. Отдельная визуальная приёмка по UI-kit обязательна.

Никаких файлов Vue/Blade/CSS, backend-обработчиков, миграций или действующих настроек этим документом не изменяется.

## Проект UX V2 — календарь и независимые окна доступности (на обсуждении)

**Не считается принятой спецификацией реализации.** Направление для следующей визуальной приёмки:

### Порядок полей модального окна

1. Title «Хочу здесь играть»; свёрнутая вводная инструкция + «Подробнее», раскрытая часть с `max-height:300px; overflow-y:auto`.
2. Гостю — уведомление авторизации (показываем и редактируем черновик до входа, сохранение после стандартного AuthDialog/Wizard и обязательного privacy setup).
3. Первый управляющий вопрос «Как часто?» — `Любые подходящие игры` (default, семантика «Не важно»), `Один раз`, `Регулярно`. Смена режима **сохраняет отдельные черновики** расписания до сохранения, не конвертирует недельные окна в календарные молча.
4. При разовом поиске: `В ближайшие N дней` (7/14/30) либо `Конкретные даты` (одна или несколько), допускается фильтр по дням недели для ближайшего периода.
5. При гибком и регулярном поиске: «Дни не важны» (default) либо выбор дней Пн–Вс. Если дни не ограничены — единая строка «Любой день» и возможность задать общее время (например, вечера в любые дни). При ограниченных днях — отдельная строка на каждый выбранный день.
6. Каждая строка дня/даты: дефолт `Время не важно`; `Утро` (06–12), `День` (12–18), `Вечер` (18–22), `Ночь` (22–06 +1 день). После выбора части суток — начало и конец с шагом 30 минут, зажатыми в границах выбранной части. «Добавить интервал» создаёт дополнительное окно того же дня, но не дублирует «Время не важно».
7. Формат — `Не важно` по умолчанию либо multiple-choice 1×1…5×5; другие условия и «Подбирать похожие» — прогрессивно.
8. Сводка «Например: Вторник 19–21, четверг 18–22; 3×3 или 5×5», редактирование до подтверждения, явный Save без обязанности играть/платить.

### Важные разграничения

- **Окно доступности — не длительность игры.** «18:00–22:00» означает, что игра достаточной продолжительности может расположиться внутри окна. Длительность игры задаётся отдельно (например, 60/90/120 минут или «не важно»), иначе matching ошибочно считает 4 часа обязательной длительностью.
- `День/время не важны` — фильтр отсутствует; **не** согласие явиться в любую минуту и не основание для уведомлений без лимитов. При последующем сборе требуется отдельное подтверждение.
- Ночной диапазон `Пт 22:00 → Сб 06:00` принадлежит выбранной пятнице (start-day semantics). Дублирующиеся/пересекающиеся интервалы объединяются для matching, не удваивая пользователя.
- «Ближайшие 14 дней» для разового интереса — **срок поиска**, не автоматическое подтверждение любой предложенной игры и не статус `completed`.
- Поиск одной игры после подтверждения участия временно приостанавливает новые похожие приглашения как `pending_event`, при отмене возвращается к поиску в действующем горизонте; `completed` только после доказуемого участия или явного ручного закрытия (различать причины).
- Тексты `Любые подходящие игры` / `Не важно` и названия полей — UX-гипотеза на отдельное согласование. Не менять API/модель до утверждения.

### Edge cases для предстоящих макетов и тестов

Пустая дата при «Конкретные даты», прошедшая дата, добавление нескольких дат, изменение режима без потери черновика, «Любой день + вечером», разные интервалы Вт/Чт, два окна в одном дне, ночь через дату, DST, обратное время (end<=start), пересечение ночного окна с следующим днём, окно меньше минимальной длительности игры, несовместимый формат, редактирование до/после входа, mobile scrolling и nested auth.

## UX-review V3 — соответствие действующему UI-kit (2026-10-24)

Пользователь **в целом одобрил структуру и функциональную логику** интерактивного UX-макета V2. Перед внедрением требуется визуальная полировка в строгом соответствии с действующей дизайн-системой. Речь **не** об одобрении реализации в приложении.

**Принято к проектированию:**
- Основной приоритет и стартовый вариант интерфейса — **светлая тема**; тёмная полностью поддерживается без отдельной предметной вёрстки. Цвета и компоненты должны происходить из текущей темы/токенов DesignTheme, а не из вручную собранного дубля палитры.
- Фокус не должен окрашивать/выделять текст `label`; видимое состояние фокуса требуется **только интерактивному полю или управляющему элементу**, согласно фактически используемому UI-kit. Программный focus заголовка модалки не рисует декоративную рамку.
- Стандартный `select-control`: нативный `select` с `appearance:none` и **штатным SVG chevron-down** из принятого Tabler-стиля справа, размер около 20 px, `pointer-events:none`, padding справа 48 px; системный fallback в forced-colors.
- Чекбоксы, кнопка закрытия модалки, радиокнопки, обычные кнопки, поля/placeholder, датапикеры, индикация состояния, размеры target и контраст должны повторять **реальные** компоненты принятого гайдлайна и текущий UI Kit. Не делать отдельный «почти похожий» комплект для `PlayIntent`.
- Закрытие модалки: общий `Modal 1.1` top-layer `showModal()`, header/body/footer, иконка X в общей кнопке 44×44 с обычной границей/радиусом, не текстовый крупный ×. Body единственная основная прокрутка, footer закреплён, высота не более 90dvh.
- Отдельно тестировать desktop 1440/1024, mobile 390/360/320, светлую/тёмную тему, keyboard Tab/focus, hover, select, checkbox, длинную инструкцию max-height 300px и auth handoff.
- Локальный standalone-прототип V3 — вспомогательная визуальная реплика, **не источник готовых CSS**. При реальной разработке использовать компоненты и `DesignThemeCss` реального приложения.

**Проверка standalone-прототипа V3:** HTML/JS работает в Chromium при рендере через `set_content` (из-за блокировки навигации `file://`), desktop 1400×900 и mobile 390×844; JS errors: 0; `select` `appearance:none`, стрелка wrapper на месте, фокус на самом поле и без выделения текстового label, modal ≤90dvh; встроенный srcdoc в оболочке загружается. **Это не проверка реальной темы на dev.**

Бизнес-логика V2 (гибкий/разовый/регулярный интерес, независимые окна времени, `Не важно`, поиск похожих) не меняется. Любые расхождения в финальном visual review нужно устранять до реализации первого этапа.

## UX-review V4 — автоматическое принятие интереса после авторизации (согласовано 2026-10-24)

Пользователь **согласовал** упрощённый happy path: если гость уже выбрал параметры «Хочу здесь играть» и перешёл по **явному действию сохранения** в стандартный вход/регистрацию, после завершения успешной авторизации и обязательного privacy-onboarding **не требовать второго нажатия «Сохранить»**. Выполнить одноразовое безопасное сохранение ранее введённого интереса и **сразу показать экран успеха «Настройки приняты»** с краткой сводкой, возможностью перейти к «Мои интересы» или изменить параметры.

Контракт для разработки:
- До открытия авторизации сохранить черновик и идентификатор намерения продолжить submit в защищённом краткоживущем state; не хранить пароль/персональные согласия в таком черновике.
- Отдельный информационный переход к авторизации (без начатого save intent) сам по себе **не** должен создавать интерес без действия пользователя.
- После login/signup + обязательные шаги privacy завершены: восстановить draft, перепроверить актуальность venue, права, параметры и данные на сервере, затем **идемпотентно** создать/обновить только запрошенный PlayIntent (token/request key — single-use, защита от двойных callback/refresh). Авторизацией не подменять согласия на маркетинг/публичность.
- При ошибке валидации или отсутствии площадки восстановить заполненную форму с ясной ошибкой; при неуспешном/отменённом входе ничего не сохранять. Если пользователь отменил первоначальный flow, исключить автоматическое создание.
- Для уже авторизованного пользователя обычная кнопка «Сохранить интерес» ведёт напрямую к тому же success screen после положительного ответа backend.
- Success screen появляется **только после серверного подтверждения записи**; в демо имитируется без реального сохранения. Не выдавать «Настройки приняты» по одному факту login, если операция save не состоялась.
- Закреплённая кнопка после успеха: «Готово» / «К моим интересам»; отдельно «Изменить настройки».

Следующий этап UX: полноценная светлая страница площадки с CTA, расписанием/доступностью, игровой активностью, галереей и характеристиками — как совместный дизайн-контекст задачи 286 и MSKBA App 006; реализация страницы ещё требует собственного scope review.

## UX-review V5 — время начала и динамические удобства (2026-10-24)

Новые уточнения пользователя к принятой функциональной логике (только UX/документация, реализация не запущена):

- Подпись над выбором части суток и временного диапазона **«Подходящее время» заменена на «Время начала»**. Требуется проверка смысловой точности на визуальной приёмке: выбранные значения `с/до` образуют допустимое временное окно для размещения игры; продолжительность самой игры задаётся отдельно.
- Удалить частную настройку **«Парковка желательна»**. В раскрытии «Подбирать похожие площадки» предусмотреть **«Удобства площадки»** из действующего каталога `Amenity`, а не из хардкодного набора.
- У каждого удобства три пользовательских состояния: **не выбрано** (по умолчанию, никак не фильтрует), **выбрано — желательно**, **выбрано — обязательно**. В интерфейсе это checkbox включения и отдельный `select` «Желательно / Обязательно», который появляется только после выбора; «Желательно» — начальный режим *выбранного* удобства. Снятие чекбокса снимает требование полностью.
- **Желательно** — soft criterion, влияющий на ranking, но не исключающий место. **Обязательно** — hard filter; при отсутствии или неподтверждённости удобства вариант не считать соответствующим и не включать в строгие совпадения. Отображать причину исключения/альтернативы при необходимости.
- Серверный источник: `amenities` (активные, неудалённые, сортировка `sort_order`, `name`) + `venue_amenities` (наличие у Venue). Использовать `Amenity.id/alias/name/icon/applies_to`, `applies_to=all/indoor/outdoor` и тип целевых площадок; не копировать набор «Парковка, Душевая…» в отдельный предметный enum.
- По состоянию текущего `dev` миграция `2026_08_02_220000_add_venue_facilities.php` содержит **18 базовых записей** с группами «Общие / для залов / для уличных». В standalone-прототипе эти 18 удобств — пример справочника; в приложении список должен быть динамическим и включать новые активные пункты без правки фронтенда.
- Сохранение формы: минимально `[{amenity_id, priority: preferred|required}]` у конкретного `PlayIntent` (предлагаемый DTO, не утверждённая БД). Валидировать id, is_active, применимость и дедупликацию на сервере; при смене каталога корректно показывать деактивированное условие для старых интересов.
- На мобильных карточках не показывать два крупных переключателя рядом с каждым из 18 удобств: компактный checkbox + небольшой стандартный `select-control`, группы свёрнуты или доступны в прокручиваемом теле Modal 1.1. Стрелка, рамка, фокус и checkbox — общие UI-kit.
- Не смешивать **удобства** со свойствами бронирования, стоимостью, временем и георадиусом: те остаются независимыми условиями поиска.
