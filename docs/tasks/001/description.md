# 001 - Прочитать всю документацию и определить ее актуальность - соответствие кодовой базе проекта

## Оригинальное описание

Прочитать всю документацию и определить ее актуальность - соответствие кодовой базе проекта.

## Подробное описание

Нужно провести аудит всей существующей документации проекта и определить, насколько она соответствует текущей кодовой базе.

В область проверки входят:

- `AGENTS.md`;
- `docs/project.md` и раскрытия в `docs/project`;
- `docs/specification.md` и раскрытия в `docs/specification`;
- `docs/tasks.md`;
- модульные README в `app/Modules`;
- внешний backlog `../backlog/todo.md` как контекст планирования.

Кодовая база для сверки:

- маршруты `routes/web.php`;
- доменные модули `app/Modules/Identity`, `app/Modules/Venue`, `app/Modules/Contract`;
- миграции `database/migrations`;
- сидеры `database/seeders`;
- тема и представления в `resources/themes`;
- Docker/Makefile/npm/composer конфигурация.

Предварительно обнаруженные зоны, которые нужно проверить и зафиксировать в итогах:

- документация описывает Docker-стек `phpfpm`, `nginx`, `db`, `redis` и dev override, но текущий `docker-compose.yml` содержит только `postgres` и `adminer`, а `docker-compose.dev.yml` отсутствует;
- в документации профиля указаны модель `UserProfile`, таблица `user_profiles` и flow `RegisterContactFirstHandler`, тогда как в коде используются модель `Profile`, таблица `profiles` и `RegisterUserHandler`/`CreateUserAccountHandler`;
- документация площадок упоминает `VenueFeatureEnum`, JSON-поле `features`, поле `created_by` и отсутствие relation к создателю, тогда как в коде нет features, используется `created_by_user_id` и есть relation `creator()`;
- в коде есть модуль `Contract`, contract routes в личном кабинете и связь договоров с доступом к площадкам, но верхняя проектная/техническая документация почти не описывает эту предметную область;
- в документации указана основная тема `resources/themes/mskba_dark`, но в коде сейчас путаница имен: активная по умолчанию `mskba_dark` является минимальной/blank-темой, а фактически проработанная основная тема лежит в `mskba_light`;
- команды в `docs/specification.md` и `docs/specification/docker-environment.md` частично не совпадают с текущим `Makefile`.
- по замечанию пользователя от 2026-05-31 добавлены отдельные корректировки: правило агента о проверке рабочей директории перед правками и переход от транслитных alias файлов документации к английским alias.

## Принцип актуализации

Документация была написана по другой, более продвинутой версии проекта. При актуализации нужно не подгонять код под старые документы, а привести документы к факту текущей кодовой базы.

Основное правило: если возможность, модуль, сервис, Docker-схема, бизнес-процесс или пользовательский сценарий не подтверждается текущим кодом, он не должен описываться как реализованный. Такие элементы нужно удалить из основной документации или явно перенести в backlog/будущие задачи.

## Фактическая картина текущей кодовой базы

### Приложение и окружение

- Laravel-приложение на PHP 8.3+.
- Frontend собирается через Vite/npm.
- `docker-compose.yml` сейчас содержит только `postgres` и `adminer`.
- `docker-compose.dev.yml` отсутствует.
- Сервисов `phpfpm`, `nginx`, `redis`, `mailpit`, `node` в Docker-схеме сейчас нет.
- `Makefile` работает через локальные `php`, `composer`, `npm`, `docker compose`; команды `make prod-up`, `make prod-down`, `make config`, `make dev-config`, `make clear`, `make artisan`, `make npm` отсутствуют.

### Presentation/theme

- Активная тема по умолчанию: `mskba_dark` из `config/themes.php`, но это не соответствует фактической роли директорий тем.
- Текущая `mskba_light` фактически является основной проработанной темой: в ней лежит большая часть страниц account, auth, venues, modal partials, меню и breadcrumbs.
- Текущая `mskba_dark` является минимальной темой-заготовкой; целевое имя для нее - `blank`.
- Целевое состояние: переименовать текущую `mskba_light` в `mskba_dark`, переименовать текущую `mskba_dark` в `blank`, а активной темой по умолчанию оставить/сделать новый `mskba_dark`.
- `ThemeResolver` выбирает тему из `APP_THEME`, подключает namespace `theme` и возвращает fallback `theme::pages.system.view_not_found`, если страница не найдена.
- В текущей директории `mskba_dark` сейчас нет страниц `auth/login`, `auth/register`, `account/*`, `venues/*` и fallback `pages/system/view_not_found`; это подтверждает, что ее нельзя считать основной темой без переименования/перенастройки.
- Страница `dashboard` отсутствует и в текущей `mskba_dark`, и в текущей `mskba_light`, хотя маршрут `/dashboard` есть.
- Breadcrumbs реально реализованы через `App\Presentation\Breadcrumbs\BreadcrumbsResolver` и partial `theme::partials.breadcrumbs`, но route defaults с `breadcrumb` сейчас есть только у маршрута `venues`.

### Identity

- `User` хранит `username`, `password`, `password_updated_at`, `is_temporary_password`, `registration_channel`, `system_role`, `status`.
- Регистрация реализована через `RegisterUserHandler`, который вызывает `CreateUserAccountHandler`.
- При создании пользователя сразу создается `Profile`.
- Текущая модель профиля называется `Profile`, таблица называется `profiles`.
- В коде нет модели `UserProfile`, таблицы `user_profiles` и flow `RegisterContactFirstHandler`.
- Вход/выход реализованы через `AuthHandler`.
- В `routes/web.php` есть маршруты `auth.restore`, `auth.confirm`, `auth.resolve-login`, `auth.verify`, но соответствующих методов в `AuthController` сейчас нет. Документация не должна описывать эти сценарии как рабочие до исправления кода.

### Роли

- Системные роли есть в `UserSystemRoleEnum`: `superadmin`, `admin`, `user`, `moderator`, `editor`, `system`.
- Роли участия есть в `UserParticipationRoleEnum`: `player`, `coach`, `referee`, `statistician`, `media`, `venue_related`.
- Роли участия хранятся в `user_participation_roles` с `status`, `assigned_at`, `expires_at`, `assigned_by`, `assigner`, `comment`.
- Для роли `venue_related` и подтвержденного пользователя через Gate `add_venue` разрешается добавление площадки.

### Venues

- Модуль `Venue` существует и содержит публичный список/просмотр площадок, личный список площадок, создание площадки из личного кабинета и заглушки редактирования.
- Таблица `venues` содержит `created_by_user_id`, `name`, `alias`, `type`, `status`, `description`, timestamps.
- `Venue` имеет relation `creator()` к `User` по `created_by_user_id`.
- `VenueFeatureEnum`, JSON-поля `features`, текстового адреса и нормализованных `Address`/`Metro` сейчас нет.
- Публично видимы только площадки со статусом `confirmed`; дополнительно пользователь может видеть площадки по договорному доступу.

### Contracts

- Модуль `Contract` есть в коде, но не описан в верхней документации.
- Контракты сейчас используются как механизм доступа пользователя к площадкам.
- Продуктово `Contract` нужно рассматривать шире: как будущий универсальный механизм договоренностей и прав доступа между разными сущностями, как частными, так и множественными. Например, команда может дать другой команде доступ к видимости своих игроков.
- Таблицы: `contracts`, `contract_parties`, `venue_contracts`, `venue_contract_permissions`.
- `Contract` связан с участниками через `ContractParty`.
- `VenueContract` связывает договор с площадкой.
- `VenueContractPermission` хранит разрешения `view`, `edit`, `edit.schedule`.
- В личном кабинете есть страницы списка и просмотра контрактов.
- В таблице `contracts` есть `assigned_by`, но в `Contract` пока нет relation/accessor `assignedByUser`; документация не должна описывать этот слой как готовый без отдельной проверки кода.
