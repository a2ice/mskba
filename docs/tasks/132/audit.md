# Аудит текущего состояния flow аренды площадки

## Резюме

В проекте уже есть качественный технический фундамент: единая проверка доступности, корректная геометрия конфликтов `whole/half`, блокировка площадки перед бронированием, типизированные coordination-опросы, договорные membership и надёжная инфраструктура уведомлений. Однако текущая `VenueBooking` является технической записью, создаваемой вместе с `Event`, а не самостоятельным коммерческим агрегатом. Поэтому расширять её добавлением нескольких полей без изменения границ модели рискованно.

Главный разрыв: сейчас flow фактически выглядит как `Event → VenueBooking`, а требуется `Coordination → VenueBooking → Event`.

## Что уже можно переиспользовать

### Проверка доступности

`VenueEventAvailability` уже:

- проверяет подтверждённость и рабочее состояние площадки;
- нормализует интервал;
- учитывает `WHOLE`, `HALF_A`, `HALF_B`;
- считает полную площадку конфликтующей с любой половиной;
- позволяет одновременно занять разные половины;
- вызывается после блокировки строки площадки в основных write-flow.

Это следует сохранить как доменный компонент расчёта конфликтов, но перевести на новые occupying-состояния и дополнить проверкой политики.

### Coordination

Подсистема уже поддерживает:

- сессии согласования и роли организатора;
- типизированные опросы `TEXT`, `DATE`, `TIME`, `DATETIME`, `TIME_INTERVAL`, `VENUE`, `PARTICIPATION`;
- порядок шагов и `depends_on_poll_id`;
- публикацию в нескольких Telegram-чатах;
- простые Telegram-опросы и расширенное голосование через Mini App;
- дедлайны, закрытие опросов, проекции результатов;
- идемпотентный переход coordination-сессии в мероприятие.

Это естественная точка V1 для выбора площадки/даты/интервала. Нельзя ломать простой Telegram flow: коммерческие действия выполняются по ссылке в web/Mini App, а обычные голоса остаются обычными callback/опросами.

### Договорные права

`ContractMembership`, `ContractPermission`, `VenueMembershipAccess` и уровни `OWNER/ADMIN/MANAGER/STAFF/AGENT` уже дают расширяемую модель прав. Сейчас права площадки ограничены `VIEW`, `EDIT`, `EDIT_SCHEDULE`, `REMOVE`. Модель подходит для добавления коммерческих capabilities без появления второй параллельной ACL.

### Уведомления и realtime

`CreateUserNotificationHandler`, durable notifications, broadcast events, Reverb и Telegram jobs можно переиспользовать. Для аренды требуется строгая публикация событий после commit и отдельная матрица получателей.

### Аудит

`Auditable` фиксирует изменения моделей и request metadata. Он полезен как технический аудит, но недостаточен для доменной истории брони: консольные изменения по умолчанию игнорируются, а одно изменение модели не объясняет бизнес-переход. Нужен отдельный append-only timeline.

## Несоответствия целевой модели

### `VenueBooking` не самостоятельна

Сейчас бронь требует `event_id`, причём связь уникальна и обязательна. Она создаётся внутри `CreateEventHandler` после создания мероприятия. Нельзя создать заявку, hold или переговоры до появления события.

Требуется:

- разрешить бронь без `Event`;
- хранить организатора/заказчика непосредственно в брони;
- оставить nullable unique-связь с событием для правила one booking → zero/one event;
- создавать событие только после подтверждения брони.

### Недостаточный lifecycle

Текущие статусы: `PENDING`, `CONFIRMED`, `CANCELLED`. Причём `PENDING` уже занимает слот. Это противоречит требованиям:

- `REQUESTED` не должна блокировать слот;
- `HELD` должна блокировать слот до `hold_expires_at`;
- `CONFIRMED` блокирует окончательно;
- нужны `REJECTED`, `EXPIRED` и явная семантика отмены.

Нельзя просто переименовать `PENDING`: существующие платные мероприятия рассчитывают на её блокирующее поведение. Нужна совместимая миграция и временное dual-read/явное отображение legacy-записей.

### Нет коммерческой политики

Цена сейчас выводится из признака бесплатности площадки, а не из версионированного предложения. Нет:

- включения аренды;
- auto-hold;
- длительности hold/payment window;
- разрешённых зон;
- правил цены и комиссии;
- методов оплаты;
- версии условий.

Эти данные нельзя читать «живьём» после принятия предложения: изменение владельцем цены не должно менять уже выданный quote.

### Нет переговоров и платёжного состояния

Не представлены counter-offer на время hold, продление окна оплаты, подтверждение внешней оплаты, отказ/просрочка и история сообщений. Добавление заметок в audit trail не подходит: разговор изменяем по правилам модерации/видимости, а аудит неизменяем.

### Создатель площадки смешан с владельцем

Текущий bootstrap-доступ создателя удобен для редактирования неподтверждённой карточки и должен сохраниться. Но коммерческое управление должно появляться только через активное contract membership после модерации ownership claim. Иначе пользователь, добавивший публичную площадку, сможет назначать цену и подтверждать оплату.

### Attendance можно запустить слишком рано

Текущий coordination может строить опрос участия от выбранных времени и площадки, не имея hold/confirmed booking. Это создаёт ложные обещания участникам. В V2 eligibility опроса должна проверять бронь и её актуальный occupying-статус.

## Замеченные технические риски

### Скоуп следующей брони

Расчёт ближайшей следующей брони требует учитывать совместимость scope. Бронь `HALF_B` не должна сокращать доступный интервал `HALF_A`. Этот сценарий нужно зафиксировать отдельным regression test до расширения модели.

### Порядок блокировок

Существующий event flow в основном блокирует площадку до проверки броней. Coordination transition сначала блокирует coordination session, затем вызывает downstream flow с блокировкой площадки. Если появится обратный путь `venue → session`, возможен deadlock.

Правило:

1. coordination transition не держит session-lock во время долгих внешних действий;
2. для booking mutation канонический порядок — venue, конфликтующие bookings, target booking, child rows;
3. внешние уведомления и payment API — только после commit;
4. повторные команды завершаются по idempotency key, а не повторяют side effects.

### Фоновое истечение

Laravel scheduler `withoutOverlapping` защищает один процесс, но не является достаточной гарантией при нескольких узлах или повторном выполнении job. Expiry должен выполняться условным update/lock с проверкой текущего состояния и дедлайна. Нужны `onOneServer` при общей cache-lock инфраструктуре, chunking и повторяемые jobs.

### События до commit

Уведомление, отправленное до фиксации транзакции, может сообщить о hold, который откатился. Все booking domain events должны попадать в after-commit dispatcher или transactional outbox.

### Проекции как источник записи

Realtime/UI-проекции нельзя использовать для изменения статуса. Команды проходят application handlers с повторной авторизацией и проверкой expected version. Иначе два клиента смогут одновременно подтвердить или продлить бронь.

## Что не следует делать

- не превращать `Event` в контейнер платёжных и переговорных полей;
- не добавлять business rules в Blade/JS;
- не считать `created_by` доказательством владения площадкой;
- не перезаписывать quote при изменении политики;
- не вызывать Telegram/payment API внутри DB transaction;
- не удалять текущие типизированные и простые Telegram-опросы;
- не вводить отдельную ACL только для аренды;
- не использовать generic audit log как чат;
- не позволять confirmed booking менять интервал обычным update.

## Рекомендованный путь внедрения

1. Закрепить regression-тестами текущую доступность и event flow.
2. Ввести права и ownership claim без включения аренды.
3. Ввести policy/version и новый booking aggregate за feature flag.
4. Перевести новые rental-flow на самостоятельную бронь, сохранив legacy event creation.
5. Подключить coordination V1 и scheduler expiry.
6. Добавить переговоры и ручную внешнюю оплату.
7. Создавать event из confirmed booking.
8. После наблюдения и backfill убрать legacy-семантику `PENDING`.
9. Отдельно включить attendance V2, contributions и реального payment provider.
