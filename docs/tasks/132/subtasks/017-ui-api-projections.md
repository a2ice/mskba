# 017 — UI, API и read projections

## Цель

Собрать единый понятный интерфейс арендатора и владельца поверх стабильных серверных команд, не дублируя бизнес-правила в Blade/JavaScript и не создавая N+1 на списках бронирований и доступности.

## Статус

Выполнена в `feature/115`.

Read models реализованы индексированными SQL query handlers без отдельной projection-таблицы: это сохраняет read-your-write и исключает drift/reconcile до появления измеренной необходимости в денормализации. Availability не раскрывает заявителя и цену, requester/owner inbox ограничены пагинацией и eager loading, timeline версионирован. Допустимые и главное следующее действие рассчитывает `VenueBookingActionState`; stale-команда возвращает актуальный `current_state`. `BookingProjectionUpdated` служит только сигналом инвалидации после commit.

## Доменные изменения

- Новых правил не добавлять: UI использует состояния и разрешённые действия, рассчитанные application/domain слоями.
- Ввести read models для availability площадки, карточки брони, входящих заявок владельца и timeline.
- Каждая проекция содержит версию aggregate для защиты от устаревших действий.

## Миграции

- При необходимости добавить денормализованные projection-таблицы только после измерения запросов; сначала использовать индексированные SQL read queries.
- Индексы проектировать по реальным фильтрам: owner/contract, status, venue, start/end, updated_at.
- Схема проекций должна перестраиваться из источника истины.

## Handlers и сервисы

- Query handlers: `GetVenueAvailability`, `GetBookingDetails`, `ListOwnerBookingInbox`, `GetBookingTimeline`.
- Command endpoints вызывают handlers из 005–013 и возвращают актуальную версию/допустимые действия.
- Ответ stale version — 409 с новым состоянием, а не молчаливое перетирание.
- Исключить lazy loading в циклах и ограничить размер страниц.

## Права

- Проекция фильтрует поля и действия согласно стороне и commercial permissions.
- Публичная доступность не раскрывает персональные данные заявителя или финансовые детали.
- Любой endpoint повторно авторизуется на сервере независимо от скрытых кнопок.

## UI/API

- Экран площадки: политика, зоны, календарь доступности и начало заявки.
- Кабинет заявителя: coordination/request/hold/payment/confirmed с одним главным следующим действием.
- Кабинет владельца: компактный inbox, фильтры и детальная панель решения.
- Единые компоненты status badge, timeline, quote, venue scope и action bar.
- Mobile-first, keyboard navigation, focus management, aria-live для смены статуса и явные состояния loading/empty/error.

## События и jobs

- Read projections обновляются синхронно там, где нужна read-your-write семантика, либо асинхронно с отображением версии и ожидаемого состояния.
- `BookingProjectionUpdated` используется для realtime-инвалидации, а не передачи доверенных бизнес-решений клиенту.
- Периодическая reconcile-job сверяет проекции с aggregate.

## Тесты

- Contract-тесты API, 403/404/409 и сериализации разрешённых действий.
- Query-count тесты ключевых списков и тесты пагинации.
- UI smoke для арендатора, владельца, mobile и keyboard-only.
- Тесты stale command, reconnect и повторной отправки формы.
- Проверка отсутствия чувствительных данных в публичном JSON/HTML.

## Обратная совместимость

- Новые экраны включаются feature flags; старые формы остаются до завершения rollout.
- API версионируется либо расширяется обратно совместимыми полями.
- Существующие ссылки на площадки и события сохраняют маршруты.

## Критерии приёмки

- Клиент не вычисляет допустимость доменных переходов самостоятельно.
- Списки не создают N+1 и имеют ограниченную пагинацию.
- Устаревшее действие не перетирает новое состояние.
- Основные сценарии доступны на мобильном устройстве и с клавиатуры.
