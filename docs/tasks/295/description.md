# 295 — «Участие → Мои игры»: заявки и участия в играх и игровых тренировках

## Проблема и цель
Сейчас route `account.my-games` (`routes/web.php`) отдаёт пустой `account.role-section`. Заявка/участие в `game_training` после действия на странице мероприятия не отображается в кабинете. Сделать работающий список **«Мои игры»**, объединяющий `EventTypeEnum::GAME` и `EventTypeEnum::GAME_TRAINING`, но не смешивающий их доменные правила.

## Бизнес-семантика
- Источник карточки — `Event`; `game_training` остаётся отдельным типом `Event`, у которого могут быть **внутренние мини-игры**, а `game` может быть самостоятельной или связанной с турниром. Не превращать игровую тренировку в `Game` и не приписывать ей команды, турнирные статусы или механизм standalone recruitment.
- Показывать **отправленную заявку до решения**, подтверждённое участие, приглашение, ожидание/«Думаю», отказ/отзыв (в соответствующей вкладке истории) и организаторскую роль. Не ждать подтверждения, чтобы запись впервые появилась в разделе.
- Для `game_training`/объявленной тренировки использовать существующие `EventParticipant` и `EventParticipantStatusEnum` (`confirmed/tentative/left`) с действующей версией подтверждения. Для standalone `game` учитывать `GameAdmission`/recruitment и/или `EventParticipant` согласно фактическому источнику заявки; агрегировать **по одному мероприятию**, не показывать отдельные карточки каждого embedded Game.
- `training` обычного типа не включать в «Мои игры» (его место — «Мои тренировки»); турнирные игры показывать с отметкой турнира и ссылкой, не изменяя игровые заявки команд.
- Данные принадлежат авторизованному **каноническому** пользователю. Чужие заявки по ID и профили участников из чужих заявок недоступны; все разрешённые действия исполняются существующими application handlers.

## UI и API
- Заменить пустой route-заглушку реальным controller/query + Blade/DTO в `mskba_app`, использовать существующие компоненты карточек и локализацию.
- Разделы: «Заявки/Приглашения», «Участвую», «История»; поля: тип, дата/часовой пояс, площадка, статус, организатор/турнир при наличии, переход на Event.
- Действия (отозвать/подтвердить/отказаться), если доступны по текущим бизнес-правилам, использовать существующие endpoints с CSRF и состоянием загрузки. Не изобретать новый альтернативный lifecycle.
- Предусмотреть пустое состояние с переходом к каталогу `events.index?type=games`, пагинацию и недублирование записей при нескольких идентичностях/связях.
- Отдельно проверить, что после отправки заявки на игровую тренировку и возврата в кабинет она видна без ручного действия администратора. Не обещать realtime, если для заявок ещё нет доменного события; актуальность при следующем открытии страницы обязательна.

## Приёмка и тесты
1. Заявка на будущую `game_training` появляется в «Мои игры» с корректным статусом; после подтверждения, отказа и переноса время/статус обновляются.
2. Аналогичный сценарий standalone `game` и турнира отображается без потери team/recruitment правил; `training` отсутствует.
3. Не появляются дубли от алиасов пользователя, мини-игр внутри тренировки или параллельных источников участников.
4. Нельзя получить чужие заявки, действия и персональные данные; отменённые/прошедшие — в истории, не в будущих.
5. Feature + UI/regression tests, mobile/desktop, зелёный CI и dev-e.

**Приоритет:** высокий. **Зависимости:** существующий `Event`, `EventParticipant`, `GameAdmission`. **Статус:** запланировано.
