# Task 162 — Несколько игровых залов внутри одной площадки

## Контекст

Одна физическая площадка (`Venue`) по одному адресу/location может содержать несколько самостоятельных игровых залов. Пример: один объект «Кампус» на Яхромской имеет несколько залов, которые должны отображаться и управляться как части одной площадки, а не как дублирующие `Venue`.

Ранее проект поддерживал только деление одной площадки на `WHOLE / HALF_A / HALF_B`. Половина остаётся способом использования конкретного игрового пространства и не является отдельным залом.

## Целевая модель

```text
Location
└── Venue
    └── VenueCourt
        └── WHOLE / HALF_A / HALF_B
```

`Venue` хранит общий контекст объекта: location/address, ownership, контакты, общие данные и публичную идентичность. `VenueCourt` представляет самостоятельный физический зал/корт внутри этого Venue.

## Scope

Добавить `venue_courts` и модель `VenueCourt` со следующими полями:

- `venue_id`;
- `name` — редактируемое название зала;
- `alias` — стабильный человекочитаемый route alias;
- `sort_order`;
- `is_primary` — основной зал, используемый старым URL площадки;
- `supports_halves` — физически возможно использовать две половины независимо;
- timestamps + soft delete.

Ограничения:

- alias уникален внутри одного Venue;
- у Venue всегда должен оставаться хотя бы один активный зал;
- у Venue должен быть один основной зал;
- существующие Venue backfill-ятся одним `Зал 1 / zal-1`;
- для backfill `supports_halves` наследует прежнюю физическую эвристику `hoops_count >= 2`;
- новые Venue получают основной `Зал 1` автоматически.

## Управление

В существующей внутренней навигации площадки добавить раздел `Залы`.

Владелец/пользователь с правом управления площадкой должен уметь:

- просматривать список залов;
- добавлять зал;
- менять название/alias/порядок;
- менять `supports_halves`;
- назначать основной зал;
- удалять зал, если после удаления остаётся хотя бы один.

Использовать существующую `VenueAccessResolver::canManage`, не создавать отдельный обход permissions.

## URL и дальнейшие шаги

Публичный старый URL Venue остаётся канонической точкой входа и позднее будет означать основной зал:

```text
/venues/{venue}
```

Дополнительные залы получат URL вида:

```text
/venues/{venue}/courts/{court-id}-{court-alias}
```

Публичный selector и привязка booking/event выполняются следующими отдельными задачами, чтобы не смешивать schema/admin, booking-conflict и публичный UI в одном рискованном PR.

## Out of scope

- публичная сущность сети/группы «Кампус»;
- отдельный `VenueGroup`/brand/network;
- отдельное расписание/цены на каждый зал в этой задаче;
- перенос booking conflict на court — Task 163;
- публичный selector/URL и фильтрация activity — Task 164.

## Acceptance criteria

- существующие Venue получают один основной зал без изменения публичных URL;
- новый Venue автоматически имеет один primary court;
- владелец может управлять залами через существующий account venue UI;
- посторонний пользователь получает 403;
- alias уникален только внутри Venue;
- последний зал нельзя удалить;
- удаление primary при наличии другого зала назначает replacement primary;
- тесты и CI зелёные.
