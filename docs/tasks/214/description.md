# 214 - Заложить финансовый контекст: кошельки, подбалансы и журнал транзакций

## Оригинальное описание

Заложить фундамент Finance для MSKBA: кошельки владельцев, раздельное происхождение
средств, общий пользовательский баланс, журнал транзакций, идемпотентные операции
и контекстные права управления. Реальные интеграции с эквайрингом, P2P-переводы,
вывод и расчёты с внешними поставщиками в первую итерацию не включать.

## Подробное описание

### Граница bounded context

Создаётся \`App\Modules\Finance\`. Он отвечает за:

- кошельки и материализованные остатки;
- происхождение движения средств;
- атомарное начисление и списание;
- идемпотентность финансовых команд;
- правила доступности операций по типу owner;
- проверку контекстного права распоряжаться средствами owner-а.

Finance не отвечает за:

- прайс-лист и каталог услуг;
- эквайринг и конкретный API банка;
- бронирование площадок;
- реферальную механику как таковую;
- пользовательские переводы между кошельками;
- вывод денег.

Эти контексты в будущем вызывают Finance через application API и передают
причину/ссылку на исходный бизнес-объект.

### Кошелёк

Owner: \`user|team|event|venue\`. Связь owner -> wallet проектируется как 1:N.
Первая версия создаёт только \`main\` в \`RUB\`, но уникальность задаётся
\`owner_type + owner_id + type + currency\`, поэтому модель не запирает нас в 1:1.

В кошельке материализованы два остатка:

- \`real_balance_minor\` — средства с реальным денежным основанием;
- \`bonus_balance_minor\` — внутренние бонусы/вознаграждения.

Отдельного reward-wallet нет: реферальное начисление — тип операции и причина
зачисления в bonus. `referral_reward` нельзя направить в real, а `top_up` нельзя
направить в bonus. Общая сумма для UI в будущем = real + bonus.

Все суммы хранятся целыми числами в минимальных денежных единицах (копейках).

### Ledger

\`wallet_ledger_entries\` — неизменяемый журнал движений. Каждая строка хранит:

- кошелёк;
- финансовую операцию;
- подбаланс \`real|bonus\`;
- signed delta;
- остаток соответствующего подбаланса после движения.

Текущий остаток читается из \`wallets\`, а не вычисляется полным проходом по
ledger. Обновление остатка и запись ledger выполняются в одной DB-транзакции под
\`lockForUpdate\`.

### Идемпотентность

Операция имеет \`idempotency_key\` и hash канонического payload. Повтор той же
команды с тем же ключом и payload возвращает уже завершённую операцию и не
меняет баланс. Повтор ключа с другим payload отклоняется.

### Списание

Для внутренних сервисов MSKBA политика по умолчанию:
\`bonus_then_real\`. Также фундамент поддерживает \`real_only\` и \`bonus_only\`,
чтобы правила использования средств не были зашиты в структуру кошелька.

### Owner operations и ACL

Операции пользовательских кошельков включены по умолчанию. Team/Event/Venue
поддерживаются схемой, но их операции выключены безопасными feature settings до
отдельного включения.

Добавляются атомарные contextual permissions:

- \`team.wallet.manage\`;
- \`event.wallet.manage\`;
- \`venue.wallet.manage\`.

Кошелёк команды/мероприятия/площадки принадлежит самой сущности. Пользователь
лишь выступает оператором при наличии соответствующего permission.

Новое право мероприятия не должно попасть в старый legacy-default автоматически:
default assignment сохраняет все прежние права, кроме финансового.

### Границы первой итерации

Не реализуются:

- UI баланса;
- пополнение через банк;
- вывод;
- P2P;
- внутренний расчёт с площадками/магазином;
- dynamic superadmin UI для включения owner-кошельков;
- прайс-лист.

Для Team/Event/Venue оставляется безопасный выключенный runtime guard. Будущий
superadmin-переключатель должен управлять этой policy и показывать явное
предупреждение перед активацией.

## Проверка

- Feature-тесты Finance на real/bonus, bonus-first, недостаточный баланс,
  идемпотентность и feature gate;
- полный CI PR: PHP tests + production compose validation + frontend build;
- документация и навигация обновлены.

## Результат

Фундамент Finance реализован в отдельном bounded context. Схема поддерживает
несколько кошельков на owner, материализованные real/bonus остатки и неизменяемый
ledger. Начисления и списания атомарны и идемпотентны. Внешние денежные сценарии
не смешаны с внутренним балансом и остаются отдельным будущим контуром.
