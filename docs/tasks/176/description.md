# 176 — Добавить заявки и активный набор в спортивные секции и выровнять hiring-инвариант команд

## Контекст

В Task 170 тренируемых в секцию добавляет управляющий пользователь. Публичного признака «секция принимает заявки» и пользовательского flow подачи заявки сейчас нет.

Для команд уже существуют две разные сущности смысла:

- `teams.accepts_join_requests` — команда принимает общие заявки;
- активные `team_hiring_positions` — команда явно ведёт набор на конкретные потребности.

Текущая реализация команд разрешает целевую заявку на активную вакансию независимо от `accepts_join_requests`. Это не соответствует новому продуктовому правилу: усиленный статус «идёт набор» не должен существовать при закрытом приёме заявок.

## Цель для секций

Развести два состояния:

1. `accepts_join_requests` (рабочее имя; при реализации допустимо выбрать более предметное `accepts_trainee_requests`) — секция открыта для подачи заявки.
2. `is_hiring` / `is_recruiting` — секция активно ищет новых участников и должна сильнее подсвечиваться в каталоге.

Инвариант:

`is_hiring = true` возможно только при `accepts_*_requests = true`.

### Поведение

- пользователь с подходящим подтверждённым player-профилем может подать заявку только в секцию, принимающую заявки;
- заявка не должна сразу превращаться в `SectionTraineeMembership`;
- нужен отдельный lifecycle заявки (`pending|accepted|rejected|cancelled` либо эквивалент, согласованный с существующими join-request patterns);
- принятие заявки атомарно создаёт/реактивирует trainee membership и завершает заявку;
- повторная pending-заявка одного canonical user в ту же секцию запрещена;
- активный участник не может подать новую заявку;
- owner/manager с `section.trainees.manage` видит и обрабатывает заявки;
- public show и каталог получают понятные CTA/badges: «Принимает заявки» и усиленный «Идёт набор».

### UX переключателей

В account UI использовать фирменные toggle controls.

- попытка включить `is_hiring` при закрытых заявках должна либо атомарно включать приём заявок, либо быть отклонена с понятным сообщением; предпочтительный вариант выбрать при реализации после короткого UX-review;
- выключение `accepts_*_requests` при активном `is_hiring` не должно оставлять невозможное состояние. Предпочтение: не молча терять состояние, а потребовать сначала выключить активный набор либо предложить единое подтверждённое действие.

## Проверка и исправление команд

В этой же задаче привести Team к тому же бизнес-инварианту:

- активная/reopened `TeamHiringPosition` не должна сосуществовать с `accepts_join_requests = false`;
- нельзя оставить активные вакансии и затем выключить общий приём заявок без явного согласованного перехода;
- targeted join request не должен обходить закрытый глобальный gate после изменения правила;
- существующие tests Task 135 обновить под новый invariant.

Важно: для Team `is_hiring` не добавляется отдельной колонкой — это вычисляемое состояние по наличию активных вакансий. Для SportsSection на первом этапе допустим простой boolean `is_hiring`, пока не появятся детализированные вакансии/направления набора.

## Реализация

### SportsSection

- добавлены `sports_sections.accepts_trainee_requests` и `sports_sections.is_recruiting`;
- server-side переход в `is_recruiting = true` автоматически включает `accepts_trainee_requests`, поэтому невозможное состояние не сохраняется;
- добавлена отдельная `SportsSectionJoinRequest` с lifecycle `pending|accepted|rejected|cancelled`;
- submit доступен только подтверждённому active player и проверяет canonical identity;
- повторная pending-заявка и новая заявка уже активного тренируемого блокируются;
- пользователь может отменить только собственную pending-заявку, в том числе через canonical alias;
- review/accept/reject доступны только membership с точным permission `section.trainees.manage`;
- accept выполняется транзакционно и создаёт/реактивирует `SectionTraineeMembership` до перевода заявки в accepted;
- public show/catalog отображают «Принимает заявки» и «Идёт набор», каталог фильтрует оба состояния;
- guest CTA «Подать заявку» использует общий `auth-entry-classic` и возвращает на страницу секции после авторизации;
- account UI получил shared toggle controls и отдельный экран заявок/набора.

### Team

- создание или reopening активной `TeamHiringPosition` автоматически включает `accepts_join_requests`;
- общий приём заявок нельзя выключить, пока существует активная вакансия;
- targeted join request на vacancy также проверяет глобальный `accepts_join_requests` gate;
- migration нормализует legacy-команды с активными вакансиями, включая им приём заявок;
- тесты Task 135 обновлены под новый invariant.

## Критерии приёмки

- секция имеет рабочий публичный flow подачи и обработки заявки;
- `is_hiring => accepts requests` гарантируется сервером и тестами;
- каталог может фильтровать `принимает заявки` и `идёт набор`;
- Team больше не имеет логической дырки, при которой активная vacancy принимает заявку при закрытом `accepts_join_requests`;
- canonical identity/IDOR/permissions покрыты tests;
- документация Team и SportsSection обновлена;
- `git diff --check` и профильные tests.
