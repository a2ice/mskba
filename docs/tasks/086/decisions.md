# 086 - Реестр архитектурных решений

## Назначение

Файл хранит решения и открытые вопросы до переноса утверждённой модели в продуктовую документацию и
новый ADR. Статусы: `предложено`, `принято`, `отклонено`, `отложено`.

## Предложенные решения

| ID | Решение | Статус | Обоснование |
|---|---|---|---|
| D01 | Event остаётся обязательной организационной оболочкой планируемой игры | принято | Площадка, бронь, публикация и планируемое время уже принадлежат Event |
| D02 | Event типа game содержит ровно одну основную Game | принято | Убирает видимую пользователю двойственность standalone-игры |
| D03 | Training/GameTraining Event может содержать несколько внутренних Game | принято | Одна бронь покрывает несколько игровых эпизодов тренировки |
| D04 | Tournament не является Event | принято | Турнир длительный, имеет несколько площадок, игр и бронирований |
| D05 | TournamentMatch, а не Game, владеет местом в турнирной схеме | принято | Матч может существовать до назначения времени и создания Game |
| D06 | Публичные title, alias, описания и планируемое время standalone-игры принадлежат Event | принято | Исключает дублирование и рассинхронизацию Event/Game |
| D07 | Ручное изменение размеров сторон переводит preset формата в custom | принято | Сохранённое значение должно честно описывать фактическую конфигурацию |
| D08 | Scoring type хранится независимо от preset и размеров сторон | принято | Custom 4×4 может использовать баскетбольный подсчёт |
| D09 | Event.ends_at обязателен для события с площадкой | принято | Открытый интервал невозможно проверить и забронировать |
| D10 | Tournament хранит `starts_on`/`ends_on` как календарные даты | принято | Точное время принадлежит Event/Game конкретного матча, а границы турнира включают даты целиком |
| D10 | Actual timestamps устанавливаются сервером, исторический импорт — отдельный flow | принято | Защищает фактический lifecycle от произвольной подмены |
| D11 | Создатель Tournament получает все права по ownership, ответственные — через контракты | принято | Не нужен искусственный контракт пользователя с самим собой |
| D12 | Soft delete турнира не каскадно удаляет Event/Game/статистику | принято | Спортивная история должна сохраняться |
| D13 | Отмена турнира блокируется при наличии Game in_progress | принято | Не допускает частичного неявного завершения живой игры |
| D14 | Турнирная таблица использует только подтверждённые результаты | принято | Исключает промежуточный и двойной учёт |
| D15 | Канонический публичный URL standalone-игры остаётся `/events/{id-alias}` | принято | Event владеет публичной идентичностью; `/games/...` допустим только как будущий 301-синоним |
| D16 | Game поддерживает whole_game либо 2/4 дочерних GamePeriod | принято | Периодные действия и score snapshots доступны без дублирования общего итога Game |
| D17 | TournamentEntry — нейтральная игровая сторона турнира | принято | Для 5×5/3×3 entry является командой, для 1×1 — игроком; фиктивная Team из одного игрока не создаётся |
| D18 | Tournament выбирает preformed teams либо individual draft | принято | Режим меняет admission flow; для 1×1 он всегда individual и после первой admission не меняется |
| D19 | Заявка и приглашение требуют подтверждения второй стороной | принято | Заявку подтверждает Tournament, приглашение — Team representative или User |
| D20 | Individual draft использует единый balanced preview flow | принято | Отдельных manual/random modes нет; balanced preview можно пересобрать и скорректировать drag-and-drop до фиксации |
| D21 | Balanced formation явно выбирает self assessment либо objective assessment | принято | Выбранный assessment совместно с ростом, весом, опытом, позициями и телосложением образует версионируемый input формулы |
| D22 | Missing player data не равны нулевой силе | принято | Неизвестные features получают нейтральное imputed-значение, а low-coverage players seeded-random равномерно распределяются между entries |
| D23 | Balanced preview редактируется drag-and-drop до явного apply | принято | Организатор может сделать 1–2 экспертные замены; rerun требует подтверждения и сбрасывает ручные правки |

## Открытые вопросы перед реализацией

1. Нужна ли самостоятельная сущность `OpenTrainingDetails` на первом этапе?
2. Обязательна ли причина отмены турнира или остаётся nullable status comment?
3. Разрешено ли переносить назначенный матч обратно в `not_scheduled`, если Game ещё не начата?
4. Может ли одна Game быть отвязана от TournamentMatch без отмены Event?
5. Нужна ли поддержка двух кругов в первой версии генератора?
6. Какая начальная формула турнирных очков и tie-break должна применяться?
7. Какие данные VDS потребуется сохранить перед будущим production deployment?

## Дополнительно принято на Gate A

- `game_training` остаётся отдельным Event type;
- для разработки целевой схемы используется fresh migration/seed без искусственного legacy-слоя;
- локальная реализация не зависит от состояния VDS и не требует подключения к нему;
- перед будущим применением на VDS выполняется отдельный аудит данных и резервная копия.

## Решения, которые нельзя принимать неявно

- изменение канонических URL;
- удаление или переписывание существующих миграций при наличии production-данных;
- каскадное удаление турнира и игр;
- автоматическая отмена начавшихся игр;
- изменение формулы статистики и турнирной таблицы;
- объединение training и game_training без продуктового определения.
