# Контрольные точки окружений (340)

## Цель

Однозначно сравнивать функциональное содержимое main/dev и отдельно подтверждать фактически развёрнутую ревизию. Не использовать Ahead/Behind как критерий совпадения. Не копировать данные БД между окружениями.

## Контракт v1

- `python3 scripts/environment-state.py compare main dev` сравнивает **конечные деревья** двух ревизий, а не diff от merge-base. Полный результат JSON: Git SHA, группы файлов, количество, SHA-256 канонического манифеста (путь, тип, режим, Git blob ID), добавленные/изменённые/удалённые файлы.
- Функциональная версия `f1-<16 символов хеша>` — удобная метка; равенство определяется по полному SHA-256 и набору файлов. История коммитов на хеш не влияет.
- Группы: функциональная — все отслеживаемые файлы, кроме `.github/workflows/**`, `docs/**`, `README.md`, `public/build/**`; эти исключения сравниваются отдельно. Различия CI/deploy не объявляются автоматически допустимыми: проверить каждое перед синхронизацией. В функциональную группу входят исходники, тесты, lock-файлы, миграции, скрипты, compose и конфиги.
- Отдельно проверяются реальные байты, executable bit и symlink отслеживаемых файлов, за исключением пересобираемого public/build; также неигнорируемые неожиданные файлы в исходных каталогах. DB, .env, storage-данные, vendor, node_modules, кеши, флаги, runtime-образ и доступность интеграций не входят в fingerprint. Артефакты сборки проверяются штатными deploy gates, не выдаются за одинаковые.
- После существующих успешных deploy gates `record production|development <expected SHA> <workflow run ID>` атомарно сохраняет историю и latest в `storage/app/private/environment-checkpoints/`. При несовпадении SHA или drift новая подтверждённая точка не записывается. Старый checkpoint не доказывает, что checkout актуален сейчас.
- `inspect` читает checkout, проверяет рабочее дерево и сопоставляет с последней точкой; результат `checkpoint_matches_checkout` не доказывает равенство с текущей GitHub-веткой — сравнить с SHA из отчёта.
- Workflow Environment checkpoints автоматически формирует сравнение при push и PR; полный JSON сохраняется как artifact на 90 дней, сводка — в истории Actions. Ручной запуск на main отдельно проверяет живые серверы по существующим SSH-секретам, без изменения файлов, БД и интеграций.
- Filament → Система → Состояние окружений: доступ только подтверждённому незаблокированному SUPERADMIN; показывает локальную историю последних 20 подтверждённых деплоев и ссылку на общий отчёт. Не показывает неподтверждённый live-статус как зелёный.

## Приёмка и последующая синхронизация

1. CI, включая unit-тесты детерминизма, изменения режима, удаления, отличий workflows, symlink, незакоммиченных исходников и отсутствующего checkpoint.
2. Merge main после зелёного CI и штатный production deployment. Проверить точку и страницу Filament.
3. Получить полный JSON main ↔ dev, сохранить dev-only работу, отдельно ревьюить различающиеся CI workflows; подготовить PR в dev (без force-push и без копирования данных).
4. После CI/dev deploy проверить обе фактические точки, равенство функциональных SHA-256 и актуальность checkout относительно веток. Только затем разрешить тестирование как соответствующего кода.
5. Проверить визуальный интерфейс Filament в обеих темах; CI сам по себе не является визуальной приёмкой.

Статус: реализация в feature-ветке; фактические CI, merge, deploy и сверка dev требуют подтверждения.

## Исправление после production run #961 (24.11.2026)

Штатное развёртывание и все 51 URL прошли успешно; отдельный шаг checkpoint завершился ошибкой `install: cannot change owner and permissions ... Operation not permitted`. Host user deploy не должен входить в группу www-data. На обоих окружениях приватную директорию создаёт root существующего PHP-контейнера с UID host deploy, группой www-data и режимом 2750 (setgid); файлы остаются 0640. Проверяется возможность записи на host и чтения latest.json от www-data. Не менять права других директорий, не ослаблять проверки fingerprint, не трогать БД. Повторный production deploy и checkpoint требуют отдельного подтверждения по логам.


## Автоматическая синхронизация после production (26.11.2026)

После успешного завершения workflow Deploy to production запускается отдельный Synchronize environments after production. Только успешный запуск main из собственного репозитория, exact verified release SHA = текущий main, dev является предком main и **все tracked files идентичны** (включая workflows/docs/generated) дают разрешение на автоматический fast-forward dev. Это исключение из ручного PR-процесса только для выравнивания истории без изменения содержимого; не меняет main и не обходится branch protection. Обычный non-force push, повторная проверка обоих refs перед записью. Если dev продвинулся независимо, деревья различаются, release устарел или branch protection блокирует push, штатный ручной PR и CI остаются обязательными. Никакого копирования .env/БД.

GITHUB_TOKEN с contents:write/actions:write только у sync job. Поскольку push с этим токеном не запускает обычные push workflows, явно dispatch ci.yml на dev с deploy_dev_now=true и environment-checkpoints.yml на dev. Сам sync не утверждает успех DEV-деплоя — последующий CI/deploy записывает точку при выполнении существующих проверок. Если refs уже совпадают, обычный повторный запуск после нового production не дублирует деплой; rerun failed sync позволяет повторить dispatch после частичного сбоя. Не использовать пользовательский PAT, force-push или автоматический конфликтный merge.

Тесты sync-plan: точное совпадение, ancestor, устаревший production SHA, отличие даже только workflow, независимый dev при одинаковом дереве. Первый реальный запуск возможен после включения workflow в main и успешного production deployment; проверить результат, отсутствие bypass, DEV CI/deploy и новые checkpoint.
