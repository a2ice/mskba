## Назначение

Документ описывает пользовательский смысл регистрации и входа без лишних технических деталей.

## Пользовательская цель

Пользователь должен иметь возможность создать аккаунт, войти в систему, выйти из аккаунта и перейти в личный кабинет после авторизации.

## Основные сценарии

- Пользователь открывает страницу входа.
- Пользователь отправляет username или подтверждённый контакт и пароль для входа.
- Пользователь открывает страницу регистрации.
- Пользователь отправляет `username`, `password`, подтверждение пароля, принимает Политику обработки
  персональных данных и, при желании, выбирает роль участия.
- После успешной регистрации пользователь перенаправляется на страницу входа.
- Авторизованный пользователь переходит в личный кабинет.
- Авторизованный пользователь выходит из аккаунта.

## Важные состояния

- Гость видит публичные страницы и формы входа/регистрации.
- Авторизованный пользователь получает доступ к личному кабинету.
- Некорректные данные возвращают пользователя к форме с ошибкой.
- Частые попытки входа и регистрации ограничиваются middleware `throttle`.
- При успешной регистрации создается базовый профиль пользователя, даже если персональные поля еще не заполнены.
- При успешной регистрации сохраняется версия принятой Политики, время и технический контекст согласия.
- Роль участия при регистрации необязательна. Если пользователь выбрал доступную роль, она сразу появляется в личном кабинете как активная роль пользователя.
- Если пользователь входит с временным паролем, система возвращает warning-сообщение о необходимости сменить пароль.
- Пользователь, созданный через Telegram Mini App, изначально не имеет пароля. В настройках аккаунта он может установить пароль и после этого использовать тот же аккаунт в обычном браузере.
- Если пароль уже установлен, для его смены нужно указать текущий пароль и дважды новый.
- Для входа подходят username, подтверждённый email, телефон или Telegram-контакт. Неподтверждённый или удалённый контакт не является идентификатором входа.
- Telegram `@username` может изменяться, поэтому он используется только вместе с актуальной подтверждённой Telegram-связью; стабильной внутренней связью остаётся Telegram user ID.

## VK ID

VK ID доступен как независимый способ входа и как привязка к уже существующему аккаунту. Интеграция использует Authorization Code Flow с PKCE и одноразовым серверным `state`. Новый VK ID создаёт неподтверждённый аккаунт с техническим логином `vk_{id}`; известный VK ID авторизует canonical-пользователя.

Токены VK после входа не сохраняются. В базе остаются стабильный VK ID, имя, фамилия, аватар и время последнего входа. Если VK ID уже связан с другой identity-группой, автоматическая перепривязка запрещена и создаётся кандидат на проверку дубля.

Для включения интеграции задаются `VK_ID_APP_ID` и зарегистрированный в приложении VK callback `VK_ID_REDIRECT_URI`. Для production callback должен точно совпадать с `https://mskba.ru/auth/vk/callback` (с учётом фактического домена проекта).

## Что не реализовано

В текущем `AuthController` реализованы регистрация, вход и выход. Установка и смена пароля выполняется в настройках аккаунта.

Маршруты `auth.restore`, `auth.confirm`, `auth.resolve-login` и `auth.verify` есть в `routes/web.php`, но соответствующих методов контроллера сейчас нет. Поэтому восстановление доступа, подтверждение контакта, resolve-login и verify не должны описываться как рабочие пользовательские сценарии.
