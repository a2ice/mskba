## Назначение

Документ описывает пользовательский смысл регистрации и входа без лишних технических деталей.

## Пользовательская цель

Пользователь должен иметь возможность создать аккаунт, войти в систему, выйти из аккаунта и перейти в личный кабинет после авторизации.

## Основные сценарии

- Пользователь открывает страницу входа.
- Пользователь отправляет username или подтверждённый контакт и пароль для входа.
- Пользователь открывает страницу регистрации.
- Пользователь отправляет `username`, `password`, подтверждение пароля, принимает Политику обработки
  персональных данных и, при желании, выбирает роль участия.
- После успешной обычной регистрации пользователь перенаправляется по сценарию текущей формы регистрации.
- Авторизованный пользователь переходит в личный кабинет.
- Авторизованный пользователь выходит из аккаунта.

## Acquisition onboarding

`/join` остаётся отдельным onboarding-flow, а нейтральным адресом конкретной acquisition-кампании является `/go/{public_code}`. Campaign entry сначала проверяет состояние кампании и затем либо открывает onboarding, либо перенаправляет на выбранную посадочную. Обычные страницы входа и регистрации этим flow не заменяются.

Для гостя flow начинается с двух явных вариантов:

- `Присоединиться` — перейти к выбору первого сценария/роли и созданию аккаунта;
- `У меня уже есть аккаунт` — войти существующим аккаунтом.

При присоединении пользователь сначала выбирает onboarding persona (`player`, `coach`, `venue`, `organizer` или `explore`), затем заполняет минимальные данные аккаунта. Для `player` и `coach` дополнительно запрашиваются обязательные для текущего ролевого flow `birth_date` и `gender`; имя и фамилия остаются необязательными.

Если существующий пользователь входит из `/join`, после логина он возвращается в тот же onboarding, а исходный acquisition visit переиспользуется и связывается с canonical account. Возврат после login не должен создавать второй маркетинговый визит и не должен терять исходный канал/кампанию.

У уже авторизованного пользователя вместо повторной регистрации показывается сворачиваемый блок текущих ролей участия. В свернутом виде он кратко показывает состояние вроде «моя роль — игрок», «игрок и тренер» или «игрок и ещё 2». В раскрытом виде роли можно включать и отключать теми же self-service тумблерами, что и в личном кабинете. Допускаются несколько ролей одновременно или отсутствие активной роли.

После продолжения `/join/success` строится не по одной onboarding persona, а по фактическому набору активных participation roles пользователя. Для каждой активной роли выводится отдельная визуальная группа с релевантными действиями. Если ролей нет, показываются нейтральные открытые разделы портала и возможность настроить роли позже.

Для QR-кампании можно включить добровольную геопроверку, если кампания связана с площадкой. Она не показывается отдельной карточкой: при ещё не выданном permission запрос запускается пользовательским нажатием на основной CTA onboarding, а при уже выданном permission проверка может выполняться автоматически. Отказ от геолокации, timeout или ошибка не блокируют вход, регистрацию или дальнейшую работу. Для online-каналов физический контекст и геопроверка в штатной форме не показываются; partner/other могут хранить площадку и подпись места как необязательный офлайн-контекст.

Acquisition channel хранится отдельно от `users.registration_channel`: маркетинговый источник не меняет технический способ создания аккаунта.

Администратор управляет конкретными acquisition-кампаниями в `/admin/acquisition`. Для офлайн QR одна физическая точка размещения — отдельная campaign: например, у одной площадки могут быть разные кампании для стенда у входа и раздаточной листовки. Канал при этом остаётся общим `qr`, а campaign хранит площадку, место размещения, период активности и собственный публичный код.

Из карточки кампании доступны canonical `/go/{public_code}`, QR в SVG/PNG, browser-preview A4-листовки и PDF для QR channel. Посадочная задаётся отдельно: onboarding, главная, публичная площадка, публичное мероприятие или активная секция. Для non-onboarding landing визит фиксируется до redirect; если пользователь позже авторизуется в той же web-session, visit связывается с canonical account.

404 используется только для неизвестного public code. Существующая выключенная кампания, будущий период и завершённый период показывают отдельные страницы состояния и не создают acquisition visit. Старый `/join/{public_code}` остаётся совместимым и для non-onboarding campaign перенаправляет через canonical `/go/{public_code}`.

Там же показывается базовая attribution-сводка: переходы, связанные визиты, уникальные пользователи и результаты добровольной геопроверки.

Текущая листовка — встроенный шаблон. Дальнейшее управление редактируемыми шаблонами планируется как общий механизм для печатных материалов и рассылок, а не отдельный редактор только для QR.

## Важные состояния

- Гость видит публичные страницы и формы входа/регистрации.
- Авторизованный пользователь получает доступ к личному кабинету.
- Некорректные данные возвращают пользователя к форме с ошибкой.
- Частые попытки входа и регистрации ограничиваются middleware `throttle`.
- При успешной регистрации создается базовый профиль пользователя, даже если персональные поля еще не заполнены.
- При успешной регистрации сохраняется версия принятой Политики, время и технический контекст согласия.
- Роль участия при регистрации необязательна. Если пользователь выбрал доступную роль, она сразу появляется в личном кабинете как активная роль пользователя.
- Если пользователь входит с временным паролем, система возвращает warning-сообщение о необходимости сменить пароль.
- Пользователь, созданный через Telegram Mini App, изначально не имеет пароля. В настройках аккаунта он может установить пароль и после этого использовать тот же аккаунт в обычном браузере.
- Если пароль уже установлен, для его смены нужно указать текущий пароль и дважды новый.
- Для входа подходят username, подтверждённый email, телефон или Telegram-контакт. Неподтверждённый или удалённый контакт не является идентификатором входа.
- Telegram `@username` может изменяться, поэтому он используется только вместе с актуальной подтверждённой Telegram-связью; стабильной внутренней связью остаётся Telegram user ID.

## VK ID

VK ID доступен как независимый способ входа и как привязка к уже существующему аккаунту. Интеграция использует Authorization Code Flow с PKCE и одноразовым серверным `state`. Новый VK ID создаёт неподтверждённый аккаунт с техническим логином `vk_{id}`; известный VK ID авторизует canonical-пользователя.

Токены VK после входа не сохраняются. В базе остаются стабильный VK ID, имя, фамилия, аватар и время последнего входа. Если VK ID уже связан с другой identity-группой, автоматическая перепривязка запрещена и создаётся кандидат на проверку дубля.

Для включения интеграции задаются `VK_ID_APP_ID` и зарегистрированный в приложении VK callback `VK_ID_REDIRECT_URI`. Для production callback должен точно совпадать с `https://mskba.ru/auth/vk/callback` (с учётом фактического домена проекта).

## Что не реализовано

В текущем `AuthController` реализованы регистрация, вход и выход. Установка и смена пароля выполняется в настройках аккаунта.

Маршруты `auth.restore`, `auth.confirm`, `auth.resolve-login` и `auth.verify` есть в `routes/web.php`, но соответствующих методов контроллера сейчас нет. Поэтому восстановление доступа, подтверждение контакта, resolve-login и verify не должны описываться как рабочие пользовательские сценарии.
