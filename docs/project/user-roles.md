## Назначение

Документ описывает, как в проекте понимаются роли пользователей на продуктовом уровне.

## Два уровня ролей

В проекте роли разделены на два разных слоя:

- системные роли;
- роли участия.

Это разделение нужно, чтобы не смешивать глобальные полномочия в системе и предметную роль пользователя в проекте.

## Системные роли

Системная роль отвечает за глобальные полномочия внутри системы. Она связана с доступом, административными функциями и служебными сценариями.

Системная роль может отсутствовать. Это означает, что пользователь не имеет специальной системной роли.

Текущий набор системных ролей:

- суперадмин;
- админ;
- пользователь;
- модератор;
- редактор;
- системный пользователь.

Административные сценарии для этих ролей пока не описываются как готовые пользовательские flow, если они не подтверждены маршрутами и контроллерами.

## Роли участия

Роль участия описывает, в каком качестве пользователь представлен в предметной модели проекта.

У одного пользователя может быть несколько ролей участия одновременно. Они не заменяют системную роль, а дополняют ее.

Текущий набор ролей участия:

- игрок;
- тренер;
- судья;
- статист;
- медиа;
- представитель площадки;
- организатор мероприятий.

`Организатор мероприятий` — именно participation role. Она описывает пользовательский контекст и может использоваться для профиля/onboarding, но сама по себе не выдаёт системные права на создание или управление объектами. Реальные полномочия продолжают определяться Gate, middleware и permission-проверками конкретного сценария.

## Управление ролями

Авторизованный пользователь управляет своим набором ролей на странице `/account/roles`. При выборе роль активируется, при снятии выбора — переводится в неактивное состояние без удаления истории. Можно выбрать несколько ролей или временно не использовать ни одной.

Тот же self-service принцип используется в acquisition onboarding `/join`: если пользователь уже авторизован или вошёл из этого flow, текущие роли показываются в сворачиваемом блоке «Моя роль». В раскрытом состоянии роли можно изменить теми же тумблерами и сохранить без повторной регистрации.

На финальном экране acquisition onboarding действия группируются по фактически активным participation roles. Поэтому пользователь с несколькими ролями получает несколько отдельных ролевых групп, а пользователь без ролей — нейтральный набор открытых действий.

## Текущее правило для площадок

На текущем этапе подтвержденный пользователь с ролью участия `представитель площадки` может добавлять площадки из личного кабинета.

Это правило реализовано технически через Gate `add_venue`.
