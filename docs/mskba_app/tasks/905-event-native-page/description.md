# 905 — Нативная страница мероприятия
## Требования и приёмка

- Для созданных через event-first мероприятий в mskba_app использовать одну страницу независимо от даты и наличия игровой сущности. Черновик не публикуется сам. При наличии пожеланий время не считается бронью.
- Площадка, зал, адрес/метро, обложка, общий popup карты, переход в двухшаговый просмотр занятости, время и альтернативы, статус мероприятия, видимость, описание, участники, личный ответ и обсуждение/история.
- Организатор остаётся в списке при отказе, право обсуждать сохраняется; лимит считает актуальные подтверждённые player-роли. Приглашение, редактирование и действия с предзаявкой показывать только по scope permissions. Черновик редактируется без принудительной даты.
- При выборе «Любой зал» не назначать автоматически основной зал event-first; явный зал сохраняется. Для брони необходим определённый зал; фактическая бронь имеет приоритет при отображении.
- Существующая бронь из обеих моделей — кликабельная строка, Modal 1.1: номер, статус, площадка/зал, время и scope. Без документов/платёжных данных в публичном представлении; ссылка к заявке только организатору новой брони, серверная авторизация прежняя.
- Разделить контексты публичного просмотра и переходов к управлению. Сохранить прежний спортивный экран через явную ссылку и старые страницы остальных сценариев до отдельной миграции; не объявлять миграцию всех событий и игрового управления завершённой.
- UI: действующий app-layout, container, panel, button, select-control, mskba-modal, токены темы, адаптивность, без новой палитры/eyebrow; карта и обсуждение используют общие механизмы.
- Тесты: нативный вид черновика, отсутствие брони/даты, смена RSVP организатора без потери роли, приватность черновика, сохранение неосновного зала, popup настоящей брони и отсутствие управления для обычного зрителя. CI и проверка main/dev deploy до приёмки. Не смешивать с #901/#902.

UI reference: [MSKBA UI Design System](../../../specification/ui-design-system.md), Modal 1.1, Form Controls.

## Корректировка UI 20.11.2026
По замечанию владельца удалены повторные заголовки/переписка с площадкой, пустая карточка описания, пояснение черновика (достаточно статуса + даты), служебные пояснения обсуждения и технический rate-limit. Сохранены смысловые статусы и требования для действий. Modal 1.1: общий native dialog, header с имеющимся drag affordance и крестиком, прокручиваемый body с mskba-scroll, fixed footer только при наличии действия, закрытие фоном только при pointerdown и pointerup вне прямоугольника. Цвета статусов через --success/--warning/--danger, общая .status-dot, размеры 24/20px padding, compact panel heading 20/26. Без отдельного контракта UI Kit. Визуальная приёмка desktop/mobile остаётся обязательной.

## Приёмка 21.11.2026 — #951

- Дата мероприятия: русская локаль, исходный часовой пояс площадки; скрыть только кнопку «Посмотреть занятость», не удаляя механизм занятости.
- Метро: существующие `app-venue-intro__station` и `app-venue-intro__metro-dot`, безопасный цвет линии с нейтральным fallback.
- Создание мероприятия и бронирование: хотя бы один реально подтверждённый контакт текущей канонической личности; статус аккаунта не заменяет контакт. Существующие права, блокировки и проверки доступа сохраняются. Старые мероприятия не удалять.
- При отсутствии контакта в блоке аренды — «Для бронирования необходимо иметь подтверждённый контакт», штатная кнопка подтверждения, красноватая рамка, стандартный отступ. Без совета изменить площадку/время. Использовать существующий контактный визард, сохранять незавершённый этап, восстановление после перезагрузки; после подтверждения повторить расчёт без потери мероприятия. Аналогично перед созданием.
- Приёмка: без контакта, pending, подтверждённый контакт при неподтверждённом аккаунте, чужой контакт, просроченный код, resend, web/API, дата, метро, mobile, green CI и main/dev deployment.

Статус: реализация продолжается в draft PR #952; полный набор проверок и публикация пока не выполнены.
