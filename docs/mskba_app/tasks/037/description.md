# 037 — Messenger UX, история по 10, Reverb и личный чёрный список

**Статус:** реализовано локально, пользовательская визуальная приёмка открыта. Только `dev` на MacBook; без GitHub push/PR/deploy.

## ТЗ и изменения (13.10.2026)

- На `account.notifications.threads.*` выделять «Сообщения» в sidebar. Профильная карточка в inbox показывает **последнее реальное сообщение и его автора**, а не статический текст. Личные диалоги также показывают автора последнего сообщения.
- Для `ProfileChangeRequest` и `DirectConversation`: компактная отдельная panel-шапка с возвратом в список, прокручиваемая отдельная panel-история, отдельная panel-композиция без избыточного заголовка; textarea на всю ширину, кнопка «Отправить» справа. Действия находятся слева в раскрывающемся **вверх** details-меню, повторно используются CSS и паттерны `app-context-actions`.
- Заявка: claim, rescue, управление участниками (приглашение/передача/исключение), одобрение, отклонение, блокировка, разблокировка и отмена — только когда позволяет backend access и состояние. Причины отклонения/блокировки требуются сервером. После решения пользователь остаётся в своём треде. В неактивном треде скрыта история и действия.
- Оба чата: начальная страница **10 сообщений/событий**, следующие 10 при скролле к верху с загрузочным индикатором `.spinner`; сохраняется вертикальная позиция после вставки. Профильная история — три индексируемых keyset-потока (`profile_change_request_events`, `request_thread_events`, `request_thread_messages`) без гигантского JOIN, а сортировка/курсор сохраняют порядок событий с одинаковыми временными метками. Direct — keyset по message.id. На сервере HTML экранируется в одной Blade partial, GET обязателен с повторной проверкой доступа.
- Cmd+Enter/Ctrl+Enter отправляет сообщение; обычный Enter добавляет строку. POST Ajax не сбрасывает страницу; текст очищается только после успеха. При отсутствии сети сохраняется текст и показывается ошибка.
- Reverb: **закрытые** `request-threads.{id}` и `direct-conversations.{id}`, проверка участников в `routes/channels.php`. Broadcast содержит только сигнал изменения/инвалидации, **никогда** текст, личные данные или имя. Передача/исключение/отзыв права/модерация инвалидируют открытые вкладки; каждое содержимое загружается авторизованным HTTP, со сверкой при возвращении вкладки/reconnect.
- Чёрный список direct: новая таблица `direct_message_blocks`, уникальная пара blocker/blocked, индексы в обоих направлениях, блокировка/разблокировка через POST/DELETE с CSRF. Проверка блокировки с обеих сторон на access/send и повторно внутри транзакции после упорядоченной блокировки строк пользователей, чтобы исключить гонку. История сохраняется read-only, после снятия блока действуют обычные настройки приватности. Это **блокировка только личных сообщений**, не блокировка аккаунта и не модерация.

## Приёмка Reverb + тостов в двух окнах (2026-10-13)

- Проблема: в `account-thread-chat.js` обработчик `refresh()` имел ранний `return` при `document.hidden`, хотя приватный Reverb-сигнал приходил. Вторая вкладка показывала новые сообщения только после `focus`/`visibilitychange`. Ограничение снято **только для доставки/подгрузки**; получение HTML по-прежнему использует авторизованный history endpoint.
- Проблема: для уже открытого чата новые уведомления не отмечались прочитанными. Исходный GET профиля делал это лишь при первом открытии, а direct имел разовый PATCH из старого `account-messages.js`. Реализован единый механизм acknowledgement для profile/direct. Создан `PATCH /account/notifications/threads/profile/{changeRequest}/read` с обязательным `ProfileRequestThreadAccess::canRead` (только свой тред); direct повторно использует существующий PATCH. На view передаются `data-chat-read-url` и начальное количество непрочитанных (после SSR GET профиля = 0).
- Правило просмотра: пока вкладка неактивна, новые сообщения **появляются в истории, но остаются непрочитанными**; PATCH отправляется только когда документ видим, окно имеет фокус и область чата прокручена к последнему сообщению. При возврате фокуса сначала синхронизируется защищённая история. Никакого auto-read при простом получении фонового Reverb события. При скролле к новым сообщениям также подтверждается прочтение.
- После успешного read клиент диспатчит `notification:count-changed`; существующий `notification-counts.js` синхронизирует непрочитанные уведомления с backend и `notification-toasts.js` удаляет прочитанные карточки. Сервер `MarkConversationNotificationsReadHandler` уже рассылает `notification.count-updated` для других сессий; другой тред/системные уведомления не затрагиваются. При повторных запросах и гонке новых событий используется revision-guard; повторный read безопасен/идемпотентен. Старый разовый direct-read отключён именно для новой chat-страницы, чтобы исключить дублирование и преждевременное прочтение.
- QA: два новых feature-теста на «уведомление после открытия», доступ чужого аккаунта 403, сохранение постороннего непрочитанного уведомления и идемпотентный read; 103 relevant PHPUnit tests / 911 assertions PASS, Vite build PASS, Blade cache PASS, Pint/JS syntax/git diff check PASS.
- Отдельная временная браузерная fixture с реальным `account-thread-chat.js` и замоканным Reverb/fetch в headless Chrome: **background** `messageVisible=true`/`reads=0`; после **foreground** `reads=1`, `notification:count-changed=1`. Это тест клиентского обработчика, а не утверждение о реальном живом подключении двух пользовательских браузеров; визуальную приёмку и живую двустороннюю проверку оставить открытыми.
- Изменения только локально в Mac dev, commit/push/PR/deploy не выполнялись.
