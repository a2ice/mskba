# 062 — Единая консоль пользователей и доступа

**Приоритет P0:** выполнить до 058–061. GitHub Issue [#512](https://github.com/a2ice/mskba/issues/512).

## Объём и принятый интерфейс

- В навигации Filament `Пользователи`. В последней колонке списка `Редактировать`: переход только при явном разрешении редактировать личные данные **и** допустимом подчинённом статусе пользователя; иначе информационная модалка `У вас нет права для редактирования пользователя` (без обхода через URL/Livewire).
- В редакторе: `Общее`, `Профиль`, по одной вкладке для каждой фактически активной роли участия (`Игрок`, `Тренер` и т.д.), `Роли и права`, `История изменений`. Общая информация использует факты из legacy `AdminUsersController::edit`: создание, канал регистрации, подтверждение, Telegram/VK, активность и алиасы.
- `Роли и права` → `Системные` (по умолчанию) / `Контекстные`. Системная таблица: роль, число базовых разрешений, изменить. В пользовательском редакторе показывается активная роль, а управление шаблонами всех ролей — из существующего `SystemRoleProfileResource` (не создавать второй каталог).
- Контекстные → `Управление площадками`: отдельно глобальный контур `BACKOFFICE_VENUE_MANAGE` и список действующих контекстных контрактов (`VenueMembershipAccess`, `ContractMembership`) с областью площадки и зала/зоны. Скоуп конкретных площадок никогда не заменяется глобальным флагом без дополнительного разрешения; не показывать истёкшие контракты. Позже добавить игры/лиги/турниры.
- Редактирование каждой группы данных — отдельная операция с подтверждением, историей до/после, actor, reason, транзакцией, защищённой серверной валидацией и rollback при отсутствии конфликтов. У изменений паролей, согласий и финансов нет универсального отката.

## Три системных разрешения и источники истины

1. `identity.profile.self_edit` — **«Редактировать данные собственного профиля»**, базовая выдача superadmin/admin. Не следует механически закрывать регистрацию, создание профиля, аватары, контактную верификацию или управление согласиями: требуется инвентаризация *каждого* self-write endpoint и разграничение данных удостоверенной личности и пользовательских игровых настроек.
2. `identity.profile_change.review` — **уже существует**. Базовая выдача admin/superadmin; курсоры заявки, отзыв разрешения, private threads и старые пользовательские формы обязаны уважать эффективный grant.
3. `identity.user.personal_edit` — **«Редактировать личные данные пользователей»**, по умолчанию только superadmin; разрешение проверяется через `UserOperationalPermissionChecker` в ресурсах Filament, действии, доменном use case и API. Для admin возможно явно делегировать только при имеющемся праве и строгой нижестоящей иерархии.

Системные роли `superadmin/admin/manager/system/user`; исторические `moderator/editor` продолжают читаться. System не назначается через человеческий редактор. Запрет на редактирование равных/старших и self-account, запрет на обход прямым URL или фальшивым Livewire payload. У superadmin сохраняется recovery инвариант.

## Аудит и откат

Существующие `Actor`, `AuditLog`, `Auditable` — базовый журнал. Откат — новая компенсирующая запись, не удаление истории. Под блокировкой строки сравнить каждое затронутое `after` со **всё ещё актуальным** значением; несовпадение → 409/ValidationException, частичного восстановления нет. Повторная авторизация иерархии и разрешений перед записью. Секреты и сессии никогда не пишутся в историю/rollback.

## Проверка и релиз

- Feature security tests на admin без разрешения, superadmin, заблокированного, равную роль, system, forged Livewire/POST.
- Review-permission default и cursor/revoke проверяются отдельно.
- Активный договор и entity-scope ACL, обновление и откат данных, конкурентное изменение, невозможность rollback секретов.
- UI Kit: `docs/specification/ui-design-system.md`, используем существующий Filament 5 Components и темы; любые новые варианты по правилам CaseRule15 в том же PR.
- Полный CI + PostgreSQL для изменений RBAC/permissions → merge dev → verified deploy → пользовательская приёмка. main/prod без изменений.

1. Ревизия существующей RBAC, интерфейс списка, новые разрешения и доступ к редактору.

## Реализация первой итерации (ветка, не принята)

- Filament: `Пользователи`; в таблице `Редактировать`, при отсутствии `identity.user.personal_edit` или недопустимой иерархии открывается только информационная модалка. Серверный `canEdit` повторяет проверку права.
- Профиль: прямое редактирование полей имени/фамилии/отчества/даты/пола через подтверждаемый Filament Action. Требуется основание; транзакция блокирует пользователя, записывает before/after в `AuditLog`. Откат — только личных данных, с проверкой текущего состояния; отдельная компенсирующая audit-запись. Секреты не затрагиваются.
- `UserOperationalPermissionEnum`: `identity.profile.self_edit`, `identity.user.personal_edit` и существующее `identity.profile_change.review`; добавлена миграция admin-базовых прав self/review с сохранением прежних шаблонов и курсором для приватных заявок. Редактор включает новые разрешения в существующий `GlobalOperationalPermissionManager`, но прямое применение `self_edit` ко всем endpoint ещё не завершено и не должно быть выкачено до аудита маршрутов.
- Форма: `Общее`, `Профиль`, динамические активные роли, `Роли и права` с `Системные/Контекстные`, `История изменений`; предметные контекстные права берутся из `VenueMembershipAccess` и действующих контрактов, глобальный backoffice флаг показан отдельно. Изменение договорного гранта из этой таблицы ещё не реализовано: редактирование через существующую страницу управления договорами, без обхода ACL.
- Остаётся: защищённое изменение параметров каждой активной роли, полный self-profile gate со всеми legacy/registration путями, изменение контекстных назначений непосредственно с экрана пользователя, права и аудит для ролей/контрактов, интеграционные тесты, CI/деплой и пользовательская приёмка. **Не сливать черновой PR в dev до завершения.**

## Реализация второй итерации (29.10.2026, ожидает CI и приёмку)

- У активной роли **Игрок** в Filament отображаются параметры `PlayerProfile`; редактирование роста, веса, телосложения, года начала и комментария — отдельным подтверждаемым действием. Сервер требует `identity.user.personal_edit`, нижестоящую роль и активную роль игрока; пишет аудит до/после с основанием. Компенсирующий откат блокирует перезапись последующих изменений; добавлены feature-тесты. Неактивные роли больше не создают вкладки.
- Контекстные права площадок отображаются по **каждому действующему договору** с различением `VENUE` и `VENUE_COURT`, без слияния прав залов и всей площадки. Кнопка «Изменить» открывает отдельное действие с договором, специализацией, разрешениями и причиной. Запись делегирует в существующий `ManageVenueMembershipHandler::change()`, сохраняет аудит и поддерживает конфликтно-безопасный откат. Владельца нельзя менять таким способом; действующая иерархия, feature flag и права на конкретную площадку/зал проверяются в серверном use case. Добавлены тесты запрета чужого договора, отказа для admin без персонального права и конфликтного отката.
- Глобальные индивидуальные права: причина изменения обязательна, кнопка сохранения требует подтверждения; серверный обработчик повторно проверяет `identity.user.personal_edit` и иерархию, делегирует изменения в старые permission managers, сохраняет сводную ревизию эффективных прав. Откат возможен только при прежней системной роли и точном совпадении текущих эффективных прав с ревизией. При восстановлении права модератора/поддержки используются существующие менеджеры грантов и их курсоры, а не прямой возврат доступа к старым заявкам. Добавлены тесты прав, причины и конфликта.
- Эти действия не дают права редактирования независимо от глобальной или контекстной авторизации; сервер проверяет оба уровня. Все изменения пока только в черновике PR #513, не на dev.

### Оставшиеся обязательные пункты перед выпуском 062

1. Убедиться, что **полный** PHP CI и PostgreSQL RBAC green после последних изменений, исправить ошибки/регрессии. Проверить реально исполненный action modal Livewire, включая путь «Изменить» из Blade таблицы и `requiresConfirmation`.
2. Для всех активных ролей участия добавлены редактирование статуса и комментария с аудитом/откатом, а также отдельная кнопка непосредственно во вкладке роли. В существующей модели предметные данные хранятся только в `PlayerProfile`; `CoachProfile`/`RefereeProfile` находятся в проектном плане и пока не являются таблицами БД. Новые вымышленные поля тренера/судьи не добавлять — развивать отдельными миграциями по утверждённым схемам.
3. Смена системной роли и специализаций менеджера теперь идут отдельными подтверждаемыми и аудируемыми операциями с основанием. Для системной роли снимок включает роль, должность, специализации и все индивидуальные grant-строки; откат выполняется старым role handler и только если можно восстановить полное состояние без прямого воскрешения отозванных разрешений. Для специализаций менеджера откат выполняется через `StaffSpecializationManager`, с авторизацией и повторной проверкой снимка. Нужна E2E проверка всех переходов.
4. Инвентаризировать и закрыть все оставшиеся пути изменения **подтверждённых личных полей** через legacy HTML/API, сохранив отдельно игровые настройки, онбординг, согласия и контактную верификацию.
5. Полная безопасность: конкурирующие Livewire запросы, блокировка пользователя/актора, истёкший контракт прямо во время операции, восстановление grants без раскрытия прежних support/review threads. Добавить интеграционные тесты этих случаев.
6. UI Kit / адаптивность / UX и проверка на dev владельцем. До этого PR оставлять draft, main/prod не менять.

### Изменение ролей участия

- Новые отдельные обработчики `AdminEditParticipationRoleHandler` / `AdminRevertParticipationRoleHandler`: статус `active/inactive`, комментарий, основание, разрешение `identity.user.personal_edit`, проверка принадлежности роли редактируемому аккаунту, блокировка и конфликтно-безопасный откат. Тесты в `UserParticipationRoleConsoleTest`.
- Реальная модель предметных профилей — `PlayerProfile`. Для тренера, судьи и других ролей пока существуют `UserParticipationRole` и его поля; отдельные таблицы профиля пока лишь планируются согласно `docs/specification/identity-participation-profiles.md`.
- Лимиты роста/веса/стажа/комментария в модальном редакторе игрока синхронизированы с текущим `UpdatePlayerProfileRequest` (150–220 см, 40–140 кг, стаж от текущего года минус 50 до минус 10 лет, комментарий максимум 1000 символов).

### Дополнительные операции системных ролей и специализаций

- `AdminChangeUserSystemRoleWithAuditHandler` / `AdminRevertUserSystemRoleHandler`: отдельная транзакционная ревизия с причиной; snapshot роли, специализаций и индивидуальных грантов. Для отката используется существующий `AdminUpdateUserSystemRoleHandler`, а не запись role/grants напрямую. При невозможности вернуть всё прежнее состояние без восстановления отозванных полномочий транзакция отказывается от отката. Тесты в `UserSystemRoleRevisionConsoleTest`.
- `AdminUpdateStaffSpecializationsWithAuditHandler` / `AdminRevertStaffSpecializationsHandler`: отдельное управление специализациями менеджера и должностью с причиной, подтверждением и проверкой полного snapshot, без обхода ограничений `StaffSpecializationManager`. Тесты в `UserStaffSpecializationsConsoleTest`.
- Эти операции не эквивалентны безусловному «восстановить всё»: подозрительные, несовместимые или сопровождавшиеся отзывом права переходы требуют отдельного назначения уполномоченным администратором.

## Повторная приёмка 29.10.2026 — inline-редактор и назначенные роли

- Убрать из заголовка три основные кнопки с отдельными формами: персональные данные, параметры игрока, роль участия. На вкладках «Общее» и «Профиль» показывать штатные элементы ввода Filament. Кнопка «Сохранить» относится только к текущей вкладке, открывает модальное подтверждение с **одним полем основания** (10–500 символов) и кнопкой «Подтвердить»; редактируемые значения остаются на самой странице.
- «Общее»: регистрационные ID/время/канал/связанные аккаунты являются историческими фактами (только просмотр); статус изменяется суперадминистратором через действующий доменный обработчик (в том числе проверка идентификации для подтверждения) с обязательным основанием.
- Вместо динамических вкладок «Роль Игрок», «Роль Тренер» и т. д. — одна «Роль»: таблица назначений, кнопки «Редактировать», «Отключить»/«Включить», «Добавить роль». Нажатие на название или редактирование открывает поля **ниже таблицы на той же вкладке**, кнопка сохранения открывает модальное подтверждение с причиной. Добавление выбирает только ещё не назначенные роли, повторная попытка блокируется транзакцией. Отключение не удаляет профиль и запись роли; повторное включение возвращает существующие данные. Специализированные поля игрока редактируются здесь; анкеты тренера/судьи пока в предметной модели не существуют, поэтому нельзя имитировать неизвестные параметры.
- «Роли и права»: отменить представление «наследуется» как «навсегда заблокировано». Базовые grants роли/специализации — **значения по умолчанию**; индивидуальное разрешение/запрет имеет приоритет, если право допустимо для системной роли получателя и делегируемо администратором. Защитные проверки (superadmin recovery, запрет SYSTEM, подтверждённость и верхний предел роли) остаются неизменяемыми. Откаты и audit должны отражать **effective** before/after.
- Контекстные права площадок и залов не должны смешиваться с глобальными; на время доработки остаются отдельными проверяемыми договорными действиями.
- Проверки: тесты на назначение/повторное назначение, отключение с сохранением данных, восстановление, запрет чужих ролей; inherited grant → индивидуальный deny → обратный grant; невозможность эскалации за пределы роли; корректность открытия inline-полей и сохранения из соответствующих вкладок. После зелёного CI только `dev` и пользовательская приёмка.

## Дополнение — саморедактирование подтверждённого профиля (30.10.2026)

- Публичные формы `/account/profile` и попап «Личные данные» на `/account/participation/player` обязаны учитывать **эффективное** право `identity.profile.self_edit` после всех разрешений и индивидуальных запретов. Для подтверждённого пользователя с этим правом разрешить прямое изменение ФИО, даты рождения, пола и отчества, без создания заявки. Проверять право повторно под блокировкой канонического аккаунта непосредственно перед записью.
- Для подтверждённого пользователя без права сохранить существующий сценарий заявки на изменение данных: закрытые поля, кнопка заявки и серверный 403 на прямую подмену PATCH. Запрещённому, удалённому или заблокированному аккаунту не разрешать запись.
- Изменения подтверждённых данных через self-service являются отдельными аудируемыми действиями `self_confirmed_profile_updated` (actor, before/after, источник/право) и доступны в истории администратора. Смена чужих данных остаётся под `identity.user.personal_edit` и иерархией; право self-edit не позволяет менять системную роль или чужой профиль.
- Подтверждённые имя/фамилия, дата рождения и пол не могут быть очищены до пустых значений; незавершённая регистрация сохраняет прежнюю nullable-валидацию.
- Контроль: superadmin/admin, индивидуальный deny у admin, делегированное право обычному пользователю, пользователь без права, ajax-проверки и реальный HTML попапа игрока. Только после зелёного CI и PostgreSQL — merge `dev` и staging smoke; production не изменять.

- Для иных ролей до появления их собственных предметных моделей показывать отдельную страницу комментария/статуса без выдуманных полей. Все изменения в PR + зелёный полный CI, далее `dev` и приёмка владельца.
