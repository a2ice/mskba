# 009 — Обязательная сверка UI с гайдлайном и согласование новых компонентов

**Статус:** Принято (документация) · **Дата:** 2026-10-08 · **Основная задача:** [#139](../../../tasks/139/description.md).

## Запрос пользователя

Перед реализацией любого нового или изменяемого UI-элемента обязательно проверять,
описан ли он в принятом дизайн-гайдлайне MSKBA App. Если описан — использовать
утверждённый компонент, контракт и стили строго по гайдлайну.
Если обнаружен новый элемент, предполагающий повторное использование на разных
экранах, — сначала согласовать его с пользователем, затем дополнить гайдлайн и
каталог, и только потом внедрять в реальные страницы.

## План фиксации правила

1. В [CaseRule15](../../../specification/agent-rules.md) закрепить обязательное
   обнаружение существующего паттерна перед разработкой UI, запрет тихих
   визуальных расхождений и порядок согласования расширения системы.
2. В [start_here](../../start_here.md) добавить конкретный preflight/DoD для
   каждой UI-задачи и ссылку на первоисточник.
3. В [гайдлайне](../../../specification/ui-design-system.md) описать процедуру
   изменения/дополнения компонентного контракта **без изменения принятой версии
   1.0 и её визуальных параметров задним числом**.
4. В [протоколе приёмки](../../../tasks/139/visual-review.md) предусмотреть
   проверяемое свидетельство соответствия: секция гайдлайна, эталонный
   образец или согласованное добавление с версией и результатом review.
5. Обновить [реестр задач](../../tasks.md) и [прогресс](../../progress.md).

## Критерии готовности

- Каждый новый UI-запрос проходит поиск по гайдлайну, каталогу и общим компонентам
  **до написания разметки и CSS**.
- Существующий паттерн используется без дублирования и локальных вариаций
  размеров, токенов, отступов, состояния или поведения.
- Новый многократно используемый элемент не появляется в продуктовой странице
  до явного согласования API/вариантов, доступности, responsive-поведения и
  визуального образца; принятый вариант отражается в документации.
- Для реально одноразовой композиции разрешена локальная разметка, но её базовые
  примитивы всё равно берутся из утверждённой системы; при повторном применении
  требуется нормализация в общий компонент.
- Отклонения и отсутствие нужного компонента — явный блокер/предмет обсуждения,
  а не повод молча создавать почти идентичный CSS-класс.
- Никаких коммитов и push без отдельной команды пользователя.

## Причина

При проверке [008 — авторизация](../008/description.md) обнаружилось, что
select в регистрации использовал браузерную стрелку вместо уже принятого
`.select-control` и Tabler chevron. Новое правило должно предотвращать
подобное повторение.
