# Wizard 1.1 — принятый визуальный контракт, реализация в планах

**Задача:** [010](description.md) · **База:** [принятая дизайн-система 1.0](../../../specification/ui-design-system.md) · **Образец:** [wizard-proposal.html](../../../../resources/themes/mskba_app/catalog/wizard-proposal.html).

**Визуальный образец принят пользователем 2026-10-08** («да, выглядит супер — принимается»), включая анимацию кнопки. Общий контракт перенесён в [ревизию Wizard 1.1](../../../specification/ui-design-system.md#wizard-11--принятый-визуальный-контракт). Этот документ остаётся детальной спецификацией для будущей Vue-реализации; часть технических API/props в примерах — предложения и ещё подлежат проверке реализации. Принятый эталон 1.0 не изменён.

## Концепция

- Универсальный `WizardShell` для сценариев регистрации, создания/редактирования сущностей и других форм; контент через Vue slots/step components, **не** прямое копирование static demo JS.
- Источник истины — конфигурация шагов + единый реактивный объект данных; порядок и видимость шагов определяются вычислением на каждом изменении зависимых полей.
- Единое отображение: компактный eyebrow «РЕГИСТРАЦИЯ» из гайдлайна 1.0, «Шаг X / N», линия прогресса, **один** смысловой заголовок активного шага, опциональная общая подсказка, контент, фиксированный по структуре футер.
- Общие подсказки `step.hint` показываются над всеми полями текущего шага в спокойной информационной поверхности с акцентной полосой. Подсказки полей `field.hint` — только если добавляют **новую, относящуюся к этому полю информацию**; иначе не дублировать общее пояснение шага. Пример: на шаге «О себе» удалена повторная подпись под датой рождения; подсказка шага сверху осталась. Полевые уточнения оформлять `.helper` и `aria-describedby`. Подсказка к варианту/опции — текст внутри card/radio или раскрываемая с помощью утверждённой tooltip-механики. Новые варианты тултипов без отдельного согласования не создавать.
- Внедряемый вариант Wizard должен использовать общие `select-control`, `field-group`, `check-label`, ошибки и кнопки из гайдлайна 1.0 без дублирования. Статический образец сейчас использует локальную визуальную оболочку только для review.
- **Обязательные поля:** не отображать постоянную общую подпись в footer.
  Визуально звёздочка `*` должна идти в той же строке, что и
  слово/фраза label. Звёздочка декоративна (`aria-hidden=true`),
  без отдельного `tabindex`. Весь родительский `label` —
  tooltip-trigger, а не вложенный `span`. Hover по всей подписи,
  click/tap, Escape (даже когда курсор остаётся на label),
  закрытие кликом снаружи. **Сам label не имеет `tabindex` и
  оранжевой focus-рамки**: при Tab переход идёт к самому `input` /
  `checkbox` и ссылкам, а не к названию поля. HTML-input по-прежнему `required`,
  сообщения об ошибках выводятся под полями.

## Выбор роли: группировка опций (уточнение 2026-10-08)

- В начале раскрыта **«Основные»**: `player` (Игрок), `coach`
  (Тренер), `referee` (Судья), `venue_related` (Представитель площадки).
- Вторая группа **«Другие»**: `media` (**«Медиа (блогер)»**),
  `statistician` (Статист), `organizer` (Организатор мероприятий).
- **Отдельной опции `later` нет.** Исходное состояние — без выбранной
  роли, основная кнопка «Пропустить», при отправке `role=null`. Пустой
  выбор в radio group допустим и не считается ошибкой.
- По умолчанию «Основные» раскрыта, «Другие» закрыта. Открытие одной
  закрывает другую и не сбрасывает выбор. **При выборе роли обе группы
  схлопываются**, в заголовке выбранной — «Выбрано: …» и отдельная
  кнопка ×. Крестик снимает роль, раскрывает её группу и возвращает
  кнопку «Пропустить». После выбора кнопка автоматически **«Далее»**.
  В прототипе использованы семантические `details/summary`, единая
  радиогруппа `name="role"` и иконка `chevron-down` из пакета.
  Уточнение: **текст выбранной роли и кнопка × идут рядом (gap 6 px)** в
  отдельном от `summary` flex-блоке: сброс не переключает accordion.
  Длинное название усекается визуально, полное значение доступно
  в aria-label.
- Общая подсказка: «Вы можете выбрать роль сразу и в будущем её
  изменить или добавить новую.» Возможность **изменить/добавить**
  роль после регистрации — обещание интерфейса, требующее поддержки
  существующего сценария управления ролями.
- Это специализация содержимого шага регистрации, а не требование
  включать такое деление в универсальный `WizardShell`.

## Конфигурация (предложение)

```js
const registrationWizard = {
  id: 'registration',
  labels: {
    back: 'Назад',
    next: 'Далее',
    skip: 'Пропустить',
    submit: 'Создать аккаунт',
    busy: 'Создаём аккаунт…',
  },
  steps: [
    { id: 'role', title: 'Кем вы хотите быть?', hint: '...', fields: ['role'], required: [], visibleWhen: () => true },
    { id: 'person', title: 'О себе', hint: '...', fields: ['gender', 'birth_date'], required: [], visibleWhen: data => data.role === 'player' },
    { id: 'sport', title: 'Спортивные характеристики', hint: '...', fields: ['height_cm', 'weight_kg', 'position', 'body_type', 'experience_started_year'], required: [], visibleWhen: data => data.role === 'player' },
    { id: 'name', title: 'Как к вам обращаться?', fields: ['last_name', 'first_name', 'middle_name'], required: [], visibleWhen: () => true },
    { id: 'account', title: 'Создайте аккаунт', fields: ['username','password','password_confirmation','privacy_consent'],
      required: ['username','password','password_confirmation','privacy_consent'], visibleWhen: () => true },
  ],
  validateStep: async ({ step, data }) => ({ ok: true, errors: {} }),
  submit: async data => ({}),
};
```

В реальном компоненте список обязательных полей должен задаваться либо на уровне шагов, либо в едином field-schema со ссылкой из шага; **не** дублировать правила по нескольким объектам. Server FormRequest — окончательный источник ограничений.

## Кнопки и валидация

| Ситуация | Основная кнопка | Действие |
| --- | --- | --- |
| Все поля шага необязательны и **пусты** | **Пропустить** | Переход без заполнения; введённые ранее значения других шагов сохраняются. |
| Все поля шага необязательны, но **хотя бы одно заполнено** | **Далее** | Проверяется корректность всех заполненных значений, пустые необязательные допускаются. Очистка возвращает «Пропустить». |
| Есть хотя бы одно обязательное поле | **Далее** | Проверяется заполненность обязательных и корректность всех заполненных полей независимо от состояния формы. |
| Последний шаг / submit | **Создать аккаунт** | Проверяется вся форма, отправляется один POST, блокируется повторная отправка; spinner/busy из системы. |
| Любой шаг, кроме первого | **Назад** | Не валидирует, ничего не очищает, возвращает на предыдущий **видимый** шаг. |

**Это единое правило для всех шагов Wizard**, без специальных исключений для выбора роли: кнопка вычисляется из `required`, текущих значений и признака финального шага; обновляется немедленно при `input` и `change`, при Back/Forward, сбросе и смене роли. Пустое необязательное значение не блокирует переход. Непустое, но некорректное поле нельзя «пропустить» — выводится ошибка под полем и устанавливается фокус. Все введённые данные сохраняются при навигации.

- Front-end step validation выполняется до перехода. Ошибка показывается **под конкретным полем**, поле получает `aria-invalid=true`, текст включается в `aria-describedby`, устанавливается фокус и прокрутка до поля; пользователь остаётся на нужном шаге.
- Backend 422 / ошибки доменного валидатора разбираются как `{ errors: { field: [message] } }`; `field -> stepId` выводится из конфигурации. При ошибке с другого шага wizard **переходит на него**, показывает ошибку под полем, устанавливает фокус. Ошибки невалидных невидимых веток не должны появляться после смены роли.
- Обязательное согласие на обработку данных не пропускается; пол и дата рождения являются необязательными только на стадии регистрации (это не меняет требований для подтверждения аккаунта позже).
- Skip не должен скрыто очищать уже введённые данные, Back/Forward сохраняют введённое в общей реактивной модели. Смена роли пересчитывает ветку, а значения невидимых веток **не отправляются**. Пароль не сохраняется в persistent storage.

## Жизненный цикл ошибок при отправке — принято 2026-10-08

- **422 с `errors[field]`:** `WizardShell` показывает ошибку под
  конкретным полем, при необходимости переводит пользователя на
  соответствующий видимый шаг и ставит фокус. Back/Forward не стирают
  ошибку, пока **значение поля не изменено**. При изменении поля
  удаляется только его ошибка; другие остаются.
- **5xx, 503, 419, 429, отсутствие сети и прочие ошибки попытки:**
  текст системного уведомления не связан с данными формы. После
  `Назад` он исчезает и не появляется при возвращении через `Далее`.
  Новый POST очищает предыдущее уведомление; при неуспехе показывает
  уже новый результат. Данные полей и пароли в памяти Wizard сохраняются.
- **Безопасность:** не использовать `result.message` для 5xx и
  прочих неожиданных ответов; никогда не показывать пользователю
  SQLSTATE, запросы PostgreSQL, внутренние пути или stacktrace.
  Для пользователя — короткая нейтральная формулировка.
- Технический контракт: `WizardShell` отправляет событие
  `step-change` при переходе, `AuthDialog` удаляет только
  `transientMessage`. Ошибки 422 живут отдельно в `issues`
  общего Wizard и сбрасываются по `changed(field)`.

## Backend-ограничение

`RegisterRequest` уже принимает ФИО, пол, дату рождения и роль. Поля `PlayerProfile` при регистрации пока **не поддерживаются**, поэтому задача 010 не считается функционально завершённой без обновления backend: валидировать спортивные поля и атомарно создать player profile внутри транзакции регистрации либо согласовать отдельный безопасный профильный шаг после успешного входа.

## Общая модальная оболочка — правило 011

Новый пользовательский контракт из [задачи 011](../011/description.md) принят как
**универсальная механика для модальных окон**: top layer через `showModal()`,
центрирование по viewport, максимальная высота `90vh / 90dvh`,
header/footer не прокручиваются, body имеет `min-height:0; overflow-y:auto`
и тематический `.mskba-scroll`. Прототип применяет размер и прокрутку,
но остаётся самостоятельной демонстрационной страницей, не настоящим popup.
Реализация Vue Wizard после визуального одобрения должна использовать общий
`css/modal.css` и не создавать отдельные z-index/modal размеры.

## Опциональная анимация внимания — предложено для Wizard UI

В legacy-мастерах главной страницы уже реализован паттерн
`home-flow-next-pulse / home-flow-next-shine`:
краткое увеличение кнопки (до 110%) с диагональным бликом за 700 мс.
По просьбе пользователя эффект добавлен **только в каталоговый прототип**,
как предложение общей конфигурируемой реакции
`attentionOnChoice` (точный prop будущего Vue-компонента на согласовании).

- Уточнение после переноса в Vue: запускать только при
  **«Пропустить» → «Далее» в текущем шаге**. Изменения
  уже выбранной роли или других заполненных значений
  не запускают/перезапускают анимацию, как и Back/Forward.
- CSS: `is-choice-attention`, отдельный псевдоэлемент блика,
  **500ms ease-in-out**, масштаб **1.06 до 480px**,
  **1.07 выше**. Исходный legacy scale 1.10 не использовать,
  чтобы кнопки не пересекались.
- При возвращении к «Пропустить» следующее первое заполнение
  вновь допускает эффект. `prefers-reduced-motion: reduce`
  полностью отключает анимацию.
  Декоративность не должна влиять на доступность/валидацию/disabled.
- При переносе в Vue использовать явные события и реактивное состояние,
  **не** jQuery/MutationObserver из старой темы; перенос в гайдлайн
  разрешён только после визуальной приёмки.
