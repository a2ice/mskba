# 337 — Event-first воронка площадки и мероприятий

**Согласование:** 19.11.2026. Полное бизнес-ТЗ, состояния, ограничения и production-checklist: [docs/tasks/337/description.md](../../../../tasks/337/description.md).

## UI contract

- Тип мероприятия «Игра» не требует вложенной Game. Чекбокс «Создать игру внутри мероприятия» включён по умолчанию; при снятии создаётся только Event, игру можно добавить позднее. Полную ревизию Game провести отдельно.

- Hero площадки: только «Хочу здесь играть» и «В избранное»; галерея mouse drag, touch swipe, клавиатура, кликабельные превью.
- «Хочу здесь играть» — единый многошаговый попап: список ближайших публичных мероприятий (empty-state, кнопка создать всегда), подробный экран мероприятия, участники/аватары/организатор, действия «Пойду», «Подумаю», «Не пойду», системная лента и сообщения.
- «В избранное» — немедленное добавление + информационный попап; при удалении только фирменный подтверждающий попап. Смена текста на «В избранном», состояния синхронизируются.
- Трёхшаговый мастер создания в обеих темах: тип/автозаголовок/площадка/параметры → необязательное расписание, выбор нескольких пожеланий → подтверждение. Отдельные режимы «варианты одного мероприятия» / «несколько самостоятельных мероприятий». До авторизации пользователь не теряет форму; инфопопап перед auth.
- Чётко отделяем предзаявку от бронирования: UI не пишет «забронировано», не скрывает занятые слоты, показывает неполученное подтверждение. Прямая аренда — из расписания.
- UX-инварианты: backdrop закрывается только после pointerdown+pointerup на backdrop; Escape допускается; клавиша Enter валидирует поле и переводит фокус; инлайн ошибки, сброс при input; несохранённые данные и текущий шаг сохраняем на странице. Ссылки и кнопки не перегружают экран. Обязательна проверка мобильного экрана.

**Согласование в логике создания не означает подтверждение арендного слота.** Уведомления по PlayIntent остаются обязательной частью релиза.


## Визуальная приёмка площадок — корректировки 19.11.2026 (PR #856)

Эталон: `docs/specification/ui-design-system.md` (Modal 1.1 и drag handle); существующие `.mskba-modal`, `.icon-button`, `.app-venue-overlay`, `modal-dragging.js`, `css/modal.css`. Новых независимых модальных систем и нестандартных скелетонов не вводить.

- Попап аренды: единый крестик 44×44 и центрированная иконка захвата; поля и кнопка разделены отступом. При ровно одном доступном зале сразу открывать штатный календарь, при нескольких — оставлять выбор зала; API бронирования без изменений.
- Загрузка календаря: показывать существующий скелетон UI Kit (класс `.skeleton` и те же дизайн-токены), `aria-busy` на области слотов, саму декоративную заглушку скрывать от ассистивных технологий. Ошибку отображать текстом, без зависшего скелетона.
- Избранное: для обоих сценариев заголовок «Избранное»; после добавления основное сообщение «Площадка добавлена в избранное.», одна кнопка «Понятно». При удалении вопрос «Вы уверены, что хотите убрать площадку из избранного?» и единственная кнопка «Убрать»; отмена — закрытие крестиком/Escape. Стандартный drag handle и close.
- «Хочу здесь играть»: без eyebrow, вступления и заголовка «Текущие мероприятия»; оставить пустое состояние или карточки и кнопку «Создать мероприятие». Детальный экран карточки/RSVP сохраняет существующее поведение.
- Оба оформления (mskba_app и mskba_dark) сохраняют корректную поверхность/фон; общая библиотека popup drag применяется без собственного контроллера. После CI требуется ручная мобильная приёмка.


## Повторная приёмка заголовков, контента и форм (19.11.2026)

Эталон: [MSKBA UI Design System](../../../specification/ui-design-system.md), секции Modal 1.1, Native Select, Form Controls, и реальный UI Kit `resources/views/design-themes/ui-kit.blade.php`.

- **«Хочу здесь играть» — начальный экран**: только заголовок, список кликабельных карточек предстоящих мероприятий **или** текст «На этой площадке пока нет предстоящих мероприятий.», и закреплённая нижняя кнопка «Создать мероприятие». Ни eyebrow, ни вводного абзаца, ни подзаголовка «Текущие мероприятия». **Нажатие карточки открывает ВНУТРИ ЭТОГО ЖЕ попапа второй экран** с описанием, организатором, участниками, действиями «Пойду / Подумаю / Не пойду», обсуждениями/сообщениями и возвратом «Назад к мероприятиям». Карточка не должна вести на отдельную страницу вместо этого экрана. При переходе на второй экран скрывается только первый список с кнопкой создания, бизнес-логика Event и auth-resume сохраняются.
- **Добавление и удаление избранного**: единый заголовок «Избранное». После добавления вместо старого побуждения основной текст «Площадка добавлена в избранное.» и единственная кнопка «Понятно». При удалении только вопрос «Вы уверены, что хотите убрать площадку из избранного?» и одна кнопка «Убрать»; отмена — крестик/Escape.
- **Аренда**: при ровно одном зале нет отдельного шага выбора — сразу существующее расписание; при нескольких — корректный стандартный `.field-group` с семантическим `label`, native `select`, оболочкой `.select-control` и фирменным Tabler `#chevron-down` (20 px). Валидация обязательного выбора: `aria-invalid`, текст ошибки. Между селектом и кнопкой достаточно места.
- **Визард создания мероприятия** и диалог авторизации: единая оболочка `.mskba-modal`, `header/body/footer`, стандартная 44×44 кнопка закрытия с Tabler glyph, одна иконка перетаскивания, центрирование и не более 90dvh. Body — единственная прокручиваемая часть, footer не исчезает при скролле. Поля и оставшиеся native select (поле площадки заменено на предиктивный ввод) соответствуют 48 px/12 px, шрифт 16/24, стрелка `#chevron-down`; не возвращать 43 px/8 px и системную стрелку без правильного контрола.
- **Обе темы** используют общую бизнес-логику; тон и оформление тем остаются своими. Перетаскивание управляется `modal-dragging.js`, без второго движка; закрытие кликом по фону только при pointerdown+pointerup на фоне.
- **Тесты**: проверка rendered Blade, контента, native-селектов и аренды одного/нескольких залов. PHPUnit/Node/CI не заменяет визуальную проверку на опубликованном сайте.

## Корректировки приёмки 19.11.2026 — избранное, поиск, география, legacy-type

- **Избранное:** для добавления и удаления заголовок **«Избранное»**. После добавления текст «Площадка добавлена в избранное.»; после удаления вопрос подтверждения. Только одно основное действие на каждом экране.
- **Первый шаг создания Event:** выбор площадки не select, а фирменный поиск с вводом названия/адреса/метро через существующий `venues.search`, выпадающим списком, очисткой и валидацией выбора из результатов; ссылка **«На карте»** под полем. Карта — MSKBA modal + Yandex Maps + существующий `venuePlacemark` и выбор по клику на точку. Выбор с карты обновляет то же поле `venue_id` и залы без потери введённых данных.
- **Автозаголовок:** до ручного редактирования динамически зависит от типа и ближайшей привязанной станции метро, иначе от адресной улицы; пример «Игра на м. Селигерская», «Тренировка на ул. Керамический проезд». После ручной правки автозамена прекращается.
- **Устаревший `game_training`:** оставляем enum и старые строки, исторические страницы, связи и поиск при «Все». Из нового UI (первый шаг, старые визарды, меню, фильтры, главная) исключаем тип; новые создания через HTTP валидируются только `EventTypeEnum::creatableValues()`. Не путать скрытие варианта в фильтрах с удалением таких мероприятий из выдачи без фильтра.
- Ручная мобильная приёмка после CI обязательна; скрипты и цвета должны работать в обеих темах.


## Визуальная приёмка карты площадок — двухэтапный выбор и позиция пользователя (19.11.2026)

- Краткая инструкция непосредственно над картой: **«Нажмите на площадку на карте.»** — без упоминания технических фирменных точек.
- **Нажатие на маркер не меняет форму**: сначала в пределах того же модального окна открывается информационная карточка площадки по образцу главной (название, адрес, привязанное метро, бесплатные/платные залы и подтверждение при наличии данных). Карточка закрывается отдельно, не закрывая карту. Только действие **«Выбрать»** меняет `venue_id`, обновляет связанные поля визарда и закрывает карту. Список площадок без координат подчиняется тому же правилу подтверждения.
- При открытии карты в защищённом браузерном контексте ненавязчиво запрашивается геолокация через стандартное браузерное разрешение. При успешном ответе на карту добавляется **отличающийся синий маркер «Вы здесь»**, под картой появляется кнопка **«Рядом со мной»**. При отказе, отсутствии API или тайм-ауте карта продолжает работать без этой опции. Местоположение не записывается в БД, сессию или localStorage и не передаётся в запросы поиска площадок.
- **«Рядом со мной»**: вычислить 5 ближайших из загруженных подтверждённых площадок с координатами; карта показывает пользователя и эти точки, сохраняя положение пользователя географическим центром области. `zoomMargin=48px` = 28px габарит фирменного маркера + не менее 20px свободного края. Кнопка меняется на **«Показать все»** с `aria-pressed=true`.
- **«Показать все»**: восстановить исходные границы общего обзора площадок, вернуть текст кнопки «Рядом со мной» и `aria-pressed=false`; выбранное в информационной карточке мероприятие и данные визарда не затрагиваются.
- Геолокационный запрос привязан к конкретному открытию карты: запоздавший ответ после закрытия не создаёт маркер и не изменяет состояние следующего открытия. Карта и кнопки действуют в обеих темах и на мобильных экранах.


## Общая карточка площадки на карте (визуальная приёмка 19.11.2026)

- **Единый рендерер и разметка**: `resources/js/components/venue-map-info-card.js` — `renderVenueMapInfoCard(venue, options)`. Общий стиль `resources/css/venue-map-info-card.css` подключается Page Builder и обеими темами. Контент совпадает с карточкой главной: фото (или штатная заглушка), название, адрес, признаки бесплатных/платных залов, условия доступа, покрытие/удобства если доступны, ссылка «Подробнее».
- **Карта главной страницы**: опубликованный в БД JavaScript компонента Page Builder не перезаписываем и не меняем текущую логику активного маркера/закрытия. `resources/js/page-builder.js` подключает `attachSharedHomeVenueCards`, который заменяет DOM карточки общим компонентом после открытия маркера и делегирует закрытие исходному контроллеру. При дальнейшей ревизии editor-owned JS можно убрать дублированный legacy `makeCard` только отдельной версионированной публикацией.
- **Карта в быстром визарде**: то же `renderVenueMapInfoCard` в компактном режиме `compact:true` с уменьшением **всех размеров текста до 90%**. Отдельный eyebrow «Площадка MSKBA» не показывать. Вместо мгновенного выбора — карта → карточка → «Выбрать»; ссылка «Подробнее» сохраняется. Данные поиска `/venues/search` обогащаются медиа и деталями по существующему `preview_url` непосредственно после открытия карточки. Устаревшие ответы игнорируются; при отказе API базовая карточка остаётся видимой.
- **Единое место для изменений**: визуал и набор контента редактировать **только** в общем рендерере и CSS, а не отдельно в двух картах. Различия допускаются только в интерфейсе действий (главная — «Подробнее», визард — «Подробнее» + «Выбрать») и коэффициенте компактности. В обеих темах проверить фото/заглушку, маркеры, действия и прокрутку на мобильном экране.


## Дополнительная приёмка UX карты и фотографий (19.11.2026)

- На обычных картах каталога, поиска, выбора площадки и прочих модулей на тачскрине вновь доступно перетаскивание **одним пальцем**; масштабирование двумя пальцами остаётся доступным. Блокировка колеса мыши без Ctrl/Cmd не меняется.
- Специальный кооперативный режим включается только явно через `data-map-touch-mode="cooperative"`. Карта **секции главной страницы** сохраняет управление двумя пальцами; CMS Page Builder-карта главной сохраняет существующий локальный запрет однопальцевого drag. Для намеренно неподвижной карты предусмотрен `data-map-touch-mode="static"`.
- Общая карточка площадки показывает **loading layer** при наличии URL фото до завершения загрузки изображения, а при запросе подробностей без заранее известного URL — до ответа preview API. Фраза «Фото площадки пока нет» используется только когда проверено отсутствие фотографии или произошла ошибка, а не во время ожидания.
- Использовать штатный UI Kit spinner `image-upload-loading__spinner` вместо добавления собственного GIF/нового лоадера (см. `docs/specification/ui-design-system.md`).
- Результат preview API и реальный DOM карточки с уже загруженным `img` кешируются в рамках открытой страницы. Закрытие не должно требовать повторного сетевого запроса на preview или новой загрузки изображения при возврате к той же площадке. При ошибке API убрать вечный loader и дать повторить запрос.
- Модульные проверки находятся в `tests/JavaScript/venue-day-booking.test.mjs`; оба оформления используют общую компоненту.

## Мобильная приёмка 20.11.2026

- «Далее» сохраняет заполненный желаемый интервал даже без нажатия «Добавить время». Неполный ввод не пропускается молча; пустой шаг остаётся допустимым. Удаление и возврат назад не создают дубликаты. При автоматическом добавлении второго интервала сначала показываем выбор режима.
- Карточка черновика в обеих темах: внутренние отступы 16–24 px, вертикальная сетка с промежутками, ограничение ширины native datetime-local и select, восстановление значений при ошибке. Проверить iOS Safari и desktop.

## Повторная приёмка карточки мероприятия 20.11.2026

- Заголовок мероприятия первым, ниже тип/дата и «Описание: …», один блок «Участники (N)»/«Участники (N/M)». Между блоками 20 px, список до 200 px с собственным скроллом; строки с gap 10 px, круглым аватаром 30×30 или штатным user-placeholder, зелёной/оранжевой точкой с tooltip статуса и времени решения, nickname/login до 20 символов + многоточие и tooltip полной строки. Организатор всегда первым, с жёлтой звездой; при отказе — красная точка. Соблюдаем приватность.
- «Пойду» и «Подумаю» доступны участнику и организатору; «Не пойду» появляется только при активном ответе. AJAX использует существующий endpoint RSVP, серверный снимок roster, штатный spinner и `mskba:action-toast` в top-layer; список после успешного действия показывает актуальный состав и прокручивается к своей строке. Ошибка понятна, без лишней перезагрузки.
- Гость видит информационный popup с одним действием «Войти», затем штатную авторизацию, возврат в тот же Event и продолжение выбранного действия. Полная страница и обсуждение сохранены. Обе темы используют один компонент.

## Участие организатора — уточнение 20.11.2026

- В публичном создании Event галочка «Я буду участвовать в мероприятии» установлена по умолчанию; снятие сохраняет роль организатора и статус left без игрового места. При авторизации значение восстанавливается.
- Организатор может сам выбрать «Пойду», «Подумаю», «Не пойду». Статус меняется независимо от полномочий. Повторное подтверждение проверяет лимит мест. Право обсуждения и управления сохраняется во всех статусах.
- Организатор всегда первый в общем списке, со звездой. При отказе красная точка, tooltip «Не идёт»; в счётчик активных участников не входит. Другие отказавшиеся скрыты. Миграция схемы для этого не требуется.
