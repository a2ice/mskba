# 029 — Сообщения в sidebar и toast вместо колокольчика

Дата: 2026-10-11. Тема: `mskba_app`. Статус: реализовано локально, ожидаются CI/deploy и визуальная приёмка.

## Решение

- Убираем отдельную иконку-колокольчик **из шапки**: она дублирует оранжевый непрочитанный индикатор на аватаре. Ссылка на кабинет по логину и аватару остаётся. Мобильная навигация оставляет переход в раздел сообщений, но использует иконку сообщения вместо колокольчика.
- Только в `mskba_app` пункт **«Уведомления»** в sidebar (desktop/mobile) переименовывается в **«Сообщения»**. Сохраняем текущий route `account.notifications`, счётчик и Reverb-интеграцию, чтобы не ломать существующие адреса и бизнес-логику. Названия, маршруты и внешний вид `mskba_dark`/production остаются прежними. Саму страницу сообщений реализуем **следующей отдельной задачей**, здесь её не переделываем.
- Если у авторизованного пользователя есть непрочитанные сообщения, на каждой открытой странице `mskba_app` отображаются отдельные постоянные toast — **один на каждую непрочитанную запись**, с заголовком, текстом и (если есть) безопасной внутренней ссылкой-действием. Нет скрытого лимита числа toast; чтобы не закрывать весь интерфейс, все карточки находятся в компактной фиксированной вертикально прокручиваемой области.
- Toast не исчезает по таймеру, чтобы счётчик и список не расходились. Крестик на карточке означает **«Отметить сообщение прочитанным»**: он отправляет `PATCH` на существующий route с CSRF, затем удаляет карточку и обновляет число на аватаре и в sidebar. Ошибка сети/сервера оставляет toast на экране с сообщением об ошибке. Когда все сообщения прочитаны, область toast скрыта, как и бейдж аватара.

## Источники данных / защита

- Единственный серверный источник — действующие `ListNewUserNotificationsHandler` + `UserNotificationPresenter` и `CountNewUserNotificationsHandler`. У API `/account/notifications/new` добавлена безопасная курсорная пагинация `before_id` по `id` с размером страницы 20 и `next_before_id`, чтобы список toast соответствовал полному unread count, а не только первой двадцатке. Авторизация и отбор canonical identity сохраняются.
- Клиент использует **общий** `notification-counts.js`: серверная синхронизация заполняет все toast; realtime `.notification.created` сразу добавляет новую карточку; `.notification.count-updated` синхронизирует прочитанные записи; повторные события и рефетчи дедуплицируются по ID. При возврате на вкладку/восстановлении связи данные синхронизируются заново; устаревшие ответы не переопределяют новые события.
- Для безопасности заголовки и тела toast всегда вставляются через `textContent`. Внешние / `javascript:` ссылки из payload не выводятся. События и данные других пользователей остаются недоступны за счёт existing private channel и user-scoped query. Не создаём новые БД-таблицы, Composer-зависимости или службы.
- Разметка использует согласованный `.toast` из design system; её список адаптивен (scrollable, mobile safe area). При появлении push новое сообщение добавляется сверху. При загрузке 23 unread сервер отдаёт страницы 20+3.
