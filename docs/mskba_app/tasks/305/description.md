# Task 305 — индивидуальные краткое и полное описания залов

## Цель
Описание площадки не должно ошибочно характеризовать другой её зал. Пример: школа №1794 имеет уличный корт и крытый школьный зал, которым нужны самостоятельные тексты.

## Модель и наследование
- `Venue.short_description` / `Venue.full_description` остаются описаниями всего комплекса.
- `VenueCourt.short_description` и `full_description` — nullable. При `NULL` выбранного поля на странице конкретного зала показывается соответствующее родительское значение.
- На обзорной странице независимо от количества залов используется только `Venue`; данные не копируются при миграции.
- В формах редактирования отсутствие полей при совместимых API-запросах не затирает сохранённые локальные описания.

## UI Kit / интерфейс
- Filament, существующая модалка «Редактировать зал» → вкладка «Игровая зона» → секция «Описание игровой зоны» с полями «Краткое описание» (3 строки) и «Полное описание» (6 строк).
- Стандартные Filament Textarea, Tabs, Section; не вводить новые CSS, цвета, шрифты, модальные окна или декоративные подсказки. Использовать существующий раздел / гайдлайн `docs/specification/ui-design-system.md`.
- В редакторах `mskba_app` и `mskba_dark` те же два поля через существующие стили `field-group` / `form-control`, без переопределения UI Kit.
- Страница зала использует существующие блоки intro и «О зале / О корте»; тексты выбирает backend DTO. В шапке название зала остается только в селекторе (см. PR #623).

## Проверки
- Общая страница школы показывает только общий текст.
- Уличный корт показывает свой текст, крытый зал — свой.
- Пустое значение наследует соответствующее описание отдельно.
- Создание/изменение через account / Filament сохраняет описания.
- Поля валидируются и HTML выводится экранированным; миграция PG16/17; desktop/mobile QA и CI.

Миграция без backfill и без изменения production до DEV-приёмки.
