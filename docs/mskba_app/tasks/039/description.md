# 039 — QA entry для личных сообщений и проверки чёрного списка

**Статус:** сценарий принят локально (2026-10-13); в `dev` передан вместе с задачей 042.

## Продуктовое ограничение

MSKBA — не универсальный мессенджер. Основной механизм общения запускается из **контекста игры, команды, приглашения, заявки, мероприятия** или другого рабочего процесса. Возможность начать произвольный direct-чат из раздела «Сообщения» — **временный тестовый интерфейс** для ручной проверки чёрного списка, Reverb и приватности. Не добавлять глобальные кнопки «Написать» в публичные профили, поиск участников или постоянные меню без отдельного продуктового решения.

## Реализация тестового сценария

1. `Сообщения` → «Новое сообщение · тест» (в интро-плашке рядом с «Написать в техподдержку») → модальное окно принятого дизайн-гайдлайна. Поиск по имени/логину после 2 символов с задержкой 240 мс, не больше 10 результатов. Показываются действующие аккаунты с разрешённой видимостью профиля, обнаружением в поиске и правом получать сообщения от текущего пользователя. **Подтверждение аккаунта не требуется** ни от отправителя, ни от получателя. Заблокированные в любую сторону контакты не предлагаются. Контроль повторяется на сервере при отправке.
2. Используется существующий `direct-message-dialog`, `DirectMessagesController::access`, `DirectMessagesController::send`, существующий direct-тред и персональные Reverb-события. Не создавать вторую таблицу сообщений/права. При выборе адресата происходит проверка доступа, затем вводится **первое** сообщение. Только отправка создаёт `direct_conversation`. После POST 201 интерфейс переходит в существующий чат с меню «Заблокировать пользователя» / «Разблокировать пользователя»; старые сообщения остаются доступны.
3. Feature gate: `config('features.direct_messages.test_entry')` через `FEATURE_DIRECT_MESSAGE_TEST_ENTRY`. По умолчанию включён только при `APP_URL` с host `localhost`, `127.0.0.1`, `dev.mskba.ru`. Для production (`mskba.ru`) выключен. Gate на UI и endpoint, throttling поиска `30/мин`, длина запроса `2..60`, HTML не строится из внешних строк.
4. Для тестов: получатель должен разрешить **«Кто может писать мне сообщения»**, а также иметь видимый профиль и быть доступным для обнаружения в поиске. Подтверждение аккаунта не требуется; заблокированные аккаунты по-прежнему исключены. Поиск не обходит `SearchDiscoverableUsers`, blacklist не даёт писать в обе стороны.

## Проверки

- Feature: скрытый тестовый вход при отключённом флаге; закрытый endpoint; серверная фильтрация доступных получателей; отсутствующие пустые чаты; создание при первой отправке; блокировка обоих направлений, разблокировка, исчезновение из поиска при выключении приватности.
- `node --check`, Blade compile, Vite build и визуальный smoke по принятому CSS. Остальные незавершённые изменения аккаунта/контактов остаются отдельно.
- **Историческая оговорка:** до явной команды deploy был запрещён; 2026-10-13 пользователь разрешил commit и push в `dev`.

## Связанные вопросы

- Управление своим чёрным списком через `Аккаунт → Настройки → Приватность` — отдельная будущая задача. Личные блокировки не запрещают официальный обмен в тредах заявок и обращений техподдержки.
- Контекстный запуск чата из команды, игры, события/площадки — самостоятельный этап с отдельной бизнес-авторизацией на создание переписки, без глобального user directory.
- Вложения сущностей шорткодами — технический долг [040](../040/description.md).

## Уточнение политики подтверждения (2026-10-13)

В тестовом поиске **снят фильтр `UserStatusEnum::CONFIRMED`**. Это согласуется с уже существующим direct-сервисом: отправка проверяет статус блокировки, разрешение получателя на сообщения и личный чёрный список, **не** требует подтверждённого аккаунта. Тест дополнен сценарием `unconfirmed → unconfirmed` с поиском, проверкой `access` и успешной отправкой. Для появления в поиске всё ещё необходимы приватность профиля, DISCOVERABILITY, разрешённый MESSAGES и завершённые требуемые настройки распространения данных.
