# 008 — Попап авторизации MSKBA App

**Статус:** На проверке · **Дата:** 2026-10-08 · **Зависит от:** [003](../003/description.md).

## Цель

Сделать доступную из header авторизацию, регистрацию и восстановление в одном адаптивном попапе, используя существующие Laravel endpoints и контракты Identity без переноса legacy jQuery-кода.

## Реализовано локально

- Vue-компонент `resources/themes/mskba_app/js/components/AuthDialog.vue`, отдельный `css/auth-dialog.css` и Blade mount `views/partials/auth-dialog-root.blade.php`.
- Общий `js/app.js` монтирует Vue-попап поверх Blade layout, включая тестовую Inertia-страницу. Header `Войти` (desktop/mobile) открывает его без перехода на fallback.
- GET `/login` и `/register` содержат полноценную Blade-оболочку с автоматическим открытием соответствующей вкладки; работают и как резервные URL.
- Вход: подтверждённый контакт/логин, пароль, remember; регистрация: username/password/confirmation, optional participation role, обязательное согласие; восстановление: email и **честное сообщение о 503**, без ложного успеха.
- POST через существующие `auth.login`, `auth.register`, `auth.restore` с session cookies, CSRF и `Accept: application/json`; отображаются ошибки валидации, 401, 422, 419, 429, 503/сетевая ошибка. Кнопка disabled во время запроса.
- После успешного ответа переход только на возвращённый бэкендом same-origin `redirect_url`. При закрытии восстанавливается фокус, реализованы backdrop, Escape, Tab trap, блокировка прокрутки и mobile layout.
- VK/Telegram предлагаются только при наличии настроенных провайдеров: VK использует существующий redirect route, Telegram — официальный widget и текущий `auth.telegram`.
- Поскольку юридические Blade-страницы новой темы ещё не перенесены, **в локальном режиме** ссылки из регистрации ведут на актуальные опубликованные документы `https://mskba.ru/privacy` и `https://mskba.ru/personal-data-consent` (оба HTTP 200). Нельзя до выпуска переключать тему production без переноса юридических страниц.

## Замечания при визуальной приёмке — 2026-10-08

- В регистрации native select «Роль в баскетболе» выглядит не как принятый эталон: системная стрелка вместо Tabler chevron-down, отличающиеся inset и фокус. **Исправление внутри 008**, переиспользовать существующий `.select-control` из `design-system.css`, список оставить нативным.
- Chrome предлагает сохранённые пароли поверх поля регистрации. Плавающий блок визуально уже самого input, хотя поле имеет полную ширину; это **встроенный интерфейс браузера/менеджера паролей**, его геометрия не контролируется CSS страницы. Не ломать стандартные `autocomplete=username/new-password` или менеджеры паролей ради косметического эффекта. Проверить реальные размеры и стили input, выровнять поля с гайдлайном, не обещать изменение popup Chrome.
- **Исправлено локально:** регистрация использует общий `.select-control` из эталона (Tabler `#chevron-down`), нативные options не заменялись; поля получили эталонный внутренний отступ 12 px и line-height 24 px.
- **Проверено Chromium:** 360/440/768/1440 CSS px; input и select имеют идентичную ширину и правую границу, SVG 20×20 расположен ровно в 16 px от правого края; `appearance:none`, `padding-inline-end:48px`; изменение выбранной роли работает, JS-ошибок/горизонтального overflow нет.
- **Chrome autofill:** подтверждено, что парольные поля имеют реальную полную ширину и `autocomplete=new-password`; плавающий менеджер паролей — интерфейс браузера, а не компонент MSKBA. Его ширину и геометрию стилизовать CSS сайта нельзя; не отключаем сохранение паролей.
- **Остаётся на визуальной приёмке:** убедиться по пользовательскому скриншоту, что select совпадает с эталоном и его native popup не вызывает вопросов.

## Доработка компактных заголовков — замечание 2026-10-08

- Пользователь попросил использовать **название формы вместо прежнего eyebrow**:
  «Вход в аккаунт», «Регистрация», «Восстановление доступа», убрать большие
  дублирующие заголовки и маркетинговые описания без функционального смысла.
  Это уточнение **текущей задачи 008**, а не новая независимая задача.
- В `AuthDialog.vue` название формы теперь является `h2#mskba-auth-title`
  с принятыми `.eyebrow.accent` и uppercase. Доступное имя диалога через
  `aria-labelledby` сохранено; удалены прежние kicker/lead.
- В `auth-dialog.css` удалены локальные стили крупных `h2` и lead;
  расстояние до формы — 24 px, используется принятый eyebrow 12/16/700
  из дизайн-системы. Существующий общий компонент **не изменяли**.
- Проверка в Chromium на CSS viewport 360/390/440/768/1440:
  открываются все три режима, заголовок остаётся `H2` (12 px, 16 px
  line-height, акцент `rgb(255,121,0)`), popup помещается при высоте 930 px,
  Escape закрывает его; нет ошибок JS и горизонтального переполнения.
- Статус — **на визуальной проверке** у пользователя; backend и OAuth здесь
  не изменялись.

## Визуальная приёмка — 2026-10-08

- Пользователь подтвердил «всё ок» после показа компактных попапов и дал команду на локальный коммит. Компоновка заголовков и формы **визуально согласована**.
- Функциональное закрытие всей задачи 008 **пока не подтверждено**: успешный вход, завершённая регистрация и внешние OAuth-провайдеры остаются непроверенными; поэтому общий статус «На проверке» сохраняется.

## Выполненные проверки

- Реальный headless Chromium: desktop 1440×900, mobile 440×956 и дополнительные 360×800, 390×844, 768×1024; прямые GET `/login`, `/register`, открытие из header, переключение вход/регистрация, закрытие Escape, отсутствие горизонтального overflow и JS console errors.
- На `/ui-preview` popап работает поверх Inertia; имитация HTTP 419 проверена отдельно (не реальный истёкший CSRF-token).
- Серверный login с заведомо несуществующим пользователем: 401 и понятная ошибка в попапе.
- Невалидная регистрация: 422 и серверная ошибка; аккаунт не создавался.
- Restore: 503 с честным сообщением поддержки.
- Vue/Inertia Preview отрисовался без ошибок; Vite production build успешен.

## Не проверено и блокеры релиза

- **Успешный вход/регистрация с разрешённым тестовым аккаунтом**, подтверждение пользовательского состояния после перенаправления; реальные учетные данные не использовались. После регистрации backend направляет пользователя в `account.privacy.distribution`, а личный кабинет и этот экран в новой теме пока не перенесены, поэтому end-to-end путь **не завершён**.
- **Реальный Telegram/VK OAuth** (домены, Bot API, callbacks, внешняя авторизация) не проверен.
- Матрица 360/390/768/1440, zoom 200%, Safari/WebView, Tab/focus на каждой форме и состояния 419/429/потери сети нуждаются в отдельном review.
- Восстановление доступа отсутствует в текущем бэкенде и в этой задаче не реализовывалось.
- Юридические документы в новой теме остаются неперенесёнными; локальные ссылки на production — временный workaround, не готовность к релизу.
