## Назначение документа

`docs/project.md` фиксирует актуальное продуктовое понимание проекта: что делает система, для кого она создается, какие пользовательские потоки поддерживает и какие решения уже приняты.

Документ обновляется при каждом важном изменении пользовательских сценариев, ролей, бизнес-процессов, правил работы системы или продуктовых решений.

## Общая идея проекта

Проект развивается как веб-система на Laravel с пользовательской частью, авторизацией и личным кабинетом. Подробная продуктовая формулировка будет уточняться по мере развития задач и принятия решений.

## Пользователи и роли

На текущем этапе в системе используется разделение ролей на два уровня:

- системные роли доступа;
- роли участия пользователя в проекте.

Системная роль нужна для глобального уровня доступа в системе. Она может отсутствовать, если у пользователя нет специальных системных полномочий.

Роли участия описывают, в каком качестве пользователь участвует в предметной части проекта. Один и тот же пользователь может иметь несколько ролей участия одновременно.

При появлении новой роли нужно фиксировать:

- кто этот пользователь;
- какие цели он решает в системе;
- какие разделы и действия ему доступны;
- какие ограничения и правила для него действуют.

Подробнее: [Роли пользователей](project/user-roles.md).

## Ключевые пользовательские сценарии

На текущем этапе выделены базовые сценарии:

- просмотр публичной части сайта;
- регистрация пользователя;
- вход пользователя;
- выход из аккаунта;
- переход в личный кабинет авторизованного пользователя.

Сценарии должны описываться простым языком: цель пользователя, стартовая точка, основные шаги, результат и важные ограничения.

## Регистрация и вход

Система содержит базовый пользовательский flow регистрации и входа. Авторизация доступна через отдельные страницы и модальные представления темы.

Подробнее: [Регистрация и вход](project/registration-and-login.md).

## Личный кабинет

Личный кабинет доступен авторизованному пользователю. Его состав и назначение будут расширяться по мере появления пользовательских функций.

При изменении личного кабинета нужно фиксировать, какие данные пользователь видит, какие действия может выполнить и какие состояния интерфейса являются значимыми.

На текущем этапе у каждого зарегистрированного пользователя сразу создается базовый профиль с персональными полями, которые могут быть заполнены позже. Это позволяет развивать личный кабинет вокруг уже существующей структуры профиля, даже если часть данных пока пустая.

## Площадки

В системе появилась базовая предметная область площадок (`Venue`). Площадка описывает место, где можно проводить или искать баскетбольную активность: зал, открытую площадку, школьный спортзал, фитнес-клуб или универсальный спорткомплекс.

На текущем этапе у площадки фиксируются название, уникальный alias, текстовый адрес, тип, статус, набор доступных удобств и ссылка на пользователя, который создал запись. Статус позволяет отделять неподтвержденные площадки от подтвержденных и заблокированных.

Удобства площадки хранятся как список значений из базового справочника: раздевалка, душ, парковка, освещение, места для зрителей, табло и аренда инвентаря.

Внешняя предметная область адресов будет добавлена отдельной задачей. После появления `Address` и `Metro` площадка должна получить нормализованную связь 1-to-1 с адресом.

## Бизнес-процессы

Бизнес-процессы пока не выделены в отдельные устойчивые группы. Каждый новый процесс должен добавляться в этот раздел или в отдельный документ `docs/project/{alias}.md`, если описание становится больше одного короткого блока.

## Продуктовые решения

В этот раздел добавляются принятые решения, которые важны для понимания продукта, но не являются техническими деталями реализации.

Формат записи:

- дата решения;
- краткое описание;
- причина;
- влияние на пользователей или процессы;
- ссылка на задачу, если решение принято в рамках задачи.
