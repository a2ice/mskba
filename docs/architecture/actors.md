# Actor Attribution

## Назначение

Actor - централизованная модель автора действия в системе. Она отвечает на вопрос: "кто или что совершило конкретное действие в момент его выполнения".

Actor не заменяет пользователя, fingerprint, владельца сущности или договорный доступ. Это слой атрибуции действий.

## Продуктовый смысл

MSKBA должен поддерживать низкий порог входа в воронку продукта. Например, человек может добавить площадку без регистрации, а уже потом зарегистрироваться или войти в аккаунт.

Для продукта это означает:

- гость может совершать часть полезных действий без аккаунта;
- система не теряет происхождение этих действий;
- после регистрации можно связать гостевые действия с аккаунтом;
- команда модерации и поддержки видит, откуда пришла заявка;
- будущие security-сценарии могут учитывать браузер, аккаунт и историю действий.

Пример:

```text
Гость добавил площадку
-> created_by_actor_id указывает на actor type=guest, user_id=null, user_fingerprint_id=12

Этот же человек вошел в аккаунт
-> создается actor type=user, user_id=5, user_fingerprint_id=12

Система находит гостевые действия по fingerprint 12 и привязывает их к user 5 через actor_claims
```

## Техническая модель

Основные таблицы:

```text
user_fingerprints
- браузерное/устройственное присутствие;
- не является пользователем;
- может быть связано с несколькими аккаунтами.

user_fingerprint_user
- история связей fingerprint <-> user;
- нужна для аналитики, security и будущего списка устройств.

actors
- централизованный субъект действия;
- хранит type, user_id, user_fingerprint_id;
- имеет уникальный actor_key для стабильного firstOrCreate.

actor_claims
- связь "гостевые действия позже были привязаны к аккаунту";
- не переписывает старый guest actor;
- позволяет пользователю видеть свои гостевые действия с другого устройства после входа в аккаунт.
```

Типы actor:

```text
guest  - действие гостя, есть fingerprint, нет user
user   - действие авторизованного пользователя, может быть fingerprint
system - действие системы, нет user и fingerprint
```

Доменные сущности должны ссылаться на actor:

```text
created_by_actor_id
updated_by_actor_id
deleted_by_actor_id
moderated_by_actor_id
```

Не нужно добавлять в новые таблицы пары:

```text
created_by_user_id
created_by_fingerprint_id
```

Исключение возможно только если поле описывает не автора действия, а отдельное доменное отношение. Например, owner/member/assignee/customer должны моделироваться своими связями, contract или membership, а не через actor.

## Как получать текущего actor

В HTTP-flow нужно использовать:

```php
CurrentActorResolver::resolveForRequest($request)
```

Resolver берет:

- `$request->user()`;
- `browser_fingerprint` из request attributes, который устанавливает `RecordBrowserFingerprint`.

В application/use case лучше передавать уже готовый `?Actor`, а не `Request`, `UserFingerprint` или cookie.

Пример:

```php
$venue = $createVenue->handle(
    actor: $actors->resolveForRequest($request),
    data: $request->validated(),
);
```

## Правила использования

- `Actor` используется для аудита происхождения действия.
- `User` используется для аккаунта, авторизации и персональных данных.
- `UserFingerprint` используется для браузера/устройства и guest-сценариев.
- Права владения и управления не должны выводиться только из `created_by_actor_id`.
- Для полноценного владения использовать отдельные доменные связи: membership, contract, role, assignment.
- Bootstrap-доступ по actor допустим как временный доступ к еще не принятой в управление сущности.
- После появления owner/member contract bootstrap-доступ создателя должен прекращаться.

## Привязка гостевых действий к аккаунту

Когда гость создает сущность, например площадку, она ссылается на guest actor:

```text
venues.created_by_actor_id = actor type=guest, user_id=null, user_fingerprint_id=12
```

После логина мы не обновляем этот actor и не записываем в него `user_id`. Это намеренное правило: actor описывает состояние субъекта в момент действия, а не текущее состояние браузера.

Вместо этого создается запись:

```text
actor_claims
- claimed_actor_id: гостевой actor
- claimed_by_user_id: пользователь, который вошел
- claimed_by_actor_id: user actor текущего входа
- claimed_at: момент привязки
```

Для пользователя это означает: "вы начали действие без регистрации, после входа оно появилось в вашем аккаунте".

Для кода это означает:

- `created_by_actor_id` остается историей создания;
- доступ текущего user может учитывать `actor_claims`;
- другой аккаунт в том же браузере не должен автоматически получать чужие гостевые действия;
- один guest actor может быть автоматически привязан только к одному user;
- один аккаунт может видеть привязанные гостевые действия с любого устройства.

## Конкурентный доступ

`CurrentActorResolver` использует `firstOrCreate` по уникальному `actor_key`. При высокой конкуренции два одинаковых запроса могут одновременно попытаться создать один actor.

Практический риск небольшой, но для высоконагруженных точек можно усилить реализацию:

- заменить на `upsert` + повторное чтение;
- ловить unique constraint violation и повторять select;
- обернуть создание actor в короткую transaction.

Сейчас выбран простой вариант, потому что actor создается редко и не содержит денежных или критичных side-effect данных.
