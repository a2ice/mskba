# Actor Attribution

## Назначение

`Actor` — централизованная модель автора действия. Она отвечает на вопрос: «кто или что совершило действие в момент его выполнения».

Actor не заменяет пользователя, владельца сущности или договорный доступ. Это исключительно слой атрибуции и аудита.

## Техническая модель

Основные таблицы:

```text
user_fingerprints
- браузерное/устройственное присутствие;
- не является аккаунтом и не предоставляет прав;
- используется для security, аналитики и будущего списка устройств.

user_fingerprint_user
- история связей fingerprint <-> user;
- не является моделью владения сущностями.

actors
- централизованный субъект действия;
- хранит type, user_id, user_fingerprint_id;
- имеет уникальный actor_key для стабильного firstOrCreate.
```

Типы actor:

```text
guest  - анонимное действие, если конкретный сценарий разрешён без аккаунта;
user   - действие авторизованного пользователя;
system - действие системы.
```

Доменные сущности могут ссылаться на actor через поля вида:

```text
created_by_actor_id
updated_by_actor_id
deleted_by_actor_id
moderated_by_actor_id
```

Не нужно добавлять в новые таблицы пары `created_by_user_id` и `created_by_fingerprint_id`. Исключение возможно, если поле описывает отдельное доменное отношение. Например, owner/member/assignee/customer моделируются своими связями или контрактами, а не через actor.

## Как получать текущего actor

В HTTP-flow используется:

```php
CurrentActorResolver::resolveForRequest($request)
```

Resolver учитывает `$request->user()` и `browser_fingerprint`, установленный middleware `RecordBrowserFingerprint`. В application/use case передаётся уже готовый `?Actor`, а не HTTP Request.

```php
$venue = $createVenue->handle(
    actor: $actors->resolveForRequest($request),
    data: $request->validated(),
);
```

## Правила использования

- `Actor` фиксирует происхождение действия.
- `User` используется для аккаунта, аутентификации и авторизации.
- `UserFingerprint` описывает браузер/устройство и никогда сам по себе не даёт прав на сущность.
- Права владения и управления не выводятся из fingerprint.
- Полноценное владение моделируется отдельными отношениями: membership, contract, role или assignment.
- Для площадки создание разрешено только авторизованному пользователю. Поэтому её creator actor всегда связан с user.
- Пока у площадки нет owner membership contract, user, связанный с creator actor, может выступать bootstrap-владельцем.
- После появления owner contract права управления определяются контрактами.
- Перенос или «присвоение» гостевых сущностей через fingerprint не поддерживается; таблицы и модель `ActorClaim` отсутствуют.

## Конкурентный доступ

`CurrentActorResolver` использует `firstOrCreate` по уникальному `actor_key`. При высокой конкуренции два одинаковых запроса могут одновременно попытаться создать actor.

При росте нагрузки реализацию можно усилить:

- использовать `upsert` с повторным чтением;
- ловить нарушение unique constraint и повторять select;
- оборачивать создание actor в короткую транзакцию.

Сейчас выбран простой вариант: создание actor не содержит денежных или иных критичных side effects.
