# Audit Logging

## Назначение

Audit logging фиксирует изменения доменных сущностей: кто изменил, какую сущность, какое событие произошло и какие поля поменялись.

Это не замена runtime-логам Laravel. Runtime-логи отвечают на вопрос "что произошло с приложением технически": исключения, предупреждения, интеграционные сбои. Audit-логи отвечают на вопрос "что изменилось в данных продукта".

## Продуктовый смысл

Аудит нужен для:

- восстановления истории изменения важных сущностей;
- модерации и разбора спорных ситуаций;
- понимания действий гостей, пользователей и системы;
- будущих security-сценариев;
- поддержки и админки.

Пример:

```text
Гость добавил площадку
-> audit_logs.event = created
-> audit_logs.actor_id указывает на Actor type=guest
-> audit_logs.auditable_type = Venue
-> audit_logs.new_values содержит поля созданной площадки
```

## Техническая модель

Основная таблица:

```text
audit_logs
- actor_id nullable
- auditable_type
- auditable_id
- event
- old_values
- new_values
- metadata
- timestamps
```

`actor_id` ссылается на `actors`. Это сохраняет единый подход для действий гостя, пользователя и системы.

`auditable_type` хранит полное имя класса модели, а не morph alias. Это сделано намеренно: audit является внутренним системным журналом и не должен зависеть от публичных morph maps отдельных модулей.

## Что логируется

Автоматически поддерживаются события:

- `created`;
- `updated`;
- `deleted`.

Логируемые модели перечислены в `config/audit.php`.

Модель должна:

- использовать trait `Auditable`;
- быть добавлена в `config('audit.auditable')`.

Если trait подключен, но модель не перечислена в конфиге, лог не пишется.

## Что не логируется

По умолчанию игнорируются:

- `created_at`;
- `updated_at`;
- `deleted_at`;
- `password`;
- `remember_token`;
- `code_hash`.

Новые секретные поля должны добавляться в `audit.ignored_attributes` до включения модели в аудит.

## Metadata

Для HTTP-запросов сохраняется:

- method;
- route;
- path;
- hashed IP;
- user agent.

IP хранится как HMAC hash, чтобы не складывать raw IP в продуктовый audit-журнал.

## Где писать audit вручную

Автоматический trait подходит для CRUD-изменений моделей.

Для бизнес-событий, которые не совпадают с изменением одной модели, нужен отдельный application/domain-level audit entry. Например:

- "пользователь прошел подтверждение аккаунта";
- "площадка принята модератором";
- "контракт активирован";
- "подозрительный вход".

Такой ручной writer нужно добавлять отдельной задачей, когда появятся эти процессы.

## Почему не готовый пакет

Готовые пакеты вроде `spatie/laravel-activitylog` полезны для стандартного user-only аудита.

В этом проекте уже есть собственная модель `Actor`, которая объединяет guest, user и system действия. Поэтому первая реализация сделана как небольшой собственный слой:

- меньше адаптации под guest-сценарии;
- прозрачная структура таблицы;
- единая связь с `Actor`;
- проще обучать и поддерживать в рамках текущей архитектуры.

Если требования сильно вырастут, например нужны batch logs, log channels, complex causer/resolver, можно повторно сравнить собственный слой с готовым пакетом.

## Конкурентный доступ

Audit insert выполняется внутри model event после изменения модели. Это простая append-only запись.

Риск deadlock низкий, потому что audit не обновляет исходную сущность и не блокирует несколько доменных таблиц. При будущих массовых операциях важно не читать audit rows с блокировками внутри той же transaction, где меняются доменные сущности.
