## PostgreSQL vs Redis — разделение ответственности

| Система | Источник истины? | Что делает в MSKBA |
| --- | --- | --- |
| PostgreSQL | **Да** для аккаунтов, броней, операций, заявок | ACID, связи, FK, unique, состояние |
| Redis | **Нет** для критичных бизнес-фактов | Быстрый кеш, метрики, presence, выделенные фоновые очереди |

В [compose.yaml](../../compose.yaml) используется redis:7-alpine с appendonly yes. В [.env.example](../../.env.example) видно CACHE_STORE=redis, но QUEUE_CONNECTION=database; отдельно TELEGRAM_QUEUE_CONNECTION=redis. Это означает, что **не все очереди обязаны использовать Redis**. Фактическое значение зависит от окружения.

## Реальный cache-aside: поиск площадок

[VenueSearchCache](../../app/Modules/Venue/Application/Services/VenueSearchCache.php):

~~~text
Запрос пользователя
 ├─ ключ venue-search:result:v{version}:{hash(filters)}
 │     ├─ HIT → вернуть результат
 │     └─ MISS → выполнить resolver, сохранить на 60 сек
 └─ поисковый индекс venue-search:index:v{version}
       └─ хранится до 3600 сек (по умолчанию)
~~~

В documents() данные собираются с eager loading tags, address, metro; rememberResult() использует хеш нормализованных фильтров. Это пример **cache-aside**: сначала проверяем кеш, при промахе считаем и запоминаем.

В [config/venue_search.php](../../config/venue_search.php) TTL настраиваются через переменные окружения. **Ограничение:** результат поиска кешируется только на некоторых путях (например, confirmedOnly), не заявляй «кешируем любой поиск для всех».

### Инвалидирование через versioned keys

Вместо удаления тысяч ключей метод invalidate() увеличивает venue-search:version. Следующий поиск идёт в новый namespace vN и не читает старые результаты. Старые записи живут до TTL.

**Плюсы:** O(1) логическая инвалидизация, не нужно перечислять keys по шаблону. **Минусы:** устаревшие ключи некоторое время занимают память; нужно корректно вызывать invalidate() после релевантных изменений.

## Redis и фоновые очереди

[compose.yaml](../../compose.yaml) содержит queue worker, отдельные Telegram workers, Reverb, scheduler, telegram-poller. В production или dev часть сервисов может быть остановлена/изменена конфигурацией; **наличие сервиса в YAML не равно фактическому uptime**.

**Job нужен**, когда внешний API, email или Telegram могут отвечать медленно или падать. HTTP-запрос должен завершать транзакционную работу, а доставку выполнять worker с retry/backoff и logging.

~~~text
HTTP → commit business data → outbox/event → queued job
                                          ↓
                                    queue worker
                                          ↓
                                 Telegram / email
~~~

**Не путай:** Redis cache — это прочитанные результаты с TTL; Redis queue — очередь заданий для worker; Reverb — отдельный WebSocket-сервер, а не сам кеш.

## Отличия, которые спрашивают

- **Cache TTL:** срок жизни данных. Малый TTL уменьшает stale data, но повышает нагрузку на БД.
- **Cache invalidation:** принудительное устаревание результата после изменения исходных данных.
- **Cache stampede:** много конкурентных MISS одновременно бьют в БД; решается locks/early refresh/stale-while-revalidate при нужной нагрузке.
- **Queue retries:** повтор возможен, значит job должна быть идемпотентной.
- **Dead letter / failed jobs:** неудачные задания нужно наблюдать и диагностировать; не заявляй, что конкретный DLQ реализован без проверки.
- **Гарантия:** Redis с AOF повышает восстановимость, но не заменяет durable PostgreSQL для финансового инварианта.

## Вопрос интервьюера

**«Зачем вам Redis, если PostgreSQL быстрый?»** Потому что часто повторяющийся, допустимо устаревающий поиск дешевле брать из памяти; фоновые отправки отделяются от HTTP, presence и оперативные счетчики не должны превращаться в тяжёлые write-запросы в основную БД. Но надо измерять экономию и не складывать критичные данные только в Redis.

**«Redis удалил кеш — приложение упало?»** Для корректного cache-aside это просто MISS → повторный расчёт. Потеря кеша не должна означать потерю брони или баланса.
