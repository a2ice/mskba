# 13. Вопросы, ответы, уточнения

[← Оглавление](README.md) · [Далее →](14-cheatsheet.md)

## Архитектура

**1. Что такое DDD и как он у вас устроен?**

Это организация модели вокруг бизнес-доменов и инвариантов. MSKBA — модульный монолит; модули Identity, Venue, VenueBooking, Finance, Rewards и т. д. имеют Domain/Application/Infrastructure/Presentation. Это pragmatic DDD, потому что Eloquent прямо используется в Domain и не для всего построены интерфейсы репозиториев.

**2. Почему не fat controller?**

HTTP — транспорт. Бизнес-действие живёт в Handler, например RequestVenueBookingHandler, а правила переходов — в VenueBookingLifecycle. Код можно вызывать и тестировать независимо от страницы.

**3. Что такое dependency injection?**

Зависимости передаются через конструктор; Laravel container собирает реализации. Это снижает скрытые зависимости и помогает заменять внешние компоненты в тестах.

**4. Когда нужна Strategy?**

Когда есть ожидаемые варианты одной операции: email/другие каналы подтверждения или разные типы начислений. Без реальных вариантов интерфейс может стать лишним.

**5. Repository pattern у вас везде?**

Нет. На практике часто применяем Eloquent Builder напрямую; Repository interface нужен там, где реально отделяется сложный доступ к данным или несколько источников.

## PHP

**6. Что даёт enum?**

Фиксированный тип с известными значениями и методами; статус брони — не произвольная string. Но enum не проверяет корректность смены состояния.

**7. Что такое VO?**

Value Object — неизменяемая концептуальная величина со своей валидацией и нормализацией. Пример UsernameVO/ContactValue. Идентичность определяется значением, не ID в БД.

**8. Зачем readonly?**

Запрет переназначения свойств после инициализации; для внешних mutable объектов это не глубокая immutability.

**9. Для чего #[Fillable]?**

PHP attribute, который Laravel считывает как декларативные метаданные mass assignment. Отдельно нужен guard бизнес-разрешений.

## События, транзакции

**10. Event vs Listener?**

Событие — факт, Listener — реакция. UserContactConfirmed приводит к независимым действиям: права, аудит дубликатов, уведомления.

**11. Event vs Job?**

Событие описывает **что произошло**; Job — **что сделать**, чаще в очереди. Событие не обязано быть асинхронным.

**12. Зачем Outbox, если есть очередь?**

Чтобы бизнес-изменение и запись о необходимости доставить событие атомарно попали в одну БД. Очередь сама не закрывает провал между COMMIT и publish.

**13. Атомарность и идемпотентность — одно?**

Нет. Транзакция защищает частичную запись, receipt/idempotency key — повторение команды после уже успешного коммита.

**14. Что, если два запроса одновременно бронируют слот?**

Делаем блокировки строк, проверяем конфликт в транзакции, проверяем version и не разрешаем недопустимый переход. Уникальные ограничения дополняют логику.

**15. Что, если после COMMIT упало уведомление?**

Исходная операция остаётся успешной; outbox повторно выбирает pending, listener/consumer должен быть устойчив к повторам.

## База и Redis

**16. Зачем нормализация?**

Избавляет от дублирования и аномалий обновления; связи и constraints сохраняют согласованность. Snapshot брони — допустимая осознанная денормализация ради истории условий.

**17. Как устранить N+1?**

Выявить повторы SQL и добавить eager loading with()/loadMissing() или withCount() вместо запроса на каждый элемент.

**18. EXISTS или JOIN?**

EXISTS — когда нужен факт наличия права, и не хотим размножать строки из many-to-many. JOIN — когда реально нужны поля связанных таблиц. Решение проверяем планом выполнения.

**19. Какие индексы использовались?**

Unique на business fact и idempotency key; составные индексы для фильтрации статусов и времени; FK для связей. Пример — migration reward_grants.

**20. Что делает Redis?**

Cache-aside для поиска площадок с TTL и version invalidation; часть очередей, presence/оперативные данные. PostgreSQL остаётся source of truth.

**21. Что если кеш устарел?**

TTL ограничивает срок, вызов invalidate() меняет версию ключа. На критичных переходах кеш не должен быть единственным источником истины.

## Security / frontend

**22. ACL vs RBAC?**

RBAC задаёт типовую роль; ACL/permissions учитывают операцию и конкретный ресурс, например управление определённой площадкой через активное договорное членство.

**23. Скрыть кнопку — достаточно?**

Нет. Проверка на сервере обязательна для каждого действия и private channel.

**24. На чём фронт?**

Основной интерфейс смешанный: Blade + JS и Vue-острова. Inertia имеется в изолированном preview, но это ещё не полноценная SPA.

**25. Composition API в Vue?**

refs/reactive, watch, lifecycle hooks и script setup. Реальный пример RegistrationWizard.vue.

**26. Зачем Reverb, если есть HTTP?**

Push для скорости, но данные всегда сверяются HTTP после reconnect/focus; private channels требуют серверной авторизации.

**27. Почему использовать Echo и Pusher JS с Reverb?**

Echo даёт удобный API подписки, Pusher JS обеспечивает совместимый протокол клиента; сам WebSocket-сервер — Reverb.

## CI/CD

**28. Что делает pipeline?**

Устанавливает PHP/Node, проверяет Compose, гоняет PHPUnit/JS-тесты, собирает Vite, предотвращает попадание локальных Reverb-секретов/адресов в bundle; dev и prod доставляются отдельно.

**29. Что такое Docker Compose?**

Декларация multi-container среды: PHP-FPM, Nginx, PostgreSQL, Redis, worker, scheduler, Reverb и интеграционные сервисы.

**30. Как откатить миграцию?**

Сначала оценить необратимые преобразования и сохранность данных; rollback кода без совместимой схемы может быть опасен. Для live-систем предпочтительны обратносуместимые изменения с планом релиза.

## Вопросы на глубину — упражнение

- **«Что быстрее: JOIN или EXISTS?»** Нельзя ответить без кардинальности, индексов и плана. EXPLAIN ANALYZE.
- **«Exactly-once delivery у вас есть?»** Не утверждать. Есть durable outbox и идемпотентные эффекты; типичная гарантия at-least-once.
- **«Почему Redis быстрее?»** In-memory для часто повторяемых чтений, но есть сетевой overhead, сериализация и invalidation.
- **«Почему нельзя положить финансовый баланс только в Redis?»** Потеря/рассинхронизация; нужны ACID и аудит ledger.
- **«Самая дорогая архитектурная ошибка?»** Ненужные абстракции и многословные связи между модулями; решать по реальным кейсам и метрикам.
