## Назначение и область применения

Это принятое архитектурное и продуктовое правило MSKBA для **заявок, требующих решения уполномоченного пользователя**: вступление в команду, изменение защищённых данных аккаунта, профильные запросы и будущие аналогичные процессы.

Паттерн задаёт **значение действий**, а не одну обязательную SQL-таблицу, enum или универсальный сервис. Предметные контексты сохраняют свои модели, права и дополнительные статусы (например, `awaiting_response`, `expired`). Новые процессы следуют общим правилам; изменение существующих несовместимых потоков проводится отдельными задачами, а не считается автоматически реализованным.

## Общая семантика решений

| Состояние | Действие и эффект | Новая заявка в том же контексте |
| --- | --- | --- |
| `pending` | Подана, рассматривается. Данные предметной сущности не применяются заранее | Запрещена, пока активна текущая заявка |
| `approved` / `accepted` | Одобрена. Предметное действие применяется один раз | Определяется конкретным сценарием |
| `rejected` | Отклонена проверяющим, причина обязательна | **Разрешена** после устранения причины либо по решению заявителя |
| `cancelled` | Отменена заявителем, если сценарий поддерживает отзыв | **Разрешена**, если другие ограничения выполнены |
| `blocked` | Проверяющий целенаправленно запрещает следующие заявки **в той же области действия**; причина обязательна | **Запрещена до явной разблокировки** |

«Отклонить» и «Заблокировать» — **разные решения**. Отклонение не является санкцией за последующие обращения и не устанавливает скрытых лимитов повторных попыток. Отмена означает отзыв заявки, а не наказание заявителя. Поддерживаемые статусы называются по-разному в отдельных модулях; там, где `cancelled` или `blocked` не предусмотрены, интерфейс не должен изображать такое действие рабочим.

Блокировка заявки **не эквивалентна** блокировке пользовательского аккаунта (`UserStatusEnum::BLOCKED`) или предметной сущности (например, площадки). Решение по заявке не меняет эти статусы без отдельного, явно санкционированного действия.

## Повторная подача и область блокировки

Область блокировки — определённый заранее **ключ повторной подачи** (request scope), а не просто ID одной заявки.

- Для заявки в команду: canonical user + конкретная команда, в рамках правил приёма этой команды.
- Для изменения подтверждённых персональных данных: canonical user + тип операции `confirmed_profile_change`. Блокируется подача всех последующих заявок этого типа, а не только изменение одного поля; другие категории запросов остаются доступными.
- Другие процессы задают аналогичный устойчивый scope с учётом subject/target, типа запроса и canonical identity.

Сервер обязан проверять по scope **действующую блокировку и активную заявку до создания/переоткрытия** новой записи, в том числе если заблокированная историческая заявка не является последней. Ни смена ID формы, ни повторный POST, ни новая регистрационная identity/alias не обходят блокировку. Проверка и создание заявки атомарны и защищены от параллельных запросов; UI не служит источником доверия.

Повторная подача после `rejected` или `cancelled` допускается при соблюдении остальных бизнес-правил. История ранее рассмотренных обращений и причины решений сохраняются.

## Разблокировка

- Разблокировать может только уполномоченный проверяющий (по правилам предметного контекста).
- Разблокировка **снимает запрет на новую подачу**, но сама по себе ничего не одобряет и не применяет предлагаемые изменения.
- Для разблокировки фиксируются исполнитель, время и аудит. Желательна причина или комментарий; старые причины блокировки не стираются из исторического следа.
- Технически отдельный контекст может переводить `blocked → rejected` (как заявки в команды) либо хранить отдельное событие снятия блокировки. Обязателен один и тот же наблюдаемый результат и возможность восстановить историю.

## Контракт реализации

1. Проверять полномочия заявителя, reviewers и область действия сервером. Воспрещать самоодобрение там, где требуется независимая модерация.
2. При отклонении и блокировке требовать причину; показывать пользователю понятный статус и объяснение с соблюдением приватности.
3. Сохранять автора, reviewer, время и решение; фиксировать события в аудите, уведомлять заинтересованных после успешного commit.
4. Хранить старое/предлагаемое значение (snapshot или revision) и применять одобренные изменения только в транзакции при повторной валидации. Данные до одобрения остаются прежними.
5. Ограничивать одновременные активные заявки в одном scope, защищать повторы, конкурентную модерацию и повторное применение решения.
6. По умолчанию отклонение не блокирует повторную подачу, блокировка — блокирует **до ручного снятия**. Не превращать очередное отклонение в неявный `blocked` без отдельного решения.
7. Для чувствительных персональных данных применять минимально необходимые права чтения, не раскрывать приватные поля в публичных логах/уведомлениях и не считать общий audit заменой журналу решений.

## Применение в действующем проекте

- **Реализованный образец:** `TeamJoinRequestStatusEnum` и `TeamJoinRequestController`: `reject` допускает новую подачу, `block` отклоняет её, `unblock` снимает запрет и переводит заявку в `rejected`.
- **Отличающийся текущий процесс:** модерация площадок использует `pending|approved|rejected`; блокировка самой площадки — другой предметный статус. Нельзя считать, что паттерн блокировки заявки уже реализован для площадок.
- **Реализовано для профиля в `mskba_app`:** заявка на изменение защищённых `first_name`, `last_name`, `birth_date`, `gender` с причиной, исходными и предлагаемыми данными, безопасным применением после одобрения, историей решений и блокировкой для scope `canonical_user + confirmed_profile_change`. Экран проверки ограничен полномочиями superadmin. Уведомления не содержат персональные значения.
- **Дальнейшая унификация:** прямое служебное редактирование профиля из прежней административной формы остаётся отдельным административным исключением. Перед production-релизом проверить политику таких изменений и существующие подтверждённые аккаунты с неполными полями.
