# Журнал значимых обновлений MSKBA (System Updates)

**Решение утверждено 2026-11-18; функциональность находится в проектировании, а не в эксплуатации.** Реализация отслеживается [задачей 327](../tasks/327/description.md). Исполняемое правило для всех AI-агентов — [GlobalRule4](agent-rules.md#globalrule4---фиксировать-значимые-обновления-проекта).

## Назначение и границы

Единая запись об интегрированном значимом изменении должна одновременно служить:
- внутренним журналом для команды (контекст, ссылки на документацию и слитый PR, исполнитель, дата и состояние доставки);
- публичным материалом в существующей ленте `/feed` (только понятный пользователю результат, без технических ссылок и служебных полей).

Это **не** журнал каждого коммита и не замена актуализации `docs/project.md`, `docs/specification.md`, `docs/tasks/{NNN}` или ревью PR. Значимость определяют изменения возможностей пользователей, поведения продукта, существенные улучшения качества и значимые этапы платформы. Не публиковать косметику, внутренние рефакторинги без продуктового результата, секреты, подробности уязвимостей и персональные данные. Одно связное изменение может объединять несколько PR; повторяющиеся попытки записи не создают дубликатов.

## Архитектура (целевой контракт, НЕ текущий endpoint)

- Расширить существующий `App/Modules/Content`: `ContentItem` получает новый тип `system_update` с отображаемой меткой «Обновления платформы». Публичное представление, фильтр по типу, SEO и редактор переиспользуют существующие механизмы Content.
- В `ContentItem` хранить **только пригодные для публичного вывода** заголовок, короткое описание, полный текст и привычные признаки публикации. Технический блок хранить отдельно, с доступом только для backoffice и защищённого внутреннего API: ссылки на один или несколько *merged* PR, документацию и задачи, SHA/источник, инициатор, целевая среда, результат деплоя и журнал синхронизации.
- Для технического блока добавить специализированную связанную сущность/таблицу, а не помещать приватные URL в `full_description`, `link_url`, SEO, Telegram или общие публичные DTO/сериализацию ContentItem. Публичный шаблон использует только белый список публичных полей. Обязательно проверить все исходящие каналы (feed, show, sitemap, API, Telegram).
- В `/backoffice/content` добавить режим управления системными обновлениями с видимыми редактору техническими ссылками; в `/feed` использовать общий фильтр типов. Никакой второй системы публикаций или отдельной CMS.
- До релиза механизма не объявлять тип/маршруты/функцию доступными.

## Жизненный цикл

1. **Работа над задачей:** документация изменяется вместе с кодом; исполнитель подготавливает краткую внутреннюю и публичную формулировки.
2. **После merge PR:** создаётся/обновляется **черновик**, связывающий текст, задачу, документацию и фактически слитый PR. Состояние merge проверяется, а не принимается по заявлению клиента.
3. **Проверка доставки:** необходимо подтверждение, что соответствующее изменение действительно развернуто и доступно в production; merge в `dev` или `main` сам по себе не является подтверждением публикации.
4. **Публикация:** явно уполномоченный редактор или отдельная разрешённая автоматизация подтверждает публичный текст и публикует запись. Неподтверждённый / сорвавшийся деплой оставляет черновик без публичной видимости.
5. **Исправление:** изменять запись с аудитом, не создавать новую новость для повторной попытки публикации того же изменения.

Если инфраструктура журнала ещё не реализована, исполнитель **не пропускает документационный след**: сохраняет подготовленный текст и технические ссылки в результате задачи/PR со статусом «ожидает записи в Content», сообщает об отсутствии API и не выдаёт подготовку за публикацию.

## Агентский API (планируемый)

- `POST /api/v1/internal/project-updates` — идемпотентное создание/обновление черновика;
- `GET /api/v1/internal/project-updates/{id}` — чтение статуса и ссылок в защищённом контексте;
- `PATCH /api/v1/internal/project-updates/{id}` — правка черновика;
- отдельное защищённое действие публикации — только после проверки production и явного разрешения. Наличие общего токена записи **не означает права публикации**.

Ответ должен содержать ID, канонический статус черновика/публикации, ошибки валидации и признаки фактического выполнения — не «успех» до подтверждения сервера. Запрос включает idempotency key, идентификаторы источника/PR, публичные поля и внутренние ссылки. Проверять ссылки и принадлежность репозиторию; PR должен быть merged. Ошибки `401/403/409/422/429` обрабатывать явно. Документировать контракт в OpenAPI перед подключением клиентов. Предполагаемый URI — дизайн, **сейчас маршрута нет**.

## Сервисная учётная запись `dev` и безопасность

Для обращения ChatGPT-исполнителей, AI-агентов и доверенных внешних интеграций **к MSKBA API** использовать уже созданную отдельную учётную запись `dev` (системная роль `system` в backoffice), а не персональный или супер-административный аккаунт. Существование учётной записи/роль `system` не равнозначны доступу к новому API: при реализации назначить только необходимые права, например scoped Sanctum ability `project-updates:write` для черновиков, отдельное право для публикации и проверки контентных разрешений. Токены по возможности индивидуальные, ограниченного срока, отзывные, раздельные для сред и исполнителей; аудит авторства и операций обязателен. Для проверки GitHub PR использовать отдельную доверенную GitHub-интеграцию с минимальными правами, а не пароль `dev`.

Запрещено сохранять в Git, чате, документации, PR или публичных материалах пароль, bearer token, refresh token и иной секрет `dev`. Токены передавать через защищённые секреты окружения/интеграции; нельзя получать их из скриншота или домысливать. Отсутствие доступного действительного токена — блокирующее условие API-записи; агент подготавливает текст и честно сообщает, что отправка невозможна. Запрещено повышать `dev` до `superadmin` ради интеграции.

## Проверки при реализации

- Подлинность и минимальные права токена `dev`, запрет чужих токенов и обычных пользовательских сессий на служебных маршрутах.
- Идемпотентность повторной доставки; PR действительно слит; корректный отказ, если нет подтверждённого production deployment.
- Нулевые технические URL, секреты и внутренние метаданные в анонимных HTML/JSON, Telegram и SEO.
- Совместимость с существующими материалами/FAQ, правами редактора и текущим каноническим маршрутом `/feed`.
- Минимальные feature-тесты на доступ, публикационный gate, идемпотентность и отсутствие утечки данных.
