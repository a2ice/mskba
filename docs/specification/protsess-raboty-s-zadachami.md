## Назначение

Процесс нужен, чтобы каждая задача имела понятный старт, план, документационный след, отдельную ветку, проверяемый результат и аккуратное завершение в `main`.

## Список задач

Общий список задач ведется в файле `docs/tasks.md`.

Формат строки:

```markdown
- [ ] NNN - Название или краткое описание задачи
```

После merge задачи в `main` строка переводится в выполненное состояние:

```markdown
- [x] NNN - Название или краткое описание задачи
```

## Старт задачи

Перед началом выполнения нужно:

1. Проверить, что текущая ветка - `main`.
2. Проверить, что `main` чистая: нет незакоммиченных изменений.
3. Найти задачу в `docs/tasks.md`.
4. Создать папку `docs/tasks/{NNN}`.
5. Создать `docs/tasks/{NNN}/description.md`.

`description.md` на старте содержит две секции:

```markdown
# NNN - Название задачи

## Оригинальное описание

Текст задачи из `docs/tasks.md`.

## Подробное описание

Заполняется на этапе планирования.
```

## Планирование

Планирование является обязательным первым этапом задачи.

На этапе планирования нужно:

- изучить `docs/project.md`;
- изучить связанные раскрытия из `docs/project/{alias}.md`, если они относятся к задаче;
- изучить `docs/specification.md`;
- изучить связанные технические раскрытия, если они относятся к задаче;
- заполнить подробное описание задачи в `docs/tasks/{NNN}/description.md`;
- определить затронутые пользовательские сценарии, документы, модули и проверки;
- запросить подтверждение на переход к следующему этапу.

## Этапы выполнения

Перед каждым этапом нужно явно обозначить, какой этап начинается, и получить подтверждение на выполнение.

Рекомендуемые этапы:

- планирование;
- декомпозиция;
- реализация;
- обновление документации;
- проверка;
- подготовка к коммиту;
- merge в `main`;
- обновление `docs/tasks.md`.

Набор этапов можно менять под задачу, но планирование, проверка и обновление документации обязательны, если задача влияет на продукт, архитектуру или процесс.

## Подзадачи

Если задача сложная или составная, она декомпозируется в `docs/tasks/{NNN}/subtasks`.

Рекомендуемый формат:

```text
docs/tasks/{NNN}/subtasks/{MMM}-{alias}.md
```

Каждая подзадача должна содержать:

- название;
- цель;
- краткое описание;
- статус;
- результат выполнения.

## Завершение задачи

После выполнения:

1. Зафиксировать результат в `docs/tasks/{NNN}/description.md`.
2. Обновить связанные документы `docs/project.md`, `docs/specification.md` и раскрытия.
3. Запустить релевантные проверки.
4. Получить подтверждение, что задача выполнена.
5. Запросить разрешение на коммит.
6. Сделать коммит в ветке задачи.
7. Запросить разрешение на merge в `main`.
8. Выполнить merge.
9. Уже из `main` отметить задачу выполненной в `docs/tasks.md`.

## Рекомендуемые дополнения

Ветка задачи должна называться в стиле conventional commit:

```text
type/NNN
```

Примеры:

- `feature/123`
- `fix/124`
- `docs/125`
- `refactor/126`

Коммит рекомендуется называть так:

```text
type(scope): краткое описание задачи
```

Пример:

```text
docs(process): add task workflow documentation
```

Если задача меняет пользовательский опыт, итоговое описание должно содержать не только технический результат, но и изменение с точки зрения пользователя или процесса.
