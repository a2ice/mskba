## Срез и включение

Локальная реализация задач [322](../tasks/322/description.md) и
[300](../tasks/300/description.md). Новый этап расчёта закрыт конфигурацией
`features.venue_rental.special_terms`, переменная
`FEATURE_VENUE_RENTAL_SPECIAL_TERMS`, по умолчанию **false**. Включать после CI,
проверки миграции и ручной приёмки на dev. При выключенном флаге автоматические
условия не меняют новые цены; явный код возвращает отказ. Выпущенные ранее
quotes сохраняются, их срок и применимость проверяются при заявке независимо
от текущего флага. Для запрета конкретного предложения использовать паузу/отзыв.

Расширяется `venue_group_offers`, без второго каталога скидок:
`audience=GROUP` по умолчанию сохраняет старое поведение Task 299;
`PUBLIC` — код для подтверждённых пользователей;
`USER_BOUND` — код только для получателей из `venue_offer_recipients`.
Персональные условия могут автоматически применяться без ввода кода.
Получатели канонизируются и должны иметь подтверждённый аккаунт.
Новые предложения имеют отдельный `group_key=special:{venue_id}` и не попадают
в групповые списки/формы Task 299. GROUP-коды пока не применяются к quote.

Поддержаны процент 1–99 (целые процентные пункты), фиксированная скидка или
фиксированная итоговая цена (integer minor units), название, причина,
площадка/зал/зона, начало действия (по умолчанию сейчас), бессрочное окончание,
период дат аренды, дни недели и дневное временное окно, минимальная итоговая
стоимость до персонального этапа, общий лимит и лимит на аккаунт. Всё время
интервала должно подходить под ограничения. Временные окна через полночь
в первой версии не поддерживаются. Пустой лимит означает отсутствие лимита,
1 — однократное использование. Даты действия нормализуются в UTC; календарные
условия проверяются в timezone площадки. Денежные поля управления сейчас
явно подписаны как копейки; дробные проценты не поддержаны.

## Расчёт и snapshot

`QuoteVenueBookingHandler`: опубликованные тарифы → существующий
`VenueCommissionCalculator` (портал и один выбранный legacy-агент) →
`VenuePersonalPricing`. Из подходящих автоматических условий и одного явно
введённого кода выбирается **наибольшая скидка**, при равенстве — меньший ID.
Суммирования нет (`best_non_stackable`). Явный неверный код всегда отклоняется,
даже при наличии другого автоматического предложения. Неподходящее
автоматическое условие пропускается. Итог не может стать нулевым/отрицательным;
скидка не обрезается молча. Процент округляется half-up в minor units:
`intdiv(amount * percent + 50, 100)`.

Обычные quotes сохраняют schema 4 и прежнюю арифметику. При персональной скидке
schema 5 сохраняет `pricing.personal_discount`: ID/версию условия, получателя,
название/причину, формулу/значение, исходную конечную цену **с комиссиями**,
скидку, конечную цену, `funded_by=venue`, `funding_venue_id`, политику сочетания.
Внутренний breakdown комиссий хранится без переинтерпретации. Финансирование
скидки является внутренней атрибуцией, не подтверждением выплаты или новым
начислением. Агентское финансирование запрещено этим API.

Quote immutable; booking копирует snapshot, платежи используют сохранённую
итоговую сумму. Управленческий preview вызывает тот же quote handler, создаёт
обычный immutable quote и не расходует лимит. Публичный preview выбранного
диапазона календаря использует существующий расчёт тарифа/комиссий и тот же
финальный `VenuePersonalPricing`, с текущим пользователем.

В публичном JSON quote и календаря больше не выдаются комиссии и исходная
цена провайдера. Это намеренное изменение публичной проекции независимо от
флага; внутренняя модель комиссий сохранена. Публичная проекция персональной
скидки ограничена ценами и причиной, без recipient IDs, кодов и внутренних
долей. Ответы персонального расчёта — `private, no-store`. Blade экранирует
причину в `title`; JS использует `textContent`. Без персональной скидки показываем
обычную итоговую цену; при ней — зачёркнутую цену до скидки и итог с причиной.
Публичные ячейки календаря показывают обычные тарифные цены, персональная цена
появляется в preview выбранного диапазона и quote.

## Права и управление

Отдельное scoped право `venue.special-terms.manage` для персональных условий
и разовых предложений. Коммерческий OWNER с действующим подтверждённым
контрактом имеет право по умолчанию, в том числе для прежних owner contracts.
ADMIN/MANAGER/STAFF/AGENT могут получить явно делегированное право через
действующие контракты; наличие роли агента само по себе его не даёт.

В аккаунте global SUPERADMIN без контракта площадки не даёт права управления.
В явно административном контексте Filament разрешён подтверждённый SUPERADMIN
с доступом к VenueResource. Административный режим передаётся внутренним
параметром сервиса, HTTP-поля не могут его включить.

Filament Venue Edit → «Специальные условия»: создание, публикация, пауза,
отзыв, ссылка на preview/историю. Аккаунт
`/account/venues/{venue}/special-terms`: те же действия, история, preview.
Все операции перепроверяют право и принадлежность площадке, используют web
CSRF middleware и общую валидацию сервиса. Условия immutable в интерфейсе:
чтобы поменять цену/получателей, отозвать и создать новое. Аудит переиспользует
`venue_group_offer_audits`; коды остаются encrypted + unique SHA-256 hash,
не передаются в логи. Поиск получателей в аккаунте — серверный поиск логинов
с ограниченным списком; Filament — searchable Select. Predictive-поиск аккаунта
ещё не подключён, это явный UX gap относительно общего паттерна.

## Списание использований

Лимит расходуется **при успешном создании REQUESTED booking**. Quote/preview
не резервируют использование и могут перестать подходить до подачи заявки.
`RequestVenueBookingHandler` блокирует venue и quote; затем создаёт booking
и вызывает redemption в **той же транзакции**. `VenuePersonalPricing` блокирует
offer, повторно проверяет получателя, статус/версию, сроки, venue/court/scope,
контекст, валюту, лимиты и атомарно записывает `venue_offer_redemptions`.
На quote и booking стоят unique-индексы. Повтор запроса возвращает существующую
booking; второй расход не создаётся. Ошибка redemption откатывает booking,
партии и outbox. Порядок блокировок: venue → quote → court → offer.

Пауза/отзыв/повторная публикация после quote запрещают его новое использование;
цена самого quote не пересчитывается. Уже созданная заявка сохраняет цену.
При отмене/отказе/истечении брони лимит **не возвращается автоматически**.
Настоящий PostgreSQL/MySQL тест параллельных транзакций остаётся отдельным
приёмочным барьером; последовательный тест двух выпущенных quotes покрывает
перепроверку последней квоты, но не заменяет проверку конкурентности.

## Границы и следующие этапы

Не реализованы: wholesale/resale и договорные границы цены; новая модель
вознаграждения агента; миграция legacy commission; агентское финансирование;
погашение старых GROUP-кодов; conversation/event/interest-specific контекст и
автоприкрепление из переписки; stacking; возврат квоты при отмене; отдельное
разрешение только для разовых предложений (пока они используют общее право
управления specials). Передаваемые этому API booking/event/conversation ID,
`funded_by` и `stacking_policy` запрещены, а не интерпретируются как новые условия.

Агент остаётся независимым продавцом по договору; membership permissions не
доказывают наличие договора продажи. В будущем wholesale/resale должен быть
отдельным выбранным договорным режимом, с валовой маржой `resale - wholesale`,
без автоматического добавления второй комиссии. В этом срезе существующие
комиссии и инвариант одного **выбранного** агента не изменены; ужесточение до
одного активного агентского договора требует самостоятельной миграции и тестов.
