## Назначение

`Contact` - отдельный доменный контекст для контактных каналов разных сущностей проекта.

Контакты нужны не только пользователям, но и площадкам, событиям и будущим доменным сущностям. Поэтому модель вынесена из `Identity`.

## Граница контекста

Код контекста расположен в `App\Modules\Contact`.

Текущие доменные модели:

- `Contact`;
- `ContactVerification`.

Текущие application DTO:

- `CreateContactDTO`.

Текущие value object:

- `ContactValue`.

Текущие strategy:

- `EmailContactVerificationStrategy`.

Текущие enum:

- `ContactTypeEnum`;
- `ContactVerificationChannelEnum`;
- `ContactVerificationStatusEnum`.

## Contact

`Contact` хранит сам контактный канал сущности.

Таблица `contacts`:

- `contactable_type` - morph alias связанной сущности;
- `contactable_id` - id связанной сущности;
- `type` - тип контакта: `email`, `phone`, `telegram`, `vk`, `other`;
- `value` - значение контакта;
- `user_email_key` — нормализованный email подтверждённого или исторически зарезервированного пользовательского контакта; иначе `NULL`;
- `user_phone_key` — нормализованный номер пользовательского контакта для поиска и проверок;
- `ownership_reserved` — сохранённое доказательство ранее подтверждённой принадлежности; удаление контакта не передаёт его другому аккаунту;
- `label` - человекочитаемая пометка, nullable;
- `comment` — внутренний комментарий (до 500 символов), nullable, скрыт из стандартной сериализации модели;
- `is_primary` - основной контакт;
- `is_public` - можно ли показывать публично;
- `verified_at` - дата подтверждения текущего значения контакта, nullable;
- `deleted_at` - soft delete контакта, nullable;
- `meta` - JSON для расширений, nullable.

`verified_at` в `contacts` фиксирует текущее агрегированное состояние контакта. История попыток и каналов подтверждения хранится в `contact_verifications`.

## ContactVerification

`ContactVerification` хранит попытку или процесс подтверждения контакта.

Таблица `contact_verifications`:

- `contact_id` - связанный контакт;
- `channel` - канал подтверждения: `email`, `sms`, `telegram`, `call`, `other`;
- `status` - статус подтверждения: `pending`, `confirmed`, `expired`, `failed`, `cancelled`;
- `code_hash` - hash проверочного кода, nullable;
- `sent_to` - адрес или номер, на который отправлялось подтверждение;
- `attempts_count` - количество попыток ввода;
- `max_attempts` - лимит попыток;
- `expires_at` - срок действия подтверждения, nullable;
- `verified_at` - дата успешного подтверждения, nullable;
- `failed_at` - дата неуспешного завершения, nullable;
- `meta` - JSON для расширений, nullable.

Тип контакта и канал подтверждения разделены намеренно. Например, `phone` может подтверждаться через `sms` или `call`, а `telegram` - через бот.

## Полиморфная связь

Для связи используется стандартный Laravel morph naming:

- `contactable_type`;
- `contactable_id`.

В базе должны храниться короткие morph alias, а не FQCN классов.

Текущая morph map:

- `user` -> `App\Modules\Identity\Domain\Models\User`;
- `venue` -> `App\Modules\Venue\Domain\Models\Venue`.

Связанные модели должны объявлять:

- `contacts(): MorphMany`.

## Аккаунт

В личном кабинете есть страница `account.contacts`.

Текущий реализованный flow:

- пользователь видит список своих контактов;
- пользователь может добавить контакт;
- пользователь может удалить контакт;
- удаление контакта выполняется через soft delete;
- основной контакт удалить нельзя: запрос на удаление `is_primary = true` возвращает ошибку;
- удаление доступно для неосновного контакта независимо от `is_verified`;
- при удалении контакта сбрасываются `verified_at` и `is_public`, а активные pending-подтверждения переводятся в `cancelled`;
- повторное добавление ранее удаленного контакта восстанавливает существующую soft-deleted запись, а не создает дубль;
- первый контакт пользователя автоматически создается с `is_primary = true`, чтобы он сразу отображался в профиле;
- следующие контакты пользователя создаются с `is_primary = false`;
- создание контакта выполняется в транзакции с блокировкой строки пользователя, чтобы два параллельных запроса не назначили `is_primary = true` двум контактам одновременно;
- при добавлении контакт создается с `is_public = false` через default таблицы.
- пользователь может запустить подтверждение email-контакта;
- при запуске подтверждения создается `ContactVerification` со статусом `pending`;
- код подтверждения хранится в БД только как `code_hash`;
- письмо с кодом отправляется через Laravel mailer.
- повторный запрос email-кода в течение 60 секунд не создает новый код и возвращает информационное сообщение;
- повторный запрос после 60 секунд отменяет старый pending-код и отправляет новый.

Добавление контакта не запускает подтверждение автоматически. Процесс подтверждения запускается отдельным действием пользователя.

Смена основного контакта должна быть отдельным flow. Для нее нужно проверять, что новый основной контакт подтвержден.

Выбор публичности контакта должен быть отдельным flow редактирования контакта. Для него тоже нужно учитывать подтверждение контакта.

Удаление контакта не удаляет историю подтверждений из `contact_verifications`. Это сохраняет техническую историю отправок и попыток. Полное удаление персональных данных должно быть отдельной maintenance/GDPR-процедурой, если такое требование появится.

Внутри одной связанной сущности пара `type + value` уникальна даже с учетом soft-deleted строк. Это защищает базу от накопления дублей одного и того же контакта.

Email уникален среди подтверждённых и исторически зарезервированных пользовательских контактов. Неподтверждённые записи разных пользователей не блокируют добавление. Первый успешный код или штатное подтверждение приглашения атомарно закрепляет email, отменяет коды и деактивирует конкурирующие неподтверждённые записи. PostgreSQL использует блокировку по нормализованному значению и уникальный индекс `user_email_key`. Старые подтверждённые удалённые email резервируются по текущему verified_at, подтверждённым попыткам и аудиту; записи без исторического доказательства не являются основанием для блокировки. Контакты площадок и других сущностей не входят в индекс.

Телефон проверяется по нормализованному значению (включая российские 8/7 и международный 00). Старые подтверждённые дубли, включая alias одной личности, не переassignяются автоматически, неоднозначный вход запрещён. Новое добавление чужого подтверждённого номера запрещено; новые подтверждения должны использовать общий ContactOwnership. SMS пока не реализован. Telegram/VK сохраняют официальную привязку по ID без передачи между аккаунтами.

Use case создания контакта принимает `CreateContactDTO`, а не слабый массив данных.

Значение контакта нормализуется через `ContactValue`. Этот value object принимает `ContactTypeEnum` и строковое значение, выполняет базовую типоспецифичную валидацию и возвращает каноническое значение для записи в `contacts.value`.

Email и Telegram username нормализуются без учёта регистра. Это не только улучшает поиск, но и не позволяет обойти уникальность email разным регистром символов.

`ContactValue` не должен работать с БД, проверять уникальность, запускать подтверждение или принимать решения о правах доступа. Эти правила остаются в application/use case слое. Такой разделение сохраняет value object маленьким и переиспользуемым, а сценарии - явно управляемыми.

Локально email отправляется через SMTP и может приниматься Mailpit, если окружение настроено на `MAIL_MAILER=smtp`, `MAIL_HOST=127.0.0.1`, `MAIL_PORT=1025`.

Запуск подтверждения построен через strategy:

- `ContactVerificationStrategy` описывает методы `supports(Contact $contact)` и `start(Contact $contact)`;
- `ContactVerificationStrategyResolver` выбирает стратегию по `supports`;
- `StartContactVerificationHandler` не содержит ветвления по типам контакта и делегирует типоспецифичную логику выбранной стратегии.

Это нужно, чтобы добавление подтверждения phone, Telegram, VK и других типов происходило через новые strategy-классы, без изменения handler.

## Контакты в Filament

В редакторе пользователя (/backoffice/backoffice-users/{id}/edit) вкладка «Контакты» доступна по действующим правилам доступа к персональным данным (BackofficeUserResource::canEdit). Она показывает тип, значение, основной/публичный признак, даты добавления и подтверждения, канал текущего подтверждения и историю попыток. Контакты связанных аккаунтов выбираются через identityContactsQuery(); удалённые контакты вынесены в отдельный сворачиваемый блок. Текущий статус берётся из contacts.verified_at, а канал — из подтверждённой записи contact_verifications с совпадающим временем (допуск 2 секунды для отдельных вызовов now()); если такой записи нет, канал не угадывается. Для социальных контактов отдельно показывается последний сохранённый источник привязки из известного набора значений meta.source, а Telegram/VK-аккаунты, включая старые связи без Contact, отображаются с ID, датой создания привязки и последней авторизации. Источник не считается доказательством первоначального способа подтверждения. История не подменяет актуальный статус. Коды, хеши и произвольные метаданные попыток не выводятся. Раздел работает только на чтение и не изменяет процессы подтверждения.

## Контакты площадок в Filament

Первый инкремент #1059: вкладка «Контакты» в редакторе площадки
использует существующий Venue::contacts() и AdminManageVenueContactsHandler.
Доступ подтверждённым сотрудникам с backoffice.access и
backoffice.venue.manage; сервер заново проверяет полномочия и принадлежность
контакта конкретной площадке при каждом действии. Удалённая площадка недоступна.
Добавление и редактирование email/телефона, назначение, внутренний комментарий,
основной контакт, публичность, soft delete. Первый контакт — основной;
при удалении основного выбирается оставшийся, приоритет подтверждённым.
Уникальность нормализованных значений в пределах площадки (включая архивные
записи), операции под блокировкой площадки, контактные блокировки
ContactOwnership. Совпадение с user contact или другой площадкой допустимо:
запись справочника не претендует на user identity.

Подтверждение email использует общие StartContactVerificationHandler и
ConfirmContactVerificationHandler, действующий mail transport, cooldown,
TTL и предел попыток. Ошибочные попытки сохраняются даже при отказе.
SMS не поддерживается. Новые контакты неподтверждённые, по умолчанию непубличные.
По решению владельца от 26.11.2026 уполномоченный сотрудник может явно включить
публичность при добавлении или редактировании контакта площадки независимо
от подтверждения, удостоверившись, что контакт предназначен для посетителей.
Публичность не отправляет OTP, не устанавливает verified_at и не позволяет
использовать неподтверждённый контакт для приглашений или автоматической аренды.
Публичный блок использует PublicVenueContacts и отдельный allowlisted DTO:
только действующие email/phone данной опубликованной площадки с is_public=true,
независимо от verified_at; основной первым, затем id. Передаются только
type/value/label/href, без внутренних комментариев, истории и метаданных.
Некорректные legacy-значения исключаются; URL формируются только как
mailto:/tel:. В mskba_app панель «Контакты площадки» после «Хочешь здесь играть?»
в правой колонке, перед будущими представителями #1061; на мобильных — в
обычном потоке, не скрывается вместе с быстрыми действиями. В mskba_dark,
где нет аналогичной правой колонки, используется стандартная секция перед
адресом. Блок скрыт при отсутствии контактов; залы наследуют контакты Venue.
Обе темы и визуальная проверка sticky/mobile входят в итоговую приёмку #1063.
Изменение типа/значения
сбрасывает подтверждение и публичность, отменяет ожидающие коды, сохраняет
историю подтверждений и аудит. Удаление также отменяет коды. Комментарий
не включается в стандартную сериализацию; показ в Filament явный.
Используется существующий Auditable. Подтверждение контакта площадки
не подтверждает личность, пользовательский email или коммерческие права.
Действие «Пригласить» в карточке подтверждённого email использует общую
форму AccountInvitationResource::issueFields с фиксированной площадкой и
адресом. AccountInvitationManager::create принимает optional venueContactId
и под блокировкой площадки повторно проверяет принадлежность, текущий email,
verified_at и права обоих контуров. Событие created сохраняет ID источника;
email приглашения неизменяем при последующем редактировании контакта.
Отправка, повтор через обновление ссылки и проверка дубликатов остаются
в штатном сервисе. В таблице контактов колонка «Подключение» использует VenueContactConnectionStatus:
только при доступе к справочнику и приглашениям и полномочиях управления
участниками данной площадки (либо superadmin). Приоритет актуальному pending
приглашению для текущего email, затем последнему по ID. Совпадение с одним
подтверждённым пользовательским email у подтверждённого контакта — справочная
связь с canonical user, не выдача полномочий. Несвязанную с площадкой личность
видит только superadmin; делегированный сотрудник — после принятого приглашения
или действующего договора. Активные договоры берутся через существующую проверку
VenueMembershipAccess, исключаются договоры других площадок и отдельных кортов,
неподтверждённые или заблокированные аккаунты не обозначаются как активные.
История контакта в модальном окне показывает до 50 последних попыток OTP,
без кода, хеша и произвольных метаданных. ContactVerification::effectiveStatus
учитывает истечение срока pending без изменения записи БД. Фильтр «Архив
контактов» открывает soft-deleted записи только для просмотра, без действий
редактирования, подтверждения, назначения основным или приглашения.
VenueContactHistory повторно проверяет полномочия и принадлежность контакта
площадке; выводит до 50 последних изменений из AuditLog с датой, ID
исполнителя и разрешёнными полями до/после (тип, значение, назначение,
комментарий, основной, публичный, дата подтверждения), без произвольных
метаданных. Публичный блок и выбор контакта для аренды — следующие
инкременты #1059.
Не отправлять тестовые коды на адреса реальных партнёров.

## Развитие модели

Следующие шаги должны добавляться отдельными use case:

- смена значения контакта;
- повторная отправка кода;
- проверка кода;
- истечение срока действия подтверждения;
- выбор основного контакта внутри сущности и типа контакта.

Ограничение "один основной контакт на тип" пока не закреплено уникальным индексом, потому что нужно отдельно определить правила для публичных, неподтвержденных и исторических контактов.
