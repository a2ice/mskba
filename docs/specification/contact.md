## Назначение

`Contact` - отдельный доменный контекст для контактных каналов разных сущностей проекта.

Контакты нужны не только пользователям, но и площадкам, событиям и будущим доменным сущностям. Поэтому модель вынесена из `Identity`.

## Граница контекста

Код контекста расположен в `App\Modules\Contact`.

Текущие доменные модели:

- `Contact`;
- `ContactVerification`.

Текущие application DTO:

- `CreateContactDTO`.

Текущие strategy:

- `EmailContactVerificationStrategy`.

Текущие enum:

- `ContactTypeEnum`;
- `ContactVerificationChannelEnum`;
- `ContactVerificationStatusEnum`.

## Contact

`Contact` хранит сам контактный канал сущности.

Таблица `contacts`:

- `contactable_type` - morph alias связанной сущности;
- `contactable_id` - id связанной сущности;
- `type` - тип контакта: `email`, `phone`, `telegram`, `vk`, `other`;
- `value` - значение контакта;
- `label` - человекочитаемая пометка, nullable;
- `is_primary` - основной контакт;
- `is_public` - можно ли показывать публично;
- `verified_at` - дата подтверждения текущего значения контакта, nullable;
- `meta` - JSON для расширений, nullable.

`verified_at` в `contacts` фиксирует текущее агрегированное состояние контакта. История попыток и каналов подтверждения хранится в `contact_verifications`.

## ContactVerification

`ContactVerification` хранит попытку или процесс подтверждения контакта.

Таблица `contact_verifications`:

- `contact_id` - связанный контакт;
- `channel` - канал подтверждения: `email`, `sms`, `telegram`, `call`, `other`;
- `status` - статус подтверждения: `pending`, `confirmed`, `expired`, `failed`, `cancelled`;
- `code_hash` - hash проверочного кода, nullable;
- `sent_to` - адрес или номер, на который отправлялось подтверждение;
- `attempts_count` - количество попыток ввода;
- `max_attempts` - лимит попыток;
- `expires_at` - срок действия подтверждения, nullable;
- `verified_at` - дата успешного подтверждения, nullable;
- `failed_at` - дата неуспешного завершения, nullable;
- `meta` - JSON для расширений, nullable.

Тип контакта и канал подтверждения разделены намеренно. Например, `phone` может подтверждаться через `sms` или `call`, а `telegram` - через бот.

## Полиморфная связь

Для связи используется стандартный Laravel morph naming:

- `contactable_type`;
- `contactable_id`.

В базе должны храниться короткие morph alias, а не FQCN классов.

Текущая morph map:

- `user` -> `App\Modules\Identity\Domain\Models\User`;
- `venue` -> `App\Modules\Venue\Domain\Models\Venue`.

Связанные модели должны объявлять:

- `contacts(): MorphMany`.

## Аккаунт

В личном кабинете есть страница `account.contacts`.

Текущий реализованный flow:

- пользователь видит список своих контактов;
- пользователь может добавить контакт;
- первый контакт пользователя автоматически создается с `is_primary = true`, чтобы он сразу отображался в профиле;
- следующие контакты пользователя создаются с `is_primary = false`;
- при добавлении контакт создается с `is_public = false` через default таблицы.
- пользователь может запустить подтверждение email-контакта;
- при запуске подтверждения создается `ContactVerification` со статусом `pending`;
- код подтверждения хранится в БД только как `code_hash`;
- письмо с кодом отправляется через Laravel mailer.
- повторный запрос email-кода в течение 60 секунд не создает новый код и возвращает информационное сообщение;
- повторный запрос после 60 секунд отменяет старый pending-код и отправляет новый.

Добавление контакта не запускает подтверждение автоматически. Процесс подтверждения запускается отдельным действием пользователя.

Смена основного контакта должна быть отдельным flow. Для нее нужно проверять, что новый основной контакт подтвержден.

Выбор публичности контакта должен быть отдельным flow редактирования контакта. Для него тоже нужно учитывать подтверждение контакта.

Use case создания контакта принимает `CreateContactDTO`, а не слабый массив данных.

Локально email отправляется через SMTP и может приниматься Mailpit, если окружение настроено на `MAIL_MAILER=smtp`, `MAIL_HOST=127.0.0.1`, `MAIL_PORT=1025`.

Запуск подтверждения построен через strategy:

- `ContactVerificationStrategy` описывает методы `supports(Contact $contact)` и `start(Contact $contact)`;
- `ContactVerificationStrategyResolver` выбирает стратегию по `supports`;
- `StartContactVerificationHandler` не содержит ветвления по типам контакта и делегирует типоспецифичную логику выбранной стратегии.

Это нужно, чтобы добавление подтверждения phone, Telegram, VK и других типов происходило через новые strategy-классы, без изменения handler.

## Развитие модели

Следующие шаги должны добавляться отдельными use case:

- смена значения контакта;
- повторная отправка кода;
- проверка кода;
- истечение срока действия подтверждения;
- выбор основного контакта внутри сущности и типа контакта.

Ограничение "один основной контакт на тип" пока не закреплено уникальным индексом, потому что нужно отдельно определить правила для публичных, неподтвержденных и исторических контактов.
