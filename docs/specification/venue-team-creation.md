## Мастер площадки

Канонические маршруты `venues.create` и `venues.store` сохраняются. Общий partial `venues.form` включается с `compactCreate` и `createWizard`; редактирование и другие использования partial остаются обычной формой. Визуальные компоненты переиспользуют мастер мероприятий, поведение двух шагов реализует отдельный `venue-create-wizard.js` без подключения event-specific handlers.

Выбор варианта кликом сразу открывает основные данные; клавиатурный выбор также поддерживается. Tooltip о документах не переключает шаг. Кнопка «Назад» на первом шаге возвращает в каталог, на втором — к вариантам без сброса данных. Условия оплаты и подтверждения бронирования вынесены из общей формы на [отдельную страницу условий](venue-conditions.md); необязательные поля существующих create/update API сохранены для совместимости.

`creation_role` — необязательный для совместимости POST-параметр с допустимыми значениями `representative|contributor` из `VenueCreationRoleEnum`. Для представителя `CreateAccountVenueHandler` сохраняет постоянный draft заявки на управление и необязательные сканы; выбор не является правом доступа. Адресные подсказки, геопозиция, модерация и серверная проверка дублей сохраняются. Подробный контракт: [Черновик заявки и документы](venue-ownership-drafts.md).

HTML-ответ по-прежнему перенаправляет на `account.venues.edit`; переход к заявке представителя определяется сохранённым draft в БД и доступен позднее. JSON-ответ сохраняет прежний payload и возвращает `management_url` на черновик и `ownership_claim.id/status`; для contributor оба значения null. Существующие API-клиенты без `creation_role` продолжают работать. Страница создания использует общую карточку справки layout, без копии контента FAQ.

## Пресеты команды

`TeamLogoPresets` предоставляет allowlist `crest-00`–`crest-14`, URL и чтение существующих WebP из `public/images/tournament-team-logos`. Произвольные пути от клиента не принимаются. Поле `logo_preset` необязательно; пустой выбор сохраняет прежнее создание без логотипа.

Выбранное изображение сохраняется `TeamLogoManager` как отдельный WebP до 500 px в `teams/{id}/{uuid}.webp` на public disk, collection `team_logo`, source `preset`. Общие пресеты остаются неизменными; после создания команда использует существующие endpoints загрузки и удаления логотипа. Изменений схемы БД нет.

## Транзакции и проверки

Команда, дисциплины, owner-контракт и Media логотипа создаются в общей транзакции. При ошибке записи файла создание откатывается; manager очищает файл при собственном сбое, а внешний обработчик также очищает файл при откате внешней транзакции. Файловое хранилище не участвует в SQL-транзакции, поэтому требуется такая компенсация.

Сохраняется порядок блокировок создания: allocator имени блокирует пользователя, затем manager блокирует новую Team и ее Media. Новая команда не доступна другим транзакциям до commit; сценарий не вводит обратного порядка блокировок существующих команд. Сохранение и замена логотипа используют прежнюю сериализацию `Team → Media`.

Профильные проверки защищают выбор разрешенного пресета, сохранение и удаление независимой копии, откат команды и owner-контракта при ошибке хранилища, сохранение неподтвержденного статуса площадки и валидацию сценария. Frontend-изменения требуют production build; визуально проверяются два шага, возврат назад, выбор эмблемы и mobile-layout.
