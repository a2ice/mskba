# Единый центр «Пользователи и права» — архитектура

## Что уже реализовано
Filament \`/backoffice/backoffice-users\`: общая карточка пользователя, отдельные глобальные
группы (создание, критичные функции, вход и действия Filament), права по умолчанию
для роли, индивидуальные запреты, просмотр источника выдачи. Данные живут в
существующей таблице \`user_operational_permissions\`, не в новой системе ролей.

Администратор может менять **некритичные глобальные права** только пользователям
с более низкой системной ролью и не может выдать право, которого сам лишён.
Superadmin управляет критичными правами, Filament и нижестоящими ролями.
Собственные и равные/старшие системные роли из этого интерфейса не редактируются.
\`REVIEW_PROFILE_CHANGES\` применимо только к пользователю admin.
Права выдаются серверными handlers, включая ограничения истории заявок,
курсоры техподдержки и немедленный отзыв доступа. Изменение роли/статуса пользователя
этой формой не поддерживается. Существующие domain permissions не меняются.

## Контекстные права — подтверждённое продуктовоe правило для следующего этапа
У каждого **типа сущности** есть полный определённый каталог прав. Этот список —
глобальное определение возможностей типа объекта, но **не глобальная выдача
пользователю доступа ко всем экземплярам**.

При обращении к **конкретному экземпляру** все права каталога имеет:
- Владелец сущности
- Создатель сущности (если роль создателя предусмотрена моделью и сохраняется)
- Администратор **данной сущности**, а не обязательно глобальный системный admin
- Superadmin MSKBA

Сотруднику или участнику могут быть выданы только разрешения из каталога
**конкретной** сущности с проверкой действительного членства/назначения.
Делегирование не расширяет полномочия выдавшего и не должно давать доступ
к другим экземплярам. Изъятие полномочий должно немедленно запрещать действия
и чтение приватной истории, как в существующих процессах заявок.

Данная архитектура не заменяет существующие записи назначения прав для Team,
Venue, Event, Tournament, SportsSection и Contract, и **не объявляет**, что
действующие реализации уже обеспечивают все перечисленные инварианты.
Перед включением единой UI-выдачи контекстных прав нужны отдельные ревизия
каждого policy/membership, тестирование owner/creator/admin, приватности
старых данных и N+1/SQL EXISTS.

## План следующего шага
1. Read-only список объектных контекстов пользователя в общей карточке без
   чтения чужих прав и тяжёлого соединения нескольких таблиц.
2. Редактор разрешений в рамках отдельного экземпляра (по переходу из списка)
   с его существующим authorization handler, без новой универсальной таблицы.
3. Регрессии: owner/creator/entity-admin/superadmin — полный каталог;
   участник только назначенный набор, отзыв действует немедленно.
4. Контролируемая миграция объектов, с сохранением текущих участников и аудита.
