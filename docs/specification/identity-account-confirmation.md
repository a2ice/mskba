## Назначение

Документ описывает техническую модель подтверждения аккаунта в `Identity`.

Подтверждение аккаунта переводит пользователя из `UserStatusEnum::UNCONFIRMED` в `UserStatusEnum::CONFIRMED` после выполнения обязательных шагов wizard.

## Граница контекста

Flow находится в `App\Modules\Identity`, потому что работает со статусом пользователя, базовым профилем `Profile` и ролями участия `UserParticipationRole`.

Подтвержденный основной контакт берется из `App\Modules\Contact`. Это внешнее для `Identity` условие, но проверка находится в wizard, потому что именно wizard принимает решение о переводе `users.status` в `confirmed`.

Текущие application DTO:

- `AccountConfirmationStepDTO`.

Текущие application services:

- `AccountConfirmationWizardService`.

Текущие use case:

- `CompleteAccountConfirmationWizardHandler`.

## Wizard

Страница wizard находится в личном кабинете:

- route `account.confirmation`;
- route `account.confirmation.complete`;
- route `account.confirmation.contact.store`;
- route `account.confirmation.contacts.verification.store`;
- route `account.confirmation.contacts.verification.confirm`;
- view `theme::pages.account.confirmation`.

На странице `/account` для пользователя со статусом `unconfirmed` отображается кнопка "Подтвердить аккаунт".

Шаги wizard вычисляются из текущего состояния пользователя. Каждый шаг имеет:

- технический ключ;
- заголовок;
- описание;
- признак обязательности;
- признак выполнения.

Обязательные шаги отображаются с маркером `(О)`, необязательные будущие шаги - с маркером `(Н)`.

Wizard заполняется пошагово на клиенте: пользователь может двигаться вперед и назад по шагам. Необязательные шаги не блокируют переход вперед или финальное подтверждение. Зависимые шаги пересчитываются на клиенте: например, шаги даты рождения и пола появляются при выборе роли `player` или `coach`.

Если у пользователя уже есть роль участия, шаг `participation_role` не выводится и wizard начинается со следующего применимого шага. В шапке шагов после выбора роли клиентский JS показывает накопленную summary-информацию из предыдущих шагов, например выбранную роль, дату рождения и пол.

Сохранение выполняется одним финальным submit формы на `account.confirmation.complete`. Серверная валидация повторно проверяет все обязательные условия, поэтому клиентский wizard не является источником доверия.

## Шаги первой итерации

Текущие обязательные шаги:

- `primary_verified_contact` - иметь подтвержденный основной контакт;
- `participation_role` - выбрать роль участия, если у пользователя еще нет роли;
- `birth_date` - заполнить дату рождения для ролей `player` и `coach`;
- `gender` - указать пол для ролей `player` и `coach`;

Текущие необязательные шаги:

- `name` - заполнить имя и фамилию.

Роль участия создается в `user_participation_roles` с:

- `status = active`;
- `assigner = user`;
- `assigned_by = id текущего пользователя`.

Если основной контакт уже подтвержден, wizard показывает его как выполненный шаг. Если основного контакта нет, wizard позволяет добавить email как первый контакт пользователя и отправить код подтверждения. Если основной контакт есть, но не подтвержден, wizard позволяет отправить код и подтвердить контакт без перехода на отдельную страницу контактов.

## Подтверждение статуса

`CompleteAccountConfirmationWizardHandler` сохраняет все данные wizard в одной транзакции.

Если пользователь находится в статусе `unconfirmed` и все обязательные шаги выполнены, статус пользователя обновляется на `confirmed` в рамках финального submit.

Финальный submit повторно проверяет наличие подтвержденного основного контакта. Пользователь без такого контакта остается в статусе `unconfirmed`.

Перевод аккаунта в `confirmed` выполняется через доменный метод `User::confirmAccount()`. Этот метод повторно защищает инвариант: подтвердить можно только `unconfirmed` аккаунт с подтвержденным основным контактом. Бизнес-flow не должен менять `users.status` прямым `update(['status' => ...])`.

Блокировка аккаунта выполняется через доменный метод `User::blockAccount()`. Удаленный аккаунт нельзя переводить в `blocked`.

Обновление роли участия выполняется в транзакции с блокировкой строки пользователя, чтобы два параллельных запроса не создали несколько стартовых ролей в одном flow.

## Развитие модели

Следующие шаги должны добавляться отдельными задачами:

- необязательные шаги wizard;
- role-specific требования для других ролей;
- отдельные профили участия, например `CoachProfile`;
- админская или модерационная проверка подтверждения аккаунта, если потребуется;
- события/уведомления после успешного подтверждения аккаунта.
