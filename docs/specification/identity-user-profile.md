## Назначение

Документ фиксирует техническую модель базового профиля пользователя в `Identity`.

## Базовая модель

Профиль пользователя вынесен в модель `Profile` и таблицу `profiles`.

Первая итерация профиля хранит минимальный набор персональных данных, которые могут быть заполнены позже.

## Связь с пользователем

- `User` -> `hasOne(Profile)`
- `Profile` -> `belongsTo(User)`

На уровне базы действует ограничение `1-to-1` через уникальный `profiles.user_id`.

## Поля профиля

Базовый набор полей:

- `first_name` - nullable;
- `last_name` - nullable;
- `middle_name` - nullable;
- `birth_date` - nullable;
- `gender` - nullable enum `UserGenderEnum`.

Для `gender` на текущем этапе используются значения:

- `male`;
- `female`.

Модель `Profile` также содержит accessor `age`, вычисляемый из `birth_date`.

## Создание профиля

При регистрации пользователя `RegisterUserHandler` вызывает `CreateUserAccountHandler`, а тот создает `User` и связанный `Profile` в одной транзакции.

На первом этапе профиль создается с пустыми nullable-полями, если дополнительные данные профиля не переданы.

`UserFactory` тоже создает связанный профиль автоматически, чтобы тестовая и development-модель пользователя соответствовала реальной бизнес-логике регистрации.

## Аватар профиля

`Profile` связан с общим `Media` через polymorphic relations `media` и `activeAvatar`; в morph map используется стабильный alias `profile`. Коллекция `avatar` содержит не более трёх записей, ровно одна из них имеет `is_featured = true` и используется в аккаунте и шапке.

`StoreProfileAvatarHandler` принимает байты доверенного после transport-валидации файла, повторно проверяет фактический формат и геометрию, преобразует изображение через GD в WebP и сохраняет только итоговую версию до 200 пикселей по большей стороне. Вход ограничен JPEG/PNG/WebP, 5 МБ и 6000×6000. Файлы находятся на `public` Storage-диске в `avatars/{profile_id}`, БД хранит путь, размер, MIME, источник и хеш ссылки источника.

PHP Docker-образ собирает GD с поддержкой JPEG и WebP. Установка и production deploy создают стандартную Laravel-ссылку `public/storage -> storage/app/public`, поэтому Nginx отдаёт аватары как обычные публичные файлы.

Смена активного файла и очистка сверх лимита выполняются в транзакции с `lockForUpdate` на профиле. Это сериализует параллельные загрузки и защищает инварианты «не более трёх» и «один активный». После commit физический файл удалённой старой записи удаляется с диска; при ошибке транзакции удаляется новый файл.

Ручная загрузка имеет источник `upload`. Асинхронная локальная копия Telegram имеет источник `telegram`; она может обновить только отсутствующий или предыдущий Telegram-аватар и не перезаписывает ручной выбор пользователя.
