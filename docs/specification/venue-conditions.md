## Страница и доступ

`GET/PUT /account/venues/{alias}/conditions` — `account.venues.conditions.edit/update`. Ссылка «Условия» включена в общую внутреннюю навигацию рядом с редактированием. Страница содержит только условия оплаты `unknown|free|paid` и необходимость подтверждения бронирования. Коммерческая booking policy остается отдельным процессом «Условия аренды».

`ShowEditableVenueHandler` и `VenueAccessResolver::canEdit` сохраняют существующие правила авторства и договорного доступа. Посторонний пользователь не может просмотреть или изменить условия. PUT требует незаблокированный аккаунт. При pending-модерации поля недоступны в UI, а use case повторно запрещает запись.

## Сохранение и модерация

`UpdateVenueConditionsRequest` принимает только два поля условий. `UpdateVenueConditionsHandler` для неподтвержденной площадки меняет два признака и увеличивает `content_version`; описание, тип, адрес, теги и фотографии не затрагиваются.

Для подтвержденной площадки handler получает общую draft revision и заменяет только два поля `payload.details`. Остальные данные и изменения ревизии сохраняются. Опубликованные признаки не меняются до обычного одобрения модерации. Ссылка «Открыть модерацию» ведет к существующей отправке ревизии.

При несовпадении `base_content_version` запись условий отклоняется существующей проверкой `assertCurrent`, чтобы не перезаписать устаревшим snapshot новую версию. Общая форма редактирования не отправляет поля условий; действующие updater/revision manager сохраняют их при отсутствии в запросе. Необязательные поля прежних API оставлены для совместимости; новая страница использует отдельный узкий запрос.

## Конкурентный доступ и проверки

Чтение для изменения и сохранение выполняются в одной транзакции с блокировкой Venue, затем draft revision, в том же порядке, что общее редактирование. Это сериализует сохранения двух страниц и предотвращает потерю изменений при read-modify-write общей ревизии. Сетевые вызовы внутри транзакции не добавляются.

Профильные проверки: сохранение условий без изменения других данных; сохранение существующей ревизии и условий при последующем редактировании; запрет для постороннего и при pending-модерации. Изменение UI мастера требует production build.
