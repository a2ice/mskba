# ADR: разделение Event и Game

## Статус

Принято 6 августа 2026 года. Реализация выполняется поэтапно в задаче 084.

## Контекст и решение

`Event` отвечает за организацию: площадку и бронирование, общий интервал, организатора,
ответственных, участников, регистрацию, видимость, публикации, обсуждение, общие медиа и итог.

`Game` отвечает за спортивное действие: формат, стороны, составы, счет, внутренний слот,
фактический lifecycle, статистику и победителя. Каждая игра обязательно принадлежит мероприятию,
но мероприятие может иметь ноль, одну или несколько игр.

Мини-игра не является отдельным доменным типом. Это обычная `Game` внутри многoигрового `Event`;
термин можно сохранить только в UI. `Game` не получает отдельное `VenueBooking`: все игры используют
площадку и бронь родительского мероприятия. Это позволяет в будущем добавить игровые зоны и
параллельные матчи без дублирования бронирований.

## Целевая схема

### games

- `id`;
- `event_id` — обязательный внешний ключ;
- `legacy_event_id` — nullable unique, временное соответствие старому игровому Event;
- `created_by_actor_id`;
- `title`, `description` — nullable;
- `status`: `scheduled`, `in_progress`, `awaiting_result`, `completed`, `cancelled`;
- `side_a_size`, `side_b_size`, `scoring_type`;
- `statistics_mode`, `statistics_status`, `statistics_version`;
- `statistics_confirmed_at`, `statistics_confirmed_by_actor_id`;
- `scheduled_starts_at`, `scheduled_ends_at` — nullable;
- `actual_started_at`, `actual_started_by_actor_id`;
- `actual_ended_at`, `actual_ended_by_actor_id`;
- `completed_at`, `completed_by_actor_id`;
- `cancelled_at`, `cancelled_by_actor_id`, `cancellation_reason`;
- `winner_game_side_id` — nullable, добавляется после создания игровых сторон;
- timestamps и soft deletes.

Отдельный `is_time_scheduled` не хранится: наличие расписания определяется nullable-полями.

### Игровые таблицы

`game_sides`, `game_roster_entries` и `game_player_statistics` переходят с `event_id` на `game_id`.
Уникальность стороны, пользователя состава и строки статистики определяется внутри `game_id`,
поэтому один участник может играть в нескольких играх одного мероприятия.
Для состава и статистики должны применяться ограничения, не позволяющие связать запись со стороной
другой игры. `game_details` после переноса данных упраздняется.

### Поля, переносимые в Game

Из `events` переносятся только фактические игровые timestamps и actor-ссылки начала, окончания,
завершения и отмены. Общий интервал, организационный статус и текстовый итог остаются у `Event`.

Из `game_details` переносятся размеры сторон, тип подсчета, режим и статус статистики, версия и
подтверждение. Счет остается у `GameSide`; победитель хранится явной ссылкой на сторону.

## Инварианты

- внутренний игровой слот находится внутри интервала Event;
- `GameRosterEntry` относится к участнику родительского Event либо к активному участнику постоянной
  команды соответствующей стороны по явно разрешенному сценарию;
- игрок не попадает автоматически во все игры мероприятия;
- запуск или завершение одной игры не меняет lifecycle соседних игр;
- Event нельзя завершить при незавершенных активных играх;
- отмененные игры не входят в агрегированную статистику;
- итог Event агрегирует подтвержденную статистику завершенных игр без двойного учета.

## Права и маршруты

Отдельная ACL для Game пока не вводится. Игровые права вычисляются через ответственных и договорные
права родительского Event, но application-сервисы принимают конкретную `Game`.

Канонические маршруты вложенные:

- `GET /events/{event}/games/{game}` — карточка игры;
- `POST /events/{event}/games` — создание;
- `PUT|DELETE /events/{event}/games/{game}` — параметры и удаление;
- `POST .../start|end`, `PATCH .../score|statistics|roster`, `PUT .../lineup` — lifecycle.

Каждый endpoint проверяет `game.event_id === event.id`; доступ через чужое мероприятие возвращает
`404`, чтобы не раскрывать существование игры. Отдельная Game ACL не вводится: разрешения вычисляются
по организатору и принятым договорным правам родительского Event.

## Миграция данных

Переход выполняется двумя releases в maintenance-окно:

1. добавить `games` и nullable `game_id` без удаления legacy;
2. создать одну Game для каждого обычного игрового Event;
3. преобразовать каждый дочерний mini-game Event в Game родительского Event;
4. перенести detail, стороны, составы и статистику и сверить количества/контрольные суммы;
5. применить промежуточный release и выполнить `php artisan games:migrate-legacy` (dry-run);
6. при нуле конфликтов выполнить `php artisan games:migrate-legacy --apply` и сверить orphan counts;
7. переключить runtime и проверить канонические и старые URL;
8. отдельным cleanup release удалить дочерние Event только после проверки отсутствия собственной
   брони и иных конфликтующих данных;
9. сделать новые ключи обязательными и удалить старые связи, `game_details`, игровые поля Event и
   `parent_event_id`.

Перенос должен быть идемпотентным благодаря `legacy_event_id`. Если дочернее событие имеет отдельную
бронь, площадку, публикацию либо собственные данные, которые нельзя однозначно объединить, миграция
останавливается и регистрирует конфликт вместо потери данных.

## Обратная совместимость URL

Старый URL обычного игрового Event остается URL мероприятия; единственная игра встраивается в его UI.
Старый URL дочернего mini-game Event сохраняется в `legacy_game_routes` до удаления Event и отвечает
постоянным redirect на `/events/{parent}/games/{game}`. Таблица mapping не зависит от существования
старой строки Event и удаляется только после согласованного срока совместимости.

## Турнирное расширение

Будущий `TournamentMatch` ссылается на `Game` через nullable `game_id`: матч описывает положение в
сетке, игра — фактическое проведение. Прямой `games.tournament_id` не добавляется. Встроенный турнир
принадлежит одному Event, полноценный объединяет несколько Event.

## Риски

- частично перенесенные production-данные — предотвращаются maintenance-окном, транзакциями и аудитом;
- опубликованные Telegram URL — сохраняются legacy mapping и redirect;
- двойной учет статистики — агрегирование только через Game и уникальные ограничения;
- cross-game side/roster — составные внешние ключи и серверные invariants;
- дедлоки при параллельном lifecycle — единый порядок блокировок: Event, затем Game, затем GameSide;
- дочерние события с собственной бронью — блокирующий migration conflict, а не автоматическое удаление.
