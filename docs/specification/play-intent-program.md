## Модули и границы

- **PlayInterest / PlayMatching (286):** запросы игрока, география и временные окна, фильтрация/совпадения, объяснимая сортировка, подписка и пользовательские уведомления. Не создаёт Event/booking и не резервирует слот.
- **PlayAssembly (287):** кандидат-группа, членство, единственный активный процесс для игровой возможности, групповое согласование и управленческие права, персональное подтверждение, переход к Event/Booking.
- **VenueDemand / Offers (288):** агрегированные проекции спроса и условия коммерческих предложений в scoped-интерфейсе площадки, доставка разрешённым адресатам, связь с существующим Assembly. Не владеет первичными записями интересов.

Чёткие границы с готовыми модулями: `Venue`/`VenueCourt`/`Amenity` — характеристики; `VenueBooking` — доступность, quote, hold, payment lifecycle; `Event` — опубликованное мероприятие и участники; `Coordination` — опросы; `Notification` — доставка; `Identity`/`Contract` — пользователи и права. Никаких независимых дубликатов бронирований/голосов/кошельков.

## Надёжность и доступность

1. **Court-aware availability**: текущий `SearchVenuesHandler` фильтрует часть занятого на уровне Venue; целевые рекомендации должны опираться на единые правила конфликта конкретного `VenueCourt` и scope `WHOLE/HALF_*` через `GetVenueAvailability`/`VenueEventAvailability`, с учётом расписаний, исключений, operational status, holds. Перед применением quote/booking занятость перепроверяется.
2. Matching: hard filters по radius/amenities/payment/длительности/формату; soft preferences для ранга. Объяснимое scoring без недоказанной «вероятности»; калибруемые веса. Если availability неизвестна — явный статус «уточняется».
3. Дедупликация: один пользователь — одно голосующее лицо/одна заинтересованность в конкретной возможности. Пересечения намерений не умножают спрос.
4. Assembly: PostgreSQL транзакция + блокировка и защищённый уникальностью active process; отдельный алгоритм обнаружения пересечений игровых возможностей, чтобы разные id Opportunity не обходили защиту. Повторное создание/уведомление идемпотентно, Event/booking transition — отдельные транзакции.
5. Снимки версий: условия игры, цена, обязательства, дедлайны, список приглашённых, результаты голосования и решения. Смена площадки/времени/суммы инвалидирует прежнее персональное подтверждение.
6. Match recalculation по событиям/очереди с безопасным TTL/идемпотентностью, ограничениями частоты и серверной проверкой доступа при чтении; не считать Redis cache источником юридически значимого состояния.

## Доступ, уведомления, приватность

- В этапе 286 ограничение CRUD `PlayIntent` своим каноническим User. Гостю разрешён предварительный подбор, сохранение после корректного auth flow — политика допуска подлежит согласованию.
- В этапе 287 члены группы имеют scoped видимость голосований; инициатор и помощники получают **точечные** permissions. Старые `CoordinationAccess::canManage` и `VoteInPollHandler` не предоставляют нужной проверки групповости автоматически — расширить доменный authorization path без ослабления чужих опросов.
- В этапе 288 владелец/сотрудник с активным договорным доступом, разрешённым через `VenueMembershipAccess`/`VenueCommercialAccess`; новые `VenuePermissionEnum` согласовать с каталогом прав и default/allowed matrices.
- Аналитика без открытых персональных данных: агрегаты, минимальный порог выборки, контроль сегментов, запрет контактов/экспортов без основания. Членство и предпочтения не публиковать как идентифицирующий список по умолчанию.
- `UserNotification` и каналы доставки для сервисных уведомлений; отдельный explicit opt-in, дедупликация, frequency cap, отмена подписки для предложений от площадок. Логировать решение о доставке и suppression.

## Интеграционные долги и этапы

- `CoordinationSession` имеет context type EVENT/VENUE/TEAM/COMMUNITY/CHAT, но ещё нет контекста PlayAssembly; на этапе 287 согласовать новый тип или явную таблицу связи, не навязывать создание Event до начала голосования.
- `VenueBookingAttendanceRound` сейчас привязан к уже удерживаемой брони: предбронировочное подтверждение группы — новая логика этапа 287.
- `BookingContributionCommitment` означает **обещание**, а `VenueBookingPaymentAttempt` обслуживает оплату аренды. Multi-payer взносы, возвраты, покупатель/получатель и финансовые документы должны быть согласованы до денежного этапа; не выдавать обещание за факт оплаты.
- `VenueBookingQuote` / policy snapshot должны принимать структурированное, ограниченное по сроку спецпредложение из этапа 288; пересчёт подчиняется существующему lifecycle, без прямой правки quote client-side.
- UI следует принятой [дизайн-системе](ui-design-system.md), реальным компонентам и [теме MSKBA App](../mskba_app/start_here.md). **Правило local-only для разработки MSKBA App остаётся в силе**: данный документ не разрешает push/deploy изменений темы.
- Каждая задача получает свой design review, технический план, миграции, тесты, scope/безопасность и QA перед реализацией. Порядок 286 → 287 → 288, и каждый старт — только после отдельного подтверждения пользователя.
