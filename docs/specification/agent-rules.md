## Назначение

Этот документ хранит правила работы AI-агента именно как исполнителя задач в данном проекте. Он не дублирует продуктовую или архитектурную документацию, а задает правила интерпретации задач, поведения при неоднозначности и фиксации повторяемых замечаний.

## Когда обращаться к этому документу

Агент должен обращаться к этому документу:

- перед началом выполнения задачи вместе с `docs/specification.md`;
- когда формулировка задачи допускает несколько вариантов реализации;
- когда пользователь дает замечание или корректировку не только по результату, но и по способу работы агента;
- когда нужно понять, следует ли уточнять решение, а не выбирать вариант самостоятельно.

## GlobalRule1 - фиксировать важные корректировки в правилах агента

Если пользователь дает важное замечание или корректировку по способу работы AI-агента, агент должен оценить, является ли это замечание повторяемым правилом.

Если замечание формирует новое устойчивое правило работы:

- агент сначала формулирует в чате намерение добавить это правило в исполняемую документацию;
- кратко объясняет, почему правило нужно и куда именно оно будет добавлено;
- вносит изменение только после согласования с пользователем.

После внесения такого правила агент должен применять его во всех последующих похожих ситуациях.

## CaseRule1 - сначала локальный паттерн, потом логика, потом уточнение

При изменении существующего поведения агент должен:

1. сначала опираться на уже существующий локальный паттерн в коде;
2. затем проверять, согласуется ли предполагаемое решение с логикой конкретной задачи;
3. затем сверять решение с общей логикой проекта;
4. если после этого остаются несколько разумных вариантов, а выбор меняет контракт, формат ответа, тип возвращаемого значения, интерфейс, структуру данных или другой значимый паттерн, остановиться и уточнить решение у пользователя до внесения изменения.

Это правило появилось после задачи `001`, где формулировка "метод должен возвращать текст" при существующем JSON-контракте была интерпретирована слишком буквально. В подобных случаях приоритет должен быть у существующего локального паттерна, если задача явно не требует его изменить.

## CaseRule2 - не добавлять переходные миграции без реальной необходимости

Если задача меняет структуру данных, агент должен уточнить, есть ли в проекте реальные данные или требуется ли поддержка уже существующей базы.

Если реальных данных еще нет и совместимость со старой схемой не требуется:

- агент должен предпочитать сразу корректную целевую схему;
- не должен по умолчанию добавлять переходные рефакторинговые миграции для переноса данных;
- должен отдельно уточнять необходимость таких миграций, если задача затрагивает эволюцию схемы и есть несколько разумных вариантов реализации.

Переходные миграции должны добавляться только тогда, когда они действительно нужны для сохранения существующих данных или поддержки уже используемой среды.

## CaseRule3 - новые enum должны повторять локальный enum-паттерн

При создании нового enum агент должен сначала проверить, как enum уже оформлены в текущем проекте.

Если в проекте для enum принят устойчивый локальный паттерн, агент должен следовать ему по умолчанию. В текущем проекте таким паттерном является наличие `label(): string` у прикладных enum.

Новый enum не должен добавляться в урезанном виде, если существующий локальный паттерн уже предполагает дополнительные методы или человекочитаемый слой представления.

Если агент не уверен, обязателен ли элемент локального паттерна для нового enum, он должен уточнить это до коммита.

## CaseRule4 - не приступать к реализации неоднозначного варианта без уточнения

Если пользователь формулирует задачу как просьбу "разработать вариант", "продумать вариант", "сделать более изящный вариант", "предложить решение" или похожим образом без прямого указания менять код, агент не должен сразу приступать к редактированию файлов.

Перед реализацией агент должен уточнить ожидаемый формат результата:

- нужен ли сначала концепт, описание, план, визуальная идея или несколько вариантов;
- можно ли уже вносить изменения в код;
- какие ограничения важны для решения, если они не следуют однозначно из документации и кода.

Если формулировка допускает и обсуждение, и непосредственную реализацию, агент должен сначала задать уточняющий вопрос или кратко предложить подход, а к изменениям в файлах переходить только после конкретного подтверждения пользователя.

Это правило появилось после случая с `partials.breadcrumbs`, где запрос на "более изящный вариант" был ошибочно воспринят как разрешение сразу менять Blade и CSS.

## CaseRule5 - проверять рабочую директорию перед правками файлов

Перед созданием, переносом или изменением файлов агент должен убедиться, что работает внутри корня основного репозитория проекта: `/Users/dmitrylosev/Projects/mskbabrandnew/site`.

Особенно это важно для `apply_patch`, потому что относительные пути применяются от текущего рабочего контекста инструмента. Если есть риск неоднозначности, нужно использовать абсолютный путь внутри `site`.

Запрещено создавать рабочие файлы задачи, документацию или код в соседних директориях workspace, если инструкция явно требует путь внутри репозитория `site`.

Если файл был случайно создан вне `site`, агент должен сразу перенести его в правильное место, удалить ошибочный внешний файл или пустые директории и сообщить об исправлении.

## Порядок внесения новых agent-rules

Новые правила добавляются в этот документ, если выполняются оба условия:

- замечание пользователя относится не только к текущему кейсу, но и к повторяемому способу работы агента;
- правило может снизить вероятность похожей ошибки в будущих задачах.

При добавлении нового правила желательно:

- дать ему короткое имя или идентификатор;
- описать триггер применения;
- описать ожидаемое поведение агента;
- при необходимости кратко указать, из какого кейса правило появилось.
