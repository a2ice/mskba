## Назначение

Этот документ хранит правила работы AI-агента именно как исполнителя задач в данном проекте. Он не дублирует продуктовую или архитектурную документацию, а задает правила интерпретации задач, поведения при неоднозначности и фиксации повторяемых замечаний.

## Когда обращаться к этому документу

Агент должен обращаться к этому документу:

- перед началом выполнения задачи вместе с `docs/specification.md`;
- когда формулировка задачи допускает несколько вариантов реализации;
- когда пользователь дает замечание или корректировку не только по результату, но и по способу работы агента;
- когда нужно понять, следует ли уточнять решение, а не выбирать вариант самостоятельно.

## GlobalRule1 - фиксировать важные корректировки в правилах агента

Если пользователь дает важное замечание или корректировку по способу работы AI-агента, агент должен оценить, является ли это замечание повторяемым правилом.

Если замечание формирует новое устойчивое правило работы:

- агент сначала формулирует в чате намерение добавить это правило в исполняемую документацию;
- кратко объясняет, почему правило нужно и куда именно оно будет добавлено;
- вносит изменение только после согласования с пользователем.

После внесения такого правила агент должен применять его во всех последующих похожих ситуациях.

## CaseRule1 - сначала локальный паттерн, потом логика, потом уточнение

При изменении существующего поведения агент должен:

1. сначала опираться на уже существующий локальный паттерн в коде;
2. затем проверять, согласуется ли предполагаемое решение с логикой конкретной задачи;
3. затем сверять решение с общей логикой проекта;
4. если после этого остаются несколько разумных вариантов, а выбор меняет контракт, формат ответа, тип возвращаемого значения, интерфейс, структуру данных или другой значимый паттерн, остановиться и уточнить решение у пользователя до внесения изменения.

Это правило появилось после задачи `001`, где формулировка "метод должен возвращать текст" при существующем JSON-контракте была интерпретирована слишком буквально. В подобных случаях приоритет должен быть у существующего локального паттерна, если задача явно не требует его изменить.

## CaseRule2 - не добавлять переходные миграции без реальной необходимости

Если задача меняет структуру данных, агент должен уточнить, есть ли в проекте реальные данные или требуется ли поддержка уже существующей базы.

Если реальных данных еще нет и совместимость со старой схемой не требуется:

- агент должен предпочитать сразу корректную целевую схему;
- не должен по умолчанию добавлять переходные рефакторинговые миграции для переноса данных;
- должен отдельно уточнять необходимость таких миграций, если задача затрагивает эволюцию схемы и есть несколько разумных вариантов реализации.

Переходные миграции должны добавляться только тогда, когда они действительно нужны для сохранения существующих данных или поддержки уже используемой среды.

## CaseRule3 - новые enum должны повторять локальный enum-паттерн

При создании нового enum агент должен сначала проверить, как enum уже оформлены в текущем проекте.

Если в проекте для enum принят устойчивый локальный паттерн, агент должен следовать ему по умолчанию. В текущем проекте таким паттерном является наличие `label(): string` у прикладных enum.

Новый enum не должен добавляться в урезанном виде, если существующий локальный паттерн уже предполагает дополнительные методы или человекочитаемый слой представления.

Если агент не уверен, обязателен ли элемент локального паттерна для нового enum, он должен уточнить это до коммита.

## CaseRule4 - не приступать к реализации неоднозначного варианта без уточнения

Если пользователь формулирует задачу как просьбу "разработать вариант", "продумать вариант", "сделать более изящный вариант", "предложить решение" или похожим образом без прямого указания менять код, агент не должен сразу приступать к редактированию файлов.

Перед реализацией агент должен уточнить ожидаемый формат результата:

- нужен ли сначала концепт, описание, план, визуальная идея или несколько вариантов;
- можно ли уже вносить изменения в код;
- какие ограничения важны для решения, если они не следуют однозначно из документации и кода.

Если формулировка допускает и обсуждение, и непосредственную реализацию, агент должен сначала задать уточняющий вопрос или кратко предложить подход, а к изменениям в файлах переходить только после конкретного подтверждения пользователя.

Это правило появилось после случая с `partials.breadcrumbs`, где запрос на "более изящный вариант" был ошибочно воспринят как разрешение сразу менять Blade и CSS.

## CaseRule5 - проверять рабочую директорию перед правками файлов

Перед созданием, переносом или изменением файлов агент должен убедиться, что работает внутри корня основного репозитория проекта: `/Users/dmitrylosev/Projects/mskbabrandnew/site`.

Особенно это важно для `apply_patch`, потому что относительные пути применяются от текущего рабочего контекста инструмента. Если есть риск неоднозначности, нужно использовать абсолютный путь внутри `site`.

Запрещено создавать рабочие файлы задачи, документацию или код в соседних директориях workspace, если инструкция явно требует путь внутри репозитория `site`.

Если файл был случайно создан вне `site`, агент должен сразу перенести его в правильное место, удалить ошибочный внешний файл или пустые директории и сообщить об исправлении.

## CaseRule6 - предлагать расширяемый паттерн при ожидаемых вариантах поведения

Если задача вводит поведение, для которого уже известны или явно ожидаются несколько вариантов реализации по типу, каналу, провайдеру, статусу, роли или другой предметной оси, агент должен до реализации оценить риск роста условных ветвлений.

Если простое ветвление `if`/`match` решает текущий кейс, но ближайшее развитие с высокой вероятностью добавит новые варианты поведения, агент должен:

- явно назвать простой вариант и его ограничение;
- предложить расширяемый вариант, например Strategy, polymorphic handler, resolver, provider interface или другой локально уместный паттерн;
- выбрать расширяемый вариант, если он не создает непропорциональной сложности и лучше соответствует уже обсужденному развитию;
- если tradeoff неоднозначен, кратко уточнить выбор у пользователя до реализации.

При этом правило не отменяет принцип "не добавлять абстракции без практической необходимости": Strategy или другой паттерн нужен не из-за формального SOLID, а когда новые варианты поведения уже видны из задачи или модели.

Правило появилось после реализации подтверждения контактов, где сначала был добавлен `if` только для email, хотя уже обсуждались будущие phone, Telegram, VK и другие каналы. В таких случаях агент должен заранее подсвечивать Strategy как альтернативу простому ветвлению.

## CaseRule7 - соблюдать task workflow и уточнять режим коммита

Для продуктовых, кодовых, архитектурных и других содержательных задач агент должен по умолчанию следовать процессу из [Task Workflow](task-workflow.md):

- не начинать реализацию прямо в `main`, если пользователь явно не попросил обойти task workflow;
- проверять чистоту `main` перед стартом задачи;
- заводить или использовать задачу в `docs/tasks.md`;
- создавать рабочие материалы в `docs/tasks/{NNN}`;
- создавать отдельную ветку задачи в формате `type/NNN`;
- выполнять коммит в ветке задачи, а merge/push в `main` делать только после явного согласования.

Если пользователь просит сделать небольшую правку без формального workflow, агент должен явно подтвердить, что это исключение из стандартного процесса, и дальше действовать только в рамках согласованного упрощения.

Перед любым коммитом агент обязан отдельно уточнить режим фиксации изменений, если пользователь не указал его явно:

- `коммит` - закоммитить только изменения, относящиеся к текущей задаче, без push;
- `коммит + пуш` - закоммитить только изменения текущей задачи и выполнить push;
- `коммит + пуш всех изменений` - закоммитить и запушить все изменения в рабочем дереве, включая параллельные правки пользователя.

Если в рабочем дереве есть изменения, которые агент не делал, агент должен явно назвать их перед коммитом и не включать их в режимы `коммит` или `коммит + пуш` без отдельного подтверждения. В режиме `коммит + пуш всех изменений` агент включает все текущие tracked и untracked изменения, но все равно предварительно показывает статус.

Правило появилось после нескольких задач, выполненных напрямую в `main` без отдельной записи в `docs/tasks.md`, ветки задачи и явного выбора режима коммита.

## CaseRule8 - сразу деплоить изменения для Telegram Mini App

Если результат задачи можно полноценно проверить только внутри Telegram Mini App, агент должен после реализации и локальных автоматизированных проверок сразу:

- закоммитить относящиеся к задаче изменения;
- выполнить push в согласованную рабочую ветку;
- дождаться деплоя и проверить, что на сервере развернут нужный commit и новые assets доступны.

Отдельно запрашивать подтверждение на commit, push и deploy в таком случае не нужно, если одновременно выполняются условия:

- в задаче нет противоречий или неоднозначности, влияющей на результат;
- не требуется уточнение продуктового или технического решения;
- в рабочем дереве отсутствуют посторонние изменения, которые могут случайно попасть в commit;
- действия укладываются в уже согласованный пользователем workflow ветки.

Это правило является специальным исключением из `CaseRule7`, потому что локальная браузерная проверка не воспроизводит окружение Telegram, его safe area, встроенную навигацию и особенности WebView.

## CaseRule9 - переиспользовать единые UI-компоненты

Перед добавлением или изменением элемента формы агент должен найти уже
используемый в теме компонент с той же ролью. Переключатели, предиктивные
селекторы, загрузчики, кнопки и другие повторяемые элементы должны собираться
из общего partial/component и использовать единые состояния, размеры и
отступы. Страничные копии разметки и локальные визуальные варианты без
продуктовой причины не допускаются.

Стили общего компонента не должны зависеть от случайного внешнего контейнера:
одинаковая разметка обязана выглядеть одинаково в любой форме. После изменения
нужно проверить существующий эталонный экран и новый экран как минимум в
desktop- и mobile-layout.

## CaseRule10 - добавлять тесты соразмерно риску

Агент не должен автоматически добавлять или расширять автотест при каждом
изменении. Новый тест оправдан, если он защищает существенное бизнес-правило,
границу полномочий, целостность или трудно восстановимое изменение данных,
миграцию, внешнюю интеграцию, асинхронный или конкурентный процесс, критический
пользовательский путь либо значимую ранее обнаруженную регрессию.

Косметические изменения текста, иконок, CSS, расположения элементов и
адаптивной разметки по умолчанию проверяются вручную. Feature-тесты не должны
фиксировать точную HTML-структуру, CSS-классы, полный текст страницы или каждый
второстепенный элемент интерфейса, если это не является устойчивым контрактом.

Перед добавлением теста агент обязан проверить существующее покрытие и ответить:
«Какую реальную регрессию обнаружит этот тест, которую с высокой вероятностью
не обнаружат существующие проверки?». Если конкретного ответа нет, тест не
добавляется. Следует выбирать самый низкий достаточный уровень: unit для
бизнес-правила, Feature для HTTP-контракта, прав и записи в БД, integration для
инфраструктурной границы, E2E только для критического пользовательского пути.

Тест не должен быть более хрупким, чем защищаемое поведение. Если обычное
изменение дизайна ломает тест при сохранении бизнес-логики, тест нужно упростить,
перенести на подходящий уровень или удалить. При сомнении агент описывает
короткий сценарий ручной проверки вместо бездумного создания нового теста.

## Порядок внесения новых agent-rules

Новые правила добавляются в этот документ, если выполняются оба условия:

- замечание пользователя относится не только к текущему кейсу, но и к повторяемому способу работы агента;
- правило может снизить вероятность похожей ошибки в будущих задачах.

При добавлении нового правила желательно:

- дать ему короткое имя или идентификатор;
- описать триггер применения;
- описать ожидаемое поведение агента;
- при необходимости кратко указать, из какого кейса правило появилось.
## CaseRule11 - выбирать сущности через predictive search

Если пользователь выбирает существующую Team, User, Venue или другую сущность из потенциально
большого набора, используй проектный predictive-search pattern с backend-поиском, debounce,
отменой stale request, явным выбором результата и повторной серверной валидацией ID. Не заменяй
его ручным вводом ID или длинным заранее загруженным select, если для этого нет явной причины.
Используй общий `partials.forms.entity-predictive-search` и `entity-predictive-search.js`, когда
полю достаточно стандартного контракта `id/name/meta`. Не копируй разметку и обработчики в feature
страницы. Видимый input должен иметь `type="text"`: у `type="search"` браузер рисует собственный
clear control поверх проектного крестика.

## CaseRule12 - использовать готовый пакет UI-иконок

При добавлении UI-иконок агент сначала выбирает подходящую иконку из принятого
общедоступного пакета. Не рисовать SVG path вручную, не конструировать собственные
аналоги и не смешивать разные пакеты/стили без согласования. Если подходящей
иконки нет, предложить готовую альтернативу, а не незаметно перерисовать её.
Сохранять лицензию, источник и версию; размеры задавать пропорционально,
не сжимать иконки flex-layout и не подменять их emoji/текстовыми символами.

Для новой темы задачи 139 выбран Tabler Icons Outline. В статическом стенде
допустим локальный subset оригинальных SVG; в Vue — официальный пакет с явными
импортами. Это правило не требует массовой замены иконок старой темы.
Зафиксировано по прямому указанию пользователя в замечаниях к этапу 002.
