# VK Publisher: two credentials, one publication mode

Community 174334075, Mini App 54729290; VK ID login app 54729329 unaffected. The real provider rejected PKCE and custom callback. Use legacy https://oauth.vk.com/authorize with redirect_uri=https://oauth.vk.com/blank.html, response_type=code, scope=photos and single-use session state. Keep the original .com redirect URI in both requests, even if the browser displays .ru. Admin opens authorization in a new tab and completes it in the first-party MSKBA superadmin form with the VK code/state response. Reject other hosts, fragments, bearer tokens and unmatched/expired state. No code or URL should be shared with third parties or chat. POST only, CSRF and session/actor binding; no query-string callback on MSKBA. Exchange on server with client secret using form POST to https://oauth.vk.com/access_token and no redirects. Save encrypted token only after photo probe. No raw provider error/body, token or code in logs or views. No live wall post in connection checks.

Separate user photo token and community wall token. Full publication requires a cover. No text-only mode. Reauthorize after expiry. Automatic refresh is not confirmed; reference implementation reports ~24 hours and no refresh token. Never claim autonomous long-term posting until confirmed. Live acceptance on MSKBA remains required: verify state survives provider blank redirect, exchange, upload and saved attachment in post. Telegram and VK ID unchanged.

Reference: https://github.com/tequilex/factory/blob/main/factory/core/vk_auth.py and its documentation. Evidence is third-party live experience, not a VK guarantee.
