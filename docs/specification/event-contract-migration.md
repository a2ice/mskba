# Мероприятия и игры — план перехода на единые контракты

**Статус:** архитектурный план и критерии готовности. Event/Game пока **не переключены** на новый ACL; не считать содержимое этого документа готовой функциональностью.

## Почему нельзя переключать Event одним заменённым условием

Сейчас `EventManagementAccess` складывает несколько источников:
- владелец-организатор через `organizer_actor_id`;
- назначенный ответственный `EventParticipant.responsibility_status=accepted` и его `EventResponsibilityPermission`;
- специальные разрешения турнира для конкретного `TournamentMatch`;
- существующее служебное исключение для подтверждённого superadmin.

`Game` управляется через `Event`: отдельные записи Game хранят игровой состав, счёт, период, статистику и результат, но не самостоятельный контракт владельца. Отдельное подтверждение участия игрока нельзя путать с назначением управляющих прав.

## Матрица целевого соответствия

| Текущая роль / связь | Целевая сущность | Правило |
|---|---|---|
| `organizer_actor_id` | Event owner membership | Создатель получает полное бессрочное назначение; выбор другого организатора из бэк-офиса требует согласия |
| Подтверждённый ответственный | Event delegated membership | Название, срок, явный permission snapshot и акцепт |
| Ожидающий ответственный | Приглашение Event | Не предоставляет прав до подтверждения |
| Отклонённый / снятый ответственный | Исторический неактивный договор | Не участвует в `effectivePermissions` |
| `EventResponsibilityPermissionEnum` | `ContractPermission` с scope Event | Проверяется одна и та же семантика каждого permission; финансовое `MANAGE_FUNDS` не выдаётся по умолчанию |
| Турнирный матч | Особое право родительского Tournament | Только предписанные `TournamentPermissionEnum::MANAGE_GAMES` возможности |
| Обычный участник / игрок / статистик | EventParticipant / GameRoster | Не создавать управляющий контракт из участия |
| Тренировка из SportsSection | Проекция секции в Event | Разделить право публикации с управлением независимым мероприятием; не создать второго владельца случайно |

## Все места создания, которые должны быть покрыты

- `CreateEventHandler`, включая обычное событие и тип `GAME`, плюс `SubmitEventWizardHandler`.
- `CreateStandaloneGameHandler`, если создаёт Event напрямую, а не вызывает `CreateEventHandler`.
- `EventBackofficeEditor::createEvent` с выбором `organizer_user_id`: сейчас работает через actor выбранного организатора; необходимо сохранить административного инициатора в audit и требовать принятия чужого контракта.
- `PublishTrainingSessionEventHandler`: проекция секции, где владелец управления и издатель могут различаться.
- Подтверждённые бронирования и все listeners / handlers, создающие Event автоматически.

## Требуемый порядок реализации

1. **Инвентаризация** текущих операций и тестов Event/Game, зафиксировать ожидаемые permissions и lifecycle, назначение участников и ответственных.
2. **Модель**: `Scope::EVENT`, единые разрешения, отдельная связка `EventParticipant` с контрактом только для управляющего назначения; не привязывать игровой состав к договору.
3. **Запись**: покрыть владельческие и делегированные контракты во всех операциях создания/изменения и приглашения.
4. **Backfill** исторических событий и ответственных: идемпотентный, безопасный для уже завершённых мероприятий, со статусами и сроками из фактических данных; не присваивать новый финансовый permission.
5. **Согласие и отзыв**: пользователь должен принять/отклонить приглашение; при отзыве доступ исчезает на следующем запросе, без остаточного «creator fallback».
6. **Атомарное переключение**: `EventManagementAccess` читает только единый контрактный источник для Event. Турнирное исключение остаётся отдельным явно названным правилом; административное право действует только в бэк-офисе.
7. **Rollback / аудит**: перед выкладкой нужен план возврата без потери новых назначений и журнал изменения контракта; не удалять legacy строки сразу.
8. **Приёмка**: тесты всех сценариев плюс CI PostgreSQL 16/17, обновление документации и ручной dev smoke.

## Запрещённые упрощения

- Нельзя одновременно принимать для одной операции `EventResponsibilityPermission` **или** новый ContractPermission: так получится два независимых источника эскалации прав.
- Нельзя назначать каждому Game нового владельца только потому, что у Game свой ID.
- Нельзя считать участие в матче или запись в секцию основанием выдачи `MANAGE_FUNDS`, `MANAGE_RESPONSIBILITIES` и редактирования счёта.
- Нельзя путать публичное полномочие владельца с `BACKOFFICE_EVENT_MANAGE`.

## Критерии безопасного слияния

- Ни один существующий способ создания Event не создаёт объект без корректного owner policy (кроме явно выделенных проекций).
- Участник матча без договора не получает новые права.
- Отзыв/истечение срока/отклонение мгновенно блокируют управление.
- Бэк-офис работает по своим permissions независимо от публичного контракта.
- Менеджер турнира получает только перечисленные игровые действия.
- Автоматически созданная тренировка не порождает конфликтующих владельцев.
- Миграция идемпотентна на старых БД и не меняет игровую историю.
