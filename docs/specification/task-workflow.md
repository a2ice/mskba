## Назначение

Процесс нужен, чтобы каждая задача имела понятный старт, план, документационный след, отдельную ветку, проверяемый результат на dev и аккуратное завершение в main при согласованном релизе. С 24.11.2026 действует [Dev First и управляемые релизы](agent-rules.md#globalrule5---dev-first-и-управляемые-релизы-с-24112026). Релиз по ситуации, без обязательного расписания.

## Список задач

Общий список задач ведется в файле `docs/tasks.md`.

Важные задачи и заметки, которые появляются по ходу работы и еще не оформлены в основной процесс, могут временно фиксироваться во внешнем файле `../backlog/todo.md`.

Формат строки:

```markdown
- [ ] NNN - Название или краткое описание задачи
```

После merge задачи в `main` строка переводится в выполненное состояние:

```markdown
- [x] NNN - Название или краткое описание задачи
```

## Внешний backlog

Файл `../backlog/todo.md` используется как внешний backlog для быстрых важных записей, которые появились в процессе работы, но еще не заведены как полноценные задачи.

Правила:

- `../backlog/todo.md` нужно просматривать при планировании, если задача затрагивает backlog или приоритеты;
- если item из `../backlog/todo.md` созрел до полноценной задачи, его нужно перенести в `docs/tasks.md`;
- после переноса запись во внешнем backlog нужно актуализировать, удалить или явно пометить как перенесенную;
- `../backlog/todo.md` не заменяет `docs/tasks.md`, а дополняет его как промежуточный слой фиксации.

## Старт задачи

Перед началом выполнения нужно:

1. Проверить актуальную ветку `dev` и создать отдельную ветку задачи от неё (для согласованного release/hotfix — от актуального `main`).
2. Проверить чистоту рабочей копии: не включать посторонние незакоммиченные изменения.
3. Найти задачу в `docs/tasks.md`.
4. Создать папку `docs/tasks/{NNN}`.
5. Создать `docs/tasks/{NNN}/description.md`.

`description.md` на старте содержит две секции:

```markdown
# NNN - Название задачи

## Оригинальное описание

Текст задачи из `docs/tasks.md`.

## Подробное описание

Заполняется на этапе планирования.
```

## Планирование

Планирование является обязательным первым этапом задачи.

На этапе планирования нужно:

- прочитать обязательные правила и через оглавления и поиск выбрать релевантные разделы по [GlobalRule2](agent-rules.md#globalrule2---читать-документацию-по-задаче);
- изучить релевантные разделы `docs/project.md`;
- изучить `../backlog/todo.md`, если задача связана с backlog, приоритизацией или появилась из внешней заметки;
- изучить связанные раскрытия из `docs/project/{alias}.md`, если они относятся к задаче;
- изучить релевантные разделы `docs/specification.md`;
- изучить связанные технические раскрытия, если они относятся к задаче;
- заполнить подробное описание задачи в `docs/tasks/{NNN}/description.md`;
- определить затронутые пользовательские сценарии, документы, модули и проверки;
- запросить подтверждение на переход к следующему этапу.

## Этапы выполнения

Перед каждым этапом обозначить его. Отдельное подтверждение требуется для существенных продуктовых/архитектурных решений, ручной приёмки и production-релиза; согласованная реализация покрывает технические этапы commit/push/CI/merge/deploy в dev по GlobalRule5.

Рекомендуемые этапы:

- планирование;
- декомпозиция;
- реализация;
- обновление документации;
- проверка;
- подготовка к коммиту;
- PR, CI, merge и подтверждённый deploy в `dev`;
- приёмка и фиксация состава ожидающего релиза;
- согласованный релиз в `main`, подтверждение деплоя и обновление `docs/tasks.md`.

Набор этапов можно менять под задачу, но планирование, проверка и обновление документации обязательны, если задача влияет на продукт, архитектуру или процесс.

Для небольших документированных правок допускается объединять близкие этапы, если пользователь явно попросил выполнить работу и ожидаемый результат не требует отдельного архитектурного решения. В таком случае агент все равно должен зафиксировать, что именно было сделано, и выполнить релевантные проверки.

## Подзадачи

Если задача сложная или составная, она декомпозируется в `docs/tasks/{NNN}/subtasks`.

Рекомендуемый формат:

```text
docs/tasks/{NNN}/subtasks/{MMM}-{alias}.md
```

`alias` в названии подзадачи должен быть на английском языке в нижнем регистре. Слова разделяются дефисами.

Каждая подзадача должна содержать:

- название;
- цель;
- краткое описание;
- статус;
- результат выполнения.

## Завершение задачи

После выполнения:

1. Зафиксировать результат в `docs/tasks/{NNN}/description.md`.
2. Обновить затронутые разделы `docs/project.md`, `docs/specification.md` и раскрытия вместе с оглавлениями, ссылками и описаниями зависимостей по [правилам актуальности и навигации](documentation-guidelines.md#актуальность-и-доступность-при-выборочном-чтении). Проверить соответствие фактическому поведению и отсутствие противоречий в затронутых описаниях.
3. Запустить релевантные проверки.
4. Сделать предметный commit/push в ветке задачи, PR в `dev` и merge после зелёного CI; подтвердить dev-деплой.
5. Предоставить критерии приёмки, ссылку на dev, PR и SHA. Получить подтверждение результата.
6. Зафиксировать принятую задачу как ожидающую релиза, сохранив ветку/PR и зависимости. Не отмечать `[x]` только по dev.
7. По ситуации согласовать состав и время релиза с владельцем; собрать release candidate от актуального main без непринятых задач и staging-only workflows.
8. Проверить CI итогового кандидата, выполнить согласованный merge, подтвердить production-деплой и контрольную точку; сверить dev без потери невыпущенных задач.
9. После подтверждения production отметить задачу выполненной в `docs/tasks.md`.
10. Для значимого продуктового изменения создать или обновить черновик `system_update` через scoped API системного `dev` с приватными ссылками на PR и документацию. Публикация разрешена только после фактического production-деплоя и проверки публичного текста. При отсутствии токена или API готовить текст в задаче, не заявляя о публикации. Подробнее: [GlobalRule4](agent-rules.md#globalrule4---фиксировать-значимые-обновления-проекта).


Если задача затрагивает frontend-ассеты, в релевантные проверки входит локальная сборка ассетов. В текущем проекте build-артефакты `public/build` нужно проверять по фактической стратегии репозитория перед commit/push.

## Рекомендуемые дополнения

Ветка задачи должна называться в стиле conventional commit:

```text
type/NNN
```

Примеры:

- `feature/123`
- `fix/124`
- `docs/125`
- `refactor/126`

Коммит рекомендуется называть так:

```text
type(scope): краткое описание задачи
```

Пример:

```text
docs(process): add task workflow documentation
```

Если задача меняет пользовательский опыт, итоговое описание должно содержать не только технический результат, но и изменение с точки зрения пользователя или процесса.
