# Настраиваемый дашборд пользователя — этап 1

Маршруты: `/account`, авторизованный `/account/dashboard/widgets`, редактор `/admin/account-dashboard`.
В новой теме `mskba_app` администратор управляет количеством, видом и порядком карточек (полная/половинная ширина), включением и признаком `can_hide`. Пользовательское скрытие и перестановка будут реализованы следующим этапом в `/account/settings`.

Типы: статус аккаунта, знакомство с порталом, сообщения, информационные карточки, реклама (с изображением, ссылкой и явной пометкой «Реклама»), а также `custom_html` (только суперадмин). Содержание, стили и JavaScript последнего исполняются в iframe с `sandbox="allow-scripts"`, **без allow-same-origin**. Дополнительно применяется iframe CSP: запрет сетевого JavaScript (`connect-src 'none'`), форм, вложенных iframe и внешних скриптов. Изображения/шрифты могут загружаться с HTTPS. Встроенный код не имеет доступа к cookies, localStorage и DOM портала. Это всё равно активный пользовательский код: включать только с отдельным ревью суперадминистратора.

Аудитория: статусы аккаунта, системные роли, роли участия (любая из отмеченных), проверенный основной контакт. Незаполненная категория не ограничивает аудиторию. Категории сочетаются через AND, внутри списка ролей — OR. Точечный include по каноническому/алиасному ID переопределяет категории; exclude имеет приоритет даже над include. Видимость не является авторизацией к доменным API; они продолжают проверять права отдельно.

Административные изменения коммитятся в БД, затем посылается публичное событие `account-dashboard / dashboard.changed` без конфигурации, пользовательских идентификаторов и персональных данных. Авторизованная вкладка запрашивает уже отфильтрованный HTML. Reverb используется как уведомление об инвалидации, предусмотрено восстановление при reconnect/focus и редкое сверочное обновление. Публичный broadcast не раскрывает аудиторию.

Таблица: `account_dashboard_widgets`; начальные карточки создаются миграцией с признаком обязательности статуса аккаунта. Обновление через AJAX не выдаёт скрытые чужие карточки. Пока пользовательские настройки не подключены, `can_hide` остаётся правилом для следующего этапа.

## Редактируемое HTML-содержимое функциональных карточек (2026-10-14)

- В Filament в разделе «Содержимое» используется встроенный CodeEditor с подсветкой HTML (без сторонних зависимостей). Поле `body` редактирует информацию, рекламу, «Возможности MSKBA» и «Мои сообщения». Пустое поле для функциональных карточек оставляет их первоначальный текст. Системная кнопка действия остаётся в карточке.
- «Статус аккаунта» имеет **три независимых HTML-поля**: `status_confirmed_html`, `status_unconfirmed_html`, `status_blocked_html`. В существующую таблицу они добавляются nullable-миграцией без изменения старых карточек; при отсутствии текста отображается стандартный вариант. Подтверждение аккаунта и статусы продолжают определяться на сервере.
- Поддерживаются `p`, `strong`, `em`, `ul`, `ol`, `li`, заголовки, ссылки и псевдокнопки `<a href="/account/roles" class="button secondary">Мои роли</a>`. Не исполняются `script`, обработчики событий и CSS: вывод неизменно проходит через `DashboardWidgetHtmlRenderer` и Symfony HTML Sanitizer; разрешены только заданные классы кнопок и безопасные схемы URL.
- Для «Мои сообщения» предусмотрен литеральный текстовый маркер `{{ unread_count }}`: заменяется в серверном HTML на экранированный актуальный счётчик до отправки пользователю, **никакой Blade-шаблон из БД не исполняется**. Отображение/обновление через Reverb используют тот же Blade partial.


## Цвет внутреннего свечения карточки

\`gradient_color\` — nullable HEX \`#RRGGBB\` (редактор: Filament → вкладка «Размещение» → «Цвет подсветки карточки»).
\`NULL\` означает строго существующий системный цвет \`--surface-corner-glow\` и исходное оформление.
При заданном цвете CSS-переменная \`--surface-glow\` выставляется **только для этой карточки**, с фиксированной прозрачностью \`1e\` (как в текущем токене \`#ff79001e\`); размеры, положение и форма radial-gradient не меняются.
В Blade значение проверяется по полному HEX-шаблону, а админские формы валидируют его серверно. JS и произвольный CSS вводить через это поле нельзя.

## Ремонт исторической миграции image_url

В дев-базе начальная миграция \`2026_10_14_200000_create_account_dashboard_widgets_table\` была применена **до** появления колонки \`image_url\` в её исходнике. Laravel не повторяет выполненную миграцию, поэтому реальные сохранения рекламных карточек возвращали PostgreSQL \`SQLSTATE[42703]\`.
Добавлена отдельная \`2026_10_14_230000_repair_dashboard_widget_image_url_column\`: проверяет \`Schema::hasColumn\` и только при отсутствии добавляет nullable \`image_url\`. На новой базе повторного ALTER TABLE не происходит; существующие записи не меняются.
Её rollback намеренно не удаляет колонку: на новых установках эта колонка принадлежит исходной миграции. Для регрессии предусмотрен тест с базой, из которой колонка перед прогоном ремонта удалена.
