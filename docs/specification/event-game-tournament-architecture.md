# ADR: Event, Game и Tournament

## Статус

Принято 7 августа 2026 года в задаче 086. Реализация выполняется поэтапно; до её завершения
отдельные части runtime продолжают соответствовать предыдущему ADR задачи 084.

Этот ADR заменяет целевую часть документа [Разделение Event и Game](event-game-separation.md), но
не отменяет уже принятые там решения о принадлежности сторон, составов, статистики и игровых
действий сущности Game.

## Контекст

MSKBA должен поддерживать самостоятельные игры, тренировки с несколькими внутренними играми и
турниры с упорядоченными матчами. Площадка, бронь и публикация нужны любому календарному событию,
а счёт, состав и статистика относятся только к спортивному проведению.

Предыдущая модель правильно вынесла спортивные данные из Event в Game, но оставила несколько
неоднозначностей:

- standalone game технически и визуально воспринималась как Event плюс вложенная Game;
- календарное наступление времени смешивалось с фактическим запуском;
- одна и та же связь Event/Game использовалась и для основной игры, и для внутренних игр тренировки
  без явного различия;
- будущий Tournament описывался как возможная надстройка, но не имел утверждённого агрегата,
  участников и матчей;
- прямой `games.tournament_id` не позволяет хранить неназначенный матч сетки.

## Решение

Используется композиция, а не наследование моделей и не одна широкая таблица:

```text
Event — календарная и организационная оболочка
Game — спортивное проведение внутри Event
Tournament — контейнер соревнования
TournamentMatch — место встречи в структуре Tournament
```

Связи:

```text
Event 1 ─── 0..N Game
Tournament 1 ─── N TournamentMatch
TournamentMatch 0..1 ─── 1 Game
```

Для пользователя `Event(type=game) + primary Game` является одной самостоятельной игрой. Разделение
остаётся внутренней архитектурой и не должно заставлять пользователя переходить между двумя
карточками для обычного сценария.

## Event

Event отвечает за:

- публичное название, alias и route identifier;
- тип `game`, `training`, `game_training` или `open_training`;
- организационный статус и видимость;
- создателя/организатора;
- площадку;
- планируемые начало и окончание;
- бронь;
- регистрацию участников;
- публикации, уведомления и общие media;
- краткое и полное публичное описание.

`ends_at` обязателен для Event с площадкой, потому что без закрытого интервала нельзя проверить
доступность и создать корректное бронирование.

## Game

Game отвечает за:

- фактический спортивный lifecycle;
- preset формата, размеры сторон, scoring type и количество периодов;
- две GameSide;
- исторический GameRosterEntry snapshot;
- starters и captains конкретной игры;
- GameAction, текущий счёт и GamePlayerStatistic;
- победителя и подтверждение результата.

Game поддерживает `whole_game` без технических периодов и `periods` с двумя либо четырьмя дочерними
GamePeriod. GamePeriod не является aggregate root: lifecycle и блокировки проходят через Game.
GameAction в периодном режиме относится к активному GamePeriod, а GamePlayerStatistic остаётся
общим итогом игрока за Game. Периодный срез строится из действий; GamePeriod хранит score snapshot.

Game не дублирует alias, площадку и организационные данные Event. Внутренние игры могут иметь собственное название и спортивный регламент.

### Планирование нескольких игр (Epic GitHub #1175)

Event-first API принимает явный массив `games` (включая пустой). При его наличии legacy-параметры одиночной игры не используются; без массива старые клиенты сохраняют прежнее поведение. Игры создаются вместе с Event в транзакции, `primary_game_id` назначается только первой игре. Запланированные постоянные команды хранятся в `planned_team_a_id` и `planned_team_b_id`; их выбор не создаёт GameAdmission, GameSide, состав или уведомление. Активность команд проверяется под блокировкой при сохранении. Для заданного формата создаются параметры сторон, система подсчёта и периоды; запуск любой игры с режимом набора требует подтверждённых сторон.

В новом API `format: null` означает неопределённый формат, а не custom. Размеры сторон, scoring, timing, recruitment и periods_count сохраняются null; заявки отключены, периоды и стороны не создаются. Старые игры без format, но с заполненными спортивными параметрами остаются настроенными. `Game::hasSportConfiguration()` используется для допуска к спортивному интерфейсу, Live и фактическому старту. Миграция сохраняет существующие данные и не допускает откат схемы с потерей неопределённых параметров. В черновом PR #1176 общий редактор подключён к event-first wizard, а новый признак `uses_event_planning` отличает планируемые игры от legacy и турнирных матчей. API `events.planned-games.store/update/destroy` разрешает создавать и редактировать игры в draft/published Event с существующими event permissions. Спортивный регламент можно изменять до начала игры и появления истории участия/спортивных действий. Удаление пока разрешено только без такой истории (soft delete; primary_game_id переводится на следующую игру или null). Legacy endpoints не должны обходить эти ограничения. UI страницы мероприятия в mskba_app использует общий редактор и подтверждение удаления, после сохранения обновляет страницу. Отмена с историей приглашений, чаты, legacy и Live-интеграция остаются отдельными этапами; до их завершения контур не готов к релизу.

Actual timestamps недоступны для обычного ручного редактирования. `actual_started_at` и
`actual_ended_at` устанавливаются сервером при lifecycle-переходах. Исторический импорт является
отдельным административным use case.

## Tournament

Регистрация участника на месте является отдельной application-командой и не ослабляет обычный
`TournamentAdmissionService`: постоянный check-in URL работает только при явном флаге турнира.
Аккаунт, согласие, роли и admission создаются атомарно. При подтверждении после фиксации balanced-пула
транзакция блокирует Tournament, admission и выбранную TournamentEntry, добавляет игрока в команду
и только в составы ещё не начавшихся игр. Это предотвращает двойное принятие и изменение истории.

Tournament является самостоятельным агрегатом и не является Event. Он отвечает за:

- публичный паспорт и даты соревнования;
- модерационный статус;
- общий preset формата;
- команды-участники;
- договорных ответственных;
- матчи, туры и последовательность;
- агрегированную турнирную таблицу.

Создавать Tournament может подтверждённый незаблокированный пользователь. По умолчанию создаваемый
им Tournament имеет статус `confirmed`. Фазы `upcoming`, `in_progress` и `finished` вычисляются по
датам и не записываются как модерационные статусы.

Boolean-поле `accepts_unconfirmed_participants` применимо только к
`recruitment_mode = individual_draft` и по умолчанию равно `false`. Create/update use cases
нормализуют его в `false` для режима готовых команд. При персональной заявке admission service под
блокировкой Tournament проверяет статус пользователя до создания `TournamentAdmission`; отказ не
создаёт запись и уведомление. Проверка не применяется к приглашениям организатора.
Персональная application-заявка также хранит непустой JSON-массив ролей из
`player|coach|manager`; каждый элемент и отсутствие повторов валидируются сервером. Для командных
заявок и приглашений поле остаётся nullable. Решение организатора применяется ко всей заявке и
всему набору ролей, выборочное подтверждение отдельных ролей не предусмотрено.

## TournamentMatch

TournamentMatch существует отдельно от Game и содержит:

- Tournament;
- две разные записи TournamentTeam;
- номер тура;
- последовательность;
- nullable ссылку на Game.

Генератор `каждый с каждым` создаёт TournamentMatch, но не создаёт Event, бронь или Game. Они
появляются только при назначении времени и площадки.

Назначение матча одной транзакцией:

1. проверяет Tournament, команды, интервал и права;
2. проверяет занятость команд и площадки;
3. создаёт Event типа game;
4. создаёт VenueBooking;
5. создаёт primary Game, стороны и roster snapshot;
6. связывает TournamentMatch с Game.

## Варианты игр

### Самостоятельная игра

```text
Event(type=game)
└── primary Game
```

У Event типа game должна быть ровно одна primary Game.

### Турнирная игра

```text
TournamentMatch
└── Game
    └── Event(type=game)
```

Она использует тот же runtime, что standalone game.

### Внутренняя игра тренировки

```text
Event(type=training|game_training)
├── embedded Game
└── embedded Game
```

Внутренние Game используют площадку и бронь родительского Event. Они не создают самостоятельные
VenueBooking. Их фактические lifecycle независимы друг от друга.

`game_training` остаётся отдельным Event type. `open_training` также остаётся типом Event; отдельная
detail-сущность для него вводится только при появлении собственных полей.

## Ownership данных

| Данные | Владелец |
|---|---|
| Public title, alias, descriptions, media самостоятельной игры | Event |
| Venue, scheduled interval, booking | Event |
| Registration, visibility, Telegram publication | Event |
| Actual timestamps и sports status | Game |
| Format preset, side sizes, scoring, periods | Game |
| Sides, roster snapshot, score, actions, statistics | Game |
| Tournament title, dates, descriptions, media, status | Tournament |
| Tournament participants | TournamentTeam |
| Pair, round, sequence | TournamentMatch |

## Lifecycle

```text
Event: draft -> published -> completed
                    \-> cancelled

Game: scheduled -> in_progress -> awaiting_result -> completed
          \-> cancelled

Tournament: unconfirmed <-> confirmed -> cancelled
```

Календарные признаки не изменяют Game status. `Live` означает наличие фактического старта и
отсутствие фактического окончания.

Для Event типа game согласованные переходы Event и primary Game выполняются одним application use
case в транзакции. Observer не используется как скрытый оркестратор бизнес-процесса.

## Права

Создатель Tournament имеет полный доступ по ownership. Ответственные используют существующие
membership contracts со scope `tournament` и атомарными permissions:

- `manage_tournament_games`;
- `manage_tournament_status`;
- `manage_tournament_description`;
- `manage_tournament_staff`;
- `delete_tournament`.

Право Tournament действует только на Game, связанную с TournamentMatch этого Tournament. Оно не
разрешает управлять другими Event, Tournament или постоянным составом Team.

## Маршруты и UI

Публичный UI показывает самостоятельную игру как одну карточку. Техническое разделение Event/Game
не дублирует заголовки и не создаёт две конкурирующие страницы.

Homepage discovery не объединяет Event и Tournament в один доменный агрегат. Это отдельная read-only проекция, которая собирает публичные Event и подтверждённые Tournament в единую выдачу для пятишагового popup. Контракт endpoint, фильтров, географии и frontend lifecycle описан в [Homepage Event Discovery](homepage-event-discovery.md).

Tournament использует ID+alias URL:

```text
/tournaments/{id}-{alias}
```

ID является источником идентичности; alias может повторяться. Канонический публичный URL
standalone-игры — `/events/{id}-{alias}`. Вложенный `/events/{event}/games/{game}` применяется для
игр тренировки; старый вложенный URL standalone-игры постоянно перенаправляется на Event URL.

Управление спортивным проведением остаётся отдельным surface
`/events/{event}/games/{primaryGame}/manage`, но не является второй публичной карточкой. Изменение
публичного названия, площадки и планируемого интервала выполняется через Event, а счёт, состав,
lifecycle и статистика — через management Game.

Публичный и управляющий контексты разделены: зритель получает read-only карточку, пользователь с
правом — явный переход в management surface.

## Транзакции и блокировки

Глобальный порядок:

```text
Tournament -> TournamentMatch -> Event -> Game -> GameSide
           -> GameRosterEntry -> GameAction/GamePlayerStatistic
```

Standalone flow начинается с Event. Reorder блокирует Tournament и Match. Назначение матча,
запуск, завершение, подтверждение результата и отмена проверяют инварианты после получения locks.
Транзакции допускают ограниченный retry при deadlock.

## Следствия

`venue_bookings.scope` хранит физический ресурс `whole|half_a|half_b`. Отдельные половины разрешены
только при `venue_characteristics.hoops_count = 2`. Проверка конфликтов выполняется после блокировки
Venue: `whole` конфликтует с любой зоной, каждая половина — с `whole` и самой собой. Поэтому два
параллельных запроса не могут занять один ресурс, а историческая зона остаётся частью бронирования.

Положительные:

- одна система бронирований сохраняется для всех событий;
- standalone и tournament games используют один sports runtime;
- TournamentMatch поддерживает неназначенные матчи и будущие сетки;
- training mini-games не дублируют бронь;
- ownership полей однозначен.

Отрицательные:

- создание standalone game требует транзакционной оркестрации Event и Game;
- DB не выражает все cross-aggregate invariants без application checks;
- доступ к турнирной Game объединяет несколько источников прав;
- переход требует пересмотра маршрутов и текущих экранов.


### Адресные приглашения (Epic #1175)

Существующий `GameAdmissionService` принимает `uses_event_planning` игры независимо от primary_game_id. Для нового контура приглашения/ответы доступны в опубликованном мероприятии с настроенным регламентом, до старта и утверждения сторон. Для режима готовых команд допустимы только запланированные team IDs. Проверка opt-out выполняется под блокировкой команды. Повторное приглашение после declined/revoked создаёт новую запись; pending/accepted блокируют дубль. Уведомления приглашений содержат game_admission_id. Чат, рассылка тиммейтам и отмена игры остаются следующими срезами.


### Диалог приглашения (Epic #1175)

Добавлена связующая сущность GameInvitationThread (unique game_id + team_id) и RequestThread type=game_invitation, subject_id=ID контекста. Контекст и тред создаются в транзакции приглашения под блокировками родителя/игры; повторные попытки используют тот же тред. История попыток остаётся в GameAdmission, обычные сообщения — в RequestThreadMessage. ACL каждый раз проверяет текущие MANAGE_PARTICIPANTS и MANAGE_GAME_PARTICIPATION; наличие старого уведомления не даёт прав. Отказ не закрывает переписку. Адресные уведомления содержат game_invitation_thread_id, открывают диалог и учитываются в общем inbox отдельно от системного треда. Native UI использует общий workspace/rail/chat-bubble, обычные POST формы и пагинацию; JSON API отдельно предоставляет последние 10 сообщений, попытки и ответ. Realtime, оповещение тиммейтов, полноценная отмена, legacy и визуальная приёмка остаются впереди. Миграция запрещает destructive rollback при наличии истории.


### Оповещение тиммейтов (Epic #1175)

GameInvitationTeammates разрешает рассылку только уполномоченному представителю команды по действующему pending/accepted приглашению настроенной запланированной игры в опубликованном незавершённом мероприятии. Получатели — подтверждённые канонические пользователи с активным контрактом, accepted членством и спортивной ролью PLAYER. Проверки под блокировками Event → Game → Admission → Team. Выбор получателей валидируется целиком, не допускается рассылка посторонним. GameInvitationRecipient хранит фактического получателя, автора оповещения, необязательный комментарий и попытку приглашения; unique(game_admission_id,user_id) исключает повторы внутри попытки. Создание записи и внутреннего уведомления транзакционное, событие доставки после commit. Новая попытка приглашения допускает новое оповещение. Оповещение не даёт доступ к закрытому диалогу, не меняет статус приглашения, участие в Event, состав игры или статистику. История всех попыток будет использована при отмене игры. Отдельная миграция защищает историю от destructive rollback.


### Отмена запланированной игры (Epic #1175)

Удаление без истории сохраняет прежний soft-delete. При наличии admissions, invitation threads, сторон или состава требуется явное подтверждение `notify` (true/false); `reason` необязателен, до 1000 символов. Под блокировками Event → Game сохраняется CANCELLED, cancelled_at/by/reason, закрывается приём заявок, прежние ответы GameAdmission остаются историческими, активные уведомления приглашений погашаются. Игра архивируется soft-delete, primary_game_id переходит на следующую доступную игру или null. Начатые игры, счёт, действия, начатые периоды и спортивная статистика защищены от удаления. При notify=true адресаты определяются по фактическим уведомлениям приглашений, GameInvitationRecipient всех попыток, индивидуальным заявкам, выбранным составам и текущим представителям приглашённых команд, с дедупликацией по canonical user. Только текущим представителям доступна ссылка на закрытый тред; остальные получают ссылку на Event. Уведомления создаются в транзакции с доставкой после commit; поздняя отправка приглашения после отмены блокируется. Диалог показывает отмену и причину, сохраняет обычную переписку и закрывает действия приглашения/оповещения. При notify=false новых уведомлений нет, но история и состояние отмены сохраняются. Reverb, Live и визуальная приёмка остаются впереди.


### Realtime диалога приглашения (Epic #1175)

Переиспользован ConversationChangedBroadcast: приватный `game-invitation-threads.{contextId}` с текущим ACL организатора/представителя. Событие `.conversation.changed` содержит только invalidation flags и отправляется после commit при создании/повторе приглашения, ответе/отзыве, сообщении, рассылке тиммейтам и отмене. Native UI запрашивает серверный HTML fragment и rail без отметки прочтения; отдельный PATCH read повторно проверяет ACL. При 401/403/404 интерфейс очищает историю и перезагружается. Reconnect/focus/visibility и fallback reconciliation каждые 15 секунд в видимой вкладке. Composer не заменяется; открытый modal сохраняет выбор и комментарий при той же попытке и закрывается при недоступности. Существующие POST формы остаются fallback. Реальная проверка Reverb между двумя сессиями и legacy ещё требуется.


### Спортивный контур запланированных игр (Epic #1175)

Для `uses_event_planning` отдельные show/manage и nested sport endpoints допускают любую игру родительского Event, не только primary. FormationService проверяет опубликованный Event, настроенный формат, состояние до старта и полномочия; в preformed_teams обе запланированные команды должны быть приняты, порядок сторон фиксирован. В individual_draft добавлен `event-participants.confirm`: явный выбор двух непересекающихся групп из подтверждённых игроков мероприятия, не обязательно всех; существующие индивидуальные приглашения и balanced остаются доступны. После утверждения используется собственный снимок состава игры, без переноса игроков к сопернику. Снятие утверждения planned game не переводит участников Event в LEFT, не затрагивает другие игры. Регламент меняется через planning editor, не через старые endpoints. Подтверждение статистики planned game не завершает Event автоматически; организатор завершает Event отдельно. Legacy standalone/tournament поведение сохраняется. Native event page ведёт в существующий game-show/manage/live (пока legacy public fallback), panel также имеет fallback. Добавлен сквозной тест двух игр с периодами, действиями, счётом и независимым завершением. QR late-join/withdrawal, полный legacy UI, фактическое двухсессионное Live/Reverb и визуальная приёмка пока не проверены/не расширены.


### Интеграционный аудит #1175 — QR и Telegram

Для запланированной individual_draft игры QR join и late-panel адресуются game_id, включая неосновную игру. Действуют правила публичного опубликованного Event, текущего регламента, открытого набора и состояния игры. Позднее принятие добавляет игрока только в выбранную игру, учитывает актуальную вместимость по каноническим игрокам; повторное подключение исключённого игрока восстанавливает прежнюю сторону без дубликата или потери истории. DELETE recruitment/participation отменяет участие в конкретной planned игре, сохраняя RSVP и составы других игр; для legacy поведение выхода прежнее. Telegram event:* callbacks относятся к Event, если его основная игра planned; карточка перечисляет игры, а не представляет первую как всё мероприятие. Ручное формирование проверяет текущую confirmation_version. Старый destructive endpoint не используется кнопкой отмены planned игры. Добавлены тесты для второго матча, позднего подключения, выхода и повторного подключения и Telegram. Автоматический CI и визуальная приёмка этого среза ещё требуются.
