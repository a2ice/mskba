## Данные и границы

`venue_rental_pre_requests` — необязывающий запрос подтверждённого клиента
публичной площадке с конкретным залом, интервалом, scope и необязательной заметкой.
Создание использует стандартную валидацию quote (включая доступность, условия
зала и время) и ограничения rental requests. Сам quote не резервирует время.
Ни Event, ни VenueBooking, ни hold, ни платёж при создании не появляются.
Уникальная пара requester_user_id/idempotency_key и hash нормализованных
параметров защищают retry; повтор с другим payload отклоняется.

`active` означает открытое обсуждение; отказ от одного предложения сохраняет
active. `resolved` фиксируется атомарно с согласием на предложение и hold,
`withdrawn` — с отзывом клиентом и отменой ещё не принятых предложений.
Последующая жизнь брони не переопределяет исторический факт согласования.
Изменения модели аудируются через существующий Auditable.

## Права

Клиент видит собственную предзаявку и может писать, отвечать и отзывать её.
Остальные пользователи должны быть подтверждены, не заблокированы и иметь
действующий Contract ACL соответствующей площадки или зала:

| Действие | Разрешение |
| --- | --- |
| Чтение | rental.interests.view либо rental.bookings.view либо rental.interests.propose-booking |
| Переписка и загрузка файлов | rental.bookings.view |
| Создание предложения | rental.interests.propose-booking |

Существующие venue owner/admin contracts сохраняют права управления;
подтверждённый superadmin использует VenueCommercialAccess. Явно делегированный
backoffice rental support может читать; просмотр логируется. Обычная staff-роль
или назначение выбранным комиссионным агентом не дают доступа к этому потоку.
Отдельные booking/payment действия продолжают проверять свои обычные права.
Для STAFF/AGENT доступно явное делегирование rental.bookings.view (диалог);
их default permissions не расширены и сами по себе права переписки не дают.
Разрешение proposal также позволяет выполнить согласованный hold и confirmation;
оплата по-прежнему требует отдельного payment permission.

## Предложение и согласие

`VenueRentalPreRequests` блокирует venue как mutex, затем предзаявку. Создание
запроса сначала блокирует пользователя для сериализации idempotency keys между
площадками. Все предложения конкретной предзаявки сериализованы под venue lock;
существующая незавершённая бронь возвращается вместо второй. Дополнительная
проверка присутствует в RequestVenueBookingHandler.

Представитель получает свежий QuoteVenueBookingHandler для **клиента**, а не для
себя. Обычный RequestVenueBookingHandler создаёт `flow=rental`, `event_id=null`,
`requester_user_id=клиент`, `pre_request_id`, `created_by_representative_id=Actor`,
`created_by_actor_id=представитель`. Snapshot не редактируется. Персональные
условия применяет существующий VenuePersonalPricing; их лимит расходуется при
создании REQUESTED, как в обычном потоке, и не возвращается при отмене.
Явный купон из формы quote относится к обычному бронированию; предзаявка цену
и код не сохраняет. При предложении заново применяются доступные автоматические
условия клиента.

Предложение остаётся REQUESTED и не занимает слот. proposal_expires_at равен
valid_until quote. До proposal_accepted_at обычные accept/confirm не допускаются.
Только клиент может принять конкретное предложение своей предзаявки. Под тем
же mutex повторно проверяются срок, актуальные права представителя, ограничения
клиента, доступность/состояние зала и конфликт слота. Consent, обычный
AcceptVenueBookingHandler и resolved сохраняются одной транзакцией. Любая
ошибка откатывает consent. Платёжное окно автоматически не открывается.

Отказ и отзыв используют CancelVenueBookingHandler. Минутная задача
`venue-pre-requests:expire-proposals` отменяет просроченные, ещё не принятые
REQUESTED через lifecycle с системным Actor и outbox; stale task не затрагивает
HELD/CONFIRMED. Новое предложение после истечения заново получает quote.
После согласия действуют стандартные сроки удержания, оплаты, подтверждения и
отмены. Event не создаётся без отдельного штатного intent/действия пользователя.

## Разговор и интерфейсы

Уникальный `venue_booking_conversations.pre_request_id` закрепляет один разговор
на весь срок предзаявки. Его venue_booking_id указывает на последнее предложение;
старые брони находят тот же разговор через conversationLookup. Чтение,
read markers и скачивание файлов проверяют принадлежность общей предзаявке.
Сообщения неизменяемы и идемпотентны по actor/client_id; вложения хранятся на
приватном local disk с теми же типами и лимитом 10 МБ, что в booking chat.

Уведомления используют существующий inbox, queued listener после commit и
message delivery receipts для дедупликации. Получатели повторно фильтруются по
ACL. Системная история жизненного цикла брони добавляется в тот же разговор
существующим outbox listener. Страница предзаявки обновляется обычным запросом;
есть явная команда «Обновить сообщения». Новый realtime-клиент не добавлен.

Обе темы дают отдельное действие «Предзаявка» на публичном quote-экране, страницы
кабинета `/account/venue-pre-requests`, ссылки из существующих rental inbox и
интересов площадки. Filament → Venue → «Заявки» сохраняет прежние табы и добавляет
«Предзаявки без мероприятия». Публичного списка предзаявок нет.
