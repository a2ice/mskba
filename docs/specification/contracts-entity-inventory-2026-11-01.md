# Контракты MSKBA: контуры, сущности и административное управление

## Основной принцип

Глобальные permissions бэк-офиса (просмотр/корректировка контрактов, управление сущностями) **не** выдаются через membership-контракты. Контракты регулируют доступ пользователей к конкретной публичной сущности, требуют принятия назначения и имеют собственную историю.

## Инвентаризация

| Сущность | Реализация на 2026-11-01 | Рекомендация |
| --- | --- | --- |
| Лига | Полноценный управленческий membership с делегированием | Использовать единый менеджер |
| Сезон | Отдельный контракт, владелец по умолчанию — владелец лиги | Использовать единый менеджер |
| Турнир | Управление турниром и сотрудниками на контрактной основе | Использовать единый менеджер, сохранить совместимость с существующими staff-связями |
| Команда | Owner, членство и спортивные роли уже связаны с контрактами | Сохранять спортивные роли отдельно от управляющих прав |
| Площадка | Membership управления каталогом + отдельно подтверждаемое коммерческое владение | Не давать коммерческие права обычному создателю каталожной записи |
| Зал/зона площадки | Уже предусмотрен scope `venue_court` и контракты конкретной зоны | Отображать в карточке площадки; коммерческие права менять через процедуру владения |
| Спортивная секция | Владелец и приглашённые тренеры через единый EntityContractManager, акцепт и сроки; занимающиеся отдельно | Следующий этап — профильная передача владельца и главного тренера без осиротевших секций |
| Мероприятие | Организатор и ответственные используют `EventResponsibilityPermissionEnum`, статусы подтверждения и права участников | Кандидат для отдельного этапа миграции; сначала обеспечить совместимость, нельзя создавать параллельный источник эффективных прав |
| Игра / мини-игра | Управляющие права проверяются относительно родительского мероприятия; турнирная игра дополнительно наследует права турнира | Не создавать самостоятельного владельца каждой игровой записи; показывать управление в контексте мероприятия/турнира |
| Тренировка / занятие | Сессия принадлежит спортивной секции | Наследовать право секции, отдельный контракт только для независимого организатора/оператора |
| Компания/организация | `company` предусмотрена в enum и в концепции, но общего полноценного владельческого workflow в текущем модуле нет | Ввести при появлении управляемого публичного каталога организаций |
| Бронирование, аренда, спонсорство, участие команды | Это отношения между сущностями, а не управленческий membership пользователя | Дальнейшая реализация как `relation` contracts с отдельной моделью подтверждения и отмены |
| Профиль игрока/тренера | Это персональные данные и роли учётной записи | Не заменять права на собственные данные контрактом; отдельные договоры применимы к представительству, агентам и услугам |

## Бэк-офис

- Независимые глобальные права `backoffice.contract.view` и `backoffice.contract.manage`.
- Общий реестр контрактов с фильтрацией по типу, статусу, пользователю, сущности и ID; доступны исторические и неактивные назначения.
- Вкладки «Контракты» в редакторах пользователей, команд, площадок, лиг, сезонов, турниров и мероприятий. Площадка включает связанные залы.
- Редактор контракта хранит обычный комментарий (`notes`) **отдельно** от служебного `comment` (который содержит legacy-маркер).
- Причина изменения обязательна; `contract_change_logs` хранит историю прав и условий, включая время и автора.
- Владелец не отзывается через редактор, для него применяется отдельная передача владения с подтверждением.
- Специальные коммерческие и спортивные контракты нельзя переписать обычной формой разрешений. Для них остаются профильные workflows.

## Сроки и согласие

- В приглашении можно выбрать окончание контракта, либо оставить его бессрочным.
- Если срок или любая делегируемая возможность выдающего пользователя ограничена, окончание нового контракта не может выходить за минимальный из соответствующих сроков.
- Новый срок на публичном сайте по умолчанию ограничивается сроком имеющихся полномочий выдающего.
- Увеличение набора разрешений при административном редактировании переводит ранее принятый контракт в ожидание повторного подтверждения.
- Отзыв не должен активироваться повторно одним переключателем статуса: создаётся новый контракт.

## Следующие независимые этапы

1. Привести мероприятие/игру к единому источнику эффективных прав, сохранив существующие роли игроков, статистов, судей и организаторов.
2. Завершить специальный сценарий передачи владельца секции с одновременной проверкой назначения главного тренера; акцепт и управление тренерами уже унифицированы (Task 553).
3. Разработать политики для `relation` contracts (команда—лига, площадка—организатор, партнёрство), не смешивая с ACL-полномочиями пользователей.

Не запускать массовую миграцию Event и Game в generic-manager до покрытия их жизненного цикла тестами и согласования иерархии с пользователем.
