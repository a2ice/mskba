## Назначение

`Location` - отдельный доменный контекст для физических локаций, структурированных адресов, канонической административной географии и метро.

Контекст нужен не только площадкам, но и событиям, тренировкам, командам, компаниям и другим сущностям, у которых может быть физическое место.

## Граница контекста

Код контекста расположен в `App\Modules\Location`.

Текущие доменные модели:

- `Location`;
- `Address`;
- `City`;
- `District`;
- `MetroLine`;
- `MetroStation`.

Текущие таблицы:

- `locations`;
- `addresses`;
- `cities`;
- `districts`;
- `metro_lines`;
- `metro_stations`;
- `location_metro_station`.

## Модель

`Location` является агрегатным корнем физического места.

`Address` хранит структурированный адрес:

- `postal_code`;
- `city_id` - nullable ссылка на канонический `City`;
- `district_id` - nullable ссылка на канонический `District`;
- `city` - строковое значение провайдера/legacy snapshot, сохраняемое для обратной совместимости;
- `street`;
- `building`;
- `latitude`;
- `longitude`;
- `full_address`.

Координаты находятся в `addresses`, потому что это свойство конкретной географической точки адреса.

Строковое поле `addresses.city` не заменяется FK: оно остаётся provider snapshot и fallback. Для фильтрации, справочников и административной логики следует использовать `city_id`/`district_id`, когда они разрешены.

## Города и районы

`City` хранит:

- `name`;
- уникальный `alias`;
- nullable `short_name`;
- nullable `description`.

`District` принадлежит одному `City` и хранит:

- `city_id`;
- `name`;
- `alias`, уникальный внутри города;
- nullable `short_name`;
- nullable `description`.

Термин `District` используется как общий технический уровень. В UI он может называться контекстно: для Москвы — `Округ`, для Химок — `Район`, в универсальных местах — `Район / округ`.

Production-safe `GeographySeeder` создаёт базовый справочник Москвы и Химок. Повторный запуск не создаёт дубли и не перезаписывает осмысленные изменения администратора. Existing `addresses.city` best-effort связывается с известным `City`; район старого адреса не угадывается без надёжного структурированного источника.

Справочник управляется из административного раздела `Города и районы`. Удаление или перенос записей не должен нарушать существующие связи адресов; ограничения приложения дублируются FK-инвариантами.

## Связь с площадками

`Venue` связан с `Location` через nullable FK:

- `venues.location_id`.

Площадка также хранит fallback-адрес:

- `venues.raw_address`.

`raw_address` нужен, когда структурированная локация еще не создана или адрес получен в сыром виде. Отображение адреса должно использовать структурированную `location`, когда она есть; если `location_id` отсутствует, можно показывать `raw_address`.

При создании/редактировании площадки форма может передавать данные локации:

- `location.raw_address`;
- `location.city_id`;
- `location.district_id`;
- `location.city`;
- `location.street`;
- `location.building`;
- `location.postal_code`;
- `location.latitude`;
- `location.longitude`;
- `location.metro_station_ids`.

`CreateVenueRequest` преобразует эти поля в `CreateLocationDTO`. `CreateAccountVenueHandler` оркестрирует создание площадки и вызывает `CreateLocationHandler`, который создаёт `Address`, `Location` и связи `location_metro_station`. Перед сохранением handler проверяет, что выбранный `District` действительно принадлежит выбранному `City`.

Сырой адрес сохраняется в `addresses.full_address`, а `venues.raw_address` продолжает заполняться как fallback для отображения и обратной совместимости.

## Yandex и разрешение географии

Форма адреса обращается к backend endpoint `/integrations/address-suggest`, а определение адреса по координатам — к `POST /integrations/address-reverse`. Ключ Yandex не передаётся клиенту.

Yandex provider извлекает структурированные административные компоненты и передаёт их через provider-neutral DTO. `GeographyResolver` нормализует варианты написания и пытается сопоставить их только с уже существующими `City`/`District`.

Основные правила:

- внешний провайдер не создаёт новые канонические города или районы автоматически;
- город может успешно разрешиться при неизвестном районе: тогда `city_id` заполняется, а `district_id` остаётся `null`;
- неизвестная административная территория не должна блокировать сохранение адреса;
- `Другие территории` является обычной записью справочника Химок, а не универсальным fallback;
- миграции не вызывают Yandex и не зависят от внешней сети;
- при ручном изменении адреса frontend очищает связанные структурированные ID, координаты и автоматически выбранное метро, чтобы не смешивать данные разных адресов.

Homepage location wizard читает города и районы через публичный read-only endpoint `GET /home/location-options`. Этот же endpoint отдаёт URL address suggest/reverse и дефолтный диапазон дат в timezone приложения.

## Метро

Метро связывается с `Location`, а не с `Address` и не напрямую с `Venue` или событием.

Причины:

- станция метро является справочником и переиспользуется многими локациями;
- один адрес может соответствовать разным объектам на территории с разной фактической близостью к станциям;
- разные сущности получают метро через общий `Location`, а не дублируют связи в своих таблицах.

Связь реализуется через pivot `location_metro_station`:

- `location_id`;
- `metro_station_id`;
- `distance_meters`;
- `walking_time_minutes`.

`MetroLine` хранит ветку метро, `MetroStation` принадлежит ветке. Станции с одинаковым названием на разных ветках не схлопываются в один option на backend-уровне: значение выбора - это конкретный `metro_stations.id`, а UI должен различать такие станции по ветке и цвету линии.

Yandex-подсказки могут вернуть названия ближайших станций метро. `AddressSuggestService` нормализует эти названия и сопоставляет их с локальным справочником `metro_stations`. Если по названию станция не найдена, но у адреса есть координаты, сервис может выбрать ближайшую локальную станцию по координатам. Автоподбор метро только выставляет значения по умолчанию: пользователь может вручную изменить выбранные станции перед отправкой формы.

## Развитие модели

Следующие расширения должны проектироваться отдельными задачами:

- дополнительные города и административные уровни за пределами текущей модели `City -> District`;
- массовый импорт или синхронизация канонической географии из доверенного источника;
- георадиус/поиск по расстоянию от текущих координат;
- подключение общего `Location` к новым сущностям, которым недостаточно локации через `Venue`.
