# Динамические данные дашборда

Epic [#1073](https://github.com/a2ice/mskba/issues/1073). Серверные источники, редактор Filament и отображение в существующих карточках ЛК.

## Контракт

- Существующие `AccountDashboardWidget`, `AccountDashboardService` и preferences сохраняются. Новые nullable `source_key`, `source_settings` задают источник и его конфигурацию для типа `dynamic`.
- `DashboardDataRegistry` разрешает только явно зарегистрированные ключи, не произвольные классы, SQL или код из БД. Неизвестный источник недоступен. `DashboardDataProvider` проверяет доступ отдельно от targeting; принудительное включение по ID не обходит эту проверку. Блокированный канонический пользователь не получает динамические данные.
- `GET /account/dashboard/widgets/{widget}/data` требует auth, активную тему mskba_app, доступность и видимость виджета; повторно проверяет провайдер, возвращает `widget_id` и `data: {total, items}`, private/no-store. Пилотный источник `unread_messages` переиспользует существующий счётчик уведомлений.
- Тип `dynamic` доступен в Filament для публикации. Новые карточки не создаются автоматически: администратор выбирает источник и аудиторию. По прямому решению владельца для этого этапа используется существующая оболочка карточек без отдельной приёмки UI Studio; проверка на dev.

## Персональные источники (серверный этап)

- `my_interests`: текущие активные PlayIntent и прямые VenueSubscription канонической identity; публичные будущие игры с открытым индивидуальным набором, тренировки и игровые тренировки на опубликованных активных площадках в пределах 30 дней. Использует существующие правила совпадения площадки/времени, исключает собственные события, дедупликация по Event, сортировка по времени. Уведомления и каналы доставки не определяют наличие совпадения в ленте. Пока без состояния «новое», свободных слотов и ценовых предложений.
- `wallet_summary`: существующий GetAccountWalletOverview; собственные балансы в minor units, последние операции (total — число возвращённых операций), без чужих кошельков, платежных реквизитов и комиссий. `summary` — опциональные агрегаты DTO; базовый контракт сохраняется.
- `upcoming_events`: опубликованные мероприятия с текущим/будущим временем окончания; подтверждённое участие с актуальной версией, принятая заявка или организатор. Общий scope с «Мои игры», приватные мероприятия дополнительно проходят существующую авторизацию просмотра. Один Event — одна запись. Пока без отдельных записей аренды и внешних тренировочных расписаний.
- `my_rental_requests`: собственные rental-заявки (ожидание, hold, предстоящие подтверждённые) и активные собственные предзаявки, только при доступности rental_flow и portal с учётом rollout. Для заявок используется тот же requester scope, что в личном кабинете; для предзаявок — канонический requester по текущему ACL. Раздельные счётчики, без чужих заявок, финансовых снимков и контактов. Предзаявка и заявка — отдельные записи.
- `needs_attention`: незавершённое подтверждение аккаунта, настройка публичности при незавершённом onboarding, актуальное непринятое предложение по собственной активной предзаявке при доступности rental/portal. Не зависит от прочитанности уведомлений; ожидающие площадку, просроченные, обработанные и чужие предложения исключаются. Ссылка ведёт в штатный сценарий, действия повторно проверяются доменом. При изменении аренды существующая приватная инвалидация обновляет весь дашборд, статус аккаунта и дедлайны — при очередной сверке. Без автоматической публикации.
- Персональные источники поддерживают limit 1–10 (по умолчанию 5). Данные отображаются в существующей оболочке карточек.

## Настройка в Filament

«Сайт и дизайн → Виджеты дашборда»: тип «Динамический виджет», источник из реестра, лимит 1–10 (для источников со списком). Аудитория, ширина, порядок, скрытие и перемещение используют существующие настройки. Установка аудитории не выдаёт доступ к доменным данным. Настройки источника нормализуются на сервере; при смене на статический тип очищаются. Публикация регулируется существующим переключателем enabled; старый fallback-редактор не позволяет создавать, изменять или удалять динамические виджеты. Существующие типы не меняют поведение. Настройки live, пустого состояния и операционных источников добавляются вместе с их реализацией, не имитируются действующими.

## Отображение

Blade dashboard-dynamic-content использует тот же DTO, что и защищённый endpoint; повторная проверка провайдера выполняется перед чтением. Существующие panel/grid/richtext/actions, без нового UIKit и без автоматической публикации. Пустые списки и отказ чтения не показывают старых данных. Ссылки из провайдера валидируются как внутренние. Если администратор не настроил действия, используется стандартная ссылка на соответствующий раздел. Существующее обновление HTML на уведомлениях, reconnect/focus и периодической сверке работает и для новых карточек; персональные данные не задерживаются таймером административного обновления. Доменные сигналы Reverb запускают ту же авторизованную HTML-сверку.

## Инвалидация

`DashboardWidgetsInvalidatedBroadcast` — контракт приватного сигнала для канонического пользователя, `users.{id}`, после commit, с ключами источников и флагом изменения каталога. Не передавать личные записи. Клиент слушает приватный сигнал и объединяет всплески (250 мс, максимум 1,5 с), повторно запрашивая текущий HTML только при наличии dynamic или изменении каталога. Существующий reconnect/focus/90-секундный fallback сохраняется. Публичный сигнал общей конфигурации не меняется.

Первый live-срез: Eloquent create/update/delete кошелька USER MAIN RUB, собственных rental-заявок/предзаявок, PlayIntent/VenueSubscription, участия и GameAdmission вызывают инвалидацию своих владельцев после commit. Предыдущий владелец также получает сигнал при смене. Queued EventChanged обновляет расписание организатора и участников/принятых заявок, а для публичных нечерновых мероприятий — интересы прямых подписчиков и потенциально подходящих активных intents независимо от настроек доставки уведомлений. Payload не содержит event/venue/booking ID, балансов и персональных записей. Приватные мероприятия не рассылаются подписчикам. Сами совпадения и права проверяются заново.

Ограничения: это первый live-срез, не полный доменный аудит. Изменения через массовый SQL, переход публичного события в private/draft или смена прежней площадки могут быть замечены только при очередной сверке; истечение сроков также через fallback. Пока обновляется целый видимый дашборд, а не отдельный widget endpoint; нагрузку на broad-intent fan-out нужно измерить. Операционные scopes, отзыв прав и точечная инвалидация остаются отдельной задачей.

## Следующие этапы

Подключить интересы, расписание, заявки, финансы и центр действий через существующие read models. Операционные провайдеры используют реальные permissions и текущий scope по площадкам/залам; не выводят сведения на основании глобального targeting. Зависимость: Epic #987. Для текущего этапа по решению владельца — существующий дизайн, тесты отрицательных сценариев, CI и dev smoke; отдельная ветка UI Studio не интегрируется.

## Операционные входящие заявки (первый срез)

`venue_rental_inbox`: только реальные активные membership grants пользователя, scoped по площадке/залу, а не системная роль или запись комиссионного агента. Для обычных заявок нужен VIEW_BOOKING_REQUESTS, для предзаявок — действующие права VIEW_EVENT_INTERESTS/VIEW_BOOKING_REQUESTS/PROPOSE_EVENT_BOOKING либо существующий owner/admin management grant; повторная проверка штатного ACL предзаявки. Нет автоматического глобального доступа даже для superadmin. Исключаются собственные, прошедшие и терминальные записи; непринятое предложение представлено активной предзаявкой, принятое — обычной заявкой при наличии booking view. Учитываются rental/portal rollout. Только название площадки, период, статус и ссылка, без контактов, платежей и внутренних данных. Доступность не зависит от числа записей. Обновление через существующие уведомления и резервную сверку; адресная доменная рассылка представителям и мгновенный отзыв прав ещё не подключены. Без новых полномочий, автоматической публикации, изменений #987 или привязки менеджера к площадке.

## Приглашения площадок (операционный первый срез)

`venue_invitations`: существующий AccountInvitationAccess (backoffice access + invitation view), дополнительно действующий venue-level MANAGE_MEMBERSHIPS, без court-only/global access; даже superadmin не получает этот операционный виджет без venue scope. Статусы и этапы берутся из AccountInvitation, счётчики всех доступных записей: pending без expired, expired, completed, revoked; последние 1–10 записей по updated_at. Только название площадки, статусы, срок непринятой активной ссылки, внутренний ID. Не выдаются контакты, произвольный title, идентификатор принятого пользователя, token/hash или ссылка принятия. Переход в штатный список Filament с независимой проверкой ACL. Без автоматической публикации. Отдельная модель закрепления менеджера ещё не интегрирована, не заменяется системной ролью. Обновление по текущей сверке/focus/reconnect; адресный Reverb и отзыв прав отдельным этапом. Не меняет Epic #987.
