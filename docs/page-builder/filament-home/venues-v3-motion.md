# Venues V3 — непрерывность движения (DEV)

## Область

CSS/JS принадлежат Filament-компоненту `venues-scene-v3`. Установщик старой арены не запускать для этого исправления. [DEV API](../../specification/page-builder-agent-api.md) и [bridge](../../../ops/page-builder/README.md) выполняют отдельные версионированные публикации CSS/JS.

## Выход из фиксации

Общий `--v3-exit-scroll` управляет двумя sticky-слоями, мячом и фоном. Пусть `r` — отрицательная viewport-координата последней правой секции, `L=250`, `p=clamp((r+L/2)/L,0,1)`. Смещение равно 0 до `r=-L/2`, затем `L*(p³−p⁴/2)`, затем `r` при `r≥L/2`.

Производная смещения равна smoothstep скорости `3p²−2p³`: 0 в начале, 1 в конце, без превышения скорости страницы. Нельзя заменять это на `r*smoothstep(r/L)`: такой вариант сначала отстаёт, а затем превышает скорость страницы. Обратная прокрутка использует ту же функцию без таймера и накопленного состояния.

Движение каждого персонажа относительно композиции заканчивается до общего выхода. Расстояние вычисляется по реальному положению последней секции, а не как `height−viewport`, чтобы CSS translate панели не создавал второй, несовпадающий порог.

## Первый кадр

CSS и JS должны совпадать по стартовым положениям: referee=0%, visitor=15%, host=30%; пики: 25%, 3%, −1%. Проценты относятся к собственной высоте изображения. При редактировании профилей обновлять соответствующие статические CSS-положения. Мобильный и reduced-motion режимы отображают пиковую позу.

Начало входной анимации — минимум viewport-триггера и исходной координаты сцены в документе. Поэтому короткий hero не запускает часть анимации ещё до скролла. CSS-геометрия сцены не зависит от отложенного JS-класса. Изображения остаются видимыми до JS; никакого conceal/fade-in обхода.

## Проверка и ограничения

Проверять загрузку с верхней позиции, медленную и быструю прокрутку вниз/вверх около последнего блока, остановку внутри перехода, resize, prefers-reduced-motion и mobile. Браузерное восстановление ненулевой позиции скролла и прямой переход к якорю требуют отдельной проверки: статический первый кадр сам по себе не вычисляет восстановленный scrollY до JS.

Публикация и фактическая проверка отслеживаются в [задаче 302](../../tasks/302/description.md). Код нельзя считать опубликованным только по merge запроса: необходим успешный результат API bridge и проверка SHA.

## Высота viewport и горизонтальная ориентация

PNG игроков (до 821px) и судьи масштабируются вместе, а не независимо от одежды: desktop `actor-canvas` получает CSS `scale(clamp(.30, (100svh - 85px)/817px, 1))` вокруг точки 68% / 110%. При достаточной высоте масштаб равен 1, исходная композиция сохраняется. Фактическая сцена строится CSS уже до запуска JS, поэтому orientation-change не добавляет отдельного рывка от инициализации контроллера.

Мяч при desktop-docking остаётся единственным элементом. Его визуальный размер умножается на тот же коэффициент, Y плавно смещается относительно 95px, X не переписывается. Исходная переменная `--v3-exit-scroll` по-прежнему вычитается ровно один раз. При высоте ≤780px sticky top плавно снижается по формуле `21.3svh - 10px` (совпадает с прежним 20svh на границе). На mobile/tablet landscape без docking установлены ограничения сцены и PNG через `100svh`, а диаметр единственного мяча Hero дополнительно масштабируется от высотного бюджета игроков; сам Hero-мяч остаётся под управлением исходного контроллера. Portrait не меняется.

CSS typed division доступно в актуальном iOS Safari 26+/Chromium 140+; старые браузеры получают ступенчатый fallback. Визуально проверить 1536×707 и 844×390 вместе с обычным desktop, portrait, возвратом из landscape и прокруткой назад. Нельзя принимать работу по одному численному тесту без просмотра на DEV.
